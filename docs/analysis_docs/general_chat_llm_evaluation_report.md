## 1. 现状描述

### 1.1 当前代码实现

`agent/nodes/general_chat.py` 是一个占位式节点，核心逻辑如下：

```python
# 已定义了 GENERAL_CHAT_PROMPT（L21-L35），但完全未被使用
GENERAL_CHAT_PROMPT = ChatPromptTemplate.from_messages([
    ("system", """你是「招投标智能助手」..."""),
    ("user", "{question}"),
])

def node_general_chat(state: AgentState) -> dict:
    # 硬编码固定文案，不调用任何 LLM
    answer = (
        "您好！我是招投标智能助手 🤖\n\n"
        "我可以帮您：\n"
        "  📚 查询招投标法规知识...\n"
        "  💰 查询历史中标价格...\n"
        "  💬 解答功能使用问题...\n\n"
        "请问有什么可以帮您的？"
    )
    return {"business_result": {...}, "messages": [AIMessage(content=answer)]}
```

**关键事实：**

| 项目 | 现状 |
|------|------|
| `GENERAL_CHAT_PROMPT` 模板 | 已定义但**完全未使用**（死代码） |
| LLM 调用 | **无** — 所有输入返回同一段硬编码文案 |
| 多轮对话感知 | **无** — 无论第几轮对话，始终返回相同回答 |
| LLM 注入机制 | 注释说明"由 graph.py 注入"，但 **graph.py 未实现** |
| 代码行数 | 81 行（含大量无用定义） |

### 1.2 上游路由机制分析

**`agent/router.py`** 中 `general_chat` 意图的触发条件（L65-L69）：

```python
@tool
def route_general_chat(reason: str) -> str:
    """通用对话：问候、自我介绍、功能咨询、操作引导等非业务聊天。
    触发：打招呼、问能力、闲聊。"""
```

这意味着以下用户输入会被路由到 `node_general_chat`：

| 用户输入示例 | 路由意图 |
|-------------|---------|
| "你好" / "Hi" / "早上好" | `general_chat` |
| "你能做什么？" / "你有什么功能？" | `general_chat` |
| "谢谢" / "好的" / "再见" | `general_chat` |
| "今天天气怎么样？"（闲聊） | `general_chat` 或 `fallback` |
| "你是AI吗？" / "谁开发了你？" | `general_chat` |

**关键洞察：** 路由器的意图分类本身已由 LLM 完成（`with_structured_output` 或 `tool_calling`），即系统已经消耗了一次 LLM 调用（约 500-1000 token）来判断用户意图为 `general_chat`，但到达节点后却用固定文案回应。**路由成本已付出，生成环节却未利用 LLM**。

### 1.3 与同体系其他节点的对比

| 节点 | LLM 参与 | 回答生成方式 | 多轮感知 |
|------|:--------:|-------------|:--------:|
| `knowledge_qa` | ✅ RAG + LLM | 检索 → LLM 生成（200-800字） | ✅ messages 历史 |
| `price_inquiry` | ✅ 意图解析用 LLM | MySQL → 模板拼接 | ✅ 多轮纠偏 |
| `general_chat` | ❌ 完全不使用 | 硬编码固定文案（~80字） | ❌ 无感知 |
| `fallback` | ❌ 不使用 | 硬编码引导文案（~120字） | ❌ 无感知 |
| `doc_qa` | ❌ 占位节点 | 硬编码占位文案 | ❌ 无感知 |

`general_chat` 是整个系统中**唯一一个路由已判定为用户意图明确、却完全不使用 LLM 生成回答的业务节点**。

## 4. 维度深度分析

### 4.1 死板的教条式固定输出 vs. 灵活多变的自然语言生成

**现状问题：**

当前固定文案对**所有**用户输入返回完全相同的回答：

```
用户: "你好"
助手: "您好！我是招投标智能助手 🤖\n我可以帮您：..."

用户: "谢谢你的帮助"
助手: "您好！我是招投标智能助手 🤖\n我可以帮您：..."  ← 完全相同的回复

用户: "再见"
助手: "您好！我是招投标智能助手 🤖\n我可以帮您：..."  ← 不合时宜
```

这种"复读机"行为在实际使用中会造成严重的**对话断裂感**。当用户说"谢谢"时，理想的回应是"不客气！如果还有其他问题随时问我"，而非再次列举功能清单。

**LLM 方案的优势：**

- 可以根据用户具体输入生成差异化回应
- 能理解对话的社交信号（感谢、告别、情绪表达）
- 引导可以在自然对话中穿插，而非一次性输出功能列表

**但需要注意：** general_chat 的定位本身就是"功能引导"，而非"深度闲聊"。如果 LLM 过于健谈，可能反而偏离核心目标，让用户迷失在闲聊中而不是使用业务功能。

### 4.2 功能引导的明确性 vs. 对话的流畅性和拟人化程度

**这是一个核心权衡点。**

固定文案的优势在于**结构化的功能引导**——用户一眼就能看到三个功能点，点击或输入即可触发。这是典型的 "command-discovery" 模式。

LLM 生成自然语言的优势在于**对话嵌入型引导**——例如：
```
用户: "我想查一下价格"
助手: "好的！询价功能可以帮您查询历史中标价格和产品报价。
      请问您想查哪个产品的价格呢？"
```

但这需要 LLM 准确地识别出用户的**潜在业务意图**，并在引导的同时不越界提供业务答案。这是 prompt engineering 的核心挑战。

**折中方案：** 在 system prompt 中要求 LLM"以结构化列表方式介绍功能，但同时根据用户的具体问题给出针对性引导"。这结合了两者的优势。

### 4.3 维护成本与潜在风险

#### 4.3.1 幻觉风险

general_chat 场景的幻觉与 knowledge_qa 的幻觉有本质区别：

| | knowledge_qa 幻觉 | general_chat 幻觉 |
|------|------|------|
| **后果** | 编造法律条文，误导用户决策 → **高风险** | 虚构功能、错误引导 → **中低风险** |
| **检测难度** | 高，需要专业法务审核 | 低，功能列表是已知的有限集合 |
| **缓解手段** | RAG 绑定资料源 | System prompt 明确限定能力边界 |

**结论：** general_chat 场景的幻觉风险显著**低于** knowledge_qa，因为其任务本质是"在已知的功能清单内做引导"，而非"从开放知识空间检索事实"。只要 prompt 设计得当，幻觉可控。

#### 4.3.2 Token 消耗

按 DeepSeek-chat 当前定价（约 ¥1/百万 token 输入，¥2/百万 token 输出）：

| 场景 | 输入 token | 输出 token | 单次成本 | 日均 1000 次 |
|------|:----------:|:----------:|:--------:|:-----------:|
| 路由 LLM（已发生） | ~300 | ~50 | ~¥0.0004 | ¥0.40 |
| general_chat LLM（新增） | ~400 | ~150 | ~¥0.0007 | ¥0.70 |

**新增 token 成本极低**，日均千次对话仅增加约 ¥0.70。这不应成为决策障碍。

#### 4.3.3 响应延迟

| 节点 | 当前延迟 | 引入 LLM 后 |
|------|:--------:|:-----------:|
| Router | ~0.8s（已含 LLM） | 不变 |
| knowledge_qa | ~5-15s（检索+生成） | 不变 |
| **general_chat（现状）** | **< 0.1s** | **~1.5-3s** |
| fallback | < 0.1s | 不变 |

从 < 0.1s 增加到 ~2s，用户可感知但属于正常 AI 对话延迟范围。在流式输出场景下（首 token 约 0.5-1s），体验可接受。

#### 4.3.4 越权回答风险

general_chat 引入 LLM 后的最大风险点：用户可能在闲聊中顺带提出业务问题，LLM 若未严格约束，可能**不经过知识库检索直接作答**，导致答案无据可查。

**缓解方案：**
- System prompt 明确："你只能做功能引导和闲聊，绝不回答招投标法律、流程、价格等业务问题。遇到此类问题，请引导用户使用对应功能"
- 可考虑在 `node_general_chat` 内部增加一个**前置检测**：如果 LLM 倾向回答业务问题，直接降级为引导话术

## 5. 风险分析

### 5.1 风险矩阵

| 风险 | 概率 | 影响 | 等级 | 缓解措施 |
|------|:----:|:----:|:----:|----------|
| LLM 在闲聊中编造招投标知识 | 中 | 高 | 🔴 | System prompt 严格限定能力边界；可选增加关键词触发过滤 |
| 用户绕过知识库直接获取答案 | 中 | 中 | 🟡 | Prompt 要求遇到业务问题必须引导至对应功能 |
| 响应延迟增加导致体验下降 | 高 | 低 | 🟢 | 流式输出降低感知延迟；temperature=0 可略微加速 |
| Token 成本不可控增长 | 低 | 低 | 🟢 | Prompt 限定回答长度（100-200字） |
| 多轮对话中偏离功能引导主线 | 中 | 低 | 🟢 | 限制对话轮次深度或定期重置上下文 |
| 与路由器的意图分发产生循环 | 低 | 中 | 🟡 | 需要在 state 中标记"已路由"防止无限循环 |

### 5.2 最坏场景分析

**场景：** 用户在 general_chat 中问"公开招标的评标委员会最少几个人？"

- **现状（方案A）：** 返回固定功能引导 → 用户不满意但不会被误导
- **方案B（纯 LLM）：** LLM 可能凭训练记忆回答"5人以上单数" → 答案可能正确但也可能不准确，且无来源引用
- **方案C（渐进引入）：** LLM 识别到这是专业知识问题 → 引导用户："这是招投标法规问题，建议您切换到专业知识问答功能，我可以从权威资料库中为您查找准确的答案"

方案C的处理方式既保持了对话流畅性，又避免了越权风险。

## 6. 技术可行性评估

### 6.1 LLM 注入可行性

当前 `graph.py` 中 `build_graph()` 已在构建时创建 LLM 实例（L122-L132）：

```python
llm = ChatOpenAI(
    model=settings.llm_model,      # deepseek-chat
    api_key=settings.llm_api_key,
    temperature=settings.llm_temperature,  # 当前为 0.0
    base_url=settings.llm_base_url,
)
```

该 LLM 实例**仅传递给 router**（`build_router_node(llm)`），业务节点并未获取。

**注入方案有两种：**

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **闭包注入** | 修改 `build_graph`，在注册 `node_general_chat` 时用闭包捕获 llm | 改动最小，与 router 模式一致 | 需修改 graph.py 注册逻辑 |
| **独立创建** | `node_general_chat` 内部自行创建 LLM 实例（类似 `knowledge_qa` 的 `_get_rag()`） | 节点自包含，不依赖 graph 层 | 创建多份 LLM 实例，浪费连接资源 |

**推荐闭包注入**，与 `build_router_node(llm)` 的模式保持一致。

### 6.2 Prompt 设计方向

基于已有的 `GENERAL_CHAT_PROMPT` 模板，应强化以下几点：

```
你是「招投标智能助手」的通用对话模块。

【核心原则】
1. 你只做三件事：问候闲聊、功能介绍、操作引导
2. 你绝不回答招投标法律、流程、价格等业务问题
3. 遇到业务问题，引导用户说出具体需求，而非尝试作答

【功能清单】
- 专业知识问答：法律法规、招标方式、评标流程等
- 智能询价：历史中标价格、产品报价、公司中标记录
- 文档问答（即将上线）：招标文件分析和解读

【回答风格】
- 简洁、友好、有帮助
- 自然融入功能引导，但不要让用户每次都看到完整功能列表
- 用户表达感谢/告别时，做恰当的社交回应
```

### 6.3 实现改动量估算

## 7. 推荐策略与实施路径

### 7.1 推荐策略：**渐进引入（方案 C）**

**不推荐"维持现状"**：固定文案在多轮对话场景下的体验缺陷过于明显，"复读机"行为会严重损害用户对系统智能程度的信任。"路由已消耗 LLM 成本，生成环节却闲置"也是资源浪费。

**不推荐"完全替换为自由 LLM"**：general_chat 的定位是**功能引导**而非**开放域闲聊**。完全放开 LLM 会带来越权回答风险，且可能让用户迷失在无尽闲聊中而不使用核心业务功能。

**推荐"Prompt 约束的 LLM + 边界锁定"**：
- System prompt 严格限定能力边界（只做引导、不答业务）
- 利用 `messages` 历史实现多轮上下文感知
- 使用 `temperature=0`（与系统其他 LLM 调用一致），降低幻觉概率
- 保留硬编码兜底逻辑（当 LLM 不可用时回退到固定文案）

### 7.2 分步实施路径

```
Phase 1: 最小可行改造（0.5 天）
├── Step 1.1: 修正 GENERAL_CHAT_PROMPT，强化能力边界约束
├── Step 1.2: 重构 node_general_chat 接收 llm 参数，使用 LCEL 链
├── Step 1.3: graph.py 注入 llm 到 general_chat 节点
└── Step 1.4: 验证基本对话流程（问候、功能问询、感谢、告别）

Phase 2: 体验打磨（0.5 天）
├── Step 2.1: 优化 prompt — 测试边界 case（业务问题、恶意 prompt）
├── Step 2.2: 多轮对话测试（连续 5+ 轮确认不偏离引导主线）
└── Step 2.3: 调整输出长度限制（100-200 字）

Phase 3: 上线观察（持续）
├── Step 3.1: 监控 general_chat 节点的 LLM 调用异常率
├── Step 3.2: 抽检 LLM 回答质量（是否越权、是否偏离引导）
└── Step 3.3: 收集用户反馈，迭代 prompt
```

### 7.3 关键决策参数

| 参数 | 推荐值 | 理由 |
|------|--------|------|
| `temperature` | `0.0` | 与系统全局一致，减少创作性幻觉 |
| `model` | `deepseek-chat` | 与 router/knowledge_qa 统一 |
| 输出最大 token | `300` | 引导文案无需过长，同时控制成本 |
| 多轮历史窗口 | `最近 3 轮（6 条消息）` | 与 router 的 `max_turns=3` 一致 |

---

## 8. 结论

### 8.1 核心判断

**应该引入 LLM，但必须加约束。** 当前硬编码固定文案是项目早期快速搭建的合理取舍，但已不适合系统当前的成熟度。在路由器已消耗 LLM token 完成意图分类的前提下，用固定文案"终结"对话是对 LLM 调用成本的浪费，也是对用户体验的损害。

### 8.2 一句话总结

> **在 general_chat 节点引入 LLM，不是"让闲聊更智能"，而是"让功能引导更自然"。** 核心目标是消除"复读机"式回复带来的对话断裂感，同时保持功能引导的明确性和业务知识的安全边界。

### 8.3 最终建议矩阵

| 评估维度 | 结论 |
|----------|------|
| **是否引入 LLM** | ✅ 是 — 渐进引入，非完全替换 |
| **技术可行性** | ✅ 极高 — 改动 < 50 行，零新依赖 |
| **实现成本** | 低 — 约 1 人天（含测试） |
| **风险评估** | 中低 — 幻觉风险可控，越权风险可通过 prompt 缓解 |
| **推荐时机** | 与流式升级的 Phase 2（General Chat 接入 LLM）合并执行 |
| **优先级** | 中 — 低于 knowledge_qa 流式化，高于 price_inquiry 摘要增强 |
