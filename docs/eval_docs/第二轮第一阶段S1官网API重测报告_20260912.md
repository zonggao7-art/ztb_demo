# 第二轮第一阶段 S1 官网 API 重测报告

记录日期：2026-09-12  
运行编号：`s1_20260912_formal_03_official`

## 一、为什么重新测 S1

历史 S1 使用 OpenRouter 的 `deepseek/deepseek-v4-flash-0731`，P50 为8.495秒，P95为38.521秒，最慢一题达到253.165秒。S2至S4改为直接调用 DeepSeek 官网 `deepseek-flash` 后，查询耗时明显下降。

为了让 S1与后续阶段使用一致的回答模型和调用平台，本次使用当前 S4冻结代码，将检索流程切回 S1，重新运行完整200题和800项质量评分。历史 S1保留，不覆盖、不删除。

## 二、本次固定条件

| 项目 | 固定值 |
|---|---|
| 题集 | `testset_200.jsonl`，SHA256=`D0960557...23E87A` |
| 题目数量与顺序 | 200题，严格按文件顺序，单并发 |
| 知识库 | `public_kb`，920条数据 |
| S1检索 | 稠密召回30条 → 余弦分数不低于0.45 → 前5条 |
| 查询嵌入 | `BAAI/bge-m3` |
| 回答模型 | `deepseek-flash` |
| 回答接口 | `api.deepseek.com` |
| 回答思考 | 关闭 |
| 裁判模型 | `MiniMax-M3`，关闭思考 |
| 评分嵌入 | `BAAI/bge-m3` |
| 源码 | 当前 S4冻结的47个文件 |

离线检查确认题集、164个标准资料块、Milvus数据与索引、回答模型列表和评分模型配置全部通过，没有生成答案或产生模型费用。

两次 S1的精确资料块 Macro Recall、Micro Recall、至少命中率和全部命中率完全一致；200题中199题的最终资料正文列表完全一致。质量分的小幅变化主要来自重新生成的答案和裁判评分变化。

修正版 S1的200题中199题比旧 S1更快，最慢题从253.165秒降到2.547秒。旧 S1观察到的异常长尾在官网 API运行中完全消失。这强烈支持“旧回答模型及其 OpenRouter调用路径是异常耗时主因”的判断。

但旧、新 S1还存在回答模型名称和源码版本差异，因此这不是只改变调用平台的单一条件实验，不能把全部变化严格归因于 OpenRouter。

修正版 S1使用最终 S4冻结源码，其中14个文件与历史 S2源码快照不同。因此这组结果可以作为统一回答模型后的实用比较，但不宣称只有检索方式一个变量。

## 六、评分过程问题

初次四题并发评分在 q024的 Faithfulness遇到一次 MiniMax 429。随后降低并发继续，q071、q077、q081的 Context Precision出现长时间无响应并超时。为避免少数请求每次占用近10分钟，剩余主评分将单项时限调整为120秒。

主评分最终得到796项成功结果。程序随后使用单并发、600秒时限，只补偿上述4项失败指标，4/4全部成功，没有重算其余796项。

正式 `scoring_usage.json` 完整记录已落盘批次和4项补偿的用量，但不包含人工中止时正在执行、尚未到达下一断点的请求。这部分额外裁判消耗无法准确补算，不影响系统查询 Token、查询耗时和最终800项分数。

## 七、结论

修正版 S1已具备完整正式结果，可以替代旧 S1作为后续分析中的实用 S1基线。旧 S1继续作为 OpenRouter异常耗时和历史排错证据保存。

重新测评确认：将回答模型统一为 DeepSeek官网 API后，S1的典型耗时与最慢耗时均回到和S2至S4接近的范围。后续比较检索链路时，应优先使用修正版 S1；引用结论时同时保留源码版本不同这一限制。
