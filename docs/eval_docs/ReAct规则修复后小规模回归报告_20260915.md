# ReAct 规则修复后小规模回归报告

> 日期：2026-09-15  
> 性质：非正式、定向、真实链路回归  
> 结论：发现 1 项稳定复现的剩余问题；不需要立即重跑完整第三轮，但当前不能宣称新规则已经完全验收通过

## 一、测试边界

本次测试按用户授权执行小规模回归，不重跑 280 题正式主集，不执行付费 Ragas，不覆盖或改写第三轮历史正式成绩。

测试分为三部分：

1. 离线规则回归：`test/test_unified_agent.py` 共 28 项；
2. 真实主链路：8 个高风险案例各重复 3 次，另加六个授权工具各 1 个正常对照，共 30 次请求；
3. 故障注入：`TR-REL-DEP-002` 上游双候选依赖场景重复 3 次。

真实链路合计 33 次。运行均使用 `agent-loop-v3 / unified-agent-v3` 当前实现，产物与原正式运行目录隔离。冻结第三轮题集只作为输入素材和历史参照；已明确需要重标的旧金标准不用于制造本次假失败。

## 四、剩余问题

### 4.1 表面状态正确，但任务没有真正部分完成

`TR-NEG-017` 的请求是：

> 查询一个项目的中标结果，并说明中标通知书的法律效力。

按已采纳产品口径，项目查询缺少 `project_number`，但“说明中标通知书的法律效力”可以独立执行。正确结果应当是：

1. 执行 `knowledge_qa` 并返回法规答案；
2. 保留 `project_number` 为未完成字段；
3. 最终状态为 `partial`。

实际三次运行虽然都返回了 `partial`，但 `knowledge_qa` 均出现：

- `tool_attempts = 1`；
- `tool_executions = 0`；
- `code = unbound_input`；
- 最终回答仅为“该次工具申请未通过程序校验”，没有法规答案。

因此不能因为最终状态字符串正确就判定通过。

### 4.2 已定位的程序条件

当前 `knowledge_qa.question` 必须同时满足：

1. 是本轮用户原文中的字符串；
2. 被规则识别为具体法规问题。

本例中的模型工具参数没有通过这项精确绑定检查，于是在实际 I/O 前被门禁拒绝。拒绝回执没有保留模型原始参数，只记录了空 `args`，所以现有运行产物能够确认“绑定失败”，但不能进一步审计模型当时究竟改写成了哪句话。

这暴露出两个相邻问题：

1. 独立法规子任务的参数绑定可能对模型措辞变化过于敏感；
2. 被拒绝动作没有保留经过安全处理的原始参数，降低了失败审计能力。

## 六、题集解释边界

第三轮冻结金标准中，以下案例已经受新产品口径影响：

- `TR-NEG-012`、`TR-NEG-016`、`TR-NEG-017`：应复核是否允许独立部分执行；
- `TR-CROSS-035`：四个公司应默认分别查询，而不是把逗号拼接字符串作为单一主体。

本次实际运行了后三个案例；`TR-NEG-012` 未进入本次样本。离线评分器仍读取旧冻结金标准，因此两个运行汇总显示 `incomplete` 是预期现象：一方面没有执行 Ragas，另一方面旧金标准与新口径不完全一致。该字段不能作为本次定向测试的最终判定。

## 七、环境观察

每次启动均出现 `.env` 第 80～84 行无法被 `python-dotenv` 解析的警告。LLM、MySQL 和 Milvus 配置仍成功加载，所有真实工具均可调用，因此该警告没有阻断本次结果；但它属于后续应单独清理的环境配置问题，不应与本次 ReAct 规则缺陷混为一谈。

## 八、结论与下一决策

本次小规模测试达到了目的：主要修复点已经在真实链路中生效，特别是精确项目编号、字段为空、多主体拆分和双候选停止下游执行；同时发现 `TR-NEG-017` 的独立法规子任务仍会稳定失败。

当前不建议重跑完整测评。下一认知步骤应由用户决定是否接受一个窄修复方向：让程序从当前轮原文中确定性提取已识别的独立法规子问题，并保留被拒绝动作的安全审计参数。完成这一窄修复后，只需重跑 `TR-NEG-017` 三次，并增加 2～3 个措辞变体和 1～2 个正常 RAG 对照；无需重跑完整第三轮。
