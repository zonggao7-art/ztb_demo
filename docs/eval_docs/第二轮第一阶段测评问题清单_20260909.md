## 四、研究后已经解决的问题

### 1. 最终5条资料足以计算六项指标

结论：**只保存最终送给回答模型的5条完整资料，不保存最初30条和中间筛选结果。**

原因如下：

| 指标 | 需要的数据 |
|---|---|
| 检索内容覆盖率 | 原始问题、标准答案、最终5条资料 |
| 检索内容精度 | 原始问题、标准答案、按真实顺序排列的最终5条资料 |
| 答案正确性 | 原始问题、实际回答、标准答案 |
| 忠实度 | 原始问题、实际回答、最终5条资料 |
| P50/P95端到端查询耗时 | 每道题完整调用 `knowledge_qa` 的耗时 |
| 平均每题 Token 消耗 | 200题实际产生的 Token 总数和题数 |

`knowledge_qa` 返回的引用数据中已经包含这5条资料的完整正文和真实顺序，而且这5条正是回答模型看到的资料。因此无需为了六项指标保存更多检索过程。

题集五个字段提供原始问题、标准答案和标准资料。运行时再产生实际回答、最终5条资料、耗时和 Token，就足以计算六项指标。

### 2. 六项指标需要评分嵌入模型

结论：**需要。评分时直接复用查询嵌入模型。**

四项质量分中，只有“答案正确性”需要评分嵌入模型。当前选定的计算方式包含两部分：

- 75%：由裁判模型检查答对、答错和遗漏。
- 25%：把实际答案和标准答案变成向量，比较两段文字是否相近。

第二部分必须使用嵌入模型。如果删除它，就改变了“答案正确性”的计算方式。为了保持六项指标的现有定义，评分嵌入模型必须保留。

它只参与离线评分，不参与 `knowledge_qa` 检索。它产生的 Token 也不算入系统查询 Token。

### 3. 查询成本只统计 Token 即可

“查询成本”容易被理解为人民币金额，因此第六项正式改名为：**平均每题 Token 消耗**。

计算方式：

**平均每题 Token 消耗 = 200题运行产生的系统 Token 总数 ÷ 200。**

系统 Token 包括：

- 查询嵌入模型的输入 Token；
- 回答模型的输入 Token；
- 回答模型的输出 Token；
- 后续阶段中，其他在线模型实际返回的 Token。

回答模型的输入 Token 已经包含内部提示词、最终5条资料和原始问题，不需要再手工计算一次。

接口返回实际 Token 数时采用实际值。接口没有返回时允许估算，并在结果中明确标记为“估算”；如果找不到该模型对应的准确计算方法，则进一步标记为“粗略估算”。估算值不能当作接口实际返回值。

报告同时列出整批总 Token、平均每题 Token，以及上面各部分的数量。核心成绩只有“平均每题 Token”，其他数字用于解释变化。

除 Token 外，还可以统计人民币金额、接口调用次数和机器资源。但本轮不关心人民币金额；接口调用次数基本固定；机器资源没有必要单独测。查询时间已经是第五项指标，因此不再增加其他成本指标。

Ragas 裁判和评分嵌入产生的 Token 单独记录，不进入第六项指标。

### 4. 查询耗时改为P50和P95

第五项正式改为：**P50/P95端到端查询耗时**。P50和P95共同组成一项速度指标。

实现方式是：

1. 每个阶段单独启动一次测评程序，先加载工具和知识库。
2. 200题按顺序一题一题调用 `knowledge_qa`。
3. 每道题调用前开始计时，返回回答或错误后立即停止。
4. 保存200个单题端到端耗时并从小到大排序。
5. 使用固定的最近名次法：第100个是P50，第190个是P95。

端到端耗时包括查询嵌入、检索、回答生成、引用整理、引用检查和工具内部重试。测评程序启动、知识库加载、Ragas评分、报告生成和结果文件写入不计入。

P50用于观察一般查询的等待时间，P95用于观察较慢查询。不能同时运行多题，否则不同题会争抢资源，阶段之间失去可比性。

如果某题调用失败，仍保存它返回错误前的实际耗时并纳入排序。报告另外列出失败数量，避免“失败得快”被误解为速度更好。

### 5. 失败和拒答的处理

- 题集没有应该拒答的问题。
- 如果 `knowledge_qa` 意外拒答，记录为异常拒答。
- 如果模型、网络或数据库失败，记录为系统失败。
- 如果 Ragas 评分失败，记录为评分失败。
- 无法得到某项质量分时，不把它伪装成0分；该项平均分同时注明实际成功评分的题数。
- P50和P95仍使用全部200次尝试的耗时，并在旁边显示失败数量。
