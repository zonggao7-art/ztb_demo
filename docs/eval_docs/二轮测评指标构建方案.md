# 二轮测评指标构建方案

整理日期：2026-09-08。本文记录本轮讨论确定的指标与使用范围，尚未产生二轮测评成绩。

## 一、这次测评要回答什么问题？

**数据治理、嵌入模型更换和后续检索调优，能不能让系统找到更有用的资料，让同一个模型回答得更好？为此多花或少花了多少时间和费用？**

二轮的重点放在上游改造，但需要同时观察最终回答。资料找得更好，不保证模型一定用得更好；只有把检索和回答放在一起看，才能知道改造是否帮助了用户。

本方案采用 **6 项核心指标：检索层 2 项、生成层 2 项、耗时和成本各 1 项。** 各项分别展示，不合成一个总分。

| 层次 | 选定指标 | 通俗理解 | 希望看到的方向 |
|---|---|---|---|
| 检索层 | **Context Recall：检索内容覆盖率** | 回答问题需要的信息，找齐了多少？ | 越高越好 |
| 检索层 | **Context Precision：检索内容精度** | 有用的资料有没有排在前面？ | 越高越好 |
| 生成层 | **Answer Correctness：答案正确性** | 最终回答与标准答案相比，是否更符合要求？ | 越高越好 |
| 生成层 | **Faithfulness：忠实度** | 回答中的说法，是否有实际提供资料的支持？ | 越高越好 |
| 效率 | **P50/P95端到端查询耗时** | 一般查询和较慢查询分别需要等多久？ | 在质量满足要求时，越低越好 |
| 费用 | **平均每次查询成本** | 一次查询实际花多少钱？ | 在质量满足要求时，越低越好 |

前四项使用 Ragas 评分。耗时和费用来自实际运行记录，不由评分模型猜测。

**计算方式说明：** 下文四项质量指标按已核对的 Ragas 0.4.3 实现解释；生成指标能否与一轮原分数直接比较，还需核实一轮实际配置。所有数字例子只用于说明算法，不是测评结果或当前服务报价。

## 二、检索层：资料找得怎么样？

### 1. Context Recall：检索内容覆盖率

**选它，是为了直接观察上游改造有没有减少必要信息的遗漏。**

它拿实际检索资料与参考答案比较，检查参考答案中的内容，有多少能从资料中找到依据。

例如，一道题同时问“申请条件”和“办理程序”。只找到条件，没有找到程序，说明检索仍然缺少一部分必要信息。仅返回了很多资料，并不代表已经找齐。

它主要能反映：

- 数据治理后，原来分散、残缺的信息是否更容易完整找回。
- 更换嵌入模型后，系统是否更容易找到问题所需的内容。
- 跨块题是否只找到了其中一部分依据。

**这里主要看内容，不要求必须命中某一个指定 chunk ID。** 不同文本块可能包含等价依据；数据重新切分后，块的编号和边界也可能改变。

Ragas 会自动拆分和判断参考答案内容，因此这是内容覆盖的自动评分。它不直接等于“命中了多少个标准块”，也不直接等于按人工固定要点逐项统计的精确比例。

**怎么计算？**

输入问题、参考答案和实际检索正文列表。评分模型把参考答案分成若干条可核查的陈述，再检查每条陈述是否能由检索资料支持。有支持记 1，没有支持记 0。

**单题 Context Recall = 获得检索资料支持的参考陈述数 ÷ 本题被判定的参考陈述总数。**

例如，参考答案拆成 4 条陈述，检索资料支持其中 3 条，得分就是 `3 ÷ 4 = 0.75`。这里的分母是参考答案中的陈述数，不是返回的 chunk 数。

资料非空、评分成功但一条都不支持时记 0。检索为空或未得到有效判定时，保留“空检索／评分失败”等原因，原始评分记缺失，不伪装成裁判已经给出 0 分。

### 2. Context Precision：检索内容精度

**选它，是为了观察系统有没有把真正有用的资料放在前面。**

采用带参考答案的评分方式，检查有序检索结果是否有助于回答问题。它包含对排名的评价，不是简单地用“相关条数除以返回条数”。

例如，两组结果都找到了所需资料，但一组把关键资料排在第一条，另一组前面放了几条不相关内容。这种差异值得记录，因为模型的上下文空间有限，无关资料可能占用空间并增加干扰。

它主要能反映：

- 更换嵌入模型后，前面的结果是否更贴近问题。
- 后续加入检索融合、重排等步骤后，结果排序是否改善。
- 返回更多资料时，是否同时带入了更多无关内容。

**两项检索指标配合使用：一项看信息是否找齐，一项看前排结果是否有用。** 重复正文仍需另行记录，不能只凭 Context Precision 判断是否已经消除了重复。

**怎么计算？**

输入问题、参考答案和按实际顺序排列的检索正文。计算分三步：

1. 评分模型逐条判断资料是否有助于回答问题，有用记 1，无用记 0。
2. 每遇到一条有用资料，计算“从第一条到当前位置，有用资料占多少”。
3. 把这些有用位置上的比例取平均。

**单题 Context Precision = 各个有用位置的前排有用比例之和 ÷ 有用资料条数。**

例如，实际返回 5 条资料：

| 排名 | 是否有用 | 这个位置参与计算的数值 |
|---|---|---|
| 1 | 有用 | 前 1 条有 1 条有用：`1 ÷ 1 = 1` |
| 2 | 无用 | 不直接加分，但会影响后面有用资料的前排比例 |
| 3 | 有用 | 前 3 条有 2 条有用：`2 ÷ 3 ≈ 0.667` |
| 4 | 无用 | 不参与加分 |
| 5 | 无用 | 不参与加分 |

本题得分为 `(1 + 2/3) ÷ 2 ≈ 0.833`，并不是 `2 ÷ 5 = 0.4`。

**这个算法的边界也要说明：** 如果第一条有用、后面四条无用，分数仍接近 1；末尾追加无关资料不一定会降低分数。因此它主要评价有用资料的前排排序，不能独自表示整份上下文有多少噪声。正文长度、重复内容和费用仍需结合查看。

返回资料非空、全部被判为无用时记 0；返回空列表或判定失败时记缺失并注明原因。保留真实顺序，不在评分前重新排序或偷偷去重。

## 三、生成层：上游改善有没有传递到最终回答？

生成层复用一轮已有的 **Answer Correctness 和 Faithfulness**。比较时固定回答模型和提示词，观察资料变化后的回答表现。

这两项反映的是“同一个模型拿到不同资料后，回答是否变好”，不能据此说模型本身的能力提高了。

### 3. Answer Correctness：答案正确性

**选它，是为了观察检索改善后，最终答案是否更符合标准答案。**

它把实际回答与参考答案比较，会受到事实错误、要点遗漏等情况的影响。因此，如果上游找回了原先缺失的信息，它可以帮助观察这些信息是否改善了回答。

它主要能反映：

- 资料更完整后，回答是否更少遗漏重要内容。
- 资料质量与匹配程度改善后，回答是否更少答错。
- 检索成绩提高，是否伴随最终回答成绩提高。

**保留一轮指标的整体口径，不把它改名为“固定必答要点召回率”或“事实正确百分比”。** 它是综合评分，分数提高不等于要点召回率同比提高；0.8 分也不表示 80% 的题完全答对。

本轮不单列答案相似度指标。已核对的 Answer Correctness 默认计算包含相似度成分；为保持复用关系，不擅自删除内部成分。正式运行前需核实并固定一轮与本轮的实际版本、权重和评分配置。无法核实旧配置时，新结果先作为本轮基线。

**怎么计算？**

输入问题、实际回答和参考答案。先把实际回答与参考答案拆成事实陈述，由评分模型分成三类：

| 记号 | 通俗含义 |
|---|---|
| TP | 回答中能得到参考答案支持的陈述 |
| FP | 回答中不能得到参考答案支持的陈述 |
| FN | 参考答案中有、回答却没有覆盖的陈述 |

FP 不必然意味着现实中是错的，也可能是参考答案没有收录的补充内容；出现争议时应回查标准原文。

在已核对版本的默认设置下，分两部分计算：

- **事实匹配分 F = `2 × TP ÷ (2 × TP + FP + FN)`。** 这个部分同时考虑答错或无支持的内容，以及漏答的内容；它对应默认参数 beta 为 1 的情况。
- **内部相似度 S：** 把回答与参考答案分别转成向量，计算两个向量的点积，再除以两个向量长度的乘积。它作为旧指标的内部组成部分，不另列为核心指标。

**默认 Answer Correctness = `0.75 × F + 0.25 × S`。** 若核实后的实际权重不是这组数，应使用实际配置，并在报告中注明；不能默认一轮一定用了这组权重。一般计算方式是“各部分得分乘以各自权重后相加，再除以权重之和”。

例如，TP 为 3、FP 为 1、FN 为 2，事实匹配分是 `6 ÷ 9 ≈ 0.667`；内部相似度为 0.8 时，默认综合分为 `0.75 × 0.667 + 0.25 × 0.8 ≈ 0.70`。

这也解释了为什么不能把 0.70 说成“70% 的题答对”或“答案召回率为 70%”。空答案不进入正常评分；没有可核查陈述或拆分结果异常时记为不可评分并复核，不能把库可能返回的默认高分当作有效成绩。

### 4. Faithfulness：忠实度

**选它，是为了观察模型是否依据真正看到的资料作答。**

它检查回答中的事实说法能否得到资料支持。评分使用经过上下文长度限制处理后，真正送入回答模型的资料。

例如，资料只说明了办理程序，模型却自行补充了一个资料中没有的办理期限，这条说法就缺少本次资料的支持。

它主要能反映：

- 上游提供的资料更充分后，模型是否减少无依据补充。
- 检索结果变化后，回答是否仍遵守依据约束。
- 答案正确性提高时，回答是否同时保有证据支持。

**忠实不代表完整，也不保证资料本身正确或仍然适用。** 模型只回答一小部分有依据的内容，也可能取得高分。因此需要与 Answer Correctness 一起看，不把忠实度直接改称真实幻觉率。

**怎么计算？**

输入问题、实际回答，以及真正送入回答模型的资料。评分模型先把回答拆成可核查的事实陈述，再逐条判断是否有资料支持。

**单题 Faithfulness = 获得输入资料支持的回答陈述数 ÷ 本题被判定的回答陈述总数。**

例如，回答共有 5 条事实陈述，其中 4 条有资料依据，得分为 `4 ÷ 5 = 0.8`。它表示本次判定中有 80% 的陈述获得支持，不表示 80% 的题没有幻觉。

它与 Context Recall 的区别在分母：Context Recall 检查参考答案需要什么；Faithfulness 检查模型实际说了什么。两项评分都不能把句子长短或陈述拆分数量当作固定不变的人工标准。

空答案、没有事实陈述的纯拒答、输入资料缺失或判定失败，均注明原因，不直接填满分。资料非空且正常完成判定、但没有一条陈述得到支持时，得分为 0。

### 为什么不再增加生成层指标？

本轮以检索改造为重点，生成层保留上述两项，分别观察回答结果与证据支持。回答相关性退出核心指标，不新增独立的相似度、答案要点召回率或幻觉率。

这个取舍意味着：可以观察“回答正确性和忠实度有没有改善”，但不能声称单独测得了“生成层要点召回率提高多少”。上游改造仍可能影响答案遗漏情况，只是本轮通过 Answer Correctness 间接观察。

## 四、效率与费用：这些改善花了什么代价？

### 5. P50/P95端到端查询耗时

**选它，是为了避免只看到质量提高，却没有看到用户等待变长。**

每道题调用 `knowledge_qa` 前开始计时，返回完整回答或错误后立即停止。它包括实际发生的查询向量化、检索、重排、生成、引用检查和工具内部重试；不包含测评程序启动、知识库加载、离线 Ragas 评分、报告生成和结果文件写入。

P50可以理解为一般查询的等待时间；P95可以理解为约95%的查询能在这个时间内完成。它们都不是第一个 token 的时间，也不是检索步骤的局部耗时。

200题必须按文件顺序逐题执行，一题完成后才能开始下一题。每道题都保留原始端到端耗时。拒答、空回答和系统失败也属于一次真实尝试，其返回结果前的耗时纳入排序，同时单独报告这些异常的数量，避免速度数字掩盖失败。

**怎么计算？**

1. 记录全部200次 `knowledge_qa` 调用的端到端耗时，单位统一为秒。
2. 将200个耗时从短到长排序。
3. 固定使用最近名次法：第100个耗时是P50，第190个耗时是P95，位置从1开始数。

例如，第100个耗时为3.1秒、第190个耗时为8.2秒，则报告“P50为3.1秒，P95为8.2秒，完成尝试200次”，并在旁边列出正常回答、异常拒答、空回答和系统失败数量。

各阶段必须使用同一种取值方法。整体P50和P95必须分别由全部200个耗时重新排序计算，不能把单跳和多跳分组的P50或P95简单平均。如果程序中途停止，本次运行标记为未完成，不形成正式速度成绩。

它主要能反映：

- chunk 变长后，传输、重排和回答处理时间是否增加。
- 更换嵌入模型后，查询向量化是否更快或更慢。
- 后续增加检索步骤后，用户需要多等多久。

P50和P95共同占用一个核心指标名额。不同阶段应在同一台机器、相近服务状态下比较，并始终按顺序执行。本轮只测完整的 `knowledge_qa`，不产生“仅检索耗时”。

### 6. 平均每次查询成本

**选它，是为了观察质量改善能否以可接受的费用获得。**

计算方式：**本批系统调用总费用 ÷ 实际发起查询数。**

系统费用包含查询嵌入、收费的重排服务、回答生成和重试。失败请求已经产生的费用也要计入；同一道题的重试不算一道新题，尚未运行的题不进入分母。

**怎么计算？**

先逐次记录实际调用费用，再归到对应查询，最后计算整批平均值。对于按输入／输出 token 收费的调用，若单价单位是“元／百万 token”：

**单次调用费用 = `输入 token 数 ÷ 1,000,000 × 输入单价 + 输出 token 数 ÷ 1,000,000 × 输出单价`。**

例如，假设输入 3,000 token、输入单价每百万 2 元；输出 1,000 token、输出单价每百万 8 元，则这次生成费用是 `0.006 + 0.008 = 0.014 元`。若查询嵌入另花 0.001 元，没有其他收费步骤或重试，这次查询合计为 0.015 元。

有缓存命中、缓存未命中等不同计费档位时，分别用实际数量乘对应单价；各档位不能重复计数。按调用次数收费的服务，按“次数 × 单价”计算。以实际账单规则处理其他收费项目，不把不存在的收费步骤估算进去。

**整批平均每次查询成本 = 所有已发起查询的费用总和 ÷ 已发起查询数。**

例如，发起 100 道题，包含失败和重试在内的系统费用共 1.50 元，平均每次查询成本就是 `1.50 ÷ 100 = 0.015 元`；即使其中只有 95 道正常交付，这个指标的分母仍是 100。

若没有发起查询，平均值记缺失。若部分账单、用量或单价缺失，应注明“费用未完整核算”；可以另列已知费用，不能把缺失项当成 0 元后宣称得到完整成本。

它主要能反映：

- 实际送入模型的资料变长后，输入费用是否增加。
- 更换模型或服务后，单次调用费用是否变化。
- 检索调优是否减少无效上下文，或增加额外收费步骤。
- 重试和生成长度变化是否影响每题费用。

费用分成三类，分别展示：

| 费用类别 | 是否计入核心每次查询成本 |
|---|---|
| 查询过程中的系统调用费用 | 计入，包含失败和重试 |
| 一次性资料处理、全库向量化与建库费用 | 单列，不混入每次查询 |
| Ragas 裁判与评分用嵌入费用 | 单列，不混入系统费用 |

优先使用接口返回的实际计费量与对应单价；估算值明确标注。字符数不能直接当作 token 数。若只核算 API 账单，就将结果明确标为“平均每次查询 API 调用成本”；本地硬件费用未核算时注明范围，不能据此宣称本地运行成本为零。

“每个合格答案的成本”暂不列为核心指标，待合格标准确定后再考虑作为补充结果。

## 五、怎样用六项指标理解改造效果？

**chunk 变长、链路变长，都可能影响质量、耗时和费用，但影响不一定始终同向。** 长文本可能提供更完整的依据，也可能带来干扰；去重可能减少无效内容；固定上下文预算也可能让更多正文被截断。应记录实际送入模型的资料与 token，而不是只根据平均 chunk 字符数推算收益或开销。

下面是可以重点查看的几类结果。这些是调查线索，需要结合逐题资料和回答确认原因。

| 看到的结果 | 说明什么，接下来查看哪里 |
|---|---|
| 检索覆盖和精度提高，回答正确性也提高 | 上游改善传递到了最终回答，再看耗时与费用是否可接受 |
| 检索提高，回答基本不变 | 查看新增依据是否真正送入模型，以及模型是否利用了这些依据 |
| 检索覆盖提高，但精度或回答下降 | 查看是否混入无关资料、发生截断或增加了理解干扰 |
| 忠实度提高，回答正确性下降 | 查看模型是否更谨慎，却漏答了重要内容 |
| 质量提高，耗时或费用明显增加 | 判断新增质量收益是否值得付出这部分代价 |
| 质量接近，耗时和费用降低 | 改造可能提高了效率，不必只有质量涨分才算有效 |

## 六、比较时必须保持哪些条件？

### 第一阶段只看已确定的组合变量

第一阶段关注 **数据治理＋嵌入模型更换**，检索方式保持“稠密向量＋固定阈值＋Top-K”。有可比对照时，报告这两项改造的组合影响，不分别宣称其中一项贡献了多少。

后续再逐步加入检索融合、重排等功能，观察新增步骤对同一组指标的影响。链路加长的代价放在对应阶段评价。

### 分清“指标复用”和“成绩可比”

比较时固定问题、审核后的参考答案、原始资料范围、回答模型、提示词、上下文预算和评分条件。两个配置的质量分差在双方都有效评分的相同题目上计算，同时保留各自完整的运行状态。只沿用相同指标名称，不代表两次总分可以直接相减。

一轮正式报告没有 RAG 检索核心成绩，但留存了 1,000 条完整检索记录和 200 条小题集记录，包含实际上下文、标准正文和检索 ID，可作为回溯补算的材料。能否与二轮构成可比样本，还需要核对；补算结果应标为后来完成的评分。

**没有可比基线时，先报告新系统的表现，不宣称数据治理和嵌入模型更换已经带来多少提升。** 这一限制同时适用于检索层和生成层。

## 七、正式成绩单怎样展示？

成绩单以六项核心指标为主，同时注明实验配置、运行范围与完成数量。

当前题集为 **200 题：130 道单跳、70 道跨块题**。除整体成绩外，分别展示单跳／跨块和资料来源分组，避免平均分掩盖某一类问题退步。

**四项质量指标怎样汇总？** 每道题先各自计算分数，再对该项成功评分的题目取普通平均：`该项有效单题分数之和 ÷ 该项有效评分题数`。每道题权重相同，不把所有题的陈述合并后重新算一个比例；这样可避免长答案自动获得更大权重。保留完整计算精度，展示时再统一四舍五入。

例如，200 题中 Context Recall 成功评分 190 题，就报告“均分 0.xx，有效评分 190／200”，并说明其余 10 题的原因。其他质量指标可能有不同的有效数量，应分别标注。算出的均分只描述有效评分样本，不能代替全部题目的交付情况。

以下是必要的背景记录，不新增核心指标：

- 每项质量分旁写清有效评分数；检索异常、零结果、空答案、拒答、未运行和评分失败分别记录，不能静默删除或一律填 0。
- 对正常可答题，空答案属于未交付，不能因没有错误陈述而得到优秀质量成绩；不可评分的项目注明原因。
- 保留每题的问题、实际检索资料、模型真实输入、回答与评分，便于复核。
- 检索计分检查实际结果；参考答案与标准正文只供评分，不能用于补齐系统未检索到的资料。
- 标准 ID 命中、全部依据命中、重复正文、分阶段耗时和 token 数可作为诊断明细，不都放进核心成绩表。
- 先审核参考答案，并用少量人工确认的正确、漏答、答错样例检查裁判。不能仅凭分数超过某个值就宣称系统合格。

仅检索实验先填写两项检索质量分与对应的检索耗时、费用；生成指标记为未运行。完整 RAG 实验再形成六项成绩，不混用两种范围的耗时与成本。
