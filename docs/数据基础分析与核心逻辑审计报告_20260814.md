### 1.2 数据类型与标注格式

**类型一：政策切块数据（`DATA/raw_data/*_data_chunks.md`）**

这是 `raw_policy/` 目录下 50 个 CSV 表经 `CsvLoader`（清洗 → 中文标题结构化 → `SemanticChunker` 切片）后导出的中间 Markdown，与最终写入 Milvus 的数据 **1:1 对应**。文件格式（`xunfei0001_policy_documents_copy2_data_chunks.md` 为例）：

```markdown
# Chunks: xunfei0001_policy_documents_copy2_data.csv
> 总行数: 314
> 总 Chunk 数: 7040

## 行 2: 国家发展改革委法规司负责同志就《评标专家...答记者问》
- **政策名称**: ...
- **发布时间**: 2024-10-20 15:31:00
- **来源**: 上海公共资源交易中心
### 前言
#### Chunk 0
```（chunk 文本）```
```

标注格式要点：每个 chunk 携带 **`doc_name`（政策名称）、`chapter`（章节路径，如"前言 > 第一章 总则 > 第一条"）、`chunk_index`（块内序号）** 三类元数据，无全局唯一 ID。

**类型二：法律法规全量 JSONL（`bidding_laws_all.jsonl`）**

每行一条法规，字段：`doc_id、title、full_text、source_url、publish_date、doc_number、law_level、publish_department、jurisdiction_name、crawl_time`。共 717 部法规，效力层级分布：

| 效力层级（law_level） | 数量 |
|---|---|
| 地方性法规 | 346 |
| 部门规章 | 345 |
| 行政法规 | 26 |

发布部门以财政部（349）、国务院（208）、国务院办公厅（38）为主。

**类型三：结构化查询测试集（`testset_*.jsonl`）**

`testset_bid_project` / `testset_company_info` / `testset_company_penalty` 各 500 条，字段为 `sample_id、question、expected_sql、expected_fields、ground_truth、answer_text、difficulty（简单/中等/困难）、source_file`。这是**面向价格询价/结构化查询链路**（而非知识库 RAG）的评测集。

### 1.3 业务覆盖范围

- **法律法规类专业知识**：`public_kb` 集合 29,729 个 chunk（去重后仅 15,955 个唯一 chunk），覆盖招标、投标、评标、政府采购、合同、监督、法律责任等全链路法规条款；`bidding_laws_all.jsonl` 为 717 部法规的完整文本。
- **政策与案例**：`xunfei0002` 系列为政策问答对（组 C，1 行≈1 chunk），`xunfei0003_policy_anli` 系列为案例类数据。
- **结构化业务数据**：`mysql_price_semantic` 集合 77,597 条，源自 `company_info` / `company_penalty` / `bid_project` 三张表（`product_info` 已下线）。

### 1.4 法规类专业知识占比与分布

从云端 Milvus 实测看，`public_kb` 中法规条文存在**大量跨文档重复引用**（详见第五节），典型如《中华人民共和国招标投标法实施条例》同一批 chunk 被 8 次写入，且部分条文（如"招标人应当在招标文件中载明投标有效期…"）同时出现在 3 部不同法规文档中。这说明知识库的**法规类内容占比极高**（≥ 95%），但**去重严重不足**，真实有效信息量显著低于名义 chunk 数。

## 二、核心系统逻辑审计

### 2.1 检索逻辑审计（Milvus 向量检索全链路）

**全链路流程**（`public_kb/qa_chain.py` 的 `_retrieve`）：

```
用户问题 → BGE-m3 稠密向量化(1024维) → 检查 sparse_vector 字段
        ├─ 存在：稠密 COSINE + 稀疏 BM25 → RRF 融合(k=60) → bge-reranker 精排 → 自适应阈值 → Top-5
        └─ 不存在（当前实际）：纯稠密 COSINE 检索 → 固定阈值 0.45 过滤 → Top-5
```

**检索参数配置（`config.py`）实测核对**：

| 参数 | 配置值 | 实际生效状态 |
|---|---|---|
| 向量生成模型 | `BAAI/bge-m3`（1024 维，SiliconFlow 端点） | ✅ 生效 |
| 索引类型 | `IVF_FLAT` | ✅ 生效（实测确认） |
| 相似度度量 | `COSINE` | ✅ 生效 |
| nlist | 配置注释/CLAUDE.md 写 128，**实测云端为 256** | ⚠️ 文档与实现不一致 |
| nprobe | 32 | ✅ 生效 |
| 稠密候选数 | 30 | ✅ 生效 |
| 稀疏检索 | `sparse_vector` 字段 + BM25 | ❌ **未生效（集合无此字段）** |
| RRF 融合 | k=60 | ❌ **未生效（依赖稀疏检索）** |
| 重排序 | `bge-reranker-v2-m3` | ❌ **未生效（依赖混合检索路径）** |
| 相似度阈值 | 自适应 0.40/0.45/0.50（仅混合路径） | ❌ **实际走固定 0.45（dense-only 路径）** |
| 最终 Top-K | 5 | ✅ 生效 |

**关键发现（检索逻辑短板）**：

1. **"混合检索"名存实亡**：代码宣称"稠密 + 稀疏 BM25 → RRF → Reranker"，但实测云端 `public_kb` 集合字段仅为 `id / text / vector` 三个，**没有 `sparse_vector` 字段**。`qa_chain.py` 在 `describe_collection` 检测到无稀疏字段后直接 `return _dense_only_retrieve()`，导致 **RRF 融合与 bge-reranker 重排序在生产环境从未被执行**。重建脚本 `rebuild_and_verify.py` 的"双向量模式"仅停留在打印文案，未真正建稀疏字段。
2. **阈值固定、无自适应**：自适应阈值逻辑（top1≥0.75 放宽至 0.40）只在混合检索路径下生效，实际退回固定 0.45 阈值，低分相关 chunk 被一刀切丢弃。
3. **无查询改写/意图解析**：`knowledge_qa` 节点直接 `embed_query(question)`，对口语化、指代、多义词无任何预处理，长尾问法召回脆弱。
4. **nlist 文档漂移**：CLAUDE.md 与 `project_overview.md` 标注 nlist=128，实现（`milvus_store.py` L73）与云端实测均为 256，说明文档已过期。

### 2.2 存储逻辑审计（数据从切片到落库全周期）

**写入流程**（`public_kb/process_csv.py` + `csv_loader.py` + `milvus_store.py`）：

```
CSV 源表 → CsvLoader._parse_csv(列名归一化/BOM/多行content)
        → _process_row(中文标题转 Markdown 标题 → TextCleaner 去噪 → SemanticChunker 切片)
        → save_chunks_to_markdown(DATA/raw_data/*_chunks.md 中间存储)
        → MilvusStoreManager.add_documents(批量向量化 bge-m3 → insert)
```

**字段定义（云端实测）**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INT64，`auto_id=True` 主键 | **Milvus 自增，无业务含义** |
| `text` | VARCHAR(65535) | chunk 文本 |
| `vector` | FLOAT_VECTOR(1024) | BGE-m3 稠密向量 |
| 动态字段（`enable_dynamic_field=True`） | — | 透传 `doc_name / chapter / chunk_index / title / source_file / source_url / publish_date` 等元数据 |

**分片与持久化**：集合未显式配置分片（默认 1 shard）；索引 `IVF_FLAT / COSINE / nlist=256`，全量 29,729 条已建索引（`indexed_rows=29729, state=Finished`）；数据持久化于云端 Milvus（第一阶段已从本地迁移至 `8.130.174.43:19530` 并通过一致性校验）。

**关键发现（存储逻辑短板）**：

1. **无业务唯一 chunkID**：`id` 为 `auto_id` 自增，每次导入同一 chunk 会得到不同 id；业务上无 `chunk_id`/`doc_id` 字段，`chunk_index` 仅在同一 `chapter` 内递增且**实测取值范围仅 0~9、其中 0 占 29,544/29,729**，完全无法作为全局唯一标识。
2. **增量导入无幂等/去重**：`add_documents` 直接批量 insert，不检查 `(doc_name, chapter, text)` 是否已存在，重复执行导入或导入同表多份快照即产生重复 chunk（实测 55.57% 重复即源于此）。
3. **切片重叠制造近重复**：`SemanticChunker` 对超长块按句子二次拆分，`overlap_chars=100` 的重叠文本使相邻 chunk 存在 100 字冗余，虽非完全重复但会干扰"内容哈希精确去重"之外的语义评估。

### 2.3 专业问答逻辑审计（法律法规垂直领域问答链路）

**响应流程**（`agent/nodes/knowledge_qa.py` + `public_kb/rag_engine.py` + `qa_chain.py`）：

```
router(意图=knowledge_qa) → node_knowledge_qa
  → PublicKnowledgeRAG.query(question)   # 惰性单例
  → LCEL 链：{"docs": _retrieve(question), "question": passthrough}
  → _decide_and_answer:
       docs 为空 → 拒答("知识库中暂无相关内容")
       docs 非空 → _format_docs 拼接上下文 → prompt | llm | StrOutputParser → 回答 + sources
```

**问题解析**：无独立 query 改写层，直接向量化原文。
**向量匹配**：纯稠密 COSINE（见 2.1）。
**结果排序**：实际无重排序（reranker 未生效），仅按 COSINE 分数降序。
**答案生成**：System Prompt 强制"严格依据参考资料作答，不添加资料外信息；不足则明确告知无法回答"，回答附带 `sources`（doc / chapter / chunk_index / content_snippet / score）。

**准确性支撑逻辑评估**：

- ✅ 正向支撑：拒答机制（无相关结果不硬答）、溯源引用（每个回答带来源章节与相关度）、领域 System Prompt。
- ⚠️ 短板：检索环节已退化（无稀疏检索、无重排序、固定阈值），导致"答案质量上限"被检索质量钳制——**相同条文因不同文档的 chunk 分数差异，可能召回非权威来源（如政策解读而非法规原文）**；且 55.57% 的重复 chunk 使 LLM 上下文被冗余内容占用，削弱关键条款的呈现密度。

## 三、测试集构建方案

结合上述审计结论（检索退化为纯稠密、55.57% 重复、chunkID 不可靠、拒答机制存在），设计**分层、可溯源、面向语义评估**的专用测试集。

### 3.1 设计原则

1. **以语义为真值锚点，不以 chunkID 为准**（由第五节结论决定）。
2. **分域分难度**：按业务域（法规/政策/案例/结构化）与难度（简单/中等/困难）分层抽样。
3. **含负样本**：纳入"知识库外/应拒答"问题，验证拒答机制。
4. **溯源标注**：每条标注 `标准答案 + 支撑证据（chunk 内容片段，而非 ID）+ 必备事实点`。

### 3.2 测试集结构（建议 4 个子集，共约 1,200 条）

| 子集 | 覆盖域 | 规模 | 说明 |
|---|---|---|---|
| T1 法规条款问答 | 招标/投标/评标/合同/监督/法律责任 | 400 | 从 `public_kb` 唯一 chunk 中抽取，标注支撑条文 |
| T2 政策文件问答 | 部门规章、地方性法规、政策解读 | 300 | 覆盖 `bidding_laws_all.jsonl` 的 717 部法规抽样 |
| T3 负样本/拒答 | 知识库外问题、跨域问题 | 200 | 验证拒答与不幻觉 |
| T4 结构化查询 | 企业/处罚/项目询价 | 300 | 复用/扩充现有 `testset_*.jsonl`（1,500 条） |

### 3.3 单条样例格式

```json
{
  "sample_id": "kb-0001",
  "question": "评标委员会由哪些人组成？",
  "category": "评标规则",
  "difficulty": "简单",
  "standard_answer": "依法必须招标的项目，评标委员会由招标人的代表和有关技术、经济等方面的专家组成，成员人数为五人以上单数……",
  "supporting_evidence": [
    {"doc_name": "中华人民共和国招标投标法", "chapter": "第四章", "content_snippet": "第三十七条 评标由招标人依法组建的评标委员会负责……"}
  ],
  "key_facts": ["五人以上单数", "技术、经济专家不少于三分之二"],
  "expect_refusal": false
}
```

### 3.4 评估维度

- **召回覆盖**：支撑证据 chunk 是否被检索命中（语义匹配，见第四节）。
- **答案忠实度**：答案是否仅依赖召回上下文（无幻觉）。
- **事实点命中率**：`key_facts` 是否全部覆盖。
- **拒答正确率**：负样本是否被正确拒答。

## 四、召回验证指标选型论证

### 4.1 方案对比

| 评估维度 | 方案1：语义对比方案 | 方案2：硬过滤 chunkID 方案 |
|---|---|---|
| **原理** | 召回结果文本与标准答案分别向量化，算余弦相似度 | 校验召回 chunk 的 chunkID 是否与标注 chunkID 完全匹配 |
| **适用场景** | 通用，支持"内容正确但来源不同/表述不同" | 仅适用于 chunkID 全局唯一且标注可信的场景 |
| **准确率** | 中高（受 embedding 质量影响，可辅以阈值标定） | 名义上高，**实际因 chunkID 不唯一而失真** |
| **实现成本** | 低（复用现有 bge-m3 向量化 + 余弦计算） | 低（ID 字符串比对），但需先重建唯一 ID 体系 |
| **对业务适配性** | 高，容忍法规条文跨文档重复引用 | 极差（见 4.2） |

### 4.2 硬过滤 chunkID 方案的致命缺陷（结合实测）

1. **chunkID 不存在唯一稳定定义**：`public_kb` 主键为 `auto_id` 自增，无业务 chunkID 字段。
2. **候选业务键均不唯一**（实测）：
   - `chunk_index` 取值范围仅 0~9，其中 0 出现 29,544/29,729 次；
   - `(doc_name, chapter, chunk_index)` 三元组存在 **2,473 组重复**；
   - 55.57% 的 chunk 内容重复，同一内容对应多个不同 id。
3. **结果失真**：标准答案标注的 chunkID 会命中多个内容相同但 id 不同的 chunk；向量召回返回"内容正确但 id 不同"的 chunk 会被硬匹配判为失败，**召回率被系统性低估**；反之若按 id 模糊匹配，又因 id 不唯一而无法判定唯一性。方案 2 在数据未去重前**不可用**。

### 4.3 选型结论

**采用方案1（语义对比方案）为主指标**，并作如下工程化增强：

- 召回结果与标准答案分别用 **bge-m3** 向量化后计算余弦相似度，设双阈值：`≥0.85` 判命中、`0.70~0.85` 判待人工复核、`<0.70` 判未命中；
- 辅以 **关键词/事实点命中**（`key_facts` 覆盖度）作为第二指标，弥补纯向量相似度对"具体条文号、数字"的钝感；
- 增加 **Top-K 召回率**（标准答案支撑 chunk 是否进入 Top-5）与 **MRR** 作为检索排序质量的补充度量；
- 在完成数据去重（见第五节）后，可**追加** chunkID 方案作为精确核验的辅助指标，但现阶段不作为主指标。

## 五、重复数据排查报告

### 5.1 检测方法

对云端 Milvus `public_kb` 全量 29,729 行分页拉取（`query_iterator`，绕过 offset+limit≤16384 窗口限制），对每个 chunk 的 `text` 做规范化（去首尾空白 + 统一换行）后计算 **MD5 内容哈希**，统计哈希重复组；同步统计 `id` 主键唯一性、`chunk_index` 取值分布、`(doc_name, chapter, chunk_index)` 三元组重复。

### 5.2 检测结果（实测数据）

| 检测项 | 结果 |
|---|---|
| 集合总行数 | 29,729 |
| 唯一文本哈希数 | **15,955** |
| 重复文本组数 | **2,746 组** |
| 重复的多余副本数 | **13,774 条** |
| 涉及重复的行数 | **16,520 条（55.57%）** |
| `id` 主键重复 | 0（主键唯一性正常） |
| `chunk_index` 不同取值数 | 10 个（0~9） |
| `chunk_index = 0` 的行数 | 29,544（99.4%） |
| `(doc_name, chapter, chunk_index)` 重复组 | 2,473 组 |
| `mysql_price_semantic` 重复 | **0**（结构化集合干净） |

**重复样本举证**（实测）：

- 《中华人民共和国招标投标法实施条例》同一批条文 chunk（如"招标人可以对已发出的资格预审文件…"）**出现 8 次**，id 各异，doc_name 相同——即同一文档被重复导入 8 份；
- 条文"招标人应当在招标文件中载明投标有效期…"**出现 10 次**，且横跨 3 个不同 doc_name（《实施条例》、《民航专业工程建设项目招标投标管理办法》、《水运工程建设项目招标投标管理办法》）——即法规条文被多部规范交叉引用。

### 5.3 重复根因分析

1. **源表多快照重复导入**：`raw_policy/` 中 `xunfei_ods`、`xunfei4_ods`、`xunfei5_ods`、`lin_gang_6_ju_tou_1_ods` 四个 CSV 均为同一张 `ods_policy` 表的快照（各 12,822 chunk）；`xunfei0001_policy_documents_copy2` 与 `xunfei07_rag_db_policy_records` 同为一张表（各 7,040 chunk）。文件名带 `copy2`、`_v1` 等后缀即表明同源多版本。
2. **增量导入无去重**：`MilvusStoreManager.add_documents` 直接 insert，无 `(doc_name, chapter, text)` 存在性检查。
3. **法规条文跨文档引用**：同一法律条文在"法律原文""政策解读""地方细则"中重复出现，属领域固有现象，但当前未做来源优先级消歧。

### 5.4 重复数据对"硬过滤 chunkID 方案"的致命影响

由于 **55.57% 的 chunk 内容重复、chunk_index 几乎全为 0、无业务唯一 chunkID**，硬过滤 chunkID 方案无法建立"标准答案 ↔ 唯一 chunk"的映射：同一标准答案的支撑证据对应多个 id，向量召回返回的"内容正确但 id 不同"的 chunk 会被硬匹配误判为失败，导致召回率评估结果完全失真、不可信。**结论：在完成数据去重与唯一 chunkID 体系建设之前，硬过滤 chunkID 方案不可用。**

### 5.5 治理建议

1. 入库侧增加 **内容哈希去重**（`(doc_name, chapter, text_hash)` 判重），增量导入前先查重；
2. 建立 **权威来源优先级**（法律原文 > 行政法规 > 部门规章 > 地方细则 > 政策解读），同内容跨文档时仅保留最高优先级来源，或在其元数据中标记 `is_canonical`；
3. 引入业务唯一 chunkID（如 `doc_id:chapter:index`，`doc_id` 用 source_file+doc_name 的确定性哈希），替代 `auto_id` 作为检索结果锚点；
4. 重建集合（`rebuild_and_verify.py` 已具备骨架），去重后预计可压缩至约 1.6 万唯一 chunk。

## 六、测评框架选型结论

### 6.1 第三方框架 vs 自研框架对比

| 评估维度 | 第三方框架（RAGAS / DeepEval / TruLens） | 自研轻量框架 |
|---|---|---|
| **适配成本** | 高：需将 Milvus 检索链路改造成其要求的 Ragas 数据格式（question/contexts/answer/ground_truth），对 `pymilvus` 原生 `query_iterator` 链路需写适配层 | 低：直接复用 `PublicKnowledgeRAG.query()` 与 `price_inquiry` 节点接口，以及现有 `testset_*.jsonl` 评测集 |
| **功能覆盖度** | 通用 RAG 三指标（faithfulness / answer_relevancy / context_relevancy）成熟，但**无招投标领域专属指标**（法条溯源准确率、拒答正确率、项目编号识别） | 可按需实现领域指标，覆盖通用 + 专属 |
| **可扩展性** | 一般：依赖其评估模型（默认 OpenAI/自选 LLM），扩展自定义指标需按框架约束 | 高：指标函数独立，直接新增 |
| **维护成本** | 外部依赖，版本升级/API 变化不可控；部分指标依赖额外 LLM 调用（成本） | 内部可控，代码量小，随项目演进 |
| **与现有 Milvus 检索链路兼容性** | 差：需桥接（本项目检索直接返回 `(Document, score)` 列表 + 元数据，非其默认 Context 结构） | **完美：直接调用现有检索函数，零改造** |

### 6.2 选型结论

**采用"自研轻量测评框架为主 + RAGAS 通用指标作参照"的混合方案**：

- **主框架（自研）**：实现 `recall@k / MRR / 语义相似度命中率 / 事实点命中率 / 拒答正确率 / 溯源准确率` 六个指标，直接对接 `public_kb.query()` 与 `node_price_inquiry()`，复用第五节去重后的测试集（第三节）。
- **参照（RAGAS 或 DeepEval）**：仅用于通用 faithfulness / answer_relevancy 的横向对标，不做链路改造，避免适配成本。
- **落地优先级**：① 先数据去重（第五节）→ ② 自研指标框架 + 测试集落库 → ③ 跑基准并归档 → ④ 视需要引入第三方通用指标对标。
