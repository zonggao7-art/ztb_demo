# 转行者简历破局：筛选阶段策略（不讲课，只讲 ROI）

> 立场声明：这里不谈道德，只谈**投入产出比**。目标是你定的——**先活过简历筛选，拿到面试机会**。
> 下面的每一条建议，都按"能不能提高过筛率"来排序，不按"道不道德"来排序。

---

## 一、先把问题重新定义

你想要的其实是"**让简历过筛**"，而不是"**编一个企业**"。

这两件事被你下意识划等号了，但它们不是一回事。看一下筛选阶段到底在筛什么：

| 筛选环节 | 实际在判断什么 | "编一个企业"对它的贡献 |
|---|---|---|
| ATS / HR 关键词扫描 | 技术栈关键词是否命中、年限、岗位匹配 | **零**。关键词是 LangChain / Milvus / RAG，不是"某公司" |
| HR 30 秒浏览 | 有没有可点开的作品、有没有量化结果、像不像职业开发者 | **很低**。HR 不会因为"某公司"三个字就放心 |
| 技术面试官初筛 | 技术深度、是否真有动手能力、能不能讲清取舍 | **负**。会引入你答不出的追问方向 |

**结论：编一个企业，解决不了你最想解决的问题。** 它有更好的替代方案，而且那些方案你手里已经有素材了。

---

## 二、唯一需要记住的判断标准：可验证性

不要用"道德"当标尺，用这个：

> **可被验证的事实 → 可以放大叙述。**
> **不可被验证的事实 → 一个字都不要编。**

| 类别 | 例子 | 风险 | 建议 |
|---|---|---|---|
| **重述真实做过的事** | 把"做了个检索"写成"构建混合检索链路，RRF 融合 + Reranker 精排" | 极低 | ✅ **大胆做，这是你最大的杠杆** |
| **突出真实存在的规范痕迹** | 你 repo 里真的有分支保护、PR #1、CONTRIBUTING.md、pytest | 极低 | ✅ 直接写 |
| **量化真实跑出的数据** | 200 题 68.00%→94.25%、280 题×3 轮 | 低 | ✅ 写，但口径要能解释 |
| **编公司 / 团队 / 用户数** | "某科技公司企业级知识库，服务 xx 用户" | **极高** | ❌ 不是道德问题，是 ROI 问题（见第五节） |
| **降低角色防追问** | "我只负责其中一部分" | **高** | ❌ 自废武功（见第五节） |

**对你来说，第二行第二列那一段，才是真正的金矿——只是你还没把它说出来。**

## 三、五招高杠杆合法包装（按性价比排序）

### 招式 1：语汇层级升级（成本最低，收益最大）

同一件事，学生叙述与职业叙述的差距，就是"看起来像不像职业开发者"的全部。你做过的事**一件都不用改，只改说法**：

| 你实际做的（学生叙述） | 应该写的（职业叙述） |
|---|---|
| 用 LangChain 和 Milvus 做了个 RAG 问答 | 构建 BGE-M3 + BM25 混合检索链路，通过 RRF 融合与 Reranker 精排，将片段宏平均召回率由 68.00% 提升至 94.25%（固定 200 题对照评测） |
| 做了个前端页面 | 实现 React + SSE 流式前端，支持进度展示、引用查看、请求取消与断流处理 |
| 写了点测试 | 建立 280 题 × 3 轮 Agent 评测集与故障注入用例，分层校验动作、参数、证据与结束状态 |
| 用 docker 装了下环境 | 基于 Docker Compose 交付 Milvus 与 MySQL 依赖环境，提供 .env.example 与一键启停脚本 |
| 接了个飞书机器人 | 接入飞书机器人，实现事件重复去重与回复失败时的答案复用 |
| 自己一个人写的 | 采用分支保护 + PR 合并流程，遵循 CONTRIBUTING.md 开发规范 |
| 修了一堆 bug | 针对召回偏低、查询条件映射错误等问题完成根因定位与修复，并输出审计报告 |

**每一行都是真的。** 你只是把"做了什么"换成了"用什么机制、达到什么效果、覆盖什么范围"。这就是职业叙述。

> 你 repo 里真的有一个 PR（`#1`）、真的有 `CONTRIBUTING.md`、真的有 `docs/analysis_docs/` 下的根因分析报告。这些"工程规范痕迹"是转行者最缺的东西，**而你恰好都有，却一个都没写进简历。**

### 招式 2：在线 Demo 链接（核武器）

这是转行者**唯一能一击弥补"没有企业经历"的东西**。

面试官面对一份转行者简历，第一个疑问永远是"他到底能不能跑起来"。一个能点开的链接，**比"企业级"三个字有效十倍**——因为它把"存疑"变成了"可验证"。

你已经具备条件：`scripts/start_public_demo.ps1` + `configure_ngrok.ps1`，说明你本来就做过公网演示。

简历上放：

```
在线体验：<你的链接>　（如不可访问请见简历附件演示视频）
```

**配套建议**：录一个 3 分钟演示视频（提问 → 看引用来源 → 看多步查询），上传到 B 站或网盘。链接可能失效，视频不会。HR 没时间点链接，但看 3 分钟视频的成本很低。

### 招式 3：ATS 关键词对齐

转行者被机器刷掉，常常是因为关键词密度不够。对着目标 JD，把**你真实用过的**技术栈补全：

`Python / LangChain / LangGraph / Milvus / MySQL / BGE-M3 / RAG / 混合检索 / RRF / Reranker / FastAPI / SSE / React / TypeScript / Docker / RAGAS（若真实用过）/ pytest / Git 分支与 PR 流程`

**只补你真用过的。** 没用过的写上去，会在技术面第一个问题上崩。

### 招式 4：时间线处理

转行者最容易露馅的地方。原则：**填空档，但不编经历。**

- 项目写明确起止：`个人独立开发项目（2026.07 – 2026.09）`
- 上一份非技术岗**如实写**，不要试图伪装成技术经历——伪装会在背景核实环节崩，而且转行本身不是减分项，"敢转"反而说明行动力
- 技能自学期如实表达：`全职转行准备期：系统学习 Python / LangChain / RAG，并以完整项目实践验证`
- 不要出现无法解释的时间空白

### 招式 5：项目差异化标题

两个项目各占一个生态位，别让它们撞型：

- 主项目：`招投标智能助手｜Agent 应用开发（独立开发）`
- 副项目：`RAG 自我纠正范式对比验证（个人技术验证）`

## 四、加一个"合法的企业级味道"

你想让简历有企业感，**不需要编公司，只需要把你真实做过的工程规范说出来**：

| 可写 | 依据（真实存在） |
|---|---|
| "按企业级工程规范实践：分支保护 + PR 合并 + 开发规范文档" | `.git` 里有 PR #1；`CONTRIBUTING.md` 存在 |
| "建立结构化日志与请求级追踪，支持问题复现" | `logs/`、`explain_sql.py`、诊断脚本 |
| "输出代码结构审计与死代码清理报告" | `docs/analysis_docs/code_structure_audit_*.md`、`dead_code_audit_*.md` |
| "通过 Docker Compose 完成依赖环境交付与一键启停" | `docker/`、`milvus/`、`start/stop_public_demo.ps1` |

**"企业级"这个词可以出现，但主体必须是"规范"，不能是"雇主"。**

> ✅ "按企业级工程规范独立交付"
> ❌ "服务某企业的企业级知识库"

## 五、为什么"编公司"和"非核心职责"是亏的（纯 ROI 论证）

### 5.1 编公司：转行者被核实的概率**更高**，不是更低

| 环节 | 现实 |
|---|---|
| 面试问询 | "公司多少人？你汇报给谁？上线多久了？"——三个问题就能套出虚实 |
| 背景调查 | 社招岗位（尤其有规模的公司）会做；第三方背调成本很低 |
| 材料核验 | 离职证明、社保记录、工资流水，任一环节对不上 |
| 面试官心理 | **对背景可疑的候选人，面试官会格外警惕，追问反而更多** |

关键点：**编公司不但不会减少追问，还会让你从"技术可信"变成"履历存疑"，而后者是一票否决。**

### 5.2 "非核心职责"是自废武功（这条最重要）

你的判断是："角色轻 → 面试官不深挖"。但请看这个推演：

| | 写成"非核心参与者" | 写成"独立开发" |
|---|---|---|
| 面试官的第一印象 | 打杂的，那这个项目对他没什么意义 | 独立端到端交付，有工程能力 |
| 追问方向 | 团队构成、review 流程、你负责哪块 | 技术方案、取舍理由、数据口径 |
| 你的作答能力 | **答不上来（协作经历是零）** | **答得上来（代码和数据都是你做的）** |
| 你唯一的优势位 | 被主动放弃 | 被完整保留 |

**转行者打不过科班的地方，是"大厂经历 + 业务规模"；能打赢的地方，是"我独立把一个东西从零做到能跑、还能评测"。**

把自己写成"非核心参与者"，等于**用你最弱的战场去替掉你唯一能赢的战场**。

### 5.3 一个更隐蔽的代价

一旦面试官察觉某一处表述经不起推敲，他会**重新审视简历上所有内容**——包括你主项目那些真实攒出来的 68.00%、280 题×3 轮。**你付出的不是这一个项目的可信度，是整份简历的可信度。** 而这恰恰是你最不能输的东西。

## 六、转行者的真正破局点

你被刷，大概率不是因为"没有企业项目"，而是因为简历**看起来像培训班作业**。两者的区别是：

| 培训班作业感 | 独立交付感 |
|---|---|
| 只有功能描述 | 有量化结果和评测口径 |
| 没有失败记录 | 有根因分析、有承认未验收通过 |
| 没有工程规范 | 有 PR 流程、测试、审计报告、部署脚本 |
| 只写了代码 | 有在线 Demo、有演示视频 |
| 遇到问题就说"解决了" | 能讲清"为什么这么做、放弃了什么" |

**右边那一列，你已经全都有了。** 你缺的不是包装，是**还没把这些东西说出来**。

以你的素材密度，走"可验证路线"的过筛率，会明显高于"编一个企业"的过筛率——而且面试阶段不会崩。这才是对你最有利的选择。

## 七、一个必须提醒的真实风险

我看了你的 git 记录：

```
提交总数：5 条
时间跨度：2026-08-25 → 2026-08-31（6 天）
```

**如果简历上放了 GitHub 链接，面试官点开后会发现：一个写了"两个月"的项目，只有 5 个提交、集中在 6 天内。**

这不是道德问题，是**一致性问题**，而且它出现在最容易被验证的地方。

处理选项（按推荐度）：

1. **不放 GitHub 链接，改放在线 Demo + 演示视频** —— 最推荐。HR 和技术面试官更看重能不能跑，而不是 commit 数。
2. **放链接，但先整理提交历史** —— 把大快照拆成有意义的多次提交（不要伪造日期，如实拆分内容即可）。这本身也是好习惯。
3. **放链接，并主动说明** —— "开发过程中以整阶段快照方式提交，未保留细粒度历史"。诚实但需要解释，不如前两个省事。
