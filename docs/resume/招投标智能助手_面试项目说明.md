# 招投标智能助手：项目经历与面试准备

整理日期：2026-09-16。目标岗位：Agent 应用开发、大模型应用开发。采用 STAR；主线为 Agent 工程能力，RAG 指标与网页、飞书演示提供支撑。

本次更新纳入本人补充的业务研究、产品线取舍、SQL 与 RAG 经历，以及项目记录中的 Agent 设计与排障案例。本文用于理解系统、解释技术决策和核对指标；完整的 STAR 故事、口述稿及逐项证据见[面试故事库](D:/DEMO/zhaotoubiao_demo/docs/resume/招投标智能助手_面试故事库.md)。先读第 1、2、9 节建立项目介绍，再按追问查阅技术章节。

## 1. 项目定位与个人职责

这是一个历时两个月、个人独立开发的招投标领域 Agent 项目。本人负责数据处理、知识库建设、工具封装、执行编排、评测、后端服务、前端与飞书接入。没有真实业务用户或企业生产使用；已有网页和飞书体验入口。

**业务定位：面向供应商信息核查与招投标法规咨询的领域助手。** 围绕已收录的同一家企业，衔接工商、经营范围、处罚、中标历史和项目详情查询；法规侧根据用户描述的场景检索相关知识并组织带来源的解答。需要多步查询时，Agent 根据当前结果选择后续工具，程序控制工具执行与结果发布的边界。

项目追求的价值是把关联信息查询与场景化知识问答接到同一交互入口，让用户能核对结果来源。现有实现提供查询和问答能力，没有覆盖供应商准入、审批、履约等完整管理流程，也没有竞品研究证明这些能力为本项目独有。

本人确认 7 月 20 日开始项目，第一周先研究行业流程、角色及业务问题，并形成业务需求文档。后续测试中，产品行情查询暴露效果问题，本人又对其增量使用价值存疑，因此阶段性下线产品线，把投入集中到企业关联信息与法规问答。这是基于当时资料和测试作出的范围取舍，尚无真实用户反馈验证市场需求。

当前最值得展示的三个能力：

1. 把 LLM 的工具调用能力接入真实数据服务，并处理参数、预算、错误与证据边界。
2. 对 RAG 的检索质量建立可复现的对照实验，能够解释提升来自哪里、代价是什么。
3. 将后端能力接入网页和飞书，处理流协议、取消、断流、状态一致性及消息重投等集成细节。

## 2. STAR 叙述

### S：背景

供应商信息核查需要衔接企业资料、处罚和中标数据；用户描述的招投标场景又需要匹配法规知识。早期项目希望进一步覆盖排名、供应商推荐和行情等开放请求，但测试出现查询条件映射错误、应有字段未返回和无关召回，促使本人重新审视范围与查询链路。

这是项目选择的应用场景，尚未测量真实用户检索时间或业务效率。面试中不应扩写成已经服务某公司、支撑某业务规模。

### T：任务

在约两个月的个人开发周期内，先确定数据和查询规则能够支撑的核心能力，再独立交付可体验的领域助手：支持场景化法规问答与五类结构化查询，能够根据中间结果继续调用工具，回答保留数据或文献来源；同时建立质量评测和异常处理机制。

### A：行动

- 沿意图解析、查询条件和返回字段排查开放查询问题，下线当时价值与效果不足以支持优先投入的产品线，明确核心查询范围及越界引导。
- 将业务能力封装为六个只读工具；从前置计划转向统一主 Agent 根据中间结果逐步选择动作，程序校验参数和结果范围，并约束调用预算和超时。
- 建设法规数据处理与混合检索链路，通过结构感知切分、正文覆盖门禁、稳定片段标识、幂等入库和引用校验维护证据关联。
- 用固定题集对照稠密检索、混合检索和重排；另对 Agent 的动作、参数、依赖、结束状态和可靠性开展分层评测。
- 用 FastAPI SSE 统一服务入口，接入 React 网页及飞书，完成正常查询、部分失败、断流与恢复等链路验证。

### R：结果

- 已有六类业务能力与可体验的网页、飞书入口。
- 历史冻结版本的 200 题离线对照中，标准证据片段宏平均召回率从 68.00% 提升至 94.25%；全部标准片段命中的题目从 123/200 增至 183/200。
- 完成 280 题 × 3 轮 Agent 主集评测及 24 场景 × 3 轮可靠性评测，暴露额外工具调用、依赖处理与状态判断问题，形成可追查的运行记录。
- 当次 Agent 正式验收未通过；评测建设是已完成的工程成果，不应将执行完成写成验收通过。

## 4. 当前系统链路

~~~mermaid
flowchart TD
    W[React 网页] --> API[FastAPI /chat/stream]
    F[飞书单聊适配器] --> API
    API --> A[统一主 Agent：本轮问题]
    A --> G[工具白名单 / Schema / 参数来源 / 预算]
    G --> K[knowledge_qa]
    G --> Q[五类精确 SQL 工具]
    K --> R[混合检索 / 重排 / RAG 回答与引用]
    Q --> M[MySQL 三张业务表]
    R --> E[范围与引用检查 / 请求级证据台账]
    M --> E
    E --> A
    A --> S[FinishAction]
    S --> P[程序发布已核验结果]
    P --> O[SSE 终态 / 网页展示 / 飞书回复]
~~~

当前默认模式为 unified：LangChain create_agent 执行主循环，外层使用 LangGraph 封装。legacy 与 hybrid 保留为显式回退入口。不能把旧 Router 先规划、再 static/ReAct 分流的架构直接作为现行默认架构介绍。

六个业务工具分别为：

| 工具 | 能力 | 主要输入 |
|---|---|---|
| knowledge_qa | 法规知识问答 | 当前轮法规问题 |
| query_company_registration | 企业工商信息 | 企业名称 |
| query_company_business_scope | 企业经营范围 | 企业名称 |
| query_company_penalty | 企业处罚记录 | 企业名称 |
| query_project_award | 项目中标情况 | 项目编号 |
| query_company_award_history | 企业中标历史 | 中标供应商名称 |

一次模型回复最多申请一个工具。主 Agent 依据工具观察继续行动或结束；最终业务正文由程序组合 SQL 事实、RAG 工具中已校验的答案及固定说明。主 Agent 不再自由改写这些事实，但 RAG 工具内部仍调用模型生成答案。

### 例子：项目查询 → 中标供应商 → 处罚查询

用户问：“查询项目 AH2024-001 的中标记录，再查中标供应商的处罚。”

1. 主 Agent 申请项目中标工具，程序检查项目编号来源与参数格式。
2. SQL 适配器按固定字段参数化查询，再检查返回记录是否属于请求的项目。
3. 返回记录中的供应商字段进入本轮证据台账，成为后续可见信息。
4. 主 Agent 使用该企业名申请处罚工具；程序再次校验输入及返回范围。
5. 程序分别发布两次查询的事实，保留记录与步骤的关联。

AH2024-001 来自离线测试夹具，用于讲解机制，不是网页演示的真实项目编号。该例展示的是结果依赖编排；当前不能据此声称所有多候选场景均能正确消歧。

## 5. 值得讲透的工程细节

### 5.1 为什么用业务工具，而不是让模型生成任意 SQL

这个选择来自实际失败。历史分析记录了“福建师范大学”被映射到 project_number 条件，导致候选在 SQL 阶段被错误过滤；另一份报告发现 SELECT 未包含回答所需的价格及工商字段。因此需要分别检查意图、字段映射、筛选条件、返回字段和数据覆盖，不能将所有问题归为模型不会写 SQL。现存早期材料描述的是模型生成意图 JSON、Python 构造 SQL；更早是否直接生成整段 SQL，本人目前不能确认。

本人将投入集中到供应商关联信息查询与法规问答。产品行情的增量价值当时尚未验证，现有报价数据和检索效果也不足以支撑可靠交付，因此阶段性下线。自然语言问法仍可变化，收敛的是可执行的业务能力与查询规则，并非只允许用户输入五句固定问题。历史 SQL 评测的 2.787% 与 99.464% 口径见第 7.4 节。

工具将可查的表、筛选列、返回字段和参数类型固定下来。SQL 值使用占位符绑定，查询使用精确条件和 LIMIT，并设置语句时限；连接使用有界池和只读事务，归还前 rollback。

这种设计便于判断“查了哪个主体、返回哪些字段、结果是否匹配请求”。代价是能力边界更窄：默认模式不支持任意组合筛选、自由统计或模糊企业探索。扩展能力需要新增或调整工具合同。

当前统一入口的参数来源检查也有不足：文本可通过当前问题子串检查，公司名还可匹配前步可见记录值。**来源存在不等于主体完整或角色正确。** 面试可以主动解释这一差别，不将其包装成完善的实体消歧。

### 5.2 为什么需要区分三种“没有查到”

| 情况 | 程序应表达的事实 | 不应推断的结论 |
|---|---|---|
| 工具成功、精确查询、记录为空 | 本系统暂未收录匹配记录 | 企业没有处罚、没有风险 |
| 主体记录存在、字段为空 | 该字段未收录 | 主体不存在，或字段现实值为空 |
| 工具失败或超时 | 数据服务未成功返回，无法判断 | 查询成功但没有记录 |

当前发布逻辑与前端都保留这些差别。SQL 返回还明确不代表完整总体；展示条数受限时不能据此判断“全部历史”“最高金额”等。

### 5.3 为什么要有证据台账

每次工具调用保留结构化结果和回执。台账把记录关联到步骤及稳定引用 ID，向模型暴露受长度约束的观察；最后由程序根据回执与证据发布结果。

这样可以追问并追查：某个字段来自哪次查询，模型看到过哪些记录，工具是否真的成功，引用对应哪个片段。它能减少无来源输出，但不能独立证明法规解释正确，也不覆盖所有提示注入或语义误判。

### 5.4 为什么取消不能只写一个 cancel

异步等待结束，不代表同步数据库线程或远端模型请求已经停止。项目对请求、阶段与工具设置时限，保留最终发布的时间预算；同步工作未退出时保留在途标识，避免误判空闲后继续调用。

工具申请与实际执行分开计数；请求内成功结果可复用，相同失败有重试上限。这些机制约束耗时和重复调用，但不是完整的线上费用统计，也不能保证浏览器停止后供应商立即停止计费。

### 5.5 SSE 不是“把所有模型 token 原样转发”

unified 在执行阶段发送进度事件，业务正文在核验发布后分块发送。网页校验请求标识与终态，处理中文 UTF-8 分片、SSE 分帧、迟到事件及断流；仅连接结束不能视为成功。

最终业务卡片通过 step_id 关联动作与记录，避免根据相似字段猜测类型。final 正文替换临时积累内容，防止重复追加。取消后保留已有内容和草稿，新请求独立处理。

### 5.6 飞书接入的工程工作

飞书适配器复用网页的 /chat/stream 接口，只采用通过校验的 final，保留业务状态和引用。接收回调先入队，后台工作线程调用 Agent，避免回调一直等待模型。

消息 ID 用于进行中去重和已回复去重；回复失败后的事件重投可以复用缓存答案，避免再次调用模型。当前为单工作线程、最多 8 个待处理问题和进程内最近 1000 条结果缓存；重启后缓存消失，不是持久化消息队列，也不是跨重启 exactly-once 保证。

### 5.7 查询规则已经固定，为什么还要改成统一主 Agent

早期 ReAct 方案由前置 Router 一次性确定任务及依赖，后续循环很大程度上只能执行清单。本人在复盘中提出：第一次计划可能不完整，工具返回意外结果时，后续应该能够调整。

因此把两类决定分开处理：工具的表列、只读属性和输出规则保持确定；下一步调用哪个工具、是否使用上一步结果继续查询，由统一主 Agent 逐步决定。程序仍检查参数来源、结果范围、预算与超时。第 4 节“项目 → 中标供应商 → 处罚”的例子展示了这种结果依赖。

这项调整提供了根据观察继续决策的空间，并不保证每个任务都规划正确。80/80 编排测试的工具为固定假实现，正式系统评测又暴露了依赖与结束状态问题，两者的验证范围见第 7 节。

### 5.8 为什么保留聊天记录，却暂时取消历史参数继承

一次历史测试中，企业查询结束后再问天气，系统重新执行了旧企业的工商、处罚及中标查询；日志记录了新的请求与实际调用。历史中存在企业名，只能说明参数有出处，不能证明用户本轮仍然要求查询它。

本人选择阶段性取消跨轮参数继承。当前 unified 内层只接收本轮问题，界面保留聊天记录，同一次请求内的多步依赖仍可执行。代价是省略式追问不再自动承接，用户需要完整表达对象和任务。原事故未保存完整路由表单，不应声称已经还原模型内部决策过程。

### 5.9 连续 fallback：相同表现如何定位不同根因

第一类故障表现为某轮 Embedding 超时后，后续问题持续兜底。排查时先区分阶段：路由已经成功，失败发生在 Embedding；再检查跨请求复用的资源，发现 CLI 每轮创建和销毁事件循环，而异步客户端及连接池仍被复用。后续改为交互会话共用 asyncio.Runner，并补充初始化失败、流关闭、取消及故障后恢复验证。

切换 DeepSeek 后再次出现 fallback，这次 HTTP 400 指向 thinking 与强制工具选择的协议冲突。兼容处理集中在模型工厂，保留结构化输出和工具约束；不能用前一次的连接池根因解释这次失败。

历史记录包含本地 HTTP keep-alive 与真实 SDK 复现、连续恢复验证及模型真实冒烟。200 请求、并发上限 16 的故障隔离属于受控测试，不能写成生产并发能力。面试展开时应能解释事件循环、连接池、异步生成器关闭和模型协议的区别；具体经过见故事库故事 5。

## 6. RAG 与数据治理如何展开

### 6.1 数据处理

现行 PDF 解析使用本地 MinerU / magic-pdf CLI。本次治理读取 content_list.json 块级产物，恢复三本书的标题层级，处理目录等噪声，将标题与正文、问题与答案绑定，保留章节和页码。同章节内容按大小打包，超长单元拆分并重叠；参数为上限 2000 字符、最小合并目标 200 字符、重叠 100 字符。这是结构感知切分，并非根据 embedding 计算语义边界。

值得讲的真实问题是：标题识别与切分可能丢正文，仅检查“有章节、有页码、块长正常”不够。历史修复记录中，第三本书曾出现归一化正文覆盖率约 84.55% 的问题；后来增加正文覆盖门禁，要求至少 99.5%，当前三份产物报告均为 100%。这个 100% 比较的是归一化文本与切片覆盖，**不等于原 PDF 的 OCR 识别准确率**。

稳定 chunk_uid 由规范化文本的哈希结合文档名、章节及片段序号生成。可以把哈希理解为内容的确定性摘要：相同输入生成相同摘要；这里 UID 还包含来源与结构信息，所以相同文本出现在不同文档中，仍可能对应不同 UID。切分或内容变化后 UID 也可能改变。

入库设置 auto_id=False，以 chunk_uid 为主键进行批量 upsert；相同 UID 再次写入时更新对应记录，而不是新增一个自动编号的副本。同一次调用中重复 UID 会被拒绝，文档换版还需要删除旧片段或执行文档级替换。它不是每条先查询再插入，也不等于跨文档全局文本去重。交接包另外检查 UID、结构 ID、文本重复及摘要一致性。

旧 CSV 法规库审计中的 55.57% 是“涉及重复文本的行占比”，多余副本约占 46.3%；记录的成因包括多快照导入、缺少幂等及跨文档引用。该审计与三书 PDF 重建属于不同数据阶段，不能说成原库简单去重后得到 920 块，也未证实“49/50 条成功后网络重试”就是实际事故主因。

### 6.2 检索链路

1. BGE-M3 dense 检索覆盖语义表达，Milvus 服务端 BM25 覆盖关键词、术语和条款号。
2. 两路默认各取 30 条候选，以 RRF 融合排名，得到 Top-30。
3. BGE-reranker-v2-m3 对候选精排，取 Top-5，并按当前规则过滤低分证据。
4. RAG 依据证据回答，返回文档、章节、片段等引用信息，完成结构校验。

RRF 依据排名融合，避免直接相加 BM25 与向量相似度这两类不同尺度分数；重排则重新评估问题与候选文本的相关性。BM25 由 Milvus 的文本函数生成，不能说 sparse 向量由 BGE-M3 在本项目中直接输出。

历史上曾出现配置为 hybrid、实际只运行 dense 的情况：服务端缺少所需的 BM25 Function 能力，schema 与降级路径使混合检索未生效，部分日志还误标重排状态。因此效果评测前先核验服务能力、集合 schema 和实际执行阶段。不能把当时的问题概括为“bge-large 无法配合 BM25”，也不能把配置开关存在当作链路生效的证据。

当前过滤阈值有 0.40 / 0.45 / 0.50 三档。200 题评测只覆盖高置信档；S3 到 S4 的精确召回没有增加，部分答案质量指标略降，所以不把动态过滤描述为已经证明普遍有效的优化。

### 6.3 引用校验的能力边界

引用结构校验可以检查字段、来源编号、片段标识、内联标记等一致性；回表还可以验证片段确实存在。它不能自动证明每一句法律解释都被原文蕴含。语义支持需要另外评估，不能把“引用关联正确”写成“零幻觉”。

### 6.4 为什么 knowledge_qa 内部保留完整的回答生成

Agent 升级时，一度将完整知识问答换成纯检索工具，出现拿到 chunk 却只堆砌原文的退化。本人当时优先验证较小改动，因此恢复完整 knowledge_qa：工具内部完成检索、回答生成与引用校验，外层使用工具结果发布。随后沿调用链确认生成归属，避免把多次模型调用误说成业务答案被重复生成。

接通时，一次约 27,287 字节的正常 RAG 请求超过共用的 16,000 字节输入预算。按实际请求大小，将 RAG 输入额度独立为 48,000 字节，调度仍保留原额度；调用次数、超时及取消约束继续共享。历史记录有预算边界测试及调整后的法规、工商加法规两条真实路径验证。这是字节预算，不是 token 上限，也不等于总费用控制或法律解释准确率保证。

## 7. 简历指标的完整口径

### 7.1 主效果指标：固定 200 题检索对照

比较新 S1 稠密基线与 S4 完整检索链路。已核对两份源码快照均有 47 个条目，逐项 SHA256 与字节数一致；题集哈希、回答模型及裁判模型配置一致。新 S1 是在 S4 之后补跑的基线，这是一组对照关系，不是开发时间顺序。

| 指标 | 新 S1 | S4 | 如何解释 |
|---|---:|---:|---|
| 标准片段 Macro Recall | 68.00% | 94.25% | 简历主指标；提升 26.25 个百分点 |
| 标准片段 Micro Recall | 179/270，66.30% | 251/270，92.96% | 汇总命中的 gold 片段数 |
| 全部标准片段命中题数 | 123/200，61.50% | 183/200，91.50% | 该题所需 gold 片段是否全部找到 |
| Ragas Context Recall | 88.58% | 98.32% | 模型裁判判断上下文对参考答案的支持 |
| Ragas Answer Correctness | 0.7508 | 0.8193 | 评分均值，不是全对题目比例 |
| Ragas Faithfulness | 0.9516 | 0.9569 | 回答对检索上下文的忠实度评分 |
| 请求 P95 | 2.047 秒 | 2.969 秒 | 质量收益伴随约 0.922 秒额外耗时 |

宏平均计算：每题先计算“命中的标准片段数 / 该题标准片段数”，再对 200 题取平均。微平均则将全题集命中数与标准片段总数相除。两者都不等同于“多少道题答案完全正确”。

解释收益时应保留以下边界：

- 这是自建领域题集、历史冻结版本上的离线结果，本次简历整理没有重跑真实模型或在线服务。
- 完整链路的提升不能全部归因于某一个组件。S1→S2、S2→S3、S3→S4 的历史比较还有各自运行条件；新 S1 与历史 S2 存在源码差异。
- 数据治理发生在这组检索基线之前，不能把 26.25 个百分点全部归因于切分或去重。阶段精确片段 Macro Recall 为 68.00% → 82.50% → 94.25% → 94.25%，S4 未继续提高该指标。
- S4 单并发评测按至少 10 秒间隔启动请求，等待不计入上述请求耗时；该数据不证明 QPS、并发能力或当前网页延迟。
- 重排增加额外调用和输入处理量，不能仅凭回答模型 Token 略降就宣称总成本降低。

### 7.2 Agent 评测：完成测量不等于通过验收

第三轮正式评测包括 280 题 × 3 轮主集执行，共 840 次；另有 24 场景 × 3 轮可靠性执行，共 72 次。主集覆盖法规、单 SQL、独立多动作、结果依赖、跨 RAG/SQL 任务和负向请求。

当次 RAG 质量层通过，但 Agent 整体验收未通过。比如工具与参数总体精确率约 99.10%，负向处置正确率仅 70%；已发布 SQL 事实全部匹配冻结真值，也仍存在应调用而未调用、范围说明和依赖处理问题。

面试可据此说明：只看最终答案或 RAG 分数会漏掉控制层缺陷。需要分别衡量是否选对动作、参数是否正确、依赖是否满足、任务是否覆盖、结束状态是否可信，以及输出事实是否有证据。

评分服务本身也可能失败。该轮 1320 个质量指标值中，15 个初次因裁判超时或重试异常缺失；恢复时仅补算这 15 个，保留原有 1305 个成功值和全部运行记录。这体现对评测数据完整性与可追溯性的处理。

### 7.3 小样本测试怎么说

早期 16 场景 × 5 次的 80/80 结果使用真实模型与固定假工具，只测动作编排，不证明真实数据库、检索或回答正确性。网页七次正常请求联调、飞书项目与法规体验也仅证明相应链路可用，不能外推所有请求稳定通过。

不建议将这些 100% 堆进短简历；在面试中按测试目标解释更有说服力。

### 7.4 历史 SQL 评测：范围收敛后如何解释结果

| 指标 | 旧开放查询评测 | 收敛后的核心业务评测 |
|---|---:|---:|
| 题目数 | 1,000 | 1,500 |
| 必填字段值总数 | 63,762 | 12,318 |
| 已召回必填字段值 | 1,777 | 12,252 |
| 必填字段召回率 | 2.787% | 99.464% |
| 平均请求耗时 | 3.022 秒 | 2.760 秒 |

两次题集、能力范围与字段分母不同，不能合成同口径的“3% → 99%”提升；旧报告简单题字段召回率已有 97.094%，也不能把总字段召回率当作答对题目比例。可以说：早期开放题集暴露能力缺口，范围收敛后，在 1,500 道核心业务题上验证到 99.464% 的必填字段召回率。

8 月 15 日高分报告仍列有 mysql_price_semantic，结构化向量层后来才退役；这个分数不是移除向量后的消融结果。现有报告也不足以证明一次查询由两分钟降至秒级及其原因。该历史指标用于解释 SQL 故事，不能代替当前 unified 的端到端评测。

## 8. 当前版本与历史记录的差异

本次按当前工作树核对时发现：9 月 14 日设计/实施记录称已新增 request_policy.py，9 月 15 日报告记录了编号原值、依赖歧义等修复回归；但当前 agent/execution/request_policy.py 不存在，unified.py 的参数绑定仍采用当前问题子串或前步可见值检查。

因此，本次短简历没有写“已完善依赖歧义拦截”“已修复所有编号截断问题”或“新规则全部验收通过”。历史报告可以用于介绍当时的实验与问题，不能直接当作当前演示代码已经具备相应能力的证明。本次没有修改业务代码，也未判断该差异是回退、迁移还是其他原因。

还需记住这些当前边界：

- 是单主 Agent 的多步骤工具调用，不是多 Agent 协作系统。
- 历史会话保存在界面中，不表示模型使用历史上下文；当前每轮独立处理。
- 默认工具为受控精确 SQL；FULLTEXT、LIKE 等历史检索链路不能与统一入口混讲。
- 文档上传问答仍是占位，不写入已完成能力；产品查询与结构化向量集合已退役。
- unified 当前发布入口是 render_unified，旧 hybrid 的 output.py 不能概括全部现行发布路径。
- 演示依赖本机服务与网络；未实现生产鉴权、完整访问配额及生产负载验收。
