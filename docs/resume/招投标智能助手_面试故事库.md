## 二、故事 1：开放查询效果不稳定，如何收敛可交付能力

### 这条故事要体现什么

体现从业务目标出发发现能力边界，区分模型问题、程序缺陷与数据条件，并做出有代价的范围取舍。讲清“保留什么、放弃什么、凭什么验收”，不要只展示一个很大的百分比涨幅。

### STAR 骨架

- **S：** 早期希望覆盖供应商推荐、行情、金额排名、企业与项目查询等开放请求，实测出现无关产品、结果为空、应有字段不显示等问题。
- **T：** 在个人开发时间有限的情况下，交付供应商管理场景中有明确输入、证据与验收标准的核心查询能力。
- **A：** 沿意图、SQL 条件、返回字段、输出模板排查；明确企业与项目业务的输入和字段合同；收敛工商、处罚、中标历史及详情等能力，对越界需求提供引导；阶段性下线产品查询，后续再移除结构化向量依赖。
- **R：** 2026-08-15 的 1,500 题核心业务评测中，必填字段召回率 99.464%，全部必填字段命中的用例占比 99.533%，平均请求耗时 2.760 秒。它验证的是当时限定范围内的能力。

### 可直接口述的版本

> 项目早期，我希望用户可以自由询问企业、项目排名、供应商推荐和产品行情。但测试中经常出现无关结果，或者数据库有字段，回答却显示未提供。我沿查询链路排查，发现问题同时存在于业务范围和程序实现：例如公司名称被错误映射成项目编号条件，查询构造器又遗漏了回答需要的价格和工商字段。
>
> 我把项目定位在供应商管理场景，优先围绕同一家企业提供工商、处罚、中标历史和项目详情。产品行情当时缺少已验证的使用价值，现有报价数据和检索效果也难以支撑可靠交付，因此我决定阶段性下线产品查询，并明确核心能力的输入、取数、输出和越界引导规则。
>
> 随后核心业务的 1,500 题评测达到 99.464% 的必填字段召回率。代价是减少了任意聚合、推荐和模糊发现的灵活性，但核心查询有了明确可验收的范围。后来引入 Agent 时，我仍保留这些工具边界，再让模型逐步组织工具调用。

### 把原叙述改准确

| 原来的说法 | 更准确的说法 |
|---|---|
| 召回率从 3% 直接提高到 99% | 旧开放查询题集暴露能力缺口；收敛后在另一份核心业务题集上验证到 99.464% |
| 模型不微调就做不了 Text2SQL | 本项目当时的模型、意图映射和程序查询链路没有满足开放需求；不能推广成所有模型的能力结论 |
| 当时模型总是生成错误 SQL | 现存 8 月 8 日材料是模型生成意图 JSON、Python 拼 SQL；更早是否自由生成 SQL 尚不确定 |
| 产品线幻觉最严重 | 已记录的是无关产品召回和 SELECT 漏字段；没有原始证据时不补写“编造价格” |
| 系统只能回答五句固定问题 | 自然语言问法仍可变化，支持的业务能力与查询合同被限定；五种业务问法也不等于五个 sub_route |
| 采购网已经有，所以用户不需要 | 当时尚未找到足够明确的增量价值，阶段性投入优先级较低；没有真实用户研究证明需求不存在 |
| 加向量让一次 SQL 从两分钟变秒级 | 暂缺两分钟基线和分段计时，不写确定因果；现有旧评测已是秒级 |

旧评测为 1,000 题，必填字段 63,762 个，召回 1,777 个，字段召回率 2.787%；新评测为 1,500 题，必填字段 12,318 个，召回 12,252 个。旧报告简单题字段召回率已有 97.094%，所以 2.787% 不能解释成“只有约 3% 的问题答对”。

8 月 15 日高分报告仍列有 mysql_price_semantic；其后 9 月退役结构化向量层，不能把这个高分直接说成移除向量后的消融结果。

## 三、故事 2：从语料质量到检索效果，建立可验证的 RAG 链路

### 这条故事要体现什么

把数据质量、实际运行路径与检索效果分开验证。主线是“发现输入与测量不可靠 → 重建数据与来源标识 → 确认链路真实生效 → 分阶段测收益与代价”。第一轮模型选型可以留给故事 9，不必塞进这段开场。

### STAR 骨架

- **S：** 旧语料存在标题层级混乱、噪声和短块；旧库还有重复导入，影响引用身份与精确召回评估。代码中的混合检索曾因运行环境不匹配而未实际生效。
- **T：** 让证据片段有完整上下文、可追溯身份及可重复入库能力，并能判断检索改造是否真正改善结果。
- **A：** 基于块级解析重建三书语料，做结构感知切分与质量门禁；稳定 chunk_uid 作主键并 upsert；核验 BM25 schema 和真实检索路径；在固定题集上比较稠密、混合、重排与过滤。
- **R：** 三本书形成 920 个片段；现存产物报告正文覆盖率 100%、短于 100 字片段比例为 0。固定 200 题中，精确片段宏平均召回率由稠密基线 68.00% 到完整链路 94.25%，P95 由约 2.047 秒增至 2.969 秒。

### 可直接口述的版本

> 做 RAG 评测时，我发现检索结果的问题不能只从模型上找。旧语料中有目录和页码噪声，标题与正文被割裂，重复导入又让相同内容对应不同 ID，影响引用和精确召回判断。
>
> 我重新处理原始资料，按章、节、法条和问答结构组织片段，保留章节与页码；使用内容和来源共同生成稳定的 chunk_uid，作为主键进行 upsert。重切分过程中还发现，原先质量检查全部通过，正文却仍有遗漏，所以补上了正文覆盖检查。
>
> 数据处理和真实检索路径确认后，我在固定 200 题上分阶段比较稠密检索、BM25 混合召回、RRF 和重排。标准片段宏平均召回率从 68% 提高到 94.25%，但 P95 也增加了约 0.92 秒。动态过滤没有继续提升精确召回，所以我保留各项指标分别判断，没有把每次加组件都当成有效优化。

### 遗忘的技术细节，按这个理解

**切分：** 本次治理直接读取 MinerU content_list.json 块级产物，恢复标题层级，将标题与正文、问题与答案绑定；同章节内容按大小打包，超长单元按句拆分并重叠。参数为最大 2000 字符、最小合并目标 200 字符、重叠 100 字符。它属于结构感知切分，并非通过 embedding 计算语义边界。

**稳定 ID：** 规范化片段文本后计算哈希，再结合文档名、章节和片段序号派生 chunk_uid。相同输入生成同一个 UID，不同来源的同一法条仍可保留不同 UID；切分或内容改变后 UID 可能改变。

**写入：** auto_id=False，chunk_uid 作主键，使用批量 upsert；同一次调用中发现重复 UID 会拒绝。不是逐条先查询库再决定是否插入。文档换版还需要删除旧片段或执行文档级替换。

**混合检索：** 本项目 embedding 接口提供 dense；Milvus 根据原文生成 BM25 sparse。旧链路不生效的主要证据是服务端缺少所需 BM25 Function 能力、schema 回退以及静默降级；不能归结为 bge-large 无法配合 BM25。

### 两个适合深入讲的子案例

**子案例 A：门禁通过，仍丢了正文。** 首次重切分时，长正文因行首编号被误判为标题，随后因“标题后无正文”被丢弃。报告的书 3 正文覆盖率为 84.55%。后来加入长正文保护、粘连法条拆分、标题救援和至少 99.5% 的覆盖要求；该门禁曾当场拦下 99.45% 的产物，修复后报告为 100%。这体现对验证盲区的识别与防回归，不仅是调 chunk_size。

**子案例 B：配置写了 hybrid，实际只跑 dense。** 老服务端没有所需 BM25 Function，代码静默走纯稠密路径，部分日志还误标为带重排。后续补 schema 检查、真实链路验证与阶段日志，确认召回、融合和重排确实被执行。它适合回答“怎么证明优化真的生效”。

### 数字与范围

- 旧库 55.57% 表示“涉及重复文本的行占比”；多余副本约 46.3%。报告根因包括同源多快照导入、无幂等以及跨文档引用，未证实“49/50 条成功后重试”是实际事故主因。
- 旧 CSV 法规库重复审计与后来的三书 PDF 重建是不同数据阶段，不说成同一数据集简单去重后得到 920 块。
- “100% 正文覆盖”针对归一化文本与片段，不是 OCR 准确率，也不证明图片表格全部识别。
- 精确片段 Macro Recall：68.00% → 82.50% → 94.25% → 94.25%。它不是答案准确率。
- 数据治理发生在上述基线之前，不能把 26.25 个百分点全部归因于数据治理。
- 新 S1 与 S4 源码快照一致；新 S1 与历史 S2 有 14 个文件不同。整段历史实验不能一概宣称严格单变量。

## 四、故事 3：固定 SQL 之后，为什么还要让 Agent 逐步决策

**核心冲突：** 旧 Router 在工具执行前一次性决定全部任务和依赖。模型虽然处于 ReAct 循环，却很难根据工具的意外结果调整计划。

本人复盘中已有明确质疑：“谁能保证第一次计划绝对正确？工具返回意外结果，后面怎么办？”因此这条故事有真实思考来源。

**口述稿：**

> SQL 能力收敛后，我继续改造 Agent，但发现前置 Router 已经把任务和依赖都定死了，后面的循环只能执行清单。如果第一次计划不完整，模型没有足够空间根据结果调整。我因此重新划分两类约束：业务工具仍保持只读、固定查询和可核验输出，下一步调用哪个工具则交给统一主 Agent。每次只申请一个动作，由程序校验参数来源、结果范围、预算和超时，再把结果交回模型决定是否继续。
>
> 这样简单问题可以一次工具结束，复杂问题也能利用上一步查询结果继续。例如先按项目编号查中标供应商，再查该供应商处罚。这个调整让我更清楚地理解：工具能力的稳定性与编排的灵活性可以分别设计。

**结果与边界：** 当前 unified 代码能核实这一循环和六工具接口。历史 16 场景 × 5 次的 80/80，是“真实模型＋固定假工具”的动作、参数、顺序与停止状态验证，不能当作端到端业务准确率。参数有来源仍不保证角色或业务意图正确，完整控制能力由故事 4 的系统评测检验。

**追问：** 固定 SQL 为什么还算 Agent？模型能改变哪些决定？程序拒绝一次提议后会怎样？为什么 FinishAction.complete 不等于语义上全部完成？

**证据：** [本人质疑与取舍](<D:/DEMO/zhaotoubiao_demo/docs/Insights and Reflections/ReAct升级对话复盘_从过度约束到明确边界_20260907.md:125>)、[统一基线与验证](D:/DEMO/zhaotoubiao_demo/docs/work_docs/统一主Agent架构基线_20260907.md:7)、[当前主循环](D:/DEMO/zhaotoubiao_demo/agent/execution/unified.py:382)。

## 五、故事 4：RAG 达标，为什么整套 Agent 仍然验收失败

**核心冲突：** 回答质量和 SQL 事实正确，仍可能伴随未请求的工具调用、依赖处理错误或过早结束。

**口述稿：**

> 完成 RAG 评测后，我把测试对象扩展到完整 Agent。它不只是回答问题，还会选工具、传参数、使用上一步结果，所以仅看最终答案分数不够。我构建了 280 题，覆盖六种任务类型，并连续执行三轮；另外设置 24 个可靠性场景，分别检查动作、参数、依赖、证据与结束状态。
>
> 结果很有启发：RAG 六项指标三轮都达标，系统正式验收仍然失败。例如上游返回两个供应商时，Agent 对两个供应商都继续查工商，但当时冻结规则要求先停止或澄清。这些查询可能返回真实数据，却不符合本轮任务的执行边界。我保留了失败基线，把内容质量和执行正确性分开验收，再围绕具体问题安排回归。

**结果：** 840 次主集执行、72 次可靠性尝试完成；当次负向处置正确率 70%，结束状态正确率约 92.5%，揭示了只看 RAG 指标会漏掉的缺陷。不能把执行完成数写成通过数。

**值得补充的细节：** 裁判评分有 15 个指标失败时，只恢复这 15 个，原有 1305 个成功值保持不变；补齐后的结论仍为 failed。这能回答“你如何保证评测不挑结果”。

**当前边界：** 9 月 14—15 日部分修复记录与当前工作树不一致，request_policy.py 当前缺失。本故事可以讲已完成的评测与问题定位，不能宣称全部缺陷已经在当前版本修复。9 月 15 日的 33 次定向真实链路只有 30 次符合新口径，也不能替代全量复验。

## 六、故事 5：连续 fallback，如何区分运行时故障与模型协议问题

**核心冲突：** 表面都是兜底回答，但一次是故障影响后续请求，另一次是换模型后稳定报错，根因不同。

**口述稿：**

> 我遇到过一次流式问答故障：某轮 Embedding 超时之后，后续明明能回答的问题也持续 fallback。我关注的是故障会延续到下一轮，因此排查共享状态和资源生命周期。日志显示路由已经成功，失败发生在 Embedding 阶段；进一步发现 CLI 每轮创建和销毁事件循环，但异步客户端和连接池仍被复用。
>
> 后续把交互会话改为共用一个 asyncio.Runner，并补上初始化失败、流关闭、取消和下一轮恢复测试。后来切换 DeepSeek 又出现 fallback，这次 HTTP 400 明确是 thinking 与强制工具选择不兼容，于是把兼容处理集中到模型工厂，保留结构化校验。两次排查让我学会按失败阶段和生命周期定位问题，而不是从同一句兜底文案推断根因。

**结果：** 记录中有本地 HTTP keep-alive 与真实 SDK 链路复现、故障后的连续恢复验证，以及 DeepSeek 路由和问答真实冒烟。200 请求、并发上限 16 的故障隔离是受控测试，不是生产压测或“支持 200 并发”。

**理解到这些程度再讲：** asyncio.Runner 为什么能对齐生命周期；连接池等待超时与远端响应超时的区别；异步生成器为什么需要关闭；thinking/tool_choice 为什么属于协议适配；为什么不原地修改共享模型配置。

**追问：** 为什么不扩大连接池或多重试？为什么初始化成功后才发布单例？你怎样证明故障没有污染下一轮？

## 七、故事 6：一句“天气怎么样”，为什么重新查询了旧企业

**核心冲突：** 参数确实来自历史消息，但这不能证明用户在当前轮仍然授权执行旧任务。

**口述稿：**

> 多轮测试时，我发现一个问题：企业查询结束后，用户问天气，系统竟然重新执行旧企业的工商、处罚和中标查询。日志中有新的请求和工具调用，所以不仅是界面展示旧答案。原机制允许历史消息里的企业名成为参数来源，但无法据此确认用户本轮仍然想查这个企业。
>
> 我当时判断，省略式追问的便利还不足以覆盖这些执行风险，所以暂时取消历史参数承接。聊天记录继续保存，同一次请求内的多工具和依赖查询也保留，但每轮需要完整表达对象和需求。代价是用户要多输入一些内容，换来更清晰、容易测试的任务边界。

**结果与边界：** 当前 unified 内层 Agent 只接收本轮 HumanMessage，相关回归覆盖历史保留和不重跑。原事故没有保存完整路由表单，不能声称已经还原模型内部如何推理。此案例证明阶段性边界取舍，不证明多轮记忆普遍不可行。

**追问：** 为什么保留聊天记录却不用于决策？同轮依赖与跨轮继承区别？未来恢复追问时至少应验证什么？

## 八、故事 7：Agent 升级后答案退化，如何复用完整 RAG 能力

**核心冲突：** 把完整知识问答换成纯检索工具后，系统能拿到 chunk，但最终答案变成原文堆砌；放宽外层生成权限又会改变既有输出边界。

**口述稿：**

> 升级 Agent 时出现过功能退化：检索工具返回了原文，但用户没有得到像原来那样经过组织的答案。我当时首先想以较小改动验证新链路，于是恢复完整 knowledge_qa 工具，由它负责检索、回答和引用校验，外层按工具结果发布。
>
> 我随后沿调用链核实，确认模型调用多次并不等于业务答案被重复生成。接通后又发现正常的五片段 RAG 请求超过了共用的 16000 字节输入预算。我按真实请求大小，将 RAG 输入额度独立为 48000 字节，调度仍保留原额度，调用次数、超时和取消约束继续共享。随后正常法规问答及工商加法规组合链路通过了验证。

**结果与边界：** 当时有约 27,287 字节请求被拦的记录，以及预算调整后的两条真实路径；独立预算测试覆盖超一字节、并发隔离与恢复。字节预算不是模型 token 上限，执行与引用结构通过也不是法律答案全部正确。

**追问：** 工具里调用 LLM 是否合理？谁负责写答案、谁发布？为何不简单裁掉检索原文？48KB 怎样估算？

**证据：** [本人真实动机与事后核实](<D:/DEMO/zhaotoubiao_demo/docs/Insights and Reflections/生成归属、最小验证与懒的边界_20260907.md:112>)、[复用、容量测量与验证](D:/DEMO/zhaotoubiao_demo/docs/work_docs/完整RAG问答复用_20260906.md:29)、[当前 RAG 结果校验](D:/DEMO/zhaotoubiao_demo/agent/execution/rag_result.py:9)。

## 九、故事 8：从接口可调用，到网页和飞书能够正确交付结果

**核心冲突：** 同一个 Agent 接到两个渠道后，会出现断流、迟到事件、重复消息，以及“答案已生成但发送失败”等接口接通本身解决不了的问题。

**口述稿：**

> 为了让面试官能直接体验，我把网页和飞书接到同一个 FastAPI 接口。集成时我重点处理结果是否完整、状态是否一致。网页按 SSE 协议解析分片，用请求标识隔离消息，只有有效终态才能标记完成；中途断流保留文字，但刷新后仍显示未完成。
>
> 飞书则将回调接收和后台查询分开，并按消息 ID 去重。我把答案缓存与发送状态分别保存，遇到生成成功、回复失败的情况，重投可以复用答案，避免再次调用模型。后续验证了网页真实查询与受控断流恢复，也验证了后端停服时飞书明确提示失败、恢复后无需重启适配器即可重新问答。

**结果与边界：** 网页六业务样例加一般对话有 7/7 当次真实联调记录，飞书项目与法规问答有用户验收；这些不能外推成所有输入通过。消息重投及发送失败主要由离线测试覆盖。飞书缓存为进程内最近 1000 条、单工作线程、最多 8 个待处理问题，不保证跨重启去重。

**重要区别：** 当前 unified 实时展示执行阶段，业务正文核验后再分块发送；不能称为原始模型 token 无缓冲直出。浏览器取消也不保证远端模型计费立即停止。

**追问：** EOF 为什么不能当成功？中文跨分片怎么办？迟到 final 怎么处理？发送超时如何避免重复推理？进程重启后如何处理？

**证据：** [网页正常与断流验收](D:/DEMO/zhaotoubiao_demo/frontend/QA.md:90)、[飞书真实接入与停服恢复](D:/DEMO/zhaotoubiao_demo/scripts/feishu_connection_probe.md:79)、[飞书生成/发送状态实现](D:/DEMO/zhaotoubiao_demo/scripts/feishu_agent_bridge.py:137)。

## 十、故事 9：模型选型与提速之后，如何保住评测可信度

这条可拆成两个短故事，按问题选择，不需要一次讲完。

### A. 为什么选择 DeepSeek

> 第一轮我先固定检索上下文，让模型面对相同资料回答，再比较质量、耗时、Token 与估算成本。三大模型使用主实验集，两小模型使用子集；提示词优化前后按共同题目对齐。DeepSeek 在当时大模型组的忠实度、正确性和平均完成速度上较好，其他模型在费用或相关性上也有优势，所以选型有明确取舍。第二轮才把主要变量转到检索链路，观察输入资料改善是否传递到答案质量。

**限制：** 这是 v1/v2 提示词对比，不是有无提示词；大模型 1000 条记录（998 个不同问题）、小模型 200 题不能直接混排；同源裁判有偏差风险。短答案也不保证 Token 或费用更低。该结果只适用于历史模型配置。

### B. 为什么重新跑稠密基线

> 第二轮后续阶段突然快了很多，但模型调用平台也发生变化。我没有直接把提速归到混合检索，而是检查耗时、Token 和可见答案长度，并用官网模型、最终冻结源码重跑稠密基线。重测后精确召回不变，199/200 题最终资料列表一致，P95 从 38.521 秒降到 2.047 秒。我因此把旧速度异常与检索收益分开报告，同时保留历史运行。

**限制：** 平台、模型标识和源码都发生过变化，不能声称严格证明某一家平台是唯一根因。历史日志缺少完整 provider 与分段计时，无法精确归因；补充这些观测项在报告中是后续建议，不能据此声称已实现。

**追问：** 为什么冻结上下文？失败样本和空答案如何处理？裁判偏好怎么办？源码快照如何比对？为什么等待间隔不计入延迟？

## 十二、准备方式与简历取材

每个主讲故事准备三层即可：

1. **一句话：** 发生了什么问题，最关键的判断是什么。
2. **约 90 秒：** 背景、目标、本人采取的动作、观测结果与取舍。
3. **追问材料：** 一个具体失败例子、一处核心实现、一份对应测试或评测记录。

优先练熟故事 1、2、3、4、5；故事 6、7、8、9 根据岗位追问展开。若偏全栈应用交付，可把故事 8 提前。

简历保留少数可验证行动与成果即可：六工具统一 Agent、200 题检索对照、分层 Agent 评测、网页与飞书交付。产品线取舍、历史重放和连续 fallback 的完整经过留在面试中讲。

本项目的经历可以串成一条清楚的演进线：

**理解业务与数据 → 确定可交付的查询范围 → 治理法规证据与检索 → 让 Agent 在工具边界内逐步决策 → 用完整评测暴露控制缺陷 → 处理运行时与双端交付。**

这条线能同时展示动手能力、判断修正与对系统边界的理解。具体选择哪一条作主讲，以本人能解释清楚、能指向真实证据为准。
