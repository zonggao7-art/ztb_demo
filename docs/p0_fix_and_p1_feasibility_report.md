## 1. P0 级紧急修复执行总结

本次严格按照深度排查报告 5.2 节的三个 P0 优化点执行，全部修改集中在
[agent/nodes/price_inquiry.py](../agent/nodes/price_inquiry.py)，未触碰其他任何代码。
修改已通过 `py_compile` 编译校验与静态检查，无语法错误。

### 1.1 优化点 5.2.1：FULLTEXT Boolean Mode 从 AND 改为 OR 语义

- **修改位置**：`_build_search_term()`（原 L445-L454，现 L445-L462）
- **修改前**：所有 `semantic_keywords` 一律加 `+` 前缀，形成 `+A +B +C` 的 AND 语义，
  要求全部关键词必须同时出现在 FULLTEXT 索引列中，多关键词查询大面积零召回。
- **修改后策略**（与报告方案一致）：
  - **单关键词**：保留 `+` 前缀，维持精确意图不变；
  - **多关键词**：去掉 `+` 前缀，改用 Boolean Mode 默认 OR 语义，任一命中即匹配，
    MySQL 按 TF-IDF 自然打分，命中词越多的记录得分越高；
  - **exact_tokens**：保持 `+"精确短语"` 强制匹配语义不变，不影响精确查询场景。
- **预期效果**：报告 3.2 节类别 B 中的口语化多关键词查询（如
  `+保温材料 +供应商 +福建`）从"大概率空"变为可正常召回，且相关性自动排序，
  排序质量由既有的 `_rank_records()` 混合重排序层兜底，无需改动排序逻辑。

### 1.2 优化点 5.2.2：增加 LIKE 降级回退机制

- **修改位置**：新增 `_build_like_fallback_sql()`（现 L597-L637）+
  `_query_tables()` 内降级分支（现 L802-L821）
- **实现方式**（按报告伪代码落地）：
  1. FULLTEXT 查询返回 0 行时，自动构造降级 SQL；
  2. 降级 SQL 使用 **第一个语义关键词** 对所有语义列做 `LIKE '%关键词%'` 的 OR 匹配，
     保留原有硬过滤条件（地区/状态类已同步改为模糊匹配，避免二次卡死）；
  3. 保持与原查询一致的字段投影（`LEFT(col, 800)`）、`LIMIT 200` 截断与排序逻辑；
  4. 降级命中时记录 `[LIKE_FALLBACK]` INFO 日志，降级失败仅记 DEBUG 日志，
     不改变原有容错语义；`_score_` 置 0，最终排序完全交给 Python 侧
     `_hybrid_score()` 关键词命中打分，保证降级结果的相关性排序合理。
- **预期效果**：彻底消除"FULLTEXT 返回 0 行即放弃"的断崖行为，覆盖报告根因 4.4
  指出的 LIKE 回退缺失问题。

### 1.3 优化点 5.2.3：硬过滤条件改为 LIKE 模糊匹配（地区/状态类）

- **修改位置**（共 4 处，全部为地区/状态类条件）：

| 位置 | 过滤维度 | 修改前 | 修改后 |
|------|---------|--------|--------|
| `_build_hard_conditions()` | `region`（地区） | `` `col` = %s `` | `` `col` LIKE %s ``（`值%`） |
| `_build_hard_conditions()` | `status`（状态/阶段） | `` `col` = %s `` | `` `col` LIKE %s ``（`值%`） |
| `_build_hard_conditions_extended()` | `province` / `city` | `` = %s `` | `` LIKE %s ``（`值%`） |
| `_build_hard_conditions_extended()` | `business_status` / `project_stage` | `` = %s `` | `` LIKE %s ``（`值%`） |
| `_query_bidding_aggregation()`（聚合路径） | `province` / `project_stage` | `` = %s `` | `` LIKE %s ``（`值%`） |

- **匹配方式**：按报告方案采用 **LIKE 前缀匹配**（如 `福建%`），可同时命中
  `福建` 与 `福建省`、`福州` 与 `福州市`、`内蒙古` 与 `内蒙古自治区` 等简称/全称差异。
- **未改动范围**：采购人、中标供应商、项目编号、公司名、统一社会信用代码等
  **实体标识类条件仍保持精确等值匹配**，避免误召回；时间/金额范围过滤不受影响。
- **补充说明**：聚合查询路径 `_query_bidding_aggregation()` 中存在与主检索路径
  相同的地区/状态精确过滤，为保证 P0 修复在所有执行分支上行为一致，一并修改。

### 1.4 P0 修复验证情况

- 三个优化点互相独立、可回滚，未改动 SearchIntent 数据模型、Router、
  二级路由映射与重排序层，影响面收敛在 SQL 构建与执行两个阶段；

## 2. P1 级优化可行性分析

以下针对报告 5.3 节的三个 P1 优化项，基于当前代码架构与基础设施逐一分析。

### 2.1 P1-1：多级降级检索链（报告 5.3.1）

**方案回顾**：构建 Level 1~5 完整降级链——
OR 语义 FULLTEXT → AND 语义 FULLTEXT → LIKE 通配 → 逐关键词拆分重试 → 全表扫描兜底。

**技术可行性：高 ✅**

- **P0 已铺平一半路径**：本次修复已实现 Level 1（OR 语义 FULLTEXT）与
  Level 3（LIKE 通配回退），剩余 Level 2/4/5 均为同构扩展，
  不涉及新的技术栈或基础设施。
- **架构契合度高**：`_query_tables()` 已是"构建 SQL → 执行 → 判空 → 降级"的
  单循环结构，扩展为多级链只需将降级逻辑抽成有序的策略列表
  （每级 = 一个 `(build_sql, needs_rows)` 对），代码改动量可控。
- **排序层天然兼容**：各级召回结果均汇入 `_rank_records()` 混合重排序，
  不同级别结果的 `_score_` 口径差异（FULLTEXT 得分 vs 0 分）可由
  Python 侧 `_hybrid_score()` 统一归一，无需新增排序组件。

**实施难度与风险：低到中**

| 风险点 | 说明 | 缓解措施 |
|--------|------|----------|
| 延迟叠加 | 最坏情况串行执行 5 级查询 | 各级保留 `LIMIT 200`；Level 5 全表扫描必须加 `LIMIT` 且仅在前 4 级全空时触发；4 张表合计约 7.76 万行（bid_project ≈17,742 / company_info ≈38,921 / company_penalty ≈1,804 / product_info ≈19,138），单次全表扫描在当前数据量下可控制在亚秒级 |
| 精确率下降 | 降级越深噪声越多 | 在结果中标记降级级别，重排序时按级别施加衰减系数 |
| 逻辑重复 | Level 2（AND）与 Level 4（逐词）部分重叠 | 逐词重试可视为"动态 AND 弱化"，实现时可合并为一级 |

**预计工作量**：**2~3 人天**。核心是降级链调度框架 + Level 4/5 两个 SQL 构造器
+ 回归测试；P0 已验证的降级模式可直接复用。

### 2.2 P1-2：LLM 关键词改写与去噪（报告 5.3.2）

**方案回顾**：在 `_UNIFIED_INTENT_SYSTEM` Prompt 中增加关键词质量控制指令，
或增加后处理去噪，剔除"推荐/查询/情况/信息"等动词与抽象名词噪声。

**技术可行性：高 ✅**

- **零基础设施依赖**：意图解析链路（`_parse_unified_intent()` +
  `_UNIFIED_INTENT_PROMPT`）已完整存在，仅需修改 Prompt 文本和/或在
  `SearchIntent.from_dict()` 之后插入一个轻量去噪函数。
- **两条实现路线可叠加**：
  1. **Prompt 层**（主）：在现有 System Prompt 的 `semantic_keywords` 输出约束中
     增加"仅保留业务实体名词（产品/地区/公司名），剔除动词与抽象名词"指令；
  2. **后处理层**（辅）：维护一个招投标领域停用词表
     （推荐/帮我/查一下/情况/数据/信息……），对 LLM 输出做二次过滤，
     兜住 LLM 不稳定输出——这正好对冲报告根因 4.5"提取粒度不稳定"。
- **与 P0 修复正交互补**：P0 的 OR 语义让噪声词"不再致命"，
  去噪则进一步提升召回结果的相关性排序质量，两者叠加效果最佳。
- **风险极低**：最坏情况是误删有效词，但 OR 语义 + LIKE 降级 + 混合重排序
  构成三重兜底，误删代价可控；可通过调整 Prompt 快速迭代回滚。

**预计工作量**：**1~2 人天**。Prompt 修改 0.5 天 + 停用词表与后处理函数
0.5~1 天 + 对照测试 0.5 天。这是三个 P1 项中投入产出比最高的一项。

### 2.3 P1-3：引入向量语义检索作为 MySQL 语义层（报告 5.3.3）

**方案回顾**：MySQL 每行记录 → 文本拼接摘要 → Embedding → Milvus；
检索时先向量召回 ID，再回 MySQL 按主键取完整数据。

**技术可行性：高 ✅（基础设施全部就绪）**

| 所需能力 | 现状 | 复用成本 |
|----------|------|----------|
| Milvus 向量库 | Docker Compose 部署已就绪（`milvus/docker-compose.yml`，Standalone 模式含 etcd + MinIO） | 零成本 |
| Embedding 服务 | `public_kb/embedding_service.py` 已封装 `embed_documents` / `embed_query` / `embed_texts`（BGE-M3，1024 维） | 零成本，直接调用 |
| Milvus 存取封装 | `public_kb/milvus_store.py` 已实现 collection 初始化、批量插入、加载、清空等完整生命周期 | 低成本，需按结构化数据特点新建 collection schema（增加 MySQL 主键/表名字段） |
| 混合检索经验 | `public_kb` 已跑通稠密+稀疏+RRF 融合+Reranker 的完整链路（见 `config.py` 混合检索参数） | 检索参数可直接借鉴 |
| 数据管道 | `rebuild_and_verify.py` 已有一键重建模式，可参照新增"MySQL → 向量化"管道 | 中等成本，需新写 ETL |

**主要工作量在数据侧而非工程侧**：

- 4 张表合计约 **77,608 条记录**需向量化，按 BGE-M3 API 批量调用估算，
  全量构建一次性耗时约数十分钟至数小时（取决于 API 速率），存储开销约
  78k × 1024 维 ≈ 300MB 原始向量，Milvus Standalone 完全可承载；
- 需为每张表定义"拼接摘要模板"（如 bid_project：`项目名称 + 采购人 + 中标供应商
  + 标的 + 省份`），并新增 `source_table` + `source_id` 标量字段用于回表；
- `node_price_inquiry` 需在 `_query_tables()` 前插入"向量召回 ID →
  `WHERE id IN (...)` 回表"分支，与既有 FULLTEXT 结果合并后统一重排序。

**实施难点**：

1. **增量同步**：Demo 阶段数据静态，可先做全量重建；若数据更新频繁，
   后续需补 MySQL → Milvus 的增量管道（本期可不做，列为 P3）；
2. **双路结果融合**：向量得分与 FULLTEXT 得分量纲不同，需归一化或统一交给
   Python 侧 `_hybrid_score()` 关键词打分收口（现有架构支持）；
3. **路由分支兼容**：`_query_all_tables()` 的多表扫描需同步接入向量召回，
   改动面比单表场景大。

**预计工作量**：**4~6 人天**。ETL 管道 2 天 + Milvus schema 与召回回表集成
1.5~2 天 + 融合排序与回归测试 1~2 天。

| P1 优化项 | 技术可行性 | 实施难度 | 预计工作量 | 依赖 |

## 3. P1 预期收益评估

### 3.1 性能提升

| 优化项 | 召回率影响 | 精确率影响 | 延迟影响 |
|--------|-----------|-----------|----------|
| 多级降级链 | 大幅提升：理论消除"零召回断崖"，除库中确无数据外不再返回空 | 轻微下降（深层级噪声），由重排序与级别衰减对冲 | 最坏情况 +2~3 次 SQL 往返，当前数据量下单次 <100ms，可接受 |
| 关键词去噪 | 间接提升：减少噪声词对 OR 匹配排序的稀释 | 明显提升：检索词更聚焦业务实体 | 无额外延迟（Prompt 内完成）；后处理去噪为纯 Python 字符串操作，可忽略 |
| 向量语义层 | 质的飞跃：覆盖同义词、近义表达、口语化描述等 ngram 无法触达的场景（报告根因 4.3/4.6 的根治方案） | 高：BGE-M3 语义相似度 + 回表取真实数据，无幻觉字段 | 增加一次向量检索（10~50ms 量级）+ 一次主键回表，总体与当前 FULLTEXT 查询同量级 |

### 3.2 用户体验改善

- **空结果率显著下降**：报告 3.2 节类别 B 的 4 类口语化查询场景，经 P0 修复后
  多数可召回；P1 降级链与向量层进一步覆盖"近义词""超长描述""单字词"等
  当前类别 C 边界场景，用户感知的"查不到"将趋近于零；
- **回答更贴题**：去噪后的检索词使 Top-K 结果与用户真实意图对齐度更高，
  减少"有结果但答非所问"的体验损耗；
- **口语自由度提升**：向量语义层上线后，用户无需迁就系统的关键词口味，
  可直接使用自然表达（如"有没有卖便宜保温板的福建商家"），
  这是从"关键词检索工具"到"对话式查询助手"的关键一步。

## 4. 结论

1. **P0 三个紧急修复已按报告 5.2 节全部完成**：AND→OR 语义、LIKE 降级回退、
   地区/状态类 LIKE 模糊匹配，共修改 `price_inquiry.py` 一个文件，
   编译与静态检查均通过，影响面收敛、可独立回滚。
2. **P1 三项优化在现有架构下全部具备高可行性**：降级链与去噪零基础设施依赖，
   向量语义层所需的 Milvus + BGE-M3 + 混合检索经验已在 `public_kb` 模块
   完整验证，扩展成本主要在数据 ETL 而非工程攻坚。
3. **总投入约 7~11 人天**，与报告"1-2 周"预估一致；建议按
   去噪 → 降级链 → 向量层的顺序分批实施，每批独立可交付、独立可验证。
