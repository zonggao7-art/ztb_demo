## 2. 已完成工作详述

### 2.1 模型配置治理（WP1）——.env 单一事实源落地

**口径（D4/D6/D7）**：项目实际调用的模型必须与 .env 配置严格同步。模型名/凭据/端点 = 身份配置，必填、无默认值、无别名兜底；未配置 → 抛错，调用失败 → 抛错。治理对象是"配置与实际调用的一致性"，不是锁死某个模型名——.env 换什么模型，项目就调用什么模型。

**代码改动**：

- `public_kb/config.py`：7 项身份配置（`EMBEDDING_MODEL/LLM_MODEL/RERANKER_MODEL` + `EMBEDDING_API_KEY/EMBEDDING_BASE_URL/LLM_API_KEY/LLM_BASE_URL`）改为 `os.getenv("X")` 无默认值形态；`Settings.__post_init__` 统一校验，缺失/空串/纯空格即抛 `ValueError` 并逐一点名缺失项；删除 Embedding 的 `SILICONFLOW_*→CLOSEAI_*→DEEPSEEK_*` 别名链与 LLM 的 `MODEL_NAME/API_KEY/BASE_URL→DEEPSEEK_*` 别名链及默认值 `"z-ai/glm-5.3-flash"`；`RERANKER_MODEL` 由硬编码改为 .env 必填（凭据复用 Embedding 提供方，有意设计保留）；`EMBEDDING_DIM` 支持 .env 覆盖；删除死配置 `similarity_threshold`（降级路径已不存在）。
- `.env`：完成规范名迁移——`LLM_MODEL/LLM_API_KEY/LLM_BASE_URL`（按历史实际生效值等价迁移，经冒烟验证）+ `RERANKER_MODEL=BAAI/bge-reranker-v2-m3`；旧别名变量保留仅作历史备注，不再被任何代码读取。
- `.env.example`：重写为"身份配置必填且唯一"的文档化模板，登记休眠变量 `MINERU_API_TOKEN`/`TAVILY_API_KEY`。

**守卫体系（可持续防回归）**：

- 新增 `test/test_model_identity_config.py`（14 项）：必填抛错（7 变量参数化）、空串抛错、报错信息点名、config.py getenv 无默认值静态扫描、旧别名链禁复活扫描、三工厂（Embedding/LLM/Reranker）配置值逐字流转断言、生产源码模型名字面量 AST 扫描（docstring/注释豁免）、显式构造豁免。
- 新增 `test/conftest.py`：autouse 夹具注入 7 个身份变量（仅当环境缺失时），使测试套件在无 .env 的环境（如 CI）离线可跑。
- 修正既有守卫缺陷：`test_config_centralization.py` 的 `CHAT_LLM_RE` 误将 `_SafeEmbeddings` 并入"对话模型直构"正则（HEAD 上即失败的既有红测），按守卫自身文档意图归位到 Embedding 守卫。

### 2.2 检索链路整改（WP2/WP3）——混合检索就绪 + 零降级

**Schema 混合化（`public_kb/milvus_store.py`）**：

- 新 schema：`id / text(jieba analyzer, enable_analyzer) / vector(IVF_FLAT+COSINE, nlist=256) / sparse_vector(SPARSE_FLOAT_VECTOR)` + 服务端 `text_bm25` BM25 Function（text → sparse_vector，客户端禁止写稀疏字段）+ 稀疏索引 `SPARSE_INVERTED_INDEX/BM25`。
- **建库后 describe 自检**：`sparse_vector` 字段与 `text_bm25` Function 必须同时在位，缺失即抛错——把当年"Function 被静默丢弃 → 检索静默降级"的事故模式转为显性失败。

**检索路修正（`qa_chain.py` / `qa_chain_async.py`）**：

- 稀疏 `AnnSearchRequest` 的 `metric_type` 由 `"IP"` 修正为 **`"BM25"`**（BM25 Function 场景服务端要求，原写法在目标环境下不正确）；稠密路 COSINE/nprobe 维持。
- 零降级（D3）：删除 `_dense_only_retrieve`（同步/异步）及全部 `except → 降级` 分支；collection/embeddings 缺失、schema 不符、检索/精排异常一律上抛（图层级 `_with_fallback` 友好呈现保留，不属于检索内部静默劣化）。
- schema 校验前移并缓存：同步链构建时校验（`_validate_mixed_schema`），异步链首次检索校验后缓存——`describe_collection` 由"每查询一次"收敛为"仅一次"。
- **Reranker 假分数回退清除**（审计新发现）：同步/异步 `rerank()` 捕获一切异常后返回"原始顺序 + relevance_score=0.5"假分数的行为全部移除，失败上抛；`_SiliconFlowReranker` 与异步版的 base_url 硬编码默认兜底（`https://api.siliconflow.cn/v1`）一并移除，缺失即抛错。
- 日志治理：误导文案（"使用稠密+Reranker 模式"等）清除；日志与文档字符串去模型名绑定，改打 .env 实配值（`embedding=%s, reranker=%s`）；补齐"RRF 融合条数 / 精排 top1 / 过滤后条数 / 动态阈值"阶段日志，使混合检索"生效"肉眼可验。

**部署配置（`milvus/docker-compose.yml`）**：Milvus 镜像 `v2.4.0 → v2.6.0`（注释标注执行时锁定 2.6 系列最新补丁版）+ Attu `v2.6` + 逐级升级（2.4→2.5→2.6）与逐级 tar 备份指引。

## 4. 下一步工作预见性指导

### 阶段一：Milvus 2.6 升级执行（运维操作，半天）

**前置条件**：Docker 环境可用；Milvus 当前未运行，无在线业务，升级窗口自由。

**操作序列**（已写入 `milvus/docker-compose.yml` 注释与计划文档 WP2.4）：

1. **锁定版本**：本环境无法访问 Docker Hub，当前镜像写的是 `v2.6.0` 起始版。执行时查询 `milvusdb/milvus` 的 2.6 系列最新补丁 tag 并替换（同时核对 etcd/MinIO 与官方 2.6 standalone compose 的版本基准）。
2. **备份**：`docker compose down` 后对 `milvus/volumes/` 整目录 tar 备份（回滚点）。
3. **逐级升级**：2.4 → 2.5 → 2.6（官方不支持跨版本直跳），每级起服后 `get_server_version` + 集合可见性校验，每级独立备份。注意：现有集合为旧 schema 旧数据（已判定无效），升级后**不做数据迁移**，直接进入阶段二。
4. **探针验证**：最终 2.6.x 上 `python -m pytest test/ -q` 全量回归；如允许，可建临时验证集合实测混合 schema 建立与 `hybrid_search` 后即销毁（不触碰正式数据）。

**风险预见**：
- 若升级后 langchain_milvus 0.4.0 出现兼容问题，回归测试会立刻暴露；langchain_milvus 在零降级改造后职责已收窄（仅集合包装），必要时可评估彻底解耦（另行变更）。
- 回滚 = `docker compose down` + 恢复对应级别 tar + 回退镜像 tag。

### 阶段二：文档重切分与数据重建专项（核心质量工作，建议独立立项）

这是本轮整改的最终目的——"获取更高质量的数据"。schema 代码已与之解耦（BM25 Function 挂在 `text` 字段，切分只改内容不改契约），重建即激活混合检索。预见性建议：

**1）切分方案设计（对症下药）**：现有 `SemanticChunker`（标题感知、2000 字符/块、100 重叠）的问题需先定位再设计。法规文本的特殊性建议重点考虑：
- **条款原子性**：以"条"为最小语义单元（"第三十七条"），条文过长时再按"款/项"二级切分——避免一条法规被腰斩导致检索命中半条；
- **结构元数据增强**：章节路径（编/章/节/条）完整入 metadata，供稀疏路（BM25 命中"第三十七条"这类精确 token）与引用溯源双重受益；
- **块大小分档**：法条短文与表格/附则差异大，固定 2000 字符对短条款过度稀释、对长条文仍可能截断，建议按结构单元自适应而非固定字符数；
- **评测先行**：切分方案先在 `testset_knowledge.jsonl`（~106 题法规评测集）上离线对比召回率，再定稿入库——避免再次"重建完才发现质量不行"。

**2）重建流程**：方案定稿 → `python -m public_kb --init --pdf-dir raw_pdfs`（幂等，自动建混合 schema + 建库自检）→ 验收。

**3）验收清单**（数据重建的完成标准）：
- [ ] `describe_collection` 含 `sparse_vector` + `text_bm25` function + 稠密/稀疏双索引（建库自检通过即已保证）；
- [ ] 检索日志稳定出现 混合检索/RRF/Reranker/动态阈值 全链路字样，无 ERROR；
- [ ] 稀疏路有效性：精确条款号、专业术语类 query（"履约保证金""评标委员会"）可命中；
- [ ] `python scripts/run_knowledge_citation_eval.py`（~106 题）建立新数据基线，指标不低于旧基线（预期长尾题召回提升）；
- [ ] `RERANKER_MODEL` 走 .env 实际生效验证；`.env` 更换 LLM/Embedding 模型后启动日志与实际调用一致性抽查。

**4）参数标定（重建后必做，当前值是"拍脑袋初值"）**：
- **动态阈值**（0.40/0.45/0.50 三级）基于 Reranker 分数分布假设——重建后用真实 reranker 分数分布重新标定，否则可能出现全拒答或全放行；
- **RRF k=60、nprobe=32、dense/sparse limit=30** 为业界常用初值，建议在评测集上做小规模网格搜索；
- **BM25 jieba 分词质量**：招投标领域词（"招标控制价""踏勘"）若分词不佳，可引入自定义词库调整 analyzer——schema 代码不变。

### 长期治理约定（已成守卫，保持即可）

1. **换模型 SOP**：只改 `.env` → `python -m agent --question "..."` 冒烟 → `python -m pytest test/ -q` 守卫全绿 → 上线。任何情况下不在代码里加模型默认值/兜底（守卫测试会拦）。
2. **检索链路不加降级**：若未来需要某种受控降级（如限流期间的只稠密模式），必须走变更评审修订 D3，禁止顺手加 except 分支。
3. **重试边界（口径 B）**：允许"同配置原样重发"（429/5xx 退避），禁止"换路径/假结果"式回退；新增外部 API 客户端时沿用此约定。
4. **CI/新环境**：无 .env 环境运行测试依赖 `test/conftest.py` 的身份变量注入；生产/联调环境必须在 .env 配齐 7 项身份配置，缺一启动即报错（报错信息会逐一点名）。
