## 3. 修复过程中发现并修掉的两个新缺陷

### 3.1 首轮产物书3 丢失 15.45% 正文（门禁缺失 + 反向规则缺失）

首轮 `--prepare-handoff` **成功产出 844 块且门禁全绿**，但交叉核对文本量发现异常：书3 规范化文本 736,011 字符 → 切块后仅 681,406 字符。用 12-gram 抽样定位到 **1,718 个块、113,722 字符实质消失**。

根因链：

```
MinerU 把多条法条/多个编号条目粘连成一个大块（长至 1155 字）
  → 归一化只看行首编号：`(三)违反决策程序和规定……` 命中 （X） 规则 → 判为 level-5 标题
  → chunker 对“标题后无正文”直接 return → 整段文本被丢弃
```

两道防线同时缺失：方案 N1 的“长句不得成为标题”反向规则未落地；P3 门禁没有内容覆盖率项，因此**丢失 15% 正文仍能“全部通过”**。

处置与效果：

| 步骤 | 动作 | 书3 覆盖率 |
|---|---|---|
| — | 首轮（缺陷未修） | 84.55%（丢 113,722 字） |
| ① ② | prose guard 全面接入 + 书3 粘连条块拆分 | — |
| ③ | 新增 `text_coverage` 门禁（≥99.5%，fail-closed） | 门禁**当场拦下**书3（99.45%），书1/书2 放行 |
| ④ | chunker 标题救援 + 书3 子项标题阈值降至 40 字（残余 192 个 55–60 字 OCR 粘连标题） | **100.00%** |

三书最终均为 100.00%，且救援机制使该类缺陷在未来任何误分类下都不可能重现（宁可降级为正文，不可静默丢弃）。

### 3.2 工作区并发写入事件（需团队处理）

修复期间观测到 `DATA/repaired_knowledge/` 出现**非本次代码产出**的内容：`book1/documents.jsonl` 850 行、仅 42 个唯一 `chunk_uid`、首块 `page_start=0`（违反书1 正文起点 15 页），与 manifest 记录的 844 块互相矛盾。同期多次出现我的编辑被外部进程改写或还原（`public_kb/normalize.py`、`test/test_book_*.py` 均被重写）。

处置：改为**同一进程内“生成 + 立即自校验”**，并以 `chunk_uid` 有序 digest 作为交付指纹；产物正确性已在隔离目录二次确认（316/316 uid 唯一、页起点 15、覆盖率 100%）。

待办：该目录未纳入版本管理且可被多端并发生成，**入库前必须复核 digest**；建议约定单一生成端或将产物目录纳入 git。

## 6. 与方案的偏差及理由

1. **切分主路径改为块级直切**（`content_list.json` → SourceBlock → chunk_blocks），不再经 markdown 中转；`normalized.md` 仅作为可读旁证，且 `load_markdown_with_sidecar()` 会校验 md 与侧车一致后产出同 digest 结果。理由：只有块级保真 `page_idx` 与结构 id，md 往返会重新引入层级推断风险。仓库既有 `SemanticChunker.chunk(md)` 路径保留（法规 CSV、未来 PDF 用），但**该路径无页码（page_idx=-1）**，需要溯源的数据必须走块级路径。
2. **P1 的 TextCleaner 注释剥离已由既有实现覆盖**（含按块剥离保留前后文），本轮未重复改造。
3. **未做**（遵循 D5“本轮不建库”）：Milvus 集合重建、`--ingest-jsonl/--ingest-markdown` 实网验证、`scripts/run_knowledge_citation_eval.py` 引用评测回归（需活库）。
4. **表格仍为部分缺失**：书2 38 张、书3 22 张表格的正文以图片形式存在，本轮只入库 caption+footnote，标记 `content_type=table_image`，留表格专项。
5. **未做 N7 OCR 抽检**：书2/书3 为扫描 OCR 版，书1 auto 路由抽样发现封面级 OCR 错误，均尚未量化评估。
