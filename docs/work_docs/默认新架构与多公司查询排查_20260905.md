# 默认新架构与多公司查询排查

更新：2026-09-05

## 1. 先看结论

按要求分成了两项工作：

- **默认入口已经修改**：正常启动进入 hybrid 新架构；固定流程能完成的任务不强制进入 ReAct。
- **多公司查询完成本轮排查，尚未修复路由规则**：原日志中的失败发生在路由表单校验阶段，工具一次都没执行。现有执行器本身支持同一个工具分别查询两家公司。

目前不能宣称“系统已经稳定可用”：真实检查发现问候也可能被路由表单校验拒绝，以及模型会擅自增加城市筛选条件。这些需要下一步修复。

## 2. 现在怎样启动

在项目目录重启程序：

```powershell
.\.venv-react\Scripts\python -B -m agent --interactive --stream
```

不再需要增加 `--execution-mode hybrid`。启动时应显示：

```text
执行入口：hybrid（受控分流）；全部会话进入新架构，按任务分流
```

这只表示进入新架构。之后每个问题仍然经过路由和程序校验，选择固定流程、ReAct、要求补充信息或明确不支持。

要临时切回旧流程：

```powershell
.\.venv-react\Scripts\python -B -m agent --execution-mode legacy --interactive --stream
```

默认值是 `AGENT_EXECUTION_MODE=hybrid`、`AGENT_REACT_ROLLOUT_PERCENT=100`。100 指所有会话进入新架构，不是所有问题都执行 ReAct。

环境变量或 `.env` 的显式设置仍优先。当前本地 `.env` 没有覆盖这两项，因此没有修改密钥文件。CLI、直接创建 `AgentGraph`、服务入口均读取同一份 Settings；已运行的进程必须重启才生效。本次未重启或部署在线服务。

生产验收仍未完成。生产环境若尚不准备开放新架构，必须显式设置旧模式或受限准入，不能直接沿用新的默认值。

## 3. 你的日志说明了什么

原问题：查询合肥市百益通商贸有限公司和合肥达斯辉机电设备有限公司的工商信息。

日志记录了两次 `schema_invalid`，最终 `router_invalid`，同时：

```text
tool_attempts = 0
tool_executions = 0
```

因此，失败发生在“模型填写任务表单 → 程序检查表单”这一步，还没有到工具执行。不能据此判断是第二次工具调用被拦截。

当前日志把多种异常统一记为 `schema_invalid`，没有保留具体字段错误；仅凭这份日志，无法还原当时究竟填错了哪一项。

## 4. 已做的验证

真实模型均为日志中的 `deepseek-v4-flash-vision-exp`。诊断只调用路由模型，不执行 SQL/RAG；没有调整生产路由提示词、任务协议、工具预算或校验规则。

| 验证 | 结果 | 能说明什么 |
|---|---|---|
| 原问题，不带历史，连续 3 次 | 均拆成两个工商任务，选择固定流程，只有公司名条件 | 未复现原始结构错误；不代表历史故障不存在 |
| 原问题，带用户补充的前两轮问题，连续 3 次 | 均通过结构校验；其中 2 次擅自增加城市条件 | 路由仍有语义约束漏洞，不能把“结构通过”当成“理解正确” |
| 普通 CLI 启动并问“你好” | 已进入 hybrid，但两次路由均失败 | 默认入口生效；问候场景仍有路由问题 |
| 单独捕获“你好”的路由表单 | 两次都返回 `tasks=[]`，被 `tasks_required` 拒绝 | 确认了一个具体的协议与模型输出不一致问题 |
| 人工给定正确任务表单，离线测试同工具两次调用 | 固定流程、官方 ReAct 循环均通过 | 执行器不是“一种工具只能用一次” |

带历史的重放使用真实前两轮用户原话，其 SHA-256 与日志两项 `question_hash` 完全一致。现有 `decide()` 只取历史用户文本及完成标记，不把历史助手答案正文送入分类，因此没有重查前两轮业务数据。

离线工具测试覆盖：两家公司都查到、第二家公司无记录、第二家公司查询失败，分别在固定流程和 ReAct 中执行，共 6 项。每项确认同一工具执行两次、结果分别归属两个任务，并拒绝用第一家公司的证据回答第二家公司。

## 5. 新发现的两个具体问题

### 问题 A：纠错只说“表单错了”，没有告诉模型哪里错

“你好”的模型返回：选择固定流程、分支为 `general_chat`，但是任务清单为空。程序要求可执行方案至少有一个任务，因此拒绝是符合当前协议的。

问题在于模型看到的协议说明没有充分强调这项要求，而一次纠错也只收到笼统的 `schema_invalid`。这次实测中，模型第二次原样提交空清单，再次失败。

这解释了问候故障，**还不能认定原来的多公司查询也是同一种字段错误**。

### 问题 B：用户原文里出现过，不等于用户授权把它作为筛选条件

带历史重放中，模型两次为两个任务都增加了：

```text
city = 合肥市
```

用户是在说公司的工商全称，并没有另行指定城市筛选。程序目前只检查“合肥市”是否出现在用户原文中；因为它确实是第一家公司名称的一部分，就通过了检查。

这可能不必要地缩小查询范围；如果库中城市字段的写法不同，甚至可能把本来存在的公司查成无匹配。本轮未执行这些查询，因此这只是风险判断，不是已确认的数据库查询结果。

## 6. 建议的下一步修复顺序（尚未实施）

1. **让错误可定位**：输出受控的字段位置、错误类型和有限原因码，不打印完整异常、密钥或模型思考内容；不要把所有失败都混成一个 `schema_invalid`。
2. **把任务表单规则讲完整**：问候也需一个 `general_chat` 任务；两家公司必须拆成两个独立任务；同一工具可以服务多个任务，工具清单不是调用次数清单。
3. **让纠错有针对性**：告诉模型是缺少任务、重复编号、同一任务重复绑定公司名，还是分支不匹配。仍只允许原定的一次纠错，不放宽 schema、不增加重试预算。
4. **收紧额外条件授权**：禁止从公司名称中自动推导省、市等筛选项；额外条件必须对应用户明确提出的限制，并核对它属于哪个任务。无法确认时应澄清，不能自行加条件或删掉用户条件。
5. **按原会话验收**：回归前两轮加多公司问题，检查任务拆分、两次精确查询、结果归属；另加问候、无记录、单任务失败和错误证据引用用例。

对“两家公司分别查工商”这类独立任务，建议使用固定顺序执行两次工具。多个主体不等于必须 ReAct，也不需要把“单次只允许一个工具调用”改成并行批量调用。
