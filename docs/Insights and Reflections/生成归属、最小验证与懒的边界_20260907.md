## 第 1 章 · 路由器是模型，不是程序

### 1.1 问题

"路由"听上去像个 if/else 就能干的活：判断用户想查法规、查企业还是闲聊，然后分发。它凭什么被叫作"结构化分类模型"？

### 1.2 核实

翻 [router.py:94-101](../../agent/execution/router.py#L94-L101)，核心只有三行：

```python
model = llm.with_structured_output(ExecutionDecision, method="function_calling")
proposal = await model.ainvoke(prompt)
return validate_decision(ctx, proposal, tools)
```

整个代码库里**找不到任何一条**"关键词 → 意图"的规则分支。"这条请求该走 static 还是 react"的判断，发生在大模型的前向计算里，由训练出的权重决定；代码做的事情只有拼 prompt、绑 schema、发请求、校验返回。更有意思的是 [router.py:19](../../agent/execution/router.py#L19) 的那句提示词——系统**明令禁止模型像程序一样工作**：

> 由语义判断现有分支能否覆盖，不以关键词、连接词、工具数量判断复杂度。

### 1.3 拆词

- **"模型"**：描述判断发生的位置——在 LLM 的权重里，不在代码的分支里。换一种问法、换一种表达，规则程序会失效，模型能泛化；代价是要靠 schema 校验和重试循环约束它不自由发挥。
- **"结构化"**：描述输出契约——模型不是自由作答，而是在填一张 Pydantic 定义的表（[contracts.py:59-65](../../agent/execution/contracts.py#L59-L65)：`execution_mode` 四值枚举、`static_branch` 只能是三个分支名、tasks 拓扑有序），填错了程序把错误位置发回去让它改一次（[router.py:95-127](../../agent/execution/router.py#L95-L127)），两次不改过就整体作废。

分工由此清晰：**模型做语义判断（分到哪类），程序做合同审查（填的表对不对）**。程序没有消失，但它管的是契约，不是语义。

> **心得二**：判断一个组件"是不是模型"，别看它的代码量，看它的决策写在谁的参数里。代码分支里查得到答案的是程序；答案只存在于权重里的，是模型。

## 第 2 章 · 查询工具为什么自带大脑

### 2.1 我的质疑

"知识库查询工具内部居然调模型？查询工具把检索结果交回给 Agent 不就行了吗，凭什么给它配一个大脑？"

### 2.2 核实：工具库里注册的本来就是两个粒度

[knowledge.py:3-8](../../agent/tools/knowledge.py#L3-L8) 的模块注释写得很直白：

- `search_public_kb` —— **我想要的那种"纯查询工具"**：只检索，返回 top-K 证据片段（原文 + chunk_uid + 章节 + 分数），内部不调模型，答案由调用方自己组织；
- `knowledge_qa` —— **能力级工具**：内部走完整 RAG 问答链，调模型，直接返回成品答案。

它内置的那个模型干三件检索本身做不到的事：

1. **拒答判断**——检索回来的片段只是"相关"，不等于"能回答"，这个判断写不成代码规则；
2. **跨片段综合**——一个法规问题的答案往往散在几部法规的几条里，得有人把它们组织成连贯的话；
3. **标准化引用生成**——【来源N】标记是生成时写进去的，随后校验引用是否真实指向检索到的 chunk_uid。

### 2.3 为什么要这么设计

如果引用校验要靠外层 Agent 的自由输出来实现，溯源强度会下降——外层的产出是无约束文本，引错了只能事后检查。把"生成 + 引用 + 校验"封进同一条链，**返回出去的答案保证引用已核验通过**，调用方原样转发即可。这是拿"多一次模型调用"的成本，换"引用协议不在外层被稀释"的保证。

> **心得三**：带脑工具不是错误设计，是"生成责任"放在了工具这一层。真正的判断标准是：这次模型调用有没有可替代者——没有，它就是必需品；有，它才是冗余。

## 第 3 章 · "双重生成"的证伪——我差点被自己的印象和我信的结论同时骗过

### 3.1 我的担心

换回 knowledge_qa 之后，我盯着"同一次查询前后两次调用模型"越想越不对：外层 Agent 本来就要整理输出，工具里又藏一个模型写答案，这不是重复劳动吗？

### 3.2 核实：四个调用，只有一次写内容

顺着 react + knowledge_qa 的完整链路数下来，是**四次模型调用、一次内容生成**：

| # | 调用 | 干什么 | 写不写内容 |
|---|---|---|---|
| 1 | decide | 意图分类 + 任务规划 | 否 |
| 2 | 选工具 | react 循环第一轮 | 否 |
| 3 | knowledge_qa 内部 | 检索 + 拒答 + 生成 + 引用 | **是（唯一一次）** |
| 4 | 提交 AnswerCandidate | 强制交"结构化信封" | 否 |

三条代码证据，条条锚死：

- **禁止改写**：[executor.py:50-51](../../agent/execution/executor.py#L50-L51)——"法规答案由程序从本任务的工具结果取回；不得重写、转抄或把生成答案当作新的原始证据"；
- **信封是被迫的**：[executor.py:141-146](../../agent/execution/executor.py#L141-L146)——全部任务成功后，middleware 清空工具列表、强制 `tool_choice=AnswerCandidate`，模型此刻除了交表无事可做；
- **发布是纯代码**：[output.py:137-148](../../agent/execution/output.py#L137-L148)——render 强制 rag 任务的 blocks 必须恰为 `["rag_answer"]`，然后从台账逐字取回工具生成的原文，转义、重排引用编号、拼装。[output.py:15-17](../../agent/execution/output.py#L15-L17) 的模块文档就是这句话的原文："最终答案里没有一个字是模型自由发挥的……模型只负责'选用哪些块、怎么组织'，不负责'写内容'。"

### 3.3 勘误与教训

这段核实纠正了两处错误，而且**两处错误都值得记下来**：

- **[前篇 09-05 的三条结论全部过时](./ReAct设计哲学与模型权力边界_20260905.md)**：`knowledge_qa` 已不是僵尸授权——[policy.py:46](../../agent/execution/policy.py#L46) 现为 `"public_kb_qa": {"knowledge_qa"}`，[executor.py:183](../../agent/execution/executor.py#L183) static 固定优先它，[output.py:93-95](../../agent/execution/output.py#L93-L95) 它的完整答案直接作为发布块。前篇的"react 剔除 / static 优先检索级 / answer 被丢弃"三条，一条都不再成立。
- **对话中途给出的"AnswerCandidate 是第二次生成"也是错的**——是我的记忆先起疑、要求回代码核实之后才被推翻的。我一开始甚至以为自己"记错了"，差点替错误的结论道了歉。

> **心得四**：我下意识以为"记错的人是我"，核实后发现错的是结论本身。对自己的记忆要存疑，对别人的断言（包括 AI 给的）同样要存疑——存疑的方式不是换个说法再问一遍，而是要求给出 `文件:行号`，亲手对一遍。

## 第 4 章 · 两条路的抉择——当年我到底在想什么

### 4.1 事件还原

发现新工具（裸检索）表现差的时候，我面前有两条路：

- **路 A**：放宽外层 Agent 的限制，给它书写答案的权限。但我当初限制它"只能原样返回查询结果"，正是为了防它自由发挥——放开这条等于动系统的安全底线。
- **路 B**：启用旧工具 knowledge_qa，它自带书写、整理答案的功能。

我选了 B。

### 4.2 我当时的真实想法

说实话，我当时心里想的只是：**我不想再动架构了，我想用最小的成本先验证新架构能不能跑通。**

但把这个"不想"翻译成决策语言，它其实是三句话：

1. 跑通之前动架构，出了问题分不清是谁的锅——架构改坏的，还是工具本来就不行的；
2. 冻结架构、只换零件，系统里"在变的东西"就只剩一个（新工具还是旧工具），测出来的好坏百分之百归因于它；
3. 放开书写权限是动安全底线的大动作，不该在"验证能否跑通"的阶段顺手做。

事后这笔账也补上了：链路通了之后我回头核实，确认旧工具在链路里只写一次内容、没有重复劳动（第 3 章），也明确了将来真要放开 Agent 书写权限，必须先把"每句标出处、事后核对"的检查机制一起跟上——不能只放权、不设防。

> **心得五**：先跑通，再选型；一次只改一个变量。要欠债，就记在账上——知道自己欠了什么、为什么欠、打算什么时候还——别欠在糊涂里。

## 第 5 章 · "懒"与工程判断的边界

### 5.1 那个让我坐立不安的问题

我一直隐约觉得自己是犯懒、投机取巧。直到这场对话把"犯懒"和"工程判断"摆在一起比对，才发现两者的**感受一模一样，都是"我不想多干活"**——区别不在动机，在于当时脑子里装没装着三样东西：

1. **知不知道另一条路的代价**——我不是没想过改架构，我是明确评估过"动安全底线 = 风险大"。真犯懒的人不会想到第二条路，只会沿着现状滑下去；
2. **知不知道当下最该验证什么**——当时的问题不是"哪种设计更优雅"，而是"新架构能不能跑通"。为了验证 A 顺手改 B，结果好不知功在谁、结果坏不知锅在谁；
3. **回头有没有还账**——跑通之后我没有把旧工具永远糊在那儿，而是回头核清了它的真实成本。

三条全中，就是工程判断，哪怕驱动它的情绪只是"不想再动脑子"。软件行业的老话"懒是程序员的美德"，前提恰恰是懒对了地方：想用最小成本验证"能不能跑通"，本身就是标准做法的教科书定义——先搭一条能走通全程的骨架，再往里填肉。

### 5.2 真正的分界线

**所有人都在省事。** 懒人和工程师的分界，从来不是"想不想省事"，而是省下来的事——记在了账上，还是假装它不存在。

## 第 6 章 · 蒸馏

### 6.1 一句话集

- 决策写在代码分支里的是程序，写在权重里的是模型；程序负责契约审查，模型负责语义判断。
- 大脑跟着综合责任走：一条执行路径，有且只有一次内容生成。
- 判断模型调用是否冗余，看它有没有可替代者，不看它出现了几次。
- 带脑工具的代价是延迟，收益是引用协议在生成时就被强制执行——这不是浪费，是交换。
- 先跑通，再选型；一次只改一个变量。
- 债要记账，不要糊涂；账要按调用链算，不能按注册表算。
- 直觉值得追查，断言需要锚点；存疑的对象包括自己的记忆。
- 省下来的事，记在账上是决策，假装不存在才是懒。

### 6.2 面试应答骨架（如果被问"你为什么把模型封在工具里"）

1. **当时的约束**：旧架构里 Agent 只是转发器，系统唯一的生成点就在工具内部——不这么干没人写答案，且引用校验必须与生成同链条才强制得住；
2. **暴露的问题**：新架构下外层自带模型，我一度担心双重生成；
3. **怎么核实的**：数了整条链路的调用账——四次调用、一次生成，外层被禁止改写、信封被迫提交、发布是纯代码；中间还有一轮删旧工具的实测，评测下滑证明综合这一步省不掉；
4. **决策叙事**：发现新工具不好用时，我评估过放开 Agent 书写权限的路线，但那是动安全底线的大改；当时首要目标是先验证链路能跑通，于是冻结架构、只换零件，把变量隔离到唯一一个；
5. **对追间的应答**："是欠债，但是记账的债，不是糊涂的债——我清楚欠了什么、为什么欠、之后还了什么。" 以及"重来一次会早点把'检索级/能力级'两个粒度拆清楚，并把设计决定写下来，避免连自己都忘了为什么这么设计。"

### 6.3 记忆口诀

> **曾经只有一支笔 → 担心两支笔 → 实验证明少一支不行 → 数了数其实一直只有一支 → 以后先数笔，再动工。**
>
> **先跑通，再选型；一次只改一个变量；要欠债，就记在账上，别欠在糊涂里。**
