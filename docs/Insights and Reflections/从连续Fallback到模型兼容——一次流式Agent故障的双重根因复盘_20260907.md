## 第 0 章 · 这不是一个 Bug，而是两种故障长着同一张脸

这场排查由两个连续事件组成。

第一个事件发生在流式问答里。我问：

> 投标需要交保证金吗

系统正确地把问题路由到了 `knowledge_qa`，但在 Embedding 请求阶段发生 `PoolTimeout`，随后进入 fallback。更值得警惕的不是这一次失败，而是我观察到：**一旦出现这次 fallback，后面即使再问知识库里明确存在的问题，也会持续失败。**

第二个事件发生在我更换对话模型之后。我把 `.env` 中的模型切换成 DeepSeek 的 `deepseek-v4-flash-vision-exp`，然后发现几乎所有问题又开始稳定地进入 fallback。表面现象和第一次一模一样，但日志已经变成 HTTP 400：

```text
Thinking mode does not support this tool_choice
```

最终证明，这是两个不同根因：

1. **第一次是运行时生命周期故障**：事件循环被销毁，但异步 HTTP 客户端和连接池继续复用；
2. **第二次是模型能力协议不兼容**：DeepSeek 思考模式与路由层的强制工具选择组合冲突。

它们共同暴露了一个很适合面试讲的事实：

> **fallback 只是症状，不是根因。相同的用户界面结果，可能来自资源生命周期、网络、模型协议、业务拒答或路由分类中的任何一层。**

## 第 1 章 · 我真正抓住的异常，不是“失败”，而是“失败会传染”

### 1.1 普通观察与有效观察的差别

如果我只看到一条 `Request timed out`，最容易得出的结论是：网络偶发抖动，重试即可。

但我没有停在这里。我强调的是：

> 当系统出现一次这样的 fallback 后，后续无论用户提什么问题，即便是知识库当中有的问题，系统也会持续报错。

这句话实际上包含了一个很强的诊断信号：**故障具有跨请求记忆。**

一个仅由输入内容触发的业务问题，通常不会让后续无关输入一起失败。能够“传染”到下一轮的东西，往往属于以下几类：

- 被复用但已失效的连接或客户端；
- 跨轮保存的状态标志；
- 半初始化后被缓存的单例；
- 没有释放的锁、信号量或池槽位；
- 未完成任务或生成器残留；
- 会话检查点里遗留的错误结果。

所以，我的观察把问题从“某个问句为什么失败”升级成了：

> **进程中有什么状态，在第一次失败后没有恢复？**

这是整场排查中最有价值的起点。

### 1.2 面试表达

我可以这样描述自己的判断：

> 单次超时首先是外部依赖问题，但“后续所有请求持续失败”说明故障已经越过请求边界。我不会先加重试，而会先检查事件循环、连接池、单例、会话状态和取消清理，因为这些才具有跨请求影响能力。

## 第 2 章 · 先按时间线定位失败边界，而不是被 fallback 文案带跑

### 2.1 日志时间线

第一次故障的关键顺序是：

```text
Router → knowledge_qa
knowledge_qa → retrieval_start
RAG → embed_query_async
OpenAI SDK → HTTPX/httpcore
PoolTimeout → APITimeoutError
graph wrapper → fallback
```

从时间线可以得出三个排除项：

1. Router 已经判定为 `knowledge_qa`，所以不是“没识别用户意图”；
2. 异常发生在 Embedding 阶段，Milvus 还没有完成检索，所以不是“知识库没有命中”；
3. LLM 还没有拿到检索上下文，所以也不是“模型不会回答保证金问题”。

因此，“超纲问题导致 fallback”是用户界面给人的感觉，不是日志证明的事实。更准确的说法是：

> **这是一个本应进入专业知识问答的问题，但基础设施在检索前失败了。**

### 2.2 我学到的故障分类

我以后会明确区分四种结果：

| 结果 | 含义 | 应有终态 |
| --- | --- | --- |
| 业务拒答 | 检索完成，但证据不足 | `final`，明确说明依据不足 |
| 意图不明确 | Router 成功，但无法判定目标 | `final`，引导澄清 |
| 基础设施失败 | 网络、连接池、数据库、模型 API 失败 | `error`，可重试但不能伪装成业务结论 |
| 用户取消/客户端断开 | 请求没有完成 | `cancelled` 或取消传播，绝不能保存为成功答案 |

> **心得一**：错误处理的第一职责不是“永远返回一句话”，而是保留失败语义。把技术错误包装成“问题不明确”，表面更友好，实际上破坏了可诊断性和用户信任。

## 第 3 章 · 第一个根因：事件循环死了，连接池却还活着

### 3.1 原来的生命周期错位

原 CLI 交互模式每轮调用一次 `asyncio.run()`：

```text
第 1 轮：创建 loop A → 使用异步客户端 → 关闭 loop A
第 2 轮：创建 loop B → 继续复用同一个异步客户端/连接池
```

但 Router、RAG、Embedding、Reranker 等对象是长生命周期对象，底层 HTTPX/httpcore 连接池也会继续存在。连接中的锁、事件和 socket 等待状态却可能已经与 loop A 绑定。

这形成了一个不对称生命周期：

```text
Agent / RAG / HTTP Client：长生命周期
Event Loop：每轮销毁
```

“长生命周期客户端依赖短生命周期运行时”本身就是设计冲突。一旦连接池经历超时、取消或竞争，后续请求就可能等待一个已经无法正常推进的状态，表现为持续 `PoolTimeout`、`APIConnectionError` 或 “event loop is closed”。

### 3.2 修复原则

修复不是把池子调大，也不是无限重试，而是让所有者生命周期对齐：

```text
一个交互会话
  └── 一个 asyncio.Runner / Event Loop
        ├── 多轮 Router 请求
        ├── 多轮 Embedding 请求
        ├── 多轮 Reranker 请求
        └── 多轮 LLM 流式生成
```

[`agent/__main__.py`](../../agent/__main__.py) 因此改成会话级复用 `asyncio.Runner`。同一次交互中的每一轮都提交给同一个事件循环，不再反复创建和销毁异步运行时。

### 3.3 为什么不选择另外两个“看起来更简单”的办法

#### 方案 A：每轮重新创建所有客户端

它可能规避跨循环复用，但代价是：

- 丢失 keep-alive 和连接复用收益；
- 每轮重新握手，增加延迟；
- 需要确保所有间接持有客户端的对象也一起重建；
- 容易遗漏 RAG 单例、Reranker 或 Router 内部的客户端。

#### 方案 B：遇到超时就多重试几次

如果根因是客户端绑定了失效运行时，重试只会重复使用同一个坏状态。它还会放大外部请求数量，让用户等得更久。

> **心得二**：连接池问题首先是“所有权和生命周期”问题，其次才是容量问题。遇到 `PoolTimeout`，不能条件反射地增加 `max_connections`。

## 第 4 章 · 不止一个跨轮状态：错误结果、半初始化单例和残留流

事件循环是主因，但排查没有停在那里。因为“失败会传染”的每一种可能都值得验证。

### 4.1 `business_result` 残留

LangGraph 会保留消息历史，但旧错误不应该自动成为新请求的业务结果。新一轮输入现在会显式清空 `business_result`，保留真正需要的对话消息。

这里的原则是：

- **记忆**应该跨轮保留；
- **请求结果**属于一次执行，不应该跨轮继承；
- **错误诊断**应进入日志/可观测系统，而不是伪装成下一轮状态。

### 4.2 RAG 单例的发布时机

原来的风险是：先把新对象写进全局 `_rag_engine`，再调用 `ensure_loaded()`。如果加载失败，全局变量里就留下一个半初始化对象，下一轮不会重新构建。

修复后的原则类似数据库事务：

```python
candidate = PublicKnowledgeRAG()
candidate.ensure_loaded()
_rag_engine = candidate
```

只有初始化完整成功后，候选对象才被“发布”为共享单例；并发初始化使用锁，避免其他线程观察到半成品。

### 4.3 生成器必须显式关闭

流式调用的资源不是只存在于函数返回值里。客户端中途断开时，以下对象都可能仍在运行：

- RAG 异步生成器；
- LLM token 流；
- SSE 正文生产任务；
- 心跳生产任务；
- LangGraph 内部执行任务。

因此，RAG、节点、LLM 流和 SSE 合并都使用 `aclosing`，并在 `finally` 中取消、等待和回收任务。

> **心得三**：异步生成器不仅是一种返回数据的语法，它还是资源作用域。消费者提前退出时，生产者是否关闭，是系统正确性的一部分。

## 第 5 章 · “暴力测试”真正要测的是恢复能力

我一开始提出的不是“跑一下看看”，而是要对流式输出做一次暴力测试。事后回看，这个要求的价值在于：**正常路径通过一次，几乎证明不了系统是否健壮。**

### 5.1 测试矩阵

新增的 [`test/test_streaming_resilience.py`](../../test/test_streaming_resilience.py) 覆盖了：

- 真实本地 HTTP/1.1 keep-alive；
- 实际 `_SafeEmbeddings → OpenAI SDK → HTTPX/httpcore` 调用链；
- `PoolTimeout`；
- `ReadTimeout`；
- HTTP 503；
- token 输出到一半后断流；
- 流自然结束但没有 `final`；
- 外部任务取消；
- 内部取消；
- 总 deadline；
- SSE 心跳；
- SSE 客户端断开；
- RAG 首次初始化失败后重试；
- 16 线程并发初始化；
- 200 请求、16 并发的会话隔离。

### 5.2 最关键的断言不是“报错了”

故障注入测试真正重要的断言是：

```text
失败请求：有且只有一个错误终态
下一请求：能够正常成功
失败会话：不污染其他 thread_id
取消之后：没有残留 asyncio 任务
已输出半截 token：不能保存成完整成功答案
```

例如，对 PoolTimeout、ReadTimeout 和取消三类真实连接池场景，每类故障之后都连续执行 20 次 Embedding 请求，以验证池槽位真正恢复，而不是只验证“下一次碰巧成功”。

### 5.3 结果

流式修复阶段的详细记录显示：

- 200 请求、16 并发，其中 40 次有意失败、160 次正常请求，状态和 request_id 互不污染；
- 四类失败场景之后，各连续 12 轮正常回答；
- 真实连接池三类故障之后，各连续 20 次成功；
- 当时全量回归为 390 passed、1 skipped；后续 ReAct 与 DeepSeek 兼容改造继续扩展了测试集。

> **心得四**：恢复测试要验证的是“失败后系统回到了哪个状态”，而不只是“失败时有没有 catch 住异常”。

## 第 6 章 · 第二个根因：OpenAI-compatible 不等于能力完全兼容

### 6.1 我为什么再次追问“为什么换模型就坏了”

流式生命周期问题修完后，我只改了 `.env` 里的对话模型，系统又开始全部 fallback。这个时间相关性很强：**唯一显著变量是模型和供应商接口。**

这时如果仍把问题归因于连接池，就会犯“刚修过什么，就认为下一次还是它”的锚定偏差。我重新拿日志说话：

```text
POST https://api.deepseek.com/chat/completions → 400 Bad Request
Thinking mode does not support this tool_choice
```

这是确定性的参数校验错误，不是偶发网络超时。

### 6.2 路由调用实际做了什么

legacy Router 的策略是：

1. 优先 `with_structured_output(RouterDecision)`；
2. 如果结构化输出方式不受支持，切换到 Tool Calling；
3. Tool Calling 使用 `tool_choice="required"`，强制模型必须选择一个路由工具。

这个策略在原模型上成立，但 DeepSeek 思考模式拒绝当前强制工具组合。更隐蔽的是，Router 会缓存 `tool_fallback=True`：一旦第一次结构化调用失败，后续请求直接走同一条不兼容的 Tool Calling 路径，于是看起来又像“失败会传染”。

这里的跨轮状态不是坏连接池，而是**已缓存的协议降级策略**。

### 6.3 “接口格式兼容”的真实含义

所谓 OpenAI-compatible，通常只说明请求路径、消息格式和 SDK 调用方式大体兼容，不代表以下能力完全一致：

- `response_format=json_schema` 是否支持；
- Pydantic schema 通过哪种机制约束；
- `tool_choice=required/auto/指定函数` 的支持范围；
- 思考模式能否与工具调用组合；
- 是否要求在多轮工具调用里回传 `reasoning_content`；
- 严格 JSON Schema 支持哪些关键字；
- 流式 chunk 中 reasoning 和 content 如何区分。

> **心得五**：模型供应商切换不是“换一个 model 字符串”，而是一次协议能力迁移。兼容层要面向能力，不要只面向品牌名。

## 第 7 章 · DeepSeek 兼容修复为什么放在模型工厂，而不是散落在 Router

### 7.1 统一适配点

项目规定所有 ChatOpenAI 实例必须经 [`public_kb/llm_factory.py`](../../public_kb/llm_factory.py) 创建。DeepSeek 兼容因此进入已有的 `BudgetedChatOpenAI`，而不是分别在 legacy Router、hybrid Router 和 ReAct executor 里打补丁。

这样做有三个好处：

1. legacy 与 hybrid 使用相同协议；
2. 未来新增结构化调用不会忘记适配；
3. 模型预算、超时、重试和提示词检查仍由原包装器负责。

### 7.2 调用级适配，而不是全局关闭模型能力

修复策略是：

- 仅当 endpoint 的准确 hostname 是 `api.deepseek.com` 时启用适配；
- 默认结构化输出和显式 `json_schema` 转换为 `function_calling`；
- Pydantic 仍然校验返回值，非法枚举不会被接受；
- 结构化输出和 `bind_tools` 的**这一次调用**设置 `thinking={"type": "disabled"}`；
- `tool_choice=required` 仍保留，不偷换成更弱的 `auto`；
- 其他 `extra_body` 字段继续保留；
- 共享模型对象不被修改；
- 普通 RAG 正文生成保持原配置，不被全局关闭思考模式；
- OpenRouter、OpenAI 和名字里包含 DeepSeek 的其他代理 endpoint 不受影响。

这是一种“最小能力降级”：只在产生冲突的控制面调用中关闭 thinking，不牺牲数据面正文生成能力。

### 7.3 为什么不能只把 `required` 改成 `auto`

如果改成 `auto`，模型可能直接输出自然语言，不调用任何路由工具。当前路由协议会把“没有工具调用”判定为 fallback。更重要的是，hybrid 受控执行依赖结构化决策和 `AnswerCandidate`，放松强制工具选择会削弱发布边界。

所以正确目标不是“让 API 不报 400”，而是同时满足：

```text
供应商接受请求
+ 模型必须返回结构化结果
+ Pydantic 校验仍有效
+ 工具选择权限不放宽
+ 原始模型输出不能绕过发布器
```

> **心得六**：兼容性修复不能以取消安全约束为代价。最危险的修复，往往是“错误消失了，但协议也被悄悄放宽了”。

## 第 8 章 · 同一个 fallback，如何快速判断是哪一种根因

以后再遇到 fallback，我会按以下顺序定位。

### 8.1 看失败发生在哪个阶段

| 最后成功阶段 | 优先调查 |
| --- | --- |
| Router 请求都没发出 | 配置加载、模型工厂、事件循环 |
| Router 返回 400 | 模型能力、参数组合、schema/tool_choice |
| Router 成功，Embedding 失败 | Embedding endpoint、连接池、并发、超时 |
| Embedding 成功，Milvus 失败 | collection、schema、索引、服务状态 |
| 检索成功，生成失败 | LLM 流、上下文、引用协议、输出长度 |
| token 已开始，随后中断 | 流关闭、取消传播、客户端断开、读取超时 |
| final 已到但状态不对 | 检查点提交时序、重复终态、旧状态残留 |

### 8.2 看错误是确定性的还是瞬态的

- 每次立即返回相同 HTTP 400：优先判断协议/参数；
- 等待固定时长后超时：优先判断网络、池、deadline；
- 首轮失败后后续全失败：优先判断共享状态和生命周期；
- 只有特定问题失败：再检查输入内容、schema 或业务数据；
- 并发时失败、串行成功：优先检查容量、锁、信号量和池槽位释放。

### 8.3 看“错误恢复动作”是否真的改变了变量

例如：

- `clear` 只清会话记忆，不能修复已关闭的事件循环；
- 重启进程可以清掉坏连接池，但不能让不兼容参数变得兼容；
- 加重试可以覆盖瞬态网络错误，但不能覆盖确定性 HTTP 400；
- 扩大池可以缓解真实容量不足，但不能让跨循环绑定变正确。

> **心得七**：每个修复动作都应该回答一句话——“它改变了哪个导致故障的变量？”回答不出来，就很可能只是碰运气。

## 第 9 章 · 从我的提问方式里能看出的思考习惯

这部分不是技术结论，而是我为面试准备时更应该保存的“我是怎么想的”。

### 9.1 我相信实测，但不满足于一次实测

我不是只报一条异常，而是提供完整时间线，并指出异常之后的长期行为。随后我要求“暴力测试”，关注的是连续失败、恢复和状态污染。

这说明我的默认标准不是：

> 能不能跑通一次？

而是：

> 失败之后还能不能继续提供服务？

### 9.2 我会主动关联最近的变量变化

第二次故障时，我没有笼统地说“系统又坏了”，而是明确补充：

> 我 `.env` 里把对话模型切换为了 DeepSeek 的模型。

这相当于给出了一个差分诊断线索：旧配置可用，新配置失败，重点检查 provider/model capability，而不是从数据库一路盲查。

### 9.3 我先问“为什么”，再问“怎么修”

先理解原因，再授权实现，是一个很好的节奏。模型兼容问题如果直接动手，最容易用 `tool_choice=auto` 或去掉 schema 来让 400 消失，却没有意识到安全协议已经变弱。

### 9.4 我开始把故障变成可复用知识

最后，我要求把对话整理成反思材料。这意味着问题的价值不止是“今天修好了”，还包括：

- 我能否下次更快识别同类故障；
- 我能否向面试官解释取舍；
- 我能否区分证据、推断和最终决策；
- 我是否形成了一套自己的排障框架。

> **心得八**：工程能力不只是解决问题的速度，还包括把一次问题压缩成下一次可以复用的认知工具。

## 第 10 章 · 对协作方式的反思：结果正确，不代表过程中的主导权足够清晰

这次对话里，AI 副驾驶快速完成了“分析 → 决策 → 实现 → 验证”的完整闭环。结果上，修复经过了故障注入、全量回归和真实调用验证；但从我的成长和主导权角度看，这个过程仍有一个不足：**关键设计取舍没有逐项停下来让我先判断。**

例如，以下问题本可以先交还给我：

1. 流式 CLI 是复用一个 Runner，还是让每轮重建全部异步客户端？
2. 技术错误应该返回 `error`，还是仍用业务 `final` 承载？
3. DeepSeek 工具调用是关闭 thinking，还是为 Router 单独配置另一个模型？
4. provider 识别应该按 endpoint、模型名，还是显式 capability profile？
5. 兼容适配应该放模型工厂、Router，还是执行层？

AI 给出的方案是合理的，但“合理”不能替代我的选择。以后更理想的协作节奏是：

```text
副驾驶提供证据和可证伪假设
→ 我判断根因
→ 副驾驶列出 2~3 个方案及代价
→ 我选择技术路线
→ 我先写关键伪代码或接口
→ 副驾驶承担实现、测试和机械检查
→ 我做最终验收
```

这不是为了降低 AI 的效率，而是为了确保：项目做完后，我不仅拥有代码，也拥有形成代码的判断。

> **心得九**：高能力副驾驶最有价值的地方，不是替我开完整段路，而是让我看见更多路况，同时仍由我握方向盘。

## 第 11 章 · 面试中的 STAR 叙事

### Situation

我负责一个基于 LangGraph、Milvus、MySQL 和多个 OpenAI-compatible 模型服务的招投标智能助手。系统在流式知识问答发生一次 Embedding 超时后，后续请求持续 fallback；之后切换到 DeepSeek，又出现稳定 HTTP 400 和连续 fallback。

### Task

我的目标不是让单个请求“看起来成功”，而是：

- 找到跨请求故障的根因；
- 区分业务拒答与基础设施错误；
- 保证流式终态一致、取消后无资源泄漏；
- 在适配 DeepSeek 时不削弱结构化输出和 ReAct 发布约束；
- 用可重复的故障注入证明恢复能力。

### Action

1. 按日志时间线定位故障边界，确认第一次失败发生在 Embedding、第二次发生在 Router 参数校验；
2. 从“失败会传染”推断存在跨请求共享状态，检查事件循环、连接池、`business_result`、单例和生成器生命周期；
3. 将 CLI 改为会话级事件循环，显式关闭异步生成器，并让新请求清空旧业务结果；
4. 单例改为初始化成功后再发布；
5. 建立唯一终态语义：业务拒答是 `final`，技术失败是 `error`，取消不能被保存为成功答案；
6. 在统一模型工厂中增加 DeepSeek 调用级适配：结构化/工具调用关闭 thinking，使用 function calling，保留 Pydantic 和强制工具选择；
7. 使用真实本地 HTTP 链、MockTransport、并发故障注入、SSE 断开和真实 DeepSeek 调用验证。

### Result

- 流式修复验证了 200 请求、16 并发下的故障隔离；
- PoolTimeout、ReadTimeout、取消之后分别连续 20 次恢复成功；
- DeepSeek 的同步结构化、异步结构化和 Tool Calling 路由均真实成功；
- 普通知识问答和流式知识问答均进入 `knowledge_qa` 并返回唯一正常终态；
- 后续完整测试集达到 451 passed、1 skipped；
- 没有通过无限重试、扩大连接池或放松输出约束掩盖问题。

## 第 12 章 · 60 秒面试回答

> 我遇到过一个很有代表性的 Agent 稳定性问题：流式 RAG 一次 Embedding 超时之后，后续所有请求持续 fallback。我注意到“失败会传染”，所以没有只加重试，而是检查跨请求状态。最后发现 CLI 每轮用 `asyncio.run()` 销毁事件循环，却复用长生命周期的 HTTPX 客户端和连接池，生命周期不对齐；同时还有旧业务结果残留、半初始化单例和流未关闭等次生风险。我把交互会话改为单一长期事件循环，统一 final/error/cancelled 语义，并做了 PoolTimeout、ReadTimeout、断流、取消、SSE 断开以及 200 请求并发故障注入。
>
> 后来切换 DeepSeek 后，同样表现为持续 fallback，但这次日志是确定性的 HTTP 400。根因是思考模式与 `tool_choice=required` 不兼容，而且 Router 缓存了失败后的工具回退路径。我没有把 required 改成 auto 来放松协议，而是在统一模型工厂里仅对 DeepSeek 的结构化和工具调用关闭 thinking，并继续用 function calling 加 Pydantic 校验。普通 RAG 生成仍保留原模型能力。最终真实同步、异步和工具路由都通过，全量测试 451 项通过。这个案例让我形成的核心方法是：同样的 fallback 必须按阶段、错误类型和跨请求状态分别定位；健壮性测试要证明失败后的恢复，而不只是证明异常被捕获。

## 第 13 章 · 面试官可能追问什么

### Q1：为什么连接池会和事件循环绑定？

回答重点：异步客户端底层依赖异步锁、事件和 socket 等待对象；这些对象在第一次竞争或等待时可能绑定运行它们的 loop。客户端比 loop 活得久，就会形成非法生命周期。不要只背“HTTPX 不能跨 loop”，要说清所有权不对齐。

### Q2：`PoolTimeout` 一定说明连接池太小吗？

不是。它只说明在 pool timeout 内没有拿到连接。可能是并发确实超限，也可能是请求未释放、取消清理失败、连接绑定旧 loop、上游卡住，或池槽位泄漏。要用串行/并发对比、在途计数和失败后恢复测试判断。

### Q3：为什么技术错误不能走普通 fallback？

因为 fallback 在这里同时承担了“意图不明确”和“节点异常”的职责。如果都输出同一业务文案，用户会误以为自己问错了，监控也无法区分业务拒答与服务失败。错误分类是产品语义，不只是日志细节。

### Q4：为什么不直接把 DeepSeek 的 `tool_choice` 改成 `auto`？

因为 Router 和受控 ReAct 依赖强制结构化结果。`auto` 允许模型直接输出自然语言，会降低协议强度，并可能绕过任务合同或最终发布结构。兼容修复必须维持原安全不变量。

### Q5：为什么只在工具调用时关闭 thinking？

冲突发生在控制面：路由、工具选择、结构化信封。普通 RAG 正文是数据面生成，没有必要一起降级。调用级关闭能缩小影响范围，也避免修改共享模型实例。

### Q6：为什么按 endpoint hostname 识别，而不是按模型名？

同一个模型名可能通过 OpenRouter、私有网关或兼容代理访问；这些平台支持的参数不一定等同于 DeepSeek 官方 API。准确 hostname 是更可靠的当前边界。但长期更好的方案是显式 capability profile，而不是无限累积 endpoint 分支。

### Q7：怎么证明没有削弱结构化约束？

不仅检查 HTTP 200，还需要注入非法枚举、缺字段和错误 schema，确认 Pydantic 仍拒绝；检查实际 SDK 请求体仍带强制工具选择；在 hybrid 完整链路中验证原始模型/工具输出仍必须经过 `execution/output.py`。

### Q8：如果再做一版，会改进什么？

可以把供应商能力从隐式 endpoint 判断升级为显式配置，例如：

```text
supports_json_schema
supports_forced_tool_choice_in_thinking
requires_reasoning_content_roundtrip
supports_strict_tools
supports_streaming_reasoning
```

然后由工厂按 capability 组合请求，而不是为每个供应商堆特殊分支。但这属于下一步架构选择，不应在修复单一生产故障时顺手扩大范围。

## 第 14 章 · 我不会在面试中夸大的部分

为了让这份材料可信，我需要主动声明边界：

1. 本地真实 HTTP 链复现了跨循环连接失败，但错误类表现为 `APIConnectionError`；它证明生命周期问题，不声称逐帧复刻原线上堆栈；
2. 真实外部接口没有做高并发压测，避免不必要的费用和供应商压力；高并发通过本地可控故障注入完成；
3. 真实问答成功不等于法律答案和引用准确率已经通过专项评测；
4. 持续供应商宕机、限流或网络中断仍应返回错误，系统不可能保证外部依赖永远成功；
5. `asyncio.timeout` 能取消异步任务，但已经在线程池中执行的同步 Milvus/SQL 调用不能被强杀，仍需要底层超时退出；
6. 修复时没有重建、清空或修改知识库和数据库，也没有把 `.env` 中的密钥写入测试或报告；
7. `conda activate .conda` 失败是独立的环境激活问题，不是 DeepSeek HTTP 400 的根因。

> **心得十**：有边界的成功比没有边界的“彻底解决”更可信。面试不是把故事讲大，而是证明我知道证据能支持到哪里。

## 第 15 章 · 我以后会复用的排障清单

### 收集证据

- [ ] 保存完整时间线，而不是只截最后一行异常；
- [ ] 标记最后一个成功阶段；
- [ ] 区分 HTTP 状态错误、连接错误、池超时、读取超时和业务拒答；
- [ ] 记录是否只影响当前请求、当前会话还是整个进程；
- [ ] 记录最近唯一变化：代码、配置、模型、endpoint、并发量或依赖版本。

### 构造假设

- [ ] 内容相关还是跨请求状态相关？
- [ ] 确定性错误还是瞬态错误？
- [ ] 单线程成功、并发失败吗？
- [ ] 重启有效但 `clear` 无效吗？
- [ ] 客户端、loop、单例和检查点由谁创建、由谁关闭？

### 最小验证

- [ ] 先 Mock 外部资源，证明控制流和状态机；
- [ ] 再用本地 TCP/MockTransport 检查真实 SDK 请求体和连接池行为；
- [ ] 最后用少量真实请求验证供应商协议；
- [ ] 每次只改变一个变量；
- [ ] 故障之后至少验证多轮恢复，不只验证下一次。

### 验收不变量

- [ ] 一个请求只有一个终态；
- [ ] `final` 只代表真正完成；
- [ ] 技术错误不能伪装成业务拒答；
- [ ] 半截 token 不能保存为完整答案；
- [ ] 不同 thread_id 不相互污染；
- [ ] 取消/断开后没有后台任务和池槽位泄漏；
- [ ] 模型兼容适配不放宽 schema、tool choice 或发布边界；
- [ ] 日志和报告不泄漏密钥、原始工具输出或敏感提示词。

## 结语 · 这次真正修复的，是我的故障观

表面上，我修了两个问题：一个流式连接池问题，一个 DeepSeek 参数兼容问题。

但更深的收获是，我开始把 Agent 故障看成一组有边界的状态机问题：

- 输入属于哪条业务路径；
- 控制面在哪一步失败；
- 数据面是否真正执行；
- 哪些状态跨请求存活；
- 谁拥有资源，谁负责关闭；
- 错误终态是否忠实表达执行结果；
- 供应商兼容是否维持原安全不变量；
- 测试是否证明失败后的恢复。

最初，我只是敏锐地发现：“为什么失败一次之后，后面全坏了？”

后来，我又追问：“为什么只换了模型，就出现同样的现象？”

这两句话看似朴素，其实分别抓住了排障中两个最重要的变量：**跨请求状态**和**最近变更**。

以后面对复杂系统，我希望继续保持这种节奏：先观察异常如何传播，再定位最后成功边界；先弄清为什么，再决定怎么修；最后不只验证成功，还要验证它失败过以后能否重新站起来。

而在与 AI 协作时，我还要再加一句：**证据可以交给副驾驶搜集，方向盘必须始终握在我手里。**
