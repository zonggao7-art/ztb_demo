# ReAct 升级对话复盘：从“限制模型”到“把边界放对地方”

> 整理日期：2026-09-07  
> 用途：个人反思、项目复盘、面试案例准备。  
> 写法：按我的视角整理，不是逐字聊天记录。直接引用的原话单独标出，其余为对话归纳。代码实施与大量诊断、测试由 AI 助手协助完成，不把这些过程包装成全部由我手写完成。  
> 范围：记录本次对话从提出 ReAct 升级，到“主体名称放行、恢复旧引导”修复交付的过程。后者交付后，我的下一轮手工实测尚未在本段对话中反馈。

**阅读边界：这是一份阶段性复盘，不是当前版本说明书。** 整理时工作树已经出现 `unified` 等后续实现。本文中的“已完成”“待讨论”和测试数字，均指本段对话截止时的状态，不据此判断后续架构是否已经完成。

阅读建议：先看“一分钟回顾”；想回想具体问题，读第 2～9 节；准备面试，先读第 10～11 节；未解决的问题留在第 12 节。

## 先用一分钟看懂这次经历

我原本希望把招投标助手升级为 ReAct，让系统能够组织已有的 RAG 和 SQL 工具，处理组合问题。但升级后出现了一个反常现象：规则越来越多，系统却不一定更好用。

模型能填出合法的任务清单，却可能理解错问题；工具取回了资料，系统却只能向用户倾倒原文；用户给出了明确的公司名称，模型却认为“不像完整公司名”而拒绝查询；新架构沿用了旧分支的名字，却没有复用旧分支的回答行为。

我的判断因此逐渐变化：

- 不是不要约束，而是要区分**业务范围、执行安全和模型工作方式**。
- SQL 查询规则可以严格固定，但这不意味着模型可以在查库前判断一家公司是否真实。
- ReAct 升级应优先复用已有能力，而不是顺便重写所有业务行为。
- 能实现的功能不一定值得现在实现；练手项目也需要管理范围和优先级。
- 我的目标不是让 AI 尽快交付，而是让我理解问题、主导决策，并能解释取舍。

这段对话最重要的收获，不是某一次测试全部通过，而是我开始追问：**这条规则在保护什么？它应该放在哪一层？它有没有把本来能完成的任务也拦掉？**

## 1. 我最初想解决什么

### 1.1 已有基础，不应该被升级过程抹掉

项目已经把 RAG 和 SQL 查询包装为工具，并建立了工具库。我最初要求先写 Markdown 升级方案，不要立即修改代码，方案交给我审核，有问题一起讨论。

我的目标不是“从零实现一个 Agent”，而是让现有能力通过新的调度方式协同工作。例如：

- 查询一家公司的工商信息，再回答一个招投标法规问题。
- 查询同一家公司的工商、处罚和中标记录。
- 同时查询两家公司的中标历史。

这些问题需要的是对已有能力的组织，不一定需要新增数据库查询逻辑。

### 1.2 我关心的是工程学习，而不只是项目完成

我在对话里明确说过：

> “我们考验这个项目的价值只有一项指标：就是我能不能从这个项目当中学到点真东西。”

我不想变成只给 AI 按确认键的人。所以我要求助手多解释、多提问，让我先形成判断；即便速度慢一点，甚至踩一些坑，也是有价值的。

但后来我也发现：多提问不等于把所有细节都展开讨论。好的协作应该让我理解关键决策，而不是把我拖进无止境的边缘问题。

## 2. 第一个困惑：到底什么时候进入 ReAct

### 我当时的疑问

我连续追问了几个问题：

- 是否靠“并且”“同时”“结合法规”等关键词启动 ReAct？
- 谁判断问题简单还是复杂？能不能交给 LLM？
- 系统是不是需要显式启动 ReAct？
- 企业实践中应该怎样控制这个判断？

这些问题的共同点是：我不认可用几个连接词代替任务理解，也不希望为了证明“用了 ReAct”，就强迫每个问题多轮调用模型。

### 当时形成的决定

**默认进入新架构，但不强制每个问题都执行 ReAct 多轮循环。**

当时的 `hybrid` 是统一入口，内部再选择：

| 名称 | 在当时架构中的含义 |
|---|---|
| `hybrid` | 进入新架构，不代表已经进入 ReAct 循环 |
| `static` | 任务可按固定顺序执行，不需要模型逐步选择工具 |
| `react` | 模型参与后续工具选择与结果处理 |
| `clarify` | 缺少必要信息，需要询问用户 |
| `unsupported` | 当前能力不支持，不执行业务查询 |

后来我看到每轮日志都写着“执行链路：hybrid”，又产生了一次困惑。这不是所有问题都被分到同一个业务分支，而是日志把“入口”和“具体执行方式”放在不同位置显示了。

### 我从这里学到什么

**架构入口、执行策略、业务能力，是三个不同层次。** 日志如果没有把它们讲清楚，开发者自己也容易误判。

例如，“新架构启动成功”“某条 ReAct 路径执行成功”“整个系统可靠”，是三种不同的结论，不能混着讲。

我也追问过，为什么复用框架的 Agent 循环，而不是手工写一遍“思考—调用—观察”。这里同样需要分层：复用框架负责消息与工具循环，不等于照搬框架的业务边界。后来实际执行代码使用了 `langchain.agents.create_agent`；最初讨论过的函数名不是整套设计的本质。面试时应结合当时版本和真实调用入口说明，不能只背一个 API 名字。

## 3. 工具不止调用一次：两家公司为什么会失败

### 现象

我测试“同时查询两家公司的工商信息”时，日志出现：

```text
分流方案未通过校验 code=schema_invalid
model_calls=2
tool_attempts=0
tool_executions=0
failure_code=router_invalid
```

我最初看到的是“系统不能一个工具调用两次”。但这些日志进一步说明：**这次还没有走到工具执行，先在任务清单阶段失败了。**

`schema_invalid` 的通俗含义是：模型交出的结构化表单不符合程序要求。可能是字段、类型、枚举、必填项等问题，不是“SQL 查不到”。只有这个通用错误码，还不足以定位具体是哪一个字段出错。

当时的路由自我纠错也不是模型无限反思，而是程序把有限的错误说明反馈给模型，允许它再填一次；仍不合规则结束请求。这个机制能修正部分表单错误，却不能保证重新理解后的任务一定正确。

对话中随后检查了任务清单、重复参数、字段白名单和纠错反馈。`city` 字段也成为我追查的重要线索，但不能把所有 `schema_invalid` 都归因于 `city`，更不能在没有原始响应的情况下编造唯一根因。

### 我的反对意见

我不认可把“两家公司查工商”作为特例，从 ReAct 中单独抽出去解决。因为这很可能导致以后每发现一种组合，就新增一条特殊通道。

我的关注点是：**任务数量和工具种类数量并不是一回事。** 两个主体可以形成两个任务，但它们完全可以调用同一个工具。

### 当时的处理与验证

任务应分别绑定主体，例如 `t1` 对应公司 A，`t2` 对应公司 B；工具名称可以相同，不能因为工具只有一种就合并两家公司的参数。

后续测试已经验证同一工具可以服务多个任务。最终交付中的真实流式测试，“张三商店和李四小铺的中标历史”执行了两次 SQL 工具调用。

这里要保留一个事实：**两次调用得到验证，不代表这个问题必须走 ReAct。** 当时它可以走固定执行路径，关键是任务表达和工具执行不要漏掉第二个主体。

## 4. 我的观点如何变化：规训模型，不等于让模型无法工作

### 4.1 我最初为什么强调限制

我担心模型偶尔犯错的代价，因此明确说过：

> “我们设计架构的目的是为了规训模型，而不是让模型去自由发挥。”

这不是在说模型不能参与判断，而是在说：要先定义规则，不能只期待它自觉正确。

后来我逐渐看到了另一面：如果每一处不确定性都用“禁止”处理，系统虽然容易拒绝，却不一定能把事情做好。

### 4.2 哪些限制开始让我警觉

当时的执行范式是：模型先列出计划，程序审核，再让模型按批准的计划执行。

我问：**谁能保证第一次计划绝对正确？如果工具返回了意外结果，确实需要调整计划，怎么办？**

进一步查看发现，当时还存在这些限制：

- 批准后不能改变任务、主体和参数。
- 一个任务取得成功工具结果后，不能改参数继续查询。
- 一次模型回复不能同时申请多个工具。
- 跨任务依赖只开放少数形式。

这里有些约束保护用户范围，有些只是当时为了降低复杂度而选择的执行方式。它们不能都被当作不可讨论的安全原则。

### 4.3 这不是一次“放弃安全”的转向

我的 SQL 规则仍然可以很严格：只能查询固定表、固定字段，按固定条件检索，不允许模型生成任意 SQL。

但我同时可以反对：模型在执行前推测一家公司是否真实；或者工具已经生成了有依据的答案，外层却把它丢掉。

两种立场并不矛盾。区别在于：

**我保留对查询范围和执行权限的控制，但开始反对没有必要的业务误拦截与重复加工。**

### 4.4 截至本段对话，哪些还没有解决

“如何允许受控的中途调整计划”仍是重要议题。本段对话最后一轮代码修改只处理了名称放行与引导复用，没有顺带修改 ReAct 循环。

这条状态只对应本段对话，不覆盖后来出现的 `unified` 等其他工作。面试时不能把“识别出了过度限制”直接说成“已经完成了动态重规划”。

## 5. RAG 取回了资料，为什么用户还是觉得没得到回答

### 5.1 我发现的体验问题

终端一次输出多个很长的 chunk，带着章节、条款和大段原文。用户很难找到重点，有种“问了跟没问一样”的感觉。

我提出：模型为什么不能根据问题提炼已有片段？直接把原始文档扔给用户，并不是好的回答。

### 5.2 我尝试过哪些思路

讨论中我先后提出：

- 给用户置信度和资料完整性评分。
- 即使结果只供参考，也尽量给用户一些有用内容。
- 限制回答长度，考虑约 200 字。
- 不要为了摘要再增加一套复杂流程，能否对已有答案进一步提炼？

这里要诚实区分：这些不是全部都实施了。尤其不能把检索分数或模型自报分数直接称为“答案正确概率”。本段对话没有建立经过校准的置信度评分系统。

### 5.3 真正简化问题的决定：复用完整 RAG 问答工具

我后来追问：RAG 怎么形成答案，不还是模型在生成吗？为什么新架构会丢掉旧工具已经生成的答案？

答案是：完整 RAG 工具内部本来就包含检索和模型作答。它不是只有向量搜索，而是一项已经封装好的问答能力。

因此我要求先恢复复用 `knowledge_qa`：让它内部检索并生成答案，外层接收答案与引用，不再强制改成原文摘录。

当时的改动包括：

- 恢复完整问答工具作为法规任务的入口。
- 保留来源数据，但终端默认不展开所有 chunk 全文。
- 将约 200 字设为软目标，不能为了凑长度删掉关键条件。
- 保留引用与结果结构检查，但不把它们称为法律正确性验证。

### 5.4 一个随后出现的工程问题：输入额度不够

恢复完整 RAG 后，又发现正常问题会被输入预算拦住。外层调度与 RAG 共用 16,000 字节限制，而 RAG 正常带入的资料可能已经超过 27,000 字节。

助手根据我提供的切片文件和实际请求测量，区分了两种需求：外层调度只需读较少内容，RAG 作答需要读完整资料。经批准，RAG 输入额度单独设为 48,000 字节，外层保持 16,000 字节。

这不是扩大回答长度，也不是增加摘要模型。**想让输出短，不意味着可以让模型少读到必要证据。**

### 5.5 关于测评，我保留了什么疑问

我担心回答里的提示语和无关信息影响测评，曾提出去掉提醒类语句。但我也说明自己并不清楚旧评测的具体做法，不是负责那次测评的人。

因此，这里不能下结论说“去掉提醒就能提高真实准确率”。文本匹配分数、用户体验和业务正确性不是同一个指标。本次选择先不展开重建评测体系，避免压过更紧急的问题。

## 6. 多轮历史为什么让我选择先不要

### 6.1 现象比普通答错更严重

连续查询、闲聊之后，用户问“天气怎么样”，系统竟再次执行上一家公司的工商、处罚和中标查询。

重要证据不是“回答看起来重复”，而是日志里出现了新的请求 ID，以及三次工具执行。也就是说：**它不是简单显示了缓存答案，而是在新请求里重新做了旧任务。**

### 6.2 当时定位到了什么

路由曾读取最近几轮历史，并允许任务参数引用历史用户输入。程序能检查“公司名是否来自一条历史消息”，却不能因此证明“当前用户仍然想查它”。

“参数确实有出处”和“本轮有查询意图”是两回事。

当时没有完整保留事故中的原始路由输出，因此不能声称已经还原了模型的全部判断过程。但源码与构造验证说明，这种历史引用机制允许旧主体进入新任务。

### 6.3 我的判断

我认为当前历史功能的收益主要是让用户少打几个字，而风险已经两次造成明显问题。对这个阶段的项目来说，收益与风险不成比例。

我也表达过：如果一定要理解历史，语义关系更适合交给模型，而不是不断增加规则。但这不意味着当前就要做它。

我最终选择：**先取消跨轮任务承接，每轮独立处理。**

聊天记录仍然保留，但不作为本轮路由与参数来源。“处罚呢”“继续”缺少对象或目的时，要求补充本轮问题。同一次问题里的多个主体、多个任务和任务依赖则继续保留。

### 6.4 我从这里学到什么

减少功能不一定是退步。尤其当某项功能不断制造故障、又不是当前核心目标时，明确暂不支持，比持续增加补丁更容易控制。

这个决定是阶段性的范围取舍，不是证明多轮对话在所有项目里都没有价值。

## 7. “张三商店”案例：到底该拦目的，还是拦主体

### 7.1 我最初看到的问题

用户问“查一下张三公司的中标历史”，系统却要求提供完整企业名称。

我认为这不合理：用户已经给了查询名称。数据库没有记录，应该说明未收录，而不是反过来认定用户输入不完整。

### 7.2 日志修正了一个重要推断

这次日志是 `clarify`，工具尝试和执行次数都为 0。所以实际情况不是“数据库查不到后要求补全”，而是**模型在查询之前就要求补全，数据库根本没有参与**。

进一步运行名称校验发现：“张三公司”通过程序的格式检查；“张三商店”和“某某小学”则会被后缀清单拒绝。

因此有两个不同问题：

- 模型受“完整工商全称”提示影响，可能提前要求补充。
- 执行前的程序又用名称后缀规则拦掉某些明确主体。

只改其中一个，另一个仍可能继续误拦截。

此前我还追查过 `company_profile` 为什么允许 `city`、省份、行业等筛选。我的原约定是工商查询只按 `company_name` 启动。这个例子提醒我：**一个字段可以出现在查询结果里，不代表它就可以成为查询条件。** 这也是后来不为注册资本等字段扩展筛选能力的基础。

### 7.3 我明确给出的业务原则

> “对于查询目的不明确可以拦截，但是对于查询主体不可拦截。”

这里的意思是：不审核主体是否真实、是否像正规公司，不是撤掉空值、长度等基本技术保护。

具体行为应为：

| 问题 | 本段对话确定的行为 |
|---|---|
| 查张三商店的中标历史 | 按名称查询，不判断商店是否真实存在 |
| 查某某小学的采购历史 | 按采购人名称查询，不要求它是公司 |
| 查一下张三商店 | 缺少查询目的，询问要查什么 |
| 张三商店在什么地方 | 按本项目当前范围说明不支持，给固定引导 |

SQL 工具仍然保留参数化、只读、固定字段、条件限制和超时。查询正常但无记录、记录中字段为空、数据库查询失败，必须分别说明。

### 7.4 对我自己判断的一次修正

我曾认为旧架构已经能精准区分“查地址”和“查中标”。助手检查后发现，旧规则实际上依赖主体格式和“查、信息、历史”等泛化关键词，并没有一个可靠的“地址查询必须拒绝”判断。

在固定意图解析结果的测试中，“张三公司查地址”可以到达 SQL 分发，而“张三商店查中标”反而被主体格式拦下。旧输出模板甚至含有地址字段。

这不代表旧系统每次都会误分流，却足以说明：**我之前对旧系统的信心，并不能替代源码和反例验证。**

“地址查询不支持”是我在本次讨论中明确的边界，不能说成已被证明一直存在于旧系统。

## 8. 为什么我坚持复用，而不是继续新增能力

### 8.1 SQL 写得死，是一种经历过失败后的取舍

我补充过：早期尝试 Text2SQL 时，模型大量生成不合法 SQL。我在对话中的回忆是，跑过 1,500 条测试，召回率只有约 3%。

**数字说明：这是我的历史陈述，本段对话没有复核原始评测口径、样本和计算方式。面试前如果不能找回报告，应只讲“早期效果不理想”，不要把 3% 当作现场核实的数据。**

这段经历解释了我为什么坚持固定查询规则：我不愿意仅因为新增一种用户问法，就重新允许模型写 SQL。

### 8.2 单独问注册资本，技术上并不需要新 SQL

助手提出是否支持单独询问注册资本、法定代表人、经营范围。我反问：已有工商工具已经返回这些字段，为什么还要新增 SQL 或工具？

源码验证了我的这一点：工具已经能取到相关字段。若要支持针对性回答，问题主要在意图归类和结果展示，而不是缺少数据库查询能力。

但这还不是最终决定。

### 8.3 我的最终决定：能做，也先不做

随后我制止了继续扩展问法的讨论，因为它优先级太低。我们更重要的问题是 ReAct 过度限制，而不是把每个字段都设计成单独服务。

最终，SQL 查询保持既定六类：

1. 企业工商信息。
2. 企业行业／经营范围。
3. 企业处罚／不良记录。
4. 企业中标历史。
5. 指定项目编号的中标情况。
6. 采购人的采购／发包历史。

范围外的问题统一固定引导，即使某个返回字段理论上可以回答，也不因此扩展支持范围。经营范围已属于第二类，不是这次新增的单字段能力；注册资本、法定代表人不另外扩展单独问法。

这六类只约束 SQL 业务查询，不是把法规 RAG 一并关闭。另外，**六类问题不等于六个独立 SQL 工具**，若干问题类别共用工具，不能把工具注册数与业务问题类别数混在一起。

### 8.4 新架构为什么让我产生“不如旧架构”的感受

至少有两个明确案例：

- 旧版欢迎语仍在，新架构却另外返回一段简化文案。
- 完整 RAG 工具本来能作答，新架构却一度丢掉生成答案，转为原文摘录。

SQL 也存在名称不变、内部路径变化的情况：hybrid 使用独立的精确查询适配。因此仅仅看到同一个工具名，不能认定旧行为全部被复用。

我希望建立的原则是：**新架构负责组织和调用，成熟能力默认保留；确实需要改变业务行为时，单独说明原因和影响。**

这不是盲目维护旧代码。旧后缀规则同样应该被质疑。复用的对象应是已经验证且符合当前边界的能力，而不是“旧”这个标签本身。

## 9. 本段对话最后实际修了什么

我最后没有要求一次性解决所有架构问题，而是明确授权先修两项：名称放行、旧引导复用。代码改完后助手先测，再交给我实测。

### 实际变更

- 修改 hybrid 路由说明，不让模型审核主体真实性、完整工商全称或名称后缀。
- 去掉 hybrid 执行前对公司和采购人的后缀检查。
- 明确六类 SQL 目的，范围外引导，不用通用搜索绕过边界。
- SQL 底层保留安全保护，并检查空值和参数长度。
- 已查空、字段为空、查询失败分别展示。
- 原欢迎语提取为共享文本，新旧入口复用同一份，文字保持原样。
- 天气等域外请求仍可记录为 `unsupported`，但用户看到的是已有友好引导，而不是生硬的内部限制说明。

### 当时验证到了什么

| 证据 | 当时结果 | 不能据此推出什么 |
|---|---|---|
| 新增专项自动化测试 | 24 项通过 | 不能证明所有自然语言问法都正确 |
| 整体回归测试 | 583 项通过，1 项跳过 | 不是 583 个全部真实联网的业务案例，也不是系统准确率 |
| 真实模型分流检查 | 15 个用例符合约定 | 只检查分流，不等于已执行 SQL/RAG |
| 同会话真实流式检查 | 连续 9 轮通过，合计 5 次 SQL 查询 | 不等于完成生产验收、压力测试或长期稳定性验证 |

真实流式用例里，“张三公司”“张三商店”分别实际查库后返回未收录；两家商店分别调用同一个 SQL 工具；已收录企业仍可查出工商记录；问候、天气和能力询问复用旧引导。

这些数字来自本段对话中的工具结果及实施记录。**本次整理 Markdown 没有重新运行测试，也没有把历史结果更新成后续版本的验收结论。**

## 10. 这段经历里，我自己的思考方式有什么变化

### 从抽象原则回到具体反例

“企业级”“受控”“防幻觉”听起来都对，但很难直接评价实现。我后来用具体问题逼近边界：

- 为什么张三商店不可以查？
- 为什么天气问题会重新执行旧企业任务？
- 为什么问候到了 `general_chat`，却没有旧欢迎语？
- 为什么工具已经有答案，外层还要丢掉？

这些反例比争论架构名称更容易暴露问题。

### 从只问“能不能做”到同时问“现在要不要做”

我几次要求停止低优先级讨论：检索相关性兜底、置信度评分、单字段问答扩展。不是因为它们永远不重要，而是它们会挤占解决已发生故障和过度约束的时间。

同样，取消历史承接不是技术上放弃，而是主动缩小当前承诺。

### 从信任方案，到要求看到执行证据

我开始要求查看源码、日志和测试，而不满足于“框架支持”“工具已经接入”。

同时我也需要约束自己：没有发生真实 SQL 查询，就不能把拒绝归因于数据库；只有格式校验通过，就不能认为语义判断正确；旧系统表现曾经不错，也不代表每条旧规则都合理。

### 从让 AI 代劳，到明确谁负责什么

我负责提出真实问题、确定业务边界、质疑方案和安排优先级。助手负责查代码、构造验证、实施已批准改动、执行测试。

对我来说，好的协作不是“助手把所有问题都想完了”，而是：**结束之后，我能比开始之前更清楚地解释为什么这样做。**

## 11. 可以怎样整理成面试案例

以下是表达骨架，不是要求背诵的标准答案。每个案例只讲到本段对话真正做过和验证过的范围。

### 案例一：为什么没有继续使用 Text2SQL

**主线：** 早期尝试效果不理想 → 收缩到明确业务类别 → 固定查询规则与参数化 SQL → 模型只负责理解和提取参数。

可以这样讲：

> 这个项目的数据库查询范围比较明确。我早期尝试过让模型生成 SQL，但实际效果不理想，所以选择固定查询路径，让模型提供参数，不让它生成任意 SQL。后续升级 ReAct 时，我保留了这条边界：改变工具编排方式，不重新开放 SQL 生成。

准备好回答：这种方案牺牲了什么？遇到范围外问题怎么办？为什么不为每种问法增加一个工具？

不要说：固定 SQL 适用于所有场景；模型参与不了数据库查询；已经彻底杜绝所有错误。没有原报告时，不把 3% 作为确定的对外指标。

### 案例二：如何发现并修复 Agent 的误拒绝

**主线：** 用户给了主体却被要求补全 → 看日志发现工具调用为零 → 区分模型拒绝和格式守卫 → 去掉真实性／后缀判断，保留工具防御 → 真实查库验证。

可以这样讲：

> 我发现系统会拒绝“张三商店的中标历史”。这个请求的业务目的明明受支持，因此我要求把主体存在性判断交给数据库，而不是由模型或名称后缀规则提前否决。随后核对了两层限制，调整后既验证了商店、学校等名称放行，也验证了 SQL 参数化、空值、异常与空结果处理没有被取消。

准备好回答：参数化 SQL 解决什么、不解决什么？“没有结果”和“主体不存在”为什么不同？模型误分流是否仍可能发生？

### 案例三：为什么暂时取消多轮任务承接

**主线：** 闲聊触发旧任务 → 发现本轮确有新工具执行 → 历史参数出处不等于当前意图 → 比较功能收益与风险 → 每轮独立处理，保留记录。

可以这样讲：

> 项目中出现过天气问题触发旧企业查询。我没有马上增加复杂记忆规则，而是先评估这个阶段是否需要历史承接。由于核心目标是明确的业务查询，我选择保留聊天记录，但不把历史作为新任务输入；同一次问题中的多任务仍然保留。这样主动降低了功能承诺，也让任务边界更容易验证。

准备好回答：记录保存和模型上下文有什么区别？什么需求出现时才值得重新考虑多轮？如何证明不是缓存显示问题？

### 案例四：为什么架构升级要先复用完整能力

**主线：** RAG 输出原文堆砌 → 发现原工具已有作答能力 → 恢复完整问答复用 → 保留引用但压缩默认展示 → 用实际输入大小修复预算误拦截。

可以这样讲：

> 新架构一度把 RAG 当成纯检索工具，导致终端充满原文。我提出复用已有完整问答工具，因为它内部本来就完成了检索和生成。外层只组织结果和处理引用，不再重复生成。之后通过真实请求大小发现，RAG 输入需要独立预算，不能套用外层调度额度。

准备好回答：检索分数为什么不等于答案正确概率？200 字限制是什么性质？RAG 内部模型和外层 Agent 各负责什么？

### 一个可以作为面试开场的短版本

> 我在招投标助手上做 ReAct 升级时，最深的体会不是 Agent 越自由越好，也不是规则越多越安全。实际问题包括历史任务串入新请求、合法查询被名称规则误拒绝，以及新架构没有复用旧 RAG 和欢迎引导。我主要负责定义边界、提出反例和审查取舍，代码与测试通过 AI 协作完成。最终我们先修复了这些可验证的问题，保留固定 SQL 和工具安全保护，而没有趁机扩大查询范围。更开放的 ReAct 执行策略，在这段阶段性工作中仍是后续议题。

## 12. 留给以后自己的问题

不要求现在一起实现，留作后续反思：

- 我能不能逐条解释，哪些限制保护用户范围，哪些只是实现方便？
- 如果首次计划错了，系统是否只能忠实地执行错计划？我准备用什么真实案例讨论这个问题？
- 我是否又在用“工具注册成功”代替“真实路径跑通”的证据？
- 我有没有因为旧实现曾经好用，就忽略其中的错误假设？
- 一项新功能是否真的服务当前目标，还是只是证明“我也能做”？
- 当我说“已解决”时，指代码已改、专项已测、真实联调通过，还是用户验收完成？

**我希望记住的不是“最后选了哪种架构”，而是：我如何发现不合理的行为，如何提出自己的判断，如何用证据修正判断，又如何在必要时主动停止扩展。**
