## 1、为什么查询项目的中标情况采用项目编号查询的方式？
项目名称搜索会引入重名和模糊匹配。基线最好先定义为“按项目编号查询”；是否支持项目名称，需要单独决定。前期尝试过支持项目名称查询，但是发现实现起来比较复杂，首先用户不一定能输入完整的项目名称，经常是输入一个模糊的名称，导致无法精确查询，只能以向量检索的方式进行模糊查询，而该条业务线是不允许返回模糊结果的，我们设计的初衷是，如果没有百分之百的把握，那就宁可什么都不给用户，也不能给出误导性信息，所以采用了项目编号查询的方式。当这条线的定位是“拿到公告后的精确查证”，不是模糊发现；发现类需求由 RAG 线承接。两条线各管一段，不是同一条线既要又要。

一轮测评解决了模型选型的问题，确定最优模型为DeepSeek V4 Flash。一轮测评的主要目的是测评下游变更对系统的影响。

## 4、二轮测评解决什么问题？
二轮测评在一轮测评的结论基础上，固定模型，对数据进行治理，对检索逻辑进行调优，我们主要的目的是测试上游变更对系统的影响。


## 5、想法
尽管二轮测评中，我们主要测的是上游改造对于系统的影响，指标构建也聚焦于检索层的表现，但是二轮测评也应该保留一到两项与模型表现相关的指标，虽然我们在一轮测评中已经测了不同模型的表现，但是二轮测评毕竟进行了数据治理和检索调优，我们需要观察这两项工作对于模型的表现是否有增益效果。
二轮回答指标的职责：检索指标负责说明上游改造做得怎样，少量回答指标负责验证这些改造最终有没有帮助用户得到更好的答案。

## 6、一二轮测评的主要变量是什么？
一轮测评中，不变的是上下文，变得是模型。
二轮测评中，不变的是模型，变得是上下文。
二轮测评时，我们要看，模型的输入变好了，回答质量有没有提升。

## 7、担忧
那就是一轮测评时，我们有没有构建检索层指标？如果没有构建的话，那就体现不出数据治理和嵌入模型更换对于检索层的增益效果（这是二轮第一阶段测评的变量），我们只能间接通过模型的表现来得知，不过有点瑕疵倒也能接受。

答：一轮测评中虽然没有明确反映检索层指标，但是可以后续补算（虽然不一定精准，但是可以反映出变化）。

## 8、二轮测评指标的构建思路
二轮6项指标，2项反映上游改造对检索层表现的影响（上下文召回率，检索内容精度，即有用的内容有没有排在前面），2项反映上游改造对模型表现的影响（答案正确性，即是否符合标准答案的要求，回答忠实度，即回答是否有给定资料支持），2项反映改造的成本（查询耗时，查询成本。）

## 9、测评指标中的三个召回率指标如何理解？
context_recall: 上下文语义召回率，基于ragas框架的裁判模型进行语义判断是否召回。把标准答案拆成若干“信息点/claims"，逐条判断检索结果是否覆盖。
精确 chunk Micro Recall:直接比较标准答案标注的 ground_truth_chunk_ids 和最终 Top-5 检索结果的 chunk_uid。直接用chunk_uid来判断是否召回。
全部标准 chunk 命中率：同样依据 chunk_uid，而且要求一道题的所有标准 chunk 全部出现。

在判断系统检索召回率时，后两个指标应作为主要判断依据，但不能作为唯一依据。因为有些题目即便没有召回出精确的chunk_uid，但是上下文语义召回率可能很高，这说明系统召回了语义相似，内容高度相关的片段。

## 10、为什么取消让历史消息参与参与新一轮任务规划和参数承继？

还原事故链：
1、用户先查询某企业的工商、处罚和中标信息。
2、随后输入“干得好”“谢谢”“天气怎么样”这样的开放问题。
3、但是系统并没有按照预期去进行引导，而是重新执行了旧企业的三个查询工具。
4、所以它不是简单复读缓存答案，而是把已经结束的历史任务重新当成了当前任务。

根因：
1、系统当时能看到最近三轮历史；
2、历史中的企业名称可以作为任务参数来源；
3、程序只验证了“这个参数确实来自某条用户消息”；
4、却无法验证“用户这一轮仍然想执行这项任务”。

参数有出处，不等于本轮需要执行这个任务。
因此，“天气怎么样”虽然与企业查询毫无关系，旧公司名称和旧任务仍可能组成一个形式合法的执行计划，并通过程序校验。我们难以证明模型内部究竟是怎样做出这一决策，但模型做出的任务规划又确实是合法且能通过程序校验的。

我们认为，历史语义信息很难通过规则去约束哪些可以参考，哪些不能参考，这是一个无限熵增的命题，即便我们让模型去判断历史信息能否用于当前这一轮的对话，仍然频繁出错。所以我决定，系统的每一轮任务都独立处理，不从历史信息中提取相关参数。最重要的是，我们当时认为这项改进的优先级不足，而且收益和风险均不可控，我们的首要任务是让系统先基本跑通，所以就取消跨轮任务承接。

## 11、第三轮测评（整个Agent系统的测评）的题集是怎么构建出来的？
共有六类题目：
1、测RAG。2、测sql单查询。3、多步执行任务，多主体任务。目的是：检查系统是否存在漏调用，重复调用，主体错配和过早结束的问题。
4、结果依赖任务。目的是：对于sql查询，系统能否根据已经查询的主体，从而正确进行扩展查询。如：查询一个企业的工商信息后，再查询该企业的处罚信息。
5、SQL+RAG任务。目的是：检测系统是否拥有跨工具执行任务，从而将证据进行合并的能力。
6、超纲任务。目的是：检测系统的零外部I/O，正确停止和发布边界。

## 12、零外部I/O的定义
这个词可以拆成三层来理解。

I/O 是什么
I/O = Input/Output，程序与“外界”之间的数据进出。程序做的所有事可以分成两类：

纯计算：只在内存里算——解析用户问题、组装参数、拼提示词、判断意图。这些不触碰任何外部系统。
外部 I/O：跨出进程边界的操作——发网络请求、查数据库、读写文件、调用付费 API。
“外部”在这个项目里具体指什么
Agent 进程之外的所有系统：MySQL、Milvus、embedding/RAG 的模型 API、付费的 Ragas 评分接口。关键对应关系是：每一次工具调用 = 至少一次外部 I/O。SQL 工具会发一条 MySQL 网络查询，RAG 工具会调 Milvus 和模型接口。所以“零外部 I/O”落到实处就是：一次工具都没调。

为什么用“零外部 I/O”而不是“不调工具”
因为 I/O 是实质，工具只是封装。约束“零外部 I/O”是在直接度量系统对真实世界做了什么，而不是它表面上走了哪段代码。这带来三个好处：

可精确计数：外部调用能被拦截器逐次记录，测评里就写成 external_io.max_calls=0（README.md:59）。判定标准是硬的——要么 0 次，要么不是 0 次，没有“调得对不对”这种模糊地带。
零成本零副作用：负向题不该消耗数据库负载或付费 token，任何一次调用本身就是误动作的直接证据。
区分两种失败：正向题考察“该调的调对了没”，负向题考察“不该调的是否忍住了”。负向题的正确行为就是“对世界什么都没做”，所以用 I/O 归零来定义。
顺带一提，这个说法在软件测试里有个对应的成熟概念叫 hermetic test（封闭测试）——测试全程不碰真实数据库和模型，全部用 mock。CLAUDE.md 里说 pytest 测试 "no live DB/LLM needed"，就是测试意义上的零外部 I/O；而测评题集里它是行为约束——负向题要求系统本身零外部 I/O

## 13、第三轮测评的指标构建思路
被测对象是完整受控链路，而不是某个单一工具调用。
'''
    用于问题
        ->统一主Agent选择一个业务工具或FinishAction
        ->程序校验工具、参数来源、结果范围和预算
        ->业务工具返回经过校验的结果
        ->统一主Agent选择下一个工具或FinishAction
        ->登记真实结果
        ->审核证据并发布答案

### 13.1 分层指标体系
分层测评，不合总分：Agent行为层+内容质量层（RAG/SQL分开）+效率+可靠性，红线指标零容忍。
一、红线：1、发布红线违规数=0：越权调用工具，编造事实，把“查询失败”说成“无记录”，绕过审核门禁的情况，一次都不允许。
2、证据关联正确率=100%：答案中每个可核查事实，必须能回溯到真实的工具证据（法规类回查chunk_uid，SQL类回查调用记录和字段）
二、Agent行为层：
链路：选对下一个动作（工具或FinishAction>98%）->调全工具（是否调用所有必要的工具>98%）->无多余(是否调用了不必要的工具<2%>)->参数准（工具与参数精确率>99%）->停对：（是否正确停止任务>98%）->真完成：（是否完成任务交付>95%）

三、内容质量层
RAG：检索质量+回答质量+chunk_recall
SQL:纯事实性核对，输出的事实是否与查询结果一致，字段是否输出完整，是否把无记录、字段为空、超时和查询失败正确区分。

SQL 工具内部没有开放式推理，因此不需要为其强行计算 Context Recall、Context Precision 或 Faithfulness。SQL 的主要判断由程序根据冻结的测试数据或同一时间点的数据库真值完成。
四、效率指标：
P50/P95耗时+token成本
五、可靠性指标：
故障后下一轮恢复能力


## 14、第三轮测评暴露了什么问题？

Agent工具执行能力强，但是控制能力不足。一旦选对工具，查询结果基本可信。真正出问题的是：该不该查，查什么，什么时候结束。

一：缺少可靠的“先停下来判断”能力。60个负向题目，只有42个正确处理了，剩下居然启动了查询，调用了工具。典型表现是：当query的主体不明确，或查询意图不明，请求模糊时，系统仍可能会启动查询。而没有在入口处封禁这类不合法的请求。

二：FinishAction只是模型判断，并没有成为程序事实。结束状态的正确率在92%左右，而预期是98%，混淆了四种结束状态。

怎么解决？
一、查询维度不明确时，请求模糊时，直接抛出clarify的系统状态，在获得明确范围前不调用工具。
二、由程序根据已执行的动作，来纠正模型状态。

## 15、系统的四种状态代表什么意思？
这四种状态是本轮请求的终态，不是程序异常。系统一旦抛出状态，本轮ReAct就结束，不会再有任何动作。

clarify     能力受支持，但是执行起来存在歧义（参数，范围，主体不明确）->    不执行存在歧义的工具->  要求用于澄清请求
unsupport   能力不支持->    不执行动作，并向用户说明原因->  要求用户改写请求
partial     至少一个独立子任务已完成，但还有部分因为参数缺失而失败->  报告已完成任务和未完成任务->    用户需要对未完成任务进一步澄清  
complete    所有任务都已完成->  返回最终结果和证据-> 会话结束
