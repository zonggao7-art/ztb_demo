## 1. 评估背景与范围界定

### 1.1 当前规则框架概览

现有 §7.4 框架是一个**配置驱动的确定性系统**，其链路如下：

```
用户查询
  ↓
[① LLM 意图解析] → SearchIntent {query_type, need_contact, need_penalty_check, …}
  ↓
[② 规则映射]      → OutputTemplate {required, conditional, optional, display_order}
  ↓
[③ 运行时引擎]    → _apply_output_template() → 最终输出字段列表
```

关键特征：
- **49 个字段**在 `_FIELD_REGISTRY` 集中注册
- **11 个 query_type** 各有独立的 `OutputTemplate`
- **条件字段**通过 `intent.need_contact` / `intent.need_penalty_check` 布尔开关驱动
- `_apply_output_template()` 是纯函数：给定 template + intent → 确定性的字段集合

### 1.2 ML 方案要解决的问题

在规则框架中，"选择哪些字段"这个决策由两步完成：
1. LLM 将自然语言解析为 `SearchIntent`（含 query_type + 布尔条件标志）
2. 规则引擎将 `SearchIntent` 映射为字段集合

ML 方案试图替代或增强步骤 2，即：**给定用户原始查询文本，直接预测应输出的字段子集**。

### 1.3 评估范围

本报告评估四种 ML 技术路线在以下五个维度的表现，最终给出明确的"引入 / 不引入"建议。

## 2. 技术实现可行性

### 2.1 候选方案总览

| 方案 | 输入 | 输出 | 复杂度 | 推理延迟 |
|------|------|------|--------|---------|
| **A. 多标签分类器** (TextCNN / FastText) | 查询文本 | 49 维 binary 向量 | 低 | <5ms |
| **B. 微调 BERT-base** (bert-base-chinese) | 查询文本 | 49 维 binary 向量 | 中 | ~50ms (CPU) |
| **C. 序列标注模型** (BERT + CRF) | 查询文本 | 字段标签序列 | 高 | ~80ms (CPU) |
| **D. 生成式 LLM** (Qwen2.5-0.5B 微调) | 查询文本 | JSON 字段列表 | 高 | ~500ms (CPU) |

### 2.2 方案 A：多标签分类器（TextCNN / FastText）

**原理**：将查询文本向量化（TF-IDF 或静态词向量），接入全连接层 + sigmoid 输出 49 个标签的概率。

```
查询文本 → Embedding → FC Layers → sigmoid → [P(company_name), P(credit_code), …]
                                                    ↓ threshold=0.5
                                              {selected fields}
```

**可行性评估**：

| 维度 | 评价 | 说明 |
|------|------|------|
| 表达能力 | ❌ 弱 | 无法理解"查一下这家公司有没有不良记录"中 "不良记录" → penalty_check 的语义跳跃 |
| 特征依赖 | ❌ 高 | 需要手工特征工程（TF-IDF n-gram），对招投标领域术语覆盖不足 |
| 训练数据需求 | ⚠️ 中 | 每 query_type 约需 200~500 条标注样本 |
| 推理速度 | ✅ 极快 | <5ms，可忽略 |
| 冷启动 | ❌ 严重 | 新字段/新 query_type 需重新收集数据并重训 |

**结论**：表达能力不足以处理招投标领域的语义复杂性，**不推荐**。

### 2.3 方案 B：微调 BERT-base-chinese（多标签分类）

**原理**：在 bert-base-chinese 预训练权重上，添加多标签分类头（`[CLS] → Linear(768→49) → sigmoid`），用标注数据微调。

```
查询文本 → BERT Encoder → [CLS] pooling → Linear → sigmoid → 49 个 P(field|query)
```

**可行性评估**：

| 维度 | 评价 | 说明 |
|------|------|------|
| 表达能力 | ✅ 强 | BERT 预训练已包含中文语义理解，微调后能捕捉领域术语 |
| 训练数据需求 | ❌ 高 | 参数规模 ~110M，需要 ≥2000 条高质量标注样本才能稳定收敛 |
| 推理速度 | ⚠️ 可接受 | CPU 推理 ~50ms（ONNX 量化后可降至 ~15ms） |
| 部署方式 | ⚠️ 中 | 本地 ONNX Runtime 推理，无外部 API 依赖 |
| 与 LangGraph 集成 | ⚠️ 中 | 需在 price_inquiry 节点内增加推理步骤，同步阻塞 ~50ms |
| 模型更新 | ❌ 高 | 新增字段 → 修改输出层维度 → 重新标注 → 全量重训 |

**结论**：技术上可行，但边际收益不足以覆盖维护成本，详见 §7。

### 2.4 方案 C：序列标注模型（BERT + CRF）

**原理**：将字段选择建模为序列生成任务，逐字段预测是否输出。

```
查询文本 → BERT Encoder → CRF Layer → [company_name:1, credit_code:0, ..., winning_amount:1]
```

**可行性评估**：

| 维度 | 评价 | 说明 |
|------|------|------|
| 适用性 | ❌ 不匹配 | 字段之间无强顺序依赖，序列标注引入了不必要的结构假设 |
| 训练复杂度 | ❌ 高 | CRF 层增加了训练难度和收敛时间 |
| 推理速度 | ❌ 慢 | ~80ms CPU，比方案 B 慢 60% |

**结论**：问题本质不是序列标注问题，**不推荐**。

### 2.5 方案 D：生成式小模型微调（如 Qwen2.5-0.5B LoRA）

**原理**：用 LoRA 微调一个小型 LLM，直接生成 JSON 格式的字段列表。

```
查询文本 → Qwen2.5-0.5B (LoRA) → '{"fields": ["company_name", "industry", "penalty_date"]}'
```

**可行性评估**：

| 维度 | 评价 | 说明 |
|------|------|------|
| 表达能力 | ✅ 最强 | 可直接输出任意字段组合，天然支持新字段 |
| 推理速度 | ❌ 慢 | ~500ms（CPU），是方案 B 的 10 倍 |
| 部署复杂度 | ❌ 高 | 需要 GPU 或量化优化，内存占用 ≥2GB |
| 输出稳定性 | ❌ 差 | 可能生成不在 `_FIELD_REGISTRY` 中的字段名（幻觉） |
| 标注需求 | ❌ 极高 | 需要 ≥5000 条 {"query": "...", "fields": [...]} 对 |

**结论**：生成式方案在字段选择这个确定性问题上是"用牛刀杀鸡"，不仅成本高，还引入了幻觉风险。**不推荐**。

### 2.6 方案对比总结

| 评估维度 | A. TextCNN | B. BERT 多标签 | C. BERT+CRF | D. Qwen LoRA | 当前规则 |
|---------|:----------:|:-------------:|:-----------:|:------------:|:--------:|
| 准确率上限 | ~70% | ~88% | ~85% | ~90% | **100%**（确定性） |
| 推理延迟 | <5ms | ~50ms | ~80ms | ~500ms | <1ms |
| 标注数据需求 | 1000 条 | 2000 条 | 2000 条 | 5000 条 | **0 条** |
| 新字段扩展成本 | 重训 | 重训 | 重训 | 重训+数据 | **1 行配置** |
| 可解释性 | ❌ 黑盒 | ❌ 黑盒 | ❌ 黑盒 | ❌ 黑盒 | ✅ 完全透明 |
| 维护人天/年 | 15~20 | 20~30 | 25~35 | 30~40 | **2~5** |

## 3. 项目改造难度与侵入性

### 3.1 架构侵入分析

下图展示了 ML 方案对现有架构的侵入点（以方案 B 为例）：

```
                    ┌── 侵入点 ①：新增推理模块 ──┐
                    │  agent/nodes/field_predictor.py  │
                    │  (BERT 模型加载 + 推理)           │
                    └──────────────────────────────────┘
                               ↓
用户查询 → LLM 意图解析 → SearchIntent ─┬→ 规则引擎 (保留)
                                       │
                                       └→ BERT 预测器 ─┬→ 字段预测
                                                        │
                          ┌── 侵入点 ② ──┐              │
                          │  字段融合逻辑  │←────────────┘
                          │  规则 vs ML   │
                          └──────────────┘
                               ↓
                    ┌── 侵入点 ③ ──┐
                    │ _apply_output │ 需支持双模式
                    │ _template()   │ (rule/ml)
                    └──────────────┘
```

| 侵入点 | 修改文件 | 改动量 | 风险 |
|--------|---------|--------|------|
| ① 新增推理模块 | `agent/nodes/field_predictor.py`（新建） | +200 行 | 模型加载失败 → 节点不可用 |
| ② 字段融合逻辑 | `agent/nodes/price_inquiry.py` | +50 行 | 规则/ML 冲突 → 需要仲裁策略 |
| ③ 引擎双模式 | `agent/nodes/output_templates.py` | +30 行 | 增加维护负担 |
| ④ 模型文件管理 | `models/bert_field_selector/`（新建） | +400MB | 部署包膨胀，版本管理复杂 |
| ⑤ 推理依赖 | `requirements.txt` | +`transformers`, `onnxruntime` | 依赖冲突风险 |

### 3.2 与现有规则引擎的共存策略

若引入 ML，必须设计**双引擎共存**方案：

```python
# 伪代码：ML + 规则 共存策略
def _select_fields(query: str, intent: SearchIntent) -> list[str]:
    rule_fields = _apply_output_template(intent)  # 确定性规则输出

    if _ml_model_available():
        ml_fields = _ml_predict(query, intent)    # ML 预测输出

        # 仲裁策略（三选一）：
        # A. ML 优先：用 ML 输出，规则兜底
        # B. 规则优先：用规则输出，ML 仅做增量补充
        # C. 交集+投票：规则 ∩ ML 必出，(规则 ∪ ML) - (规则 ∩ ML) 按置信度阈值决定

        return _arbitrate(rule_fields, ml_fields, strategy="intersection")
    else:
        return rule_fields  # 降级到纯规则
```

**共存策略评估**：

| 策略 | 优点 | 缺点 |
|------|------|------|
| ML 优先 | 灵活性最高 | 模型错误 → 用户看到错误字段，无法修复 |
| 规则优先 | 核心场景不受模型影响 | ML 价值被削弱，边际收益趋近于零 |
| 交集+投票 | 结合两者优势 | 逻辑复杂，调试困难 |

**无论哪种策略，都会引入一个根本问题**：当 ML 输出与规则输出不一致时，以谁为准？如果以规则为准，ML 的增量价值被限制在边缘场景；如果以 ML 为准，确定性优势丧失。

## 5. 正向收益分析

### 5.1 ML 方案声称的改进点 vs 实际有效性

#### 声称改进 1："减少冗余字段，提升用户阅读效率"

| 分析 | 结论 |
|------|------|
| 规则方案现状 | 每个 query_type 已精确控制字段数量（supplier_recommend: 5 required + 9 optional，NULL 的 optional 自动隐藏） |
| ML 增量价值 | **极低**。规则已实现了字段精简。ML 可能因过拟合而错误隐藏关键字段 |
| 量化估计 | 规则方案的字段冗余率 < 10%（仅 optional 字段中存在非 NULL 但用户不关心的），ML 最多将此降至 5%，绝对提升仅 **5%** |

#### 声称改进 2："避免关键字段缺失"

| 分析 | 结论 |
|------|------|
| 规则方案现状 | required 字段保证必出，NULL 时显示占位文本 "未提供" |
| ML 增量价值 | **负收益**。ML 存在假阴性（概率 < 0.5 的 required 字段被误删），引入新的缺失风险 |
| 量化估计 | 规则方案字段缺失率 = 0%（required 必出保证）。ML 方案因误分类可能引入 3~8% 的假阴性 |

#### 声称改进 3："处理模糊语义和隐性需求"

这是 ML 方案**理论上最有价值**的场景。举例：

| 用户查询 | 规则行为 | 理想行为 | ML 能否做到？ |
|---------|---------|---------|:---:|
| "帮我看看这家公司" | 默认 supplier_recommend 模板 → 展示行业/等级/地区 | 展示公司基础信息（名称/法人/注册资本/经营状态） | ⚠️ 可能（如果训练数据中有类似样本） |
| "这个产品怎么样" | 默认 supplier_search 模板 | 展示产品参数 + 价格 + 供应商 | ⚠️ 可能，但 label 模糊 |
| "有什么要注意的吗" | 无匹配 → mixed 回退 | 展示不良记录（隐含风险关注） | ❌ 几乎不可能（语义跳跃太大） |

**关键发现**：这些"模糊查询"问题的根因在**意图解析层（LLM）**，不在字段选择层。如果 LLM 不能正确识别 query_type，ML 字段选择器也无力回天。反之，如果 LLM 已能解析出 query_type + 条件标志，规则引擎就能正确处理。

#### 声称改进 4："个性化字段偏好学习"

| 分析 | 结论 |
|------|------|
| 技术可行性 | 可以通过用户历史查询日志学习偏好（如 User A 80% 的查询都要 contact 信息） |
| ML 必要性 | **不需要 ML**。简单的规则即可实现：为每个用户维护 `user_preference = {"need_contact": True, "favorite_fields": [...]}`，在 `_eval_condition` 中叠加用户偏好权重 |
| 量化估计 | 规则 + 用户画像 可实现同样的个性化效果，且可解释、可控制 |

### 5.2 收益总结

| 改进点 | 规则现状 | ML 增量上限 | 有效性 |
|--------|---------|------------|:------:|
| 字段冗余控制 | 已较好（<10% 冗余） | +5% | 低 |
| 字段缺失防护 | 已保证（required 必出） | -3~8%（负收益） | 无 |
| 模糊语义适应 | 受限于 LLM 意图解析 | 取决于训练数据覆盖度 | 低~中 |
| 个性化 | 可通过用户画像实现 | 等同 | 无增量 |
| 可解释性 | 100% 透明 | 0%（黑盒） | 负收益 |

**综合评估**：ML 方案在字段选择环节的增量价值**不超过 5%**，且引入新风险。

## 6. 风险分析

### 6.1 ML 特有风险

| 风险 | 级别 | 触发场景 | 影响 | 缓解难度 |
|------|:----:|---------|------|:------:|
| **模型不确定性** | 🔴 高 | 边缘 query 超出训练分布 | 输出错误字段集，用户看到无关信息或缺失关键信息 | 难以缓解（需持续标注） |
| **冷启动困难** | 🔴 高 | 系统上线初期无标注数据 | 模型不可用，只能回退规则 → ML 投入白费 | 需预标注 2000+ 条 |
| **概念漂移** | 🟡 中 | 数据表新增字段 / 业务场景变化 | 旧模型在新场景下表现退化 | 需持续监控 + 重训 |
| **维护成本飙升** | 🟡 中 | 每次 schema 变更 | 见 §4.2 对比表 | 需投入专职人力 |
| **调试困难** | 🟡 中 | 用户反馈"为什么没显示某个字段" | 无法快速定位原因（黑盒 vs 配置可见） | 需额外开发可解释性工具 |
| **推理延迟** | 🟢 低 | BERT CPU 推理 50ms | 叠加 LLM 意图解析（~500ms）后，总延迟逼近 1s 用户体验阈值 | 可通过 ONNX 量化优化 |

### 6.2 当前规则方案已知风险及缓解

| 风险 | 缓解措施 | ML 是否更好？ |
|------|---------|:---:|
| 条件表达式有限（仅布尔） | 扩展 `_eval_condition` 支持比较运算 | 否 |
| 无法感知用户偏好 | 引入 user_profile 叠加权重 | 否 |
| 新 query_type 需手写模板 | 提供 `OutputTemplate` 配置向导 + 校验工具 | 否 |

## 7. 收益-成本比定量对比

### 7.1 量化模型

定义：
- **收益 \(G\)**：ML 方案相比规则方案提升的用户满意度百分比（字段精准度提升）
- **成本 \(C\)**：ML 方案相比规则方案额外投入的人天（一次性 + 年度维护）

基于 §5 的分析：
- 字段精准度提升上限：5%（最优估计，忽略负收益场景）
- 实际加权提升（考虑模糊 query 占比 ~15%，其中 ML 能改善的约 30%）：\(5\% \times 0.15 \times 0.30 = 0.225\%\)
- 保守估计：**ML 实际净收益 ≈ 0.2%~1%**

## 8. 最终建议

### 8.1 结论：🛑 不引入 ML 模型

**核心论据**：

1. **问题本质不匹配**：字段选择是确定性映射问题（query_type → fields），而非概率推理问题。ML 的不确定性在这里是劣势而非优势。

2. **边际收益极低**：规则方案已实现 100% 的准确率（在正确意图解析的前提下），ML 最多在 15% 的模糊查询中改善 ~30% 的体验，综合增量 **<1%**。

3. **真正的瓶颈在意图解析层**：当前系统中，"哪个 query_type"和"need_contact=True?"已经由 LLM 完成。如果这部分准确，字段选择必然准确；如果这部分不准，ML 字段选择器无济于事。因此，资源应投向**改进 LLM Intent Prompt**，而非替代下游确定性的字段映射。

4. **三年 TCO 差 10 倍以上**：规则方案 6~15 人天 vs ML 方案 94~144 人天，而用户能感知的体验提升 <1%。

5. **ML 引入负收益风险**：字段缺失（假阴性）比字段冗余（假阳性）对用户的伤害大得多。规则方案通过 required 必出机制保证了关键字段不丢失；ML 无法提供同等保障。

### 8.2 替代优化方向

不引入 ML 不代表停滞。建议在以下四个方向深化规则框架：

#### 方向一：扩展条件表达式能力

当前 `_eval_condition()` 仅支持简单布尔检查：

```python
# 现状：仅支持 intent.xxx 布尔字段
"intent.need_contact" → getattr(intent, "need_contact", False)
```

**增强方案**：支持比较运算和组合逻辑，**不改变架构**，只扩展 `_eval_condition`：

```python
# 扩展后的条件表达式语法（纯配置，零 ML 依赖）
_CONDITION_EXAMPLES = {
    # 比较运算
    "intent.sort_by == 'price_asc'": [...],
    # 范围判断
    "intent.top_n >= 10": [...],
    # 组合逻辑
    "intent.need_contact and intent.query_type == 'supplier_search'": [...],
    # 字段存在性
    "has_field('winning_amount') and intent.sort_by == 'amount_desc'": [...],
}
```

**收益**：将条件字段的覆盖范围从 2 个布尔开关扩展到算术/逻辑组合，无需 ML。

#### 方向二：引入用户画像（User Profile）叠加权重

```python
@dataclass
class UserProfile:
    """用户偏好记忆 — 基于历史查询行为自动更新。"""
    user_id: str
    preferred_fields: dict[str, float]   # {"contact_person": 0.9, "contact_info": 0.85}
    frequent_query_types: dict[str, int] # {"supplier_search": 15, "penalty_check": 3}
    last_updated: str

def _apply_user_preferences(
    template: OutputTemplate,
    profile: Optional[UserProfile],
) -> OutputTemplate:
    """基于用户画像调整字段优先级。"""
    if profile is None:
        return template

    # 将高频偏好字段从 optional 提升到 required
    boosted = set()
    for field, score in profile.preferred_fields.items():
        if score > 0.7 and field in template.optional:
            template.required.append(field)
            template.optional.remove(field)
            boosted.add(field)

    return template
```

**收益**：实现个性化字段展示，例如经常要联系方式的用户在 product_query 中自动展示 contact 字段。

#### 方向三：A/B 测试驱动的模板迭代

```
线上查询 → 随机分组
  ├─ A 组：当前 OutputTemplate（对照组）
  └─ B 组：实验性 OutputTemplate（实验组）
       ↓
  收集用户行为信号（停留时长、追问率、点击率）
       ↓
  统计分析 → 决策：采用 / 回退 / 继续优化
```

实现方式：在 `_SUB_ROUTE_MAP` 中增加 `experiment_template` 字段，按 `user_id` hash 分流。

**收益**：用真实用户行为数据驱动字段选择优化，而非拍脑袋决定。

#### 方向四：LLM Intent Prompt 精调（ROI 最高的方向）

字段选择的准确性根本上取决于意图解析的准确性。建议重点投入：

1. **构建意图解析评测集**：覆盖 3 路由 × 11 query_type 各 ≥30 条真实用户 query
2. **Few-shot 示例注入**：在 Intent Prompt 中为每个 query_type 增加 2~3 个 few-shot 示例
3. **Chain-of-Thought 推理**：让 LLM 在输出 JSON 前先输出推理步骤：`"用户提到'有没有不良记录'，应设置 need_penalty_check=true"`
4. **模糊查询二次确认**：当 LLM 置信度 < 0.7 时，追加澄清问题而非直接输出不确定的字段

| 投入 | 预期收益 | 实施周期 |
|------|---------|---------|
| 5~8 人天 | 意图解析准确率 +10~15% | 1~2 周 |
