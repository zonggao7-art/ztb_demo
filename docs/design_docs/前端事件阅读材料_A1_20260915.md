# 前端事件阅读材料：一次提问怎样变成页面内容

日期：2026-09-15。阅读对象：准备为本项目编写第一版前端的开发者。

本轮只理解数据流，不决定页面布局，不实现前端，也不修改后端。

**先记住一件事：浏览器发出一次提问，后端会陆续返回多条事件；每条事件负责告诉页面一件事。**

本文区分三种依据：

- **实测记录**：两次资源测量保存的事件数量、阶段顺序、耗时和结果数量。
- **代码事实**：当前 `unified` 路径怎样构造事件、字段和终态。
- **教学示例**：下文 JSON 使用虚构编号、企业和占位正文，时间也为示意值；不是实测原始响应，不是法规答案，不能用于引用回查或正确性评测。

资源测量没有保存逐条完整事件或每条事件的到达时间，因此不能还原当时的完整响应。本文不为整理材料再次调用模型。

## 1. 从浏览器发出的问题开始

假设用户输入：“查询项目编号为 DEMO001 的中标供应商和中标金额。”浏览器会向后端发送：

```http
POST /chat/stream
Content-Type: application/json
```

```json
{
  "question": "查询项目编号为 DEMO001 的中标供应商和中标金额。",
  "thread_id": "demo-session-01",
  "deadline_s": 90
}
```

| 字段 | 用日常语言解释 | 当前约束 |
| --- | --- | --- |
| `question` | 这次问什么 | 必填，字符串长度至少为 1；只含空格并不会被这个长度校验自动拒绝 |
| `thread_id` | 放在哪个会话里 | 不传时默认为 `default` |
| `deadline_s` | 希望给这次请求多少秒 | 可不传；传入时大于 0、不超过 120；Agent 还会取它与自身配置上限的较小值 |

这里没有模型密钥、数据库密码；这些由后端读取。

`thread_id` 与后面出现的 `request_id` 用途不同：同一聊天窗口的多次提问可以使用同一个 `thread_id`，但每次请求应有各自的 `request_id`。当前 FastAPI 会为每次调用生成新的请求 ID。

需要知道但暂不展开：当前 `unified` 实现只把本轮问题交给主 Agent，提示词明确禁止使用历史。因此，复用 `thread_id` 并不证明“它能理解上一轮指代”；这项多轮能力还需要单独确认。

代码位置：[请求模型](../../service/schemas.py)、[HTTP 处理入口](../../service/api.py)、[当前主 Agent](../../agent/execution/unified.py)。

## 2. 后端返回的是一串事件

响应类型为 `text/event-stream`，也就是本项目使用的 SSE。

可以把它理解为：后端暂时保持响应打开，有新进展就发一条消息，不必等所有工作结束才一次性回复。

一次传来的文本可能长这样。最后的空行用于结束这一帧：

```text
id: demo-request-01
event: token
data: {"type":"token","request_id":"demo-request-01","payload":{"delta":"这里是一段示例正文。"},"ts":1700000009.0}

```

先看懂 `data` 内的 JSON 即可：

```json
{
  "type": "token",
  "request_id": "demo-request-01",
  "payload": {
    "delta": "这里是一段示例正文。"
  },
  "ts": 1700000009.0
}
```

| 字段 | 回答的问题 | 例子 |
| --- | --- | --- |
| `type` | 发生了什么？ | `token`：来了一段正文 |
| `request_id` | 属于哪一次请求？ | `demo-request-01` |
| `payload` | 具体内容是什么？ | `delta` 内是要追加的文字 |
| `ts` | 后端何时构造了这条事件？ | Unix 时间戳，单位为秒，不是耗时或浏览器接收时间 |

外层 SSE 的 `event` 与 JSON 的 `type` 一致，`id` 与 `request_id` 一致。当前所有帧复用本次请求的 ID，它不是逐条递增的事件序号，也不代表已经支持断线续传。

后续编写解析器时再处理一个细节：一次网络读取不一定正好是一帧，也可能只有半帧或包含多帧。

代码位置：[事件模型](../../agent/streaming/events.py)、[SSE 格式化](../../agent/streaming/protocol.py)。

## 3. 先读懂一条法规问答

**实测记录**：法规问答耗时 9.406 秒，最终状态为 `complete`，返回 5 条引用。记录中有 1 条 `meta`、6 条 `stage`、2 条 `token`、1 条 `citations`、1 条 `final`。

下表的阶段顺序来自实测报告；阶段附加字段及与其他事件的先后关系由当前代码核对。页面显示是供理解的建议文案，不是已经实现的界面。

| 顺序 | 收到的事件 | 含义 | 页面可以怎样变化 |
| --- | --- | --- | --- |
| 1 | `meta` | 本次 Agent 流开始，模式为 `unified` | 关联本次请求，显示等待状态 |
| 2 | `stage: agent_start` | Agent 开始处理 | 显示“正在处理问题” |
| 3 | `stage: tool_call`，`running` | 开始执行 `knowledge_qa` | 显示“正在查询法规知识库” |
| 4 | `stage: tool_call`，`done` | 工具返回；还要看 `ok` | 工具成功时显示“法规查询已返回” |
| 5 | `stage: agent_finish` | Agent 决定结束工具调用 | 仍然等待最终校验 |
| 6 | `stage: validation_start` | 程序开始校验待发布结果 | 显示“正在校验结果” |
| 7 | `stage: validation_done` | 这一轮结果校验结束 | 等待正文与最终结果 |
| 8—9 | `token` × 2 | 发送已校验正文的两个片段 | 依次追加助手文字 |
| 10 | `citations` × 1 | 一个事件内含 5 个引用对象 | 展示 5 张引用卡片 |
| 11 | `final` | 返回完整结果与业务状态 | 根据业务状态结束本轮等待 |

**这里的文本分片是在校验后发送的。**当前代码先取得完整 `business_result`，再将答案按最多 80 个 Python 字符一段发送。事件虽然叫 `token`，这里并不代表模型 tokenizer 的一个 token。

因此，这次首段正文出现在约 9.406 秒，几乎与请求完成同时；此前页面可以显示阶段进展。不能把这种行为描述为模型一边生成、浏览器一边立即显示原始输出。

阶段不代表固定百分比；`agent_finish` 也不是流的终态。多工具请求可能多次出现 `tool_call`，不能把本次“6 条阶段事件”写死成所有请求的规则。

依据：[法规实测报告](../../test_report/deployment_resource_probe_20260915_134144.json)、[受控流实现](../../agent/graph.py)、[阶段事件产生位置](../../agent/execution/unified.py)。

## 4. 几个关键事件长什么样

以下都是**经过缩短的教学示例**，仅用于辨认字段，不拼成一条完整实测流。

**`meta`：建立本次请求的关联。**

```json
{
  "type": "meta",
  "request_id": "demo-request-01",
  "payload": {"mode": "unified", "started_at": 1700000000.0},
  "ts": 1700000000.0
}
```

**`stage`：报告可公开的执行状态。**不是模型的私有思考过程。

```json
{
  "type": "stage",
  "request_id": "demo-request-01",
  "payload": {
    "stage": "tool_call",
    "tool": "knowledge_qa",
    "status": "running",
    "step_id": "s1"
  },
  "ts": 1700000001.0
}
```

同一个工具调用结束时，可收到 `status: "done"`，并附带 `ok: true` 或 `false`。`done` 表示执行结束，是否成功要另看 `ok`。`step_id` 用来关联这次请求内的工具步骤。

**`token`：追加正文。**第 2 节的 `payload.delta` 就是具体片段。多次收到时按顺序拼接，不替换为仅剩最后一段。

**`citations`：补充结构化引用。**

```json
{
  "type": "citations",
  "request_id": "demo-request-01",
  "payload": {
    "citations": [
      {
        "context_index": 1,
        "chunk_id": "demo-chunk-01",
        "chunk_uid": "demo-chunk-01",
        "doc_name": "示例法规（教学占位）.pdf",
        "chapter": "示例章节",
        "chunk_index": 0,
        "text": "这里应是知识库返回的完整原文片段；此处仅为教学占位文本。",
        "score": 0.8,
        "metadata": {}
      }
    ]
  },
  "ts": 1700000009.0
}
```

`context_index: 1` 对应正文中的 `【来源1】`。标题看 `doc_name`，章节看 `chapter`，展开后的原文看 `text`。`score` 是相关度分数，不是答案正确概率。`chunk_id`、`chunk_uid` 用于溯源；这里的虚构 ID 不能真实回查。

引用对象不保证附带可打开的公网 PDF 链接，不能看到文件名就默认“点击即可下载”。完整字段定义见 [Citation 模型](../../public_kb/citations.py)。

## 5. 中标查询与法规问答有什么不同

**实测记录**：中标查询耗时 2.594 秒，最终状态为 `complete`，返回 1 条记录。它包含 1 条 `meta`、6 条 `stage`、4 条 `token`、1 条 `table`、1 条 `final`。

两次实测的阶段名称顺序相同；中标查询对应的工具是 `query_project_award`。

```text
meta → stage 若干 → token 若干 → table → final
```

`table` 的教学示例：

```json
{
  "type": "table",
  "request_id": "demo-request-02",
  "payload": {
    "records": [
      {
        "step_id": "s1",
        "record_ref": "demo-record-01",
        "project_number": "DEMO001",
        "successful_bidder": "示例供应商有限公司",
        "winning_amount": "123456.00"
      }
    ]
  },
  "ts": 1700000102.0
}
```

`records` 是记录数组，一条记录可以显示为表格的一行；字段名可以映射为“项目编号”“中标供应商”“中标金额”。`step_id` 和 `record_ref` 是关联标识，不必直接显示为业务列。

金额示例没有声明单位，不能自行补“元”或换算“万元”。当前结果正文会按已核定的配置提示单位，未核定时会明确说明；表格的单位展示仍需后续确认。字段值的类型也要进一步核对，不能用这个示例固定所有金额都是字符串。

这次查询没有 `citations`；法规问答没有 `table`。页面应看收到的数据，不应强制两块内容都存在。复合问题可能同时有表格与引用，当前代码发送顺序为正文、表格、引用、最终结果。

依据：[中标实测报告](../../test_report/deployment_price_resource_probe_20260915_134328.json)、[表格记录构造](../../agent/execution/unified.py)。

## 6. `final` 到来时，要看两层意思

下面仅展示 `final.payload` 中本轮需要理解的字段；实际 `business_result` 还有数据、执行统计等字段，这不是完整响应样本。

```json
{
  "answer": "完整的示例答案。",
  "intent": "agent",
  "business_result": {
    "branch": "agent",
    "answer": "完整的示例答案。",
    "execution_status": "complete"
  }
}
```

第一层：`type: "final"` 表示后端已经给出本轮最终结果。

第二层：`payload.business_result.execution_status` 说明业务完成到什么程度。

| 当前可能的业务状态 | 含义 |
| --- | --- |
| `complete` | 本轮处理完成；也可能是精确查询成功但没有匹配记录 |
| `clarify` | 需要用户补充必要条件 |
| `unsupported` | 当前能力不支持这个请求 |
| `partial` | 仅完成部分工作，或结果存在明确缺口 |
| `insufficient_evidence` | 程序返回受控的证据不足或失败兜底结果 |

工具失败、预算耗尽等情况也可能经程序处理后返回 `final`，所以不能只凭事件名判断所有业务都成功。`intent` 在当前正常 `unified` 业务结果中可能是 `agent`，不能依赖它一定等于旧版的 `knowledge_qa` 或 `price_inquiry` 来选择组件。

`final.answer` 是完整答案，前面的 `token` 已经发送过相同正文。页面可以用最终答案校准本轮正文，但不应把它再次追加一遍。这个行为是后续待你确认的前端处理规则，不是已经写好的 reducer。

HTTP 层会重写顶层 `request_id`；嵌套执行统计中的请求 ID 不保证与它相同。页面归属判断应以顶层 envelope 的 `request_id` 为准。

## 7. 暂时只认识这些异常边界

这一节是代码核对结果，**不是刚才两次成功请求已经验证过的异常测试**。

| 情况 | 当前事实 | 页面不能误判的地方 |
| --- | --- | --- |
| 未被业务层收敛的流错误 | 当前 `unified` 外层可发送 `error`，代码为 `unified_stream_failed` | 与已经拿到完整业务结果的 `final` 区分 |
| 处理超时 | 可能变成受控 `final`，也可能进入上述通用 `error` | 当前不能保证每种超时都有独立、准确的错误码 |
| 用户点击停止 | 当前取消异常会向上传播，连接也可能已经关闭 | 不能一直等服务器发 `cancelled` 才停止页面等待 |
| 未收到终态就断开 | 浏览器可能只有半截事件或正文 | 不能自动当作成功完成 |
| 等待较久 | HTTP 层可插入 `heartbeat`，payload 为空 | 心跳不是正文，也不意味着任务完成 |
| 请求体校验不通过 | FastAPI 可先返回普通 HTTP 422 错误 | 不能假定每个 HTTP 响应都是 SSE |

`cancelled`、`retrieval`、`partial` 虽然存在于事件枚举中，但不等于当前 `unified` 成功路径一定发出它们；尤其注意 `partial` 事件类型和 `execution_status: "partial"` 不是同一件事。

当前心跳按配置间隔发送，不是“仅在没有正文时才发送”。前面的成功测量耗时均短于当前 15 秒间隔，报告中没有心跳事件。HTTP 层是并发合并心跳和业务事件，边界情况还需单独验证，不能把成功样本的固定序列当成完整协议验收。
