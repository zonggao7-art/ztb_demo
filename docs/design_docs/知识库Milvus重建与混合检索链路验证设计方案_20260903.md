## 1. 目标与范围

1. **建库**：以 `DATA/repaired_knowledge` 三本书的 920 个 chunk 为唯一数据源，在 Milvus 2.6.23 上按混合 schema（稠密 IVF_FLAT/COSINE + 稀疏 BM25 Function）重建 `public_kb` 集合并完成向量化入库。
2. **防重**：入库以 `chunk_id`（Milvus 行级主键）与 `chunk_uid`（内容派生稳定标识）为唯一标识，保证重复写入不产生重复数据，重复执行入库是幂等的。
3. **验证**：建库完成后，端到端验证 混合检索（稠密+稀疏）→ RRF 融合 → Reranker 精排 → 动态阈值过滤 全链路真实生效（这是 2026-08 以来该链路第一次带真实数据运行）。

不在本轮范围：`mysql_price_semantic` 集合（D2 维持现状）；切分逻辑再调整（数据已定稿）；阈值参数的最终标定落码（本轮只采集分布、出建议，见 Q6）。

## 3. 入库设计方案

### 3.1 数据前置校验（硬门槛，防"并发写入残留"复发）

上轮曾发生 `DATA/repaired_knowledge` 被外部进程写坏的事件（850 行/仅 42 个唯一 uid 的脏产物）。因此入库前强制三步校验，任一失败即终止：

1. **digest 复核**：重新读取三本书 `documents.jsonl`，按序抽取 `chunk_uid` 计算 sha256，与 `manifest.json` 的 `chunk_uid_digest`（及逐书 digest）比对；
2. **门禁复跑**：对合并后的 920 块重跑 `validate_documents`（P3 全部指标 + `text_coverage`）；
3. **联合唯一性断言**：三书合并后 `chunk_uid` 无冲突、`structural_id` 无冲突、文本无完全重复（当前已知全部为 0，复跑是防线不是形式）。

### 3.2 唯一标识与防重设计（核心决策，见 Q1/Q2）

**推荐方案 A：`chunk_uid` 直接作 Milvus 主键（VarChar PK，`auto_id=False`），写入一律 upsert**

- 主键取值即 `chunk_uid`（`ck-<32hex>`，35 字符）——`chunk_id`（行级主键）与 `chunk_uid`（业务唯一标识）**合二为一**：存储层天然防重，同 uid 重复写入=同 PK 覆盖（upsert 幂等），不可能产生重复行；引用契约 R1（chunk_id）/R2（chunk_uid）两字段保留、取值相同，语义各自成立。
- uid 由 (doc_name|chapter|chunk_index|text_hash) 派生：同 uid 必同内容，覆盖与跳过等价，upsert 语义最简单且重跑安全。
- 两条入库路径（documents.jsonl 直读 / md+sidecar 重切）产出**完全相同的主键**——比旧契约（"仅 Milvus 主键 id 不同"）更强。
- 需要的代码改动（实施前逐项过测试）：
  1. `milvus_store.py`：schema `auto_id=False`，主键字段改为 `chunk_uid`（VarChar 64, is_primary）；`_batch_insert` → `upsert`；`_create_vector_store_wrapper`（`auto_id=False, primary_field="chunk_uid"`）；
  2. `citations.py`：`chunk_id: Optional[int]` → `Optional[str]`（R1 校验逻辑不变）；
  3. `qa_chain.py` / `qa_chain_async.py`：确认检索结果解析对主键类型无 int 假设（`output_fields=['*']` 直取，预期无改动，实施时验证）；
  4. 新增 `--ingest-handoff <dir>` 入口（解决 G2）：读 manifest → 校验（3.1）→ 三书合并一次 `initialize_collection`；
  5. pytest 全量回归 + 相关用例适配。

**备选方案 B（保守）：维持 auto_id INT64 主键，应用层防重**

- 入库前 `query(expr="chunk_uid in [...]")` 取存量 uid 集合 → 差集计算 → 仅写新增（或按拍板语义报错）；写后断言"行数 == 去重后 uid 数"。
- 优点：schema 与 langchain 包装零改动；缺点：防重是应用层约定而非存储约束，`chunk_id` 与 `chunk_uid` 仍是两套标识，增量路径每次都要全量比对。

> 选 A 的理由：用户口径是"以 chunk_id 和 chunk_uid 作为唯一标识避免重复写入"——A 让防重成为存储层性质（主键唯一），不依赖调用方自觉；且 920 行规模下 VarChar PK 的成本可忽略。A 的主要风险是 langchain_milvus 包装器对 VarChar PK 的兼容性，实施第一步就是兼容性探针（建临时集合实测，不行即回退 B——回退路径已明）。

### 3.2.1 跨批次碰撞分析与元数据守卫（2026-09-03 评审后细化，方案 A → A′）

**uid 生成策略**（`public_kb/chunk_ids.py`）：`chunk_uid = ck-md5(doc_name | chapter | chunk_index | md5(text)[:16])`。方案 A 下 Milvus 主键取值即 uid，故"撞主键"⟺"同一文档 + 同一位置 + 同一内容"。

**跨批次碰撞矩阵**（回应评审问题：跨批次是否会撞、撞了是否丢数据）：

| 场景 | 是否撞 uid | 后果 | 与目标语义的关系 |
|---|---|---|---|
| 跨文档同文（如同一法条出现在两本书） | **不撞**（doc_name 参与哈希） | 两条独立入库，跨文档重复保留 | ✅ 目标语义 |
| 同文档重复灌入 | 撞（设计如此） | upsert 覆盖；同 uid ⟹ text/chapter/index 逐字相同，覆盖无损 | ✅ 目标语义 |
| 同文档换切分参数重灌 | 不撞（位置与内容均变） | 新旧两版并存（内容冗余而非遗漏） | ⚠️ 由"文档级替换"处理 |
| **新增数据缺元数据** | **会撞**：兜底计算时 doc_name/chapter/index 取空串/-1，uid 退化为纯文本哈希 → 跨文档同文被误合并 | **合法跨文档重复被覆盖删除（真实的数据遗漏风险）** | ❌ 必须守卫拦截 |

**结论**：uid 去重是"文档+位置+内容"级而非"文本级绝对去重"，与目标语义（文档内不重复、跨文档重复保留）天然一致；唯一漏洞在元数据缺失的兜底路径。因此方案 A 细化为 A′，追加三道守卫：

1. **doc_name 必填门槛**：入库批次中任一行缺 doc_name → 拒绝入库（fail-fast）；文档级缺失时由 CLI 显式指定（如取自文件名）。禁止 uid 退化为纯文本哈希；
2. **chapter / chunk_index 自动补齐**：缺 chapter 置空串、缺 index 按批内顺序注入，保证同文档内不同位置的块 uid 必不同；
3. **文档级替换策略**：新增文档 → 直接 upsert；已存在文档的更新版本 → `--replace-doc <doc_name>` 先按 doc_name 删除旧版全部行再写新版（"同文档版本唯一"交给文档级操作，不靠 uid 硬去重）。

附加收益：方案 A 下 chunk_uid 为显式主键字段，绕过项目管道的直写若不带 chunk_uid 会被 Milvus 主键约束拒绝——堵住"无标识数据悄悄入库"的口子。

**Q2（重复写入语义）在 A′ 语义下的推荐**：日常写入一律 **upsert 幂等覆盖**（同 uid 必同内容，覆盖=跳过=无损）；`--ingest-handoff` / 增量入口提供 `--replace-doc <doc_name>` 做文档级替换。

### 3.3 向量化与批量写入

- Embedding：`.env` 实配 `EMBEDDING_MODEL`（BAAI/bge-m3，1024 维）经 `create_embeddings` 工厂，逐字透传（D4）；`_SafeEmbeddings` 的 2000 字符截断属输入保护——本轮 chunk 含面包屑前缀后约 0.5%~1% 超过 2000 字符，**仅影响向量计算的尾部截断**，存储文本完整。可接受；如需消除，将 `_MAX_TEXT_CHARS` 提至 4000（bge-m3 上限 8192 token），列为可选小改动（Q5）。
- 批量：现 `_batch_insert` batch=100（每批约 19 万字符 ≈ 19 万 token），SiliconFlow TPM 限额下可能连续 429。口径 B（D-重试）：SDK `max_retries=1` 偏薄，建议 batch_size 参数化并默认降为 32（每批约 6 万 token），配合 429 退避；属小改动，与 Q5 一并拍板。
- 写入：920 块 × 10~29 批 upsert → flush → 行数断言。

### 3.4 写后校验（建库完成的判定标准）

1. `describe_collection`：sparse_vector 字段 + text_bm25 Function + 双索引（既有自检）；
2. `row_count == 920`；
3. 全量 `chunk_uid` 回读集合 == manifest 的 uid 列表（集合级与逐书级）；
4. 抽样 5 块/书回读 text + metadata（chapter/page_start/page_end/content_type）与源文件逐字段一致；
5. embedding 维度抽查 = `EMBEDDING_DIM`（1024）。

## 4. 检索链路验证方案（建库后执行）

链路预期：`query → 混合检索（dense COSINE k=30 nprobe=32 + sparse BM25 k=30）→ RRF 融合 k=60 取 Top-30 → Reranker 精排 → 动态阈值（按 top1 三级 0.40/0.45/0.50）过滤 → top_k=3 进 LLM`。

| # | 验证项 | 方法 | 通过标准 |
|---|---|---|---|
| T1 | schema 静态验证 | `describe_collection` | 同 3.4-1 |
| T2 | 链路日志验证 | 任一 query 的日志序列 | 依次出现：混合检索双路发起 → RRF 融合前后条数 → Reranker top1 分 → 动态阈值取值 → 过滤后条数；全程无 ERROR、无"降级/回退"字样（output_fields 回退 warning 除外，属已知无害回退） |
| T3 | 稀疏路有效性 | 精确条款/术语 query：「第三十七条」「评标委员会」「履约保证金」「投标保证金」 | 命中含对应条款号/术语的 chunk（BM25 对"第X条"与领域词的精确命中；我们的 chunk text 含 leaf 标题与法条号，可命中） |
| T4 | 稠密路有效性 | 语义改写 query：「投标保证金什么情况下可以退」（对应"投标保证金的提交与清退"节） | top3 命中语义相关 chunk（允许非字面匹配） |
| T5 | RRF 融合有效性 | T3+T4 各选 1 query，对比单路与融合排序 | 融合结果包含两路高相关候选，日志显示融合条数正常 |
| T6 | Reranker 真实生效 | 任一 query，记录 rerank 前后顺序变化与 relevance_score | 分数非 COSINE 值域/非 0.5 假分数；日志模型名为 .env 实配（D6 抽查） |
| T7 | 动态阈值三级触发 | 高相关 query（期望放行）+ 低相关/无关 query（期望拒答） | 阈值随 top1 分数在 0.40/0.45/0.50 间切换；无关 query 触发拒答而非硬凑答案 |
| T8 | fail-fast 回归 | 停止 milvus-standalone 后发 query；构造坏 schema 临时集合 | 均为明确报错上抛（图层友好提示），无静默劣化（D3） |
| T9 | Reranker 分数分布采集 | ~20 条典型 query 的 top1/top5 分数直方图 | 产出分布报告 → 判定 0.40/0.45/0.50 初值合理性 → 给出标定建议（本轮不改值，Q6） |
| T10（可选） | 106 题引用评测建新基线 | `scripts/run_knowledge_citation_eval.py` | **被 G3 阻塞**：`testset_knowledge.jsonl` 缺失，需用户提供了测试集才能跑（Q4） |

冒烟命令：`python -m public_kb --question "..."` 与 `python -m agent --question "..."`（知识问答分支端到端）。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| langchain_milvus 包装器不兼容 VarChar PK / auto_id=False（方案 A） | S1 首步做临时集合兼容探针；不兼容即回退方案 B（schema 不动、应用层查重） |
| SiliconFlow TPM 限流导致入库中断 | batch_size 参数化调小（Q5）；口径 B 退避重试；持续限流则分书分批入库（upsert 幂等，中断重跑无副作用） |
| 动态阈值初值（0.40/0.45/0.50）未标定 → 全拒答或全放行 | T8 先验证行为、T9 采集分数分布出标定建议；调值另行拍板（不属本轮代码） |
| `DATA/repaired_knowledge` 再次被并发写坏 | 3.1 digest 硬门槛；建议建库窗口内暂停其他会话对该目录的写入 |
| 三书分次入库相互覆盖（G2） | `--ingest-handoff` 一次合并入库，从编排上消除 |
| chunk 文本尾部被 2000 字符 embedding 截断（约 1%） | 影响仅限向量计算，存储完整；可选 `_MAX_TEXT_CHARS`→4000（Q5） |
