# 第二轮测评方案（简明版）

> 2026-09-08｜初步方案，尚未开始改造或跑测评。

这次分两部分：**先单独测 RAG，看看资料处理和检索改造有没有用；再测完整 Agent，看看它能否稳定完成实际任务。**

所有实验都在已有副本 `D:/DEMO/zhaotoubiao_demo_copy` 中进行。

## 一、已经确定的五件事

1. **先让 ReAct 不参与。** 直接测试 RAG 工具，检索先用“稠密向量＋固定阈值＋Top-K”，之后逐步加入新功能。
2. **先把数据治理和嵌入模型更换放在一起比较。** 只看两项改造合起来带来的变化，暂不分别计算贡献。
3. **沿用第一轮有用的指标和题目。** 先检查、修正，再使用。
4. **采用 Ragas 评分。**
5. **只改测评副本。** 原系统继续保留，实验数据也要与原数据分开。

## 二、具体怎么测

### 第一步：比较“旧组合”和“新组合”

两组使用相同的检索方式：

| 对照组 | 使用的数据 | 嵌入模型 |
|---|---|---|
| 旧组合 | 治理前的文本块 | 旧模型 |
| 新组合 | 治理后的文本块 | 新模型 |

这里的“相同资料”，指来自**同一批原文、同一版本**。可以改变清洗和切分方式，但不能一组有某份法规，另一组没有，再把差异算成改造收益。

为了方便比较，两组还要使用相同的问题、回答模型、提示词、上下文长度限制和评分方法。每组的查询向量与库内向量必须由配套的嵌入模型生成。

已找到的旧检索代码是：**先找 30 条候选，保留分数不低于 0.45 的结果，再取前 5 条。** 这可以作为配置依据；旧模型的实际名称、对应数据和最终采用的旧版本，还需要核实。

这一步回答的是：

> 在检索方式相同的情况下，数据治理和嵌入模型一起更换后，找资料和回答问题的效果有没有改善？耗时和费用怎样变化？

暂不增加“新数据＋旧模型”的中间组，避免为单独归因再建一份向量库。

**同时保存过滤前后的结果。** 不同嵌入模型的分数分布可能不同；这样才能看出是资料没找到，还是找到了却被 0.45 的门槛过滤掉了。同样取 5 条，文本长度也可能不同，因此还要记录真正送给模型的资料和 token 数。

### 第二步：逐渐加回新的检索功能

固定新数据和新嵌入模型，建议按下面的顺序增加：

| 加入的功能 | 通俗理解 | 主要看什么 |
|---|---|---|
| BM25＋RRF | 增加关键词检索，再把两路结果合并排序 | 原来漏掉的资料能否找到 |
| 重排模型 | 重新判断候选资料与问题的关系，把更有用的放前面 | 前几条资料是否更准确、更完整 |
| 动态过滤 | 根据重排结果调整过滤门槛 | 是否减少误拒答，同时少放入无关资料 |

每增加一步，观察效果、耗时和费用。先用检索结果比较，只有必要时才对中间方案生成答案、运行 Ragas，控制调用成本。

这里有一个必须注意的地方：**向量相似度、合并后的分数、重排分数不是同一种分数，不能都套用 0.45。** 前几步先比较过滤前的前 K 条资料；固定过滤与动态过滤，则放在同一种重排分数上比较。各阶段的具体过滤设置，在实施前确定。

报告只说明“在前一步的基础上，加这一项产生了什么变化”，不把各项涨分硬凑成独立贡献占比。

### 第三步：测完整 Agent

这一部分单独记录，不混进前面的 RAG 对照成绩。

- **任务完成：** 工具选得对不对，有没有漏做用户要求，能否根据前一步结果继续查询。
- **并发：** 多个用户同时提问时，速度和错误率如何，会不会串会话。
- **流式交付：** 多久收到进度反馈、多久看到第一段有效答案、断开连接后能否清理任务。
- **故障恢复：** 超时、断流或取消之后，下一次请求能否正常完成。
- **完整成本：** 一次任务中的 Agent、RAG、工具和重试合计花费多少。

当前系统在一次请求中逐个调用业务工具；新入口也是先得到经过校验的完整答案，再分块发送。因此，“多用户并发”和“单次任务并行”、“收到进度”和“看到答案”要分开记录。

先说明当前系统能做到什么。只有准备写“比旧版提高了多少”时，才补相应的旧版对照。

## 三、看哪些指标

第一轮已经记录了三项 Ragas 质量分，以及速度、token、费用和失败情况。第二轮继续使用，补上“资料是否找齐”和“用户是否真正拿到答案”。

| 看什么 | 具体记录 |
|---|---|
| 回答有没有依据 | Faithfulness：回答是否得到提供资料的支持 |
| 回答有没有回应问题 | Answer relevancy：是否答在点上 |
| 回答是否正确 | Answer correctness：与审核后的参考答案是否相符 |
| 资料找得怎么样 | 必需资料找到了多少、有没有全部找齐、是否重复、是否被错误过滤 |
| 用户等多久 | 第一段有效答案出现时间、总耗时；保留平均值、P50、P95，必要时看 P99 |
| 花费多少 | 输入／输出 token、每题费用、完成一个任务的费用 |
| 是否可靠 | 完成、失败、空答案、拒答情况，以及评分工具本身的失败 |
| 其他参考项 | 输出速度、答案长度、单跳与多跳的分组表现 |

P50 可以理解为“一半请求在这个时间内完成”，P95 是“95% 的请求在这个时间内完成”。

旧报告还保存了样本数、单跳／多跳分类、同源模型自评标记等信息，后续一起保留。[旧指标完整字段](/D:/DEMO/eval_data/scores_v2/deepseek_v4_flash_summary.json)

评分时守住四点：

- **参考答案先核对。** Ragas 分数不能替代人工审核，0.75 分也不等于 75% 的题答对。
- **空答案和失败都记录。** 不能只给成功的回答算平均分，却不说明有多少题没有完成。
- **费用分开算。** 系统回答、一次性建库、Ragas 打分分别记账；token 标明是接口返回还是估算。
- **评分条件保持一致。** 固定 Ragas 版本、裁判模型和评分设置。裁判是负责打分的模型，不随被测嵌入模型一起更换。

Ragas 的具体版本尚未确定。先在副本环境用少量题目跑通，再开始正式评分。

旧回答、评分和检索记录保存在 `D:/DEMO/eval_data`，可以用于找失败案例。**旧的检索结果不能拿来代替新检索重新运行。**

复用前先解决已经发现的问题：

1. 有些参考答案与原文不一致，需要修正。
2. 有些问题重复，有些旧题不在当前资料范围内，需要筛选。
3. 旧检索中存在大量重复正文，不能只按不同 chunk ID 判断“找到了不同资料”。
4. 旧报告出现过空答案却未计失败，需要修改成功／失败的判断方法。

每道正式题只需先写清：**问题、必须答出的要点、原文依据，以及应该回答还是拒答。** 再给题目固定编号，记录审核结果。原文依据使用条款或片段，新旧切分可以映射到不同的 chunk。

调参用的题与最后报告成绩的题要分开。先审核一小批，再决定是否扩大，不预设必须跑满 200 或 1,000 题。

## 五、怎样保护现有系统

测评副本已经存在，但还需要确认内容和配置。

- 核对副本是否包含当前完成版代码，尤其是尚未提交到 Git 的改动。
- 副本使用独立的环境、配置、输出目录和会话记录；保留一份完整 Agent 配置，方便后续测试。
- 实验建库、删除、写入只指向实验数据。**复制代码后若仍连接原来的数据库，风险并没有消失。**
- 旧库作为来源时只读；不直接复制运行中的数据库文件来冒充可用备份。
- 跑性能测试时固定机器和负载，避免其他程序抢资源影响结果。

是否共用 Milvus 服务、只分开集合，还是另起一套服务，实施前再决定。原系统不承担实验写入。
