## 1. 背景与排查结论摘要

本轮整改源于两项排查结论（完整证据链见附录 A）：

### 1.1 结论一：嵌入模型调用一致性

| 检查项 | 结论 |
|---|---|
| 运行时实际模型 | ✅ `.env` 实配 `EMBEDDING_MODEL=BAAI/bge-m3`（SiliconFlow API），运行时调用正确 |
| 构造点收口 | ✅ 全项目唯一构造点 `create_embeddings`（`public_kb/embedding_service.py`），由 `test/test_config_centralization.py` 静态扫描强制；`rag_engine`、`price_inquiry/semantic.py`、工具层均走同一工厂 |
| 显式"换模型"兜底逻辑 | ✅ 不存在（无 try/except 换模型、无异常时切换模型名） |
| **违规残留** | ❌ `public_kb/config.py:86` 的代码默认值为 `"BAAI/bge-large-zh-v1.5"`——`.env` 缺失该项、拼写错误或新环境未配置时**静默换模型**；且 bge-large-zh-v1.5 与 bge-m3 同为 1024 维，Milvus 维度校验不报错，检索语义空间悄悄错配，极难发现 |
| 次要不一致 | ⚠️ ① `EMBEDDING_API_KEY` / `EMBEDDING_BASE_URL` 存在 `SILICONFLOW_*` / `CLOSEAI_*` 别名兜底链（非模型兜底，但与"未配置即抛错"的目标口径不一致，见待确认 Q2）；② `config.py:104` 注释写"bge-m3"而默认值是 bge-large，注释与代码矛盾；③ reranker 模型名硬编码于 config.py 不经 .env（见 Q2） |

### 1.2 结论二：混合检索 / Reranker / RRF / 动态阈值未生效的根因

**当前实际生效的检索策略 = 稠密向量检索 + 固定阈值 0.45 + top-5**（与前期测试结论一致）。混合检索能力代码**完整存在但全部是死代码**：

| 能力 | 代码位置 | 未生效原因 |
|---|---|---|
| 稀疏检索路（BM25） | `qa_chain.py:338-343`、`qa_chain_async.py:193-198` | 触发条件 `has_sparse=True` 恒不成立 |
| RRF 融合（k=60） | `qa_chain.py:346-352` | 同上 |
| Reranker 精排 | `qa_chain.py:374-381`、`public_kb/reranker.py` | 同上（降级路径中从未调用过 Reranker） |
| 动态阈值 `_adaptive_threshold` | `qa_chain.py:537-549` | 同上 |

**根因链（四层）**：

1. **直接原因**：`milvus_store.py initialize_collection()` 建的 schema 只有 `id / text / vector(FLOAT_VECTOR, IVF_FLAT, COSINE)` 三字段——无 `SPARSE_FLOAT_VECTOR` 字段、无 BM25 Function、无稀疏索引。向量库数据确实缺乏稀疏向量字段。
2. **历史原因**：2026-08-07 重建时曾尝试 `sparse_vector + BM25 Function`，服务端 `describe_collection()` 返回 `Functions: []`（Function 被静默丢弃），见 `../work_docs/milvus_rebuild_summary.md` 问题 1，随后 schema 回退纯稠密。
3. **技术根因（对"原 embedding model 无法映射稀疏字段"初判的修正）**：卡点不在嵌入模型——bge-m3 本身具备稀疏（lexical_weights）能力，SiliconFlow `/embeddings` API 只返回稠密向量也不构成阻塞。真正的根因是：
   - Milvus **服务端锁定 v2.4.0**（`milvus/docker-compose.yml:47`），而 **BM25 Function 是 Milvus 2.5.0+ 才引入的能力**，2.4.0 服务端根本没有 Function 概念——这正是当年 Functions 被静默丢弃的原因，换任何客户端版本都无法解决；
   - 客户端 pymilvus 实装 **3.0.1**（requirements 仅约束 `>=2.4.5` 未锁上限），与 2.4.0 服务端 schema 序列化不兼容，加剧问题；
   - 本轮已实测确认：pymilvus 3.0.1 客户端具备全部所需 API（`FunctionType.BM25`、`CollectionSchema.add_function`、`MilvusClient.hybrid_search`），**唯一阻塞点是服务端版本**。
4. **掩盖机制**：schema 缺字段后降级是静默的——仅一条 info 级日志 `"当前 Schema 无稀疏向量字段，使用稠密+Reranker 模式"`（`qa_chain.py:325`），且该文案本身是错的（降级路径里没有 Reranker），导致"混合检索已生效"的假象长期存在。

**连带发现**：重建报告验证记录声称降级模式"稠密 + Reranker"5/5 通过（score 标注"重排后"），但 git 初始快照（2026-08-25）中降级路径即无 Reranker 调用，那些分数实为 COSINE 分——Reranker 很可能从未真正生效过；`describe_collection` 每次查询都调用一次（可缓存）；CLAUDE.md / requirements 中"pymilvus 2.4.x、setuptools<70"的表述已与实装（3.0.1）脱节；Milvus 服务当前未运行（localhost:19530 拒绝连接），线上实时 schema 无法即刻探测。

### 1.3 全模型调用点配置口径审计（v3 新增，回应 Q1）

对项目内**全部模型类 API 调用**逐一核查"模型名 / 凭据 / 端点"的配置来源（Q1 拍板：统一口径覆盖所有模型）：

| 调用点 | 模型名来源 | 凭据/端点来源 | 结论 |
|---|---|---|---|

| MinerU（PDF 解析） | 本地 `magic-pdf` 命令行（`mineru_parser.py` subprocess 调用），其内部模型由 MinerU 自身配置文件管理 | 项目代码**不消费** `MINERU_API_TOKEN` | ✅ 不属项目内模型调用；`.env` 中 `MINERU_API_TOKEN` 为**休眠预留变量**（全仓 grep 无消费点），仅登记 |
| Tavily（web 检索 API） | 无代码消费 | `.env` 中 `TAVILY_API_KEY` 为**休眠预留变量**（全仓 grep 无消费点） | ✅ 仅登记；未来若启用 web 检索工具，纳入统一口径 |

### 2.1 统一模型调用口径定义（D4 + D6 落地条款）

| 配置类别 | 字段 | 口径 |
|---|---|---|
| **身份配置**（错配 = 检索/对话静默劣化，绝对禁止） | 模型名：`EMBEDDING_MODEL` / `LLM_MODEL` / `RERANKER_MODEL`；凭据：`EMBEDDING_API_KEY` / `LLM_API_KEY`；端点：`EMBEDDING_BASE_URL` / `LLM_BASE_URL` | **.env 必填**：`os.getenv("X")` 不得携带默认值参数；`Settings.__post_init__` 校验缺失/空串即 `raise ValueError`；**不得存在任何别名兜底链**（一层都不行）；实际调用值与配置值**逐字一致**（工厂透传）；**调用失败一律上抛**——口径 B（Q3 拍板）：同配置原样重发（同模型/同凭据/同参数，仅退避）允许存在，重试耗尽必抛错；假分数 / 换路径 / 换模型类回退一律禁止 |
| **操作参数**（非模型身份，允许文档化默认值，.env 可覆盖） | timeout / max_retries / 并发 / 温度 / 各类开关等数字、布尔旋钮（如 `LLM_TIMEOUT`、`llm_temperature`、`MYSQL_SEMANTIC_*`、`MILVUS_HOST` 等） | 允许带文档化默认值（现状保留）。理由：默认值只影响运行参数，不存在"实际调用模型 ≠ .env 配置"的身份错配风险；D4/D6 治理对象是身份配置 |

> 边界说明：上表为执行 D4/D6 时的判定边界——若需把操作参数也升级为必填（如 `MILVUS_HOST` 不允许 `localhost` 默认值），另行拍板，默认不在本计划范围。

### 6.2 Q3 详述：什么是"同配置重试"，两种口径的差异

**1）问题的由来——HTTP 429（限流）是什么**

SiliconFlow 等 API 服务商对每个账号设有速率限制（RPM=每分钟请求数、TPM=每分钟 token 数）。当单位时间内的请求量超过限额时，服务端不执行请求，而是返回 HTTP **429 Too Many Requests**，含义是"请求本身没有错，只是这一分钟你请求太多了，稍等片刻再发即可"。它**不是**配置错误、不是模型错误、也不是网络故障——只要稍后原样重发同样的请求，通常就会成功。

批量场景下 429 几乎必然周期性出现：例如询价语义库 bootstrap 需要把 MySQL 全量行送 embedding API（数万次调用），即使主动限速也会撞上平台偶发限流。

**2）项目中现存的"同配置重试"共三层**（§1.3 盘点表）

| 层 | 位置 | 现行为 |
|---|---|---|
| ① | `_embed_semantic_batch`（`semantic.py:211-235`） | 遇 429 → 同一批文本、**同一模型、同一凭据、同一参数**，退避等待（15s→90s 封顶）后原样重发，最多 6 次；非 429 错误或 6 次耗尽 → raise |
| ② | 异步 Reranker tenacity（`reranker.py:165-200`） | 遇 429/5xx/超时/网络异常 → 指数退避重发，默认 2 次尝试；耗尽 → 异常继续上抛 |
| ③ | OpenAI SDK 内建重试（`llm_max_retries=1`、`embedding_max_retries=1`） | ChatOpenAI / OpenAIEmbeddings 底层对连接错误/429/5xx 自动同配置重发一次；耗尽 → raise |

三层的共同点：**只做"原样重发"，绝不换模型、绝不换凭据、绝不换路径、绝不返回假结果**；最终失败都 raise。

**3）D4 说"如果调用失败，抛出错误"——429 算不算"调用失败"？两种口径：**

| | 口径 A：严格字面——任何失败立即抛错 | 口径 B（建议）：区分"重试"与"降级" |
|---|---|---|
| 定义 | 第一次 429 / 5xx / 超时就 raise，不做任何重发 | **同配置原样重发**（同模型/同凭据/同参数，仅退避等待）允许存在；重试耗尽后失败必 raise |
| 429 的处置 | 第一次即抛错 | 重发若干次，耗尽才抛错 |
| 对批量入库的后果 | 一次偶发限流即中断整个 bootstrap，需人工重跑 | 限流被退避吸收，任务继续；持续限流最终仍报错 |
| 对线上问答的后果 | 偶发限流直接变成用户可见报错 | 偶发限流用户无感；持续故障如实报错 |
| 需要的代码改动 | 删除三层全部重试（`max_retries` 置 0、删 tenacity、删 429 重试） | 保留三层现状，仅把"重试"与"降级"的边界写进口径定义（§2.1） |
| 是否存在"实际调用 ≠ .env 配置" | 不存在 | 同样不存在（重发的是**同一个请求**） |
| 是否存在静默劣化 | 不存在 | 不存在（重试耗尽必报错，无任何假结果/换路径） |

**4）无论选择 A 还是 B，都确定执行的事项**（不依赖 Q3 结论）：

- **Reranker 假分数回退必须删除**（WP3.6）：当前同步/异步 Reranker 在重试耗尽后还有最后一层"捕获一切异常 → 返回原始顺序 + relevance_score=0.5 假分数"（`qa_chain.py:528-534`、`reranker.py:145-151`）。这不是重试也不只是降级——它**返回了假数据**混入精排结果，是最恶劣的静默劣化，按 D3 一律改为异常上抛。
- 三层重试中"重发同一请求"的语义不会改变模型/凭据/参数——即口径 B 下同样满足"实际调用模型与 .env 配置严格同步"。

**5）建议：口径 B**。理由：429 是平台运营常态而非故障，口径 A 会让批量任务随机中断、线上偶发限流直接变成用户可见报错，而换来的一致性收益为零（两种口径下都不存在身份错配和静默劣化）；口径 B 把 D4 的本质（绝不静默劣化、最终失败必报错、绝不身份错配）完整保留，同时区分了"再试一次同样的请求"与"换一种方式应付过去"——后者才是被绝对禁止的降级。

> **已拍板（2026-09-01）：口径 B**。三层同配置重试保留现状；"同配置原样重发 ≠ 降级"边界已写入口径定义（§2.1）；WP3.6 Reranker 假分数回退清除不受影响。
