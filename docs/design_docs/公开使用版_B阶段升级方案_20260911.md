# 招投标智能助手：公开使用版 B 阶段升级方案

> 版本：2026-09-11  
> 前置条件：[作品集前端 A 阶段实施与学习方案](./作品集前端_A阶段实施与学习方案_20260911.md)已通过验收  
> 文档性质：升级路线讨论稿；B 的架构选择需要由 A 的实际数据和用户目标驱动

## 1. 为什么 B 不能与 A 一次完成

A 证明“真实 Agent 可以被网页和飞书正确使用”。B 要解决的是另一类问题：**不受信任的外部用户长期使用时，系统怎样识别用户、隔离数据、控制成本并持续恢复**。

如果跳过 A 直接做 B，会同时面对前端、API、流式、飞书、登录、数据库、部署和安全问题。出现故障时很难判断是哪一层造成的，也不利于学习。

## 2. B 阶段目标

B 的目标是将 A 的受控演示升级为有限公开使用版本：

- 面试官可以通过稳定 URL 访问；
- 用户身份和会话边界明确；
- 会话历史可持久化并可删除；
- 网页和飞书共享一致的业务语义；
- 有限流、并发、超时、成本预算和审计；
- 部署、监控、备份与故障恢复有明确流程；
- 任何渠道都不能绕过 SQL、引用和最终输出门禁。

B 不自动等于商业化产品。是否支持真实客户、敏感招投标数据或跨企业租户，需要单独立项和合规评估。

## 3. B 的候选系统边界

```text
网页用户 ───────┐
               ▼
         统一接入与身份层
               │
飞书应用机器人 ─┤
               ▼
        会话 / 请求应用服务
               │
       ┌───────┴────────┐
       ▼                ▼
  AgentGraph       持久化与审计
       │                │
       ▼                ▼
 MySQL / Milvus / LLM  状态、配额、运行记录
```

这里的“统一”不意味着把所有代码写进一个文件，而是两个渠道必须遵守相同的：

- 用户与会话标识；
- 请求状态机；
- 工具权限；
- 超时与取消；
- 引用和输出验证；
- 审计字段。

## 4. 从 A 复用什么、升级什么

| A 阶段资产 | B 阶段处理 |
| --- | --- |
| React 组件和响应式布局 | 复用 |
| TypeScript `StreamEvent` 类型 | 复用并增加版本兼容策略 |
| SSE 解析器与 reducer | 复用，补断线和重连语义 |
| 引用卡片与表格 | 复用 |
| FastAPI `/chat/stream` | 保留契约，补身份、限流和观测 |
| 浏览器生成的临时 `thread_id` | 替换为后端授权的会话标识 |
| 本地会话历史 | 迁移到服务端持久化 |
| 飞书长连接演示 | 根据部署方式决定保留或改 HTTPS 回调 |
| 单进程受控使用 | 增加并发预算、健康检查和优雅关闭 |
| 本地 `.env` | 迁移到部署平台的 Secret 管理 |

## 5. B 必须先做的五个产品决策

### 5.1 谁能访问网页

候选方案：

| 方案 | 优点 | 风险 |
| --- | --- | --- |
| 匿名访客 + 严格限额 | 面试官打开即用 | 容易被滥用，需要验证码或访问码等保护 |
| 飞书登录 | 身份可信，适合组织内使用 | 外部面试官可能不在你的租户或可用范围 |
| 邮箱/第三方登录 | 通用 | 增加账号、隐私和找回流程 |
| 邀请码演示账号 | 边界清楚，实施较轻 | 仍要处理凭据和会话隔离 |

不能因为飞书已接入，就默认网页用户也适合用飞书登录。

### 5.2 哪些数据允许公开

需要逐项确认：

- MySQL 数据是否适合向外部用户展示；
- 法规 PDF 和引用是否允许公开；
- 日志可以保存哪些问题和答案；
- 是否需要脱敏公司、联系人或项目字段；
- 数据保留期限和删除方式。

### 5.3 会话属于谁

浏览器、飞书私聊和飞书群聊不能仅凭字符串拼接就视为同一身份。需要决定：

- 网页用户与飞书用户是否允许绑定；
- 群聊上下文是按群、按话题还是按用户隔离；
- 谁可以读取、导出和删除历史；
- 退出登录或机器人移出群后怎样处理历史。

### 5.4 允许多少成本和并发

需要先设预算，再选择技术：

- 单用户每分钟请求数；
- 单请求最长时间；
- 最大并发 Agent 运行数；
- 每日模型预算；
- 超限时是排队、拒绝还是降级。

只有实际并发证明单进程不够时，再决定是否增加任务队列或更多实例。

### 5.5 飞书使用长连接还是 HTTPS 回调

| 方案 | 更适合 | 主要成本 |
| --- | --- | --- |
| SDK 长连接 | 常驻服务、快速接入、A 阶段延续 | 连接保活、实例归属和重连 |
| HTTPS 事件回调 | 已有稳定公网域名和网关 | 请求验签、加解密、回调时限和部署配置 |

这项选择应由部署环境和运行数据决定，不在方案阶段武断固定。

## 6. B 阶段需要新增的知识

在 A 的基础上分层补充：

### 6.1 身份与授权

- 登录态、Cookie、Token 的区别；
- 身份认证与权限授权的区别；
- 后端为什么不能信任前端传来的 `user_id`；
- 最小权限和租户隔离。

### 6.2 持久化

- 用户、会话、消息、运行记录之间的关系；
- 数据库事务和唯一约束；
- 幂等键；
- 数据迁移、备份和删除。

### 6.3 部署与网络

- 域名、DNS、HTTPS；
- 静态前端与 FastAPI 服务；
- 反向代理；
- SSE 代理缓冲与超时；
- 健康检查和优雅关闭。

### 6.4 安全与滥用防护

- CORS 不是身份认证；
- XSS、Markdown/HTML 安全渲染；
- API 限流和请求体限制；
- Secret 管理和轮换；
- 飞书事件验证、重复投递和自回复循环；
- Prompt Injection 不能获得新的工具权限。

### 6.5 可观测性

- 日志、指标、追踪各回答什么问题；
- 请求 ID、用户 ID、会话 ID、飞书消息 ID怎样关联；
- TTFT、首个有效答案、最终帧和总请求耗时不能混成一个指标；
- 错误率、取消率、空答案率和成本怎样分开统计。

## 7. B 阶段实施顺序

### B0：用 A 的数据决定范围

收集 A 的真实情况：

- 演示中最常用的三类问题；
- 请求耗时、失败和取消情况；
- 飞书权限和事件接入是否稳定；
- 面试官是否真的需要自己打开链接；
- 是否有人提出登录、历史或分享需求。

通过条件：B 的每项需求都有来源，不因为“看起来专业”而加入。

### B1：威胁模型与数据边界

输出：

- 资产清单；
- 用户与信任边界；
- 可公开字段和敏感字段；
- 主要滥用路径；
- 日志保留和删除政策；
- 飞书权限清单。

通过条件：能够回答“如果陌生人拿到 URL，他最多能做什么”。

### B2：身份与会话模型

实施内容：

- 选择网页身份方案；
- 后端生成并授权会话；
- 建立用户、渠道身份、会话、消息和运行记录模型；
- 明确网页与飞书身份是否绑定；
- 增加会话读取和删除权限检查。

通过条件：两个用户无法读取或继续对方会话；伪造 `thread_id` 无效。

### B3：持久化与幂等

实施内容：

- 保存已完成消息与明确终态；
- 技术错误、取消和半截流不能伪装成成功；
- 飞书消息 ID、HTTP 请求幂等键建立唯一约束；
- 建立数据库迁移和备份恢复演练。

通过条件：服务重启后合法历史仍在；重复事件不会重复调用 Agent 或重复发送答案。

### B4：公开部署

实施内容：

- 独立构建前端；
- 部署 FastAPI 常驻服务；
- 配置 HTTPS 和反向代理；
- 确认 SSE 不被代理缓存或错误缓冲；
- 使用部署平台 Secret；
- 增加 readiness、liveness 和优雅关闭。

通过条件：非开发机器可以访问；部署重启不会留下假成功请求。

### B5：飞书生产化

实施内容：

- 根据 B0 数据选择长连接或 HTTPS 回调；
- 固化事件验证、权限、可用范围和版本发布流程；
- 建立消息去重、重试和失败审计；
- 长答案选择摘要、分段回复或消息卡片；
- 不把模型内部工具参数、SQL 或隐私数据发送到群聊。

通过条件：机器人在私聊、群聊、重复投递、回复失败和服务重启场景下行为可解释。

### B6：限流、预算和观测

实施内容：

- 按用户、IP、飞书会话设置限流；
- 设置请求超时、并发上限和每日预算；
- 记录结构化请求状态和渠道；
- 建立错误率、取消率、TTFT、总耗时和成本指标；
- 告警只在有意义的变化或故障时触发。

通过条件：达到上限时系统明确拒绝或排队，不以超时和资源泄漏代替容量控制。

### B7：安全与恢复验收

至少验证：

- 跨用户会话读取；
- 伪造身份或 `thread_id`；
- 高频请求；
- 超长输入；
- 恶意 Markdown/HTML；
- Prompt Injection 申请越权工具；
- 飞书事件伪造或重复；
- 断线、重连、重启；
- 模型、MySQL、Milvus 和飞书部分故障；
- Secret 泄漏扫描和轮换演练。

通过条件：失败有审计、资源能回收、下一次合法请求能恢复。

## 8. B 阶段验收门槛

### 产品

- [ ] 面试官能通过稳定 HTTPS URL 使用核心能力；
- [ ] 网页和飞书输出语义一致；
- [ ] 用户能查看并删除属于自己的历史；
- [ ] 移动端可用。

### 身份与隔离

- [ ] 用户身份由后端可信验证；
- [ ] 会话和历史不能跨用户访问；
- [ ] 飞书私聊、群聊和网页的身份映射规则有文档。

### 稳定性

- [ ] 取消、超时、断开和重启有明确终态；
- [ ] 飞书事件和 HTTP 请求具备幂等保护；
- [ ] 设有并发、速率和成本预算；
- [ ] 关键依赖失败后能够恢复。

### 安全

- [ ] 全链路 HTTPS；
- [ ] Secret 不进入前端、Git 和日志；
- [ ] 飞书只申请最小权限；
- [ ] 模型提议不能绕过工具授权和输出验证；
- [ ] 数据保留、导出和删除规则明确。

### 证据

- [ ] 每个对外声明都能指向实现、测试或监控证据；
- [ ] 一次成功演示不被描述成生产稳定性；
- [ ] 已完成、范围验证和待完成工作分别列出。

## 9. 面试展示如何从 A 升级

A 阶段的表达重点：

> 我把已有 Agent 的统一 SSE 协议接入 React，分别渲染执行阶段、文本、引用和表格；同时通过飞书应用机器人完成第二渠道接入，并针对取消、重复事件和后续请求恢复做了测试。

B 阶段只有通过对应验收后，才能增加：

> 我进一步完成了可信身份、会话隔离、持久化、幂等、限流、部署和可观测性，使网页与飞书在同一安全边界下提供有限公开服务。

不要把“接入登录”“服务能启动”或“一次机器人回复成功”描述成生产验收。

## 10. B 启动门槛

满足以下条件后再启动 B：

- A 的 P0 和异常恢复验收通过；
- 完成至少一次完整面试式演练；
- 确认确实需要外部 URL 或多用户；
- 明确网页访问身份方案；
- 明确允许公开的数据范围；
- 能承担持续部署、模型和数据库成本。

如果这些条件尚未满足，继续打磨 A 通常比扩张架构更有价值。
