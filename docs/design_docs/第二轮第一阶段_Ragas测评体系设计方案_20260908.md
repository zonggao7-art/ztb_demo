# 第二轮第一阶段：Ragas 测评体系设计方案

> 更新日期：2026-09-12  
> 当前状态：S1至S4均已完成。2026-09-12使用DeepSeek官网API和当前S4冻结代码重新完成修正版S1，运行编号为`s1_20260912_formal_03_official`；200题全部正常回答，800个单项评分全部成功。历史OpenRouter版S1继续保留为异常耗时证据。

## 一、这次到底测什么

本次直接测试完整的 `knowledge_qa`。

`knowledge_qa` 不是一个单纯搜索资料的工具。它内部会依次完成：

1. 把问题变成查询向量；
2. 从知识库查找资料；
3. 按当前阶段规定处理和筛选资料；
4. 把最终资料和原始问题交给回答模型；
5. 生成回答，必要时拒答；
6. 返回回答、引用资料和引用检查结果。

因此，检索和回答必须作为同一次 `knowledge_qa` 调用进行测评，不能拆成两套独立流程。

本次不启动 ReAct，不经过意图判断、任务规划或其他业务工具，也不测试已经废弃的 `search_public_kb`。`search_public_kb` 只有检索能力，不能代表真实使用的“检索加回答”流程，也无法产生答案正确性和忠实度所需的实际回答。

```text
固定200题
    ↓ 每次只传入原始 question
knowledge_qa
    ↓ 查询嵌入
本阶段规定的检索步骤
    ↓ 最终0～5条完整资料
knowledge_qa 内部回答模型与内部提示词
    ↓
实际回答、拒答状态、引用资料
    ↓
四项 Ragas 质量评分 + P50/P95端到端查询耗时 + 平均每题 Token
```

## 二、怎样在不启动 ReAct 的情况下调用 `knowledge_qa`

测评程序直接从现有工具注册中心取得 `knowledge_qa`，然后逐题调用。这样保留了正式工具的参数检查、错误处理、回答生成、拒答和引用行为，同时绕过 ReAct。

一次调用只传入：

```text
question = 题集中的原始 question
```

题集中的 `reference`、`ground_truth_chunk_ids`、`ground_truth_text` 和 `query_type` 只供测评与人工检查使用，绝不能进入 `knowledge_qa` 的问题、内部提示词或检索条件。

不在原始问题前后增加任何测评提示词。`knowledge_qa` 内部原有的系统提示词、资料格式、拒答规则和引用要求继续生效，因为它们本来就是被测工具的一部分。

## 三、怎样冻结第一阶段的检索步骤

当前 `knowledge_qa` 默认使用完整检索流程：稠密向量和稀疏检索、RRF 合并排序、重排模型、动态过滤。第一阶段不能直接使用这个默认流程，否则无法建立最简单的起点。

需要在同一个 `knowledge_qa` 内部增加一个只供测评程序设置的“检索阶段”。它只改变检索部分，不改变工具名称、输入参数、回答模型、内部提示词、拒答规则、引用规则和返回格式。

第一阶段固定为：

```text
原始 question
    ↓
查询嵌入模型
    ↓
稠密向量搜索，取30条候选
    ↓
只保留 COSINE 分数不低于0.45的资料
    ↓
按分数取前5条
    ↓
交给 knowledge_qa 内部回答模型
```

固定参数如下：

| 参数 | 第一阶段取值 |
|---|---:|
| 查询方式 | 只用稠密向量 |
| 候选资料数 | 30 |
| 分数类型 | COSINE |
| 固定阈值 | 0.45 |
| 最终资料数 | 最多5条 |
| `nprobe` | 32 |
| 稀疏检索 | 关闭 |
| RRF 合并排序 | 关闭 |
| 重排模型 | 关闭 |
| 动态过滤 | 关闭 |

### 测评设置怎样避免影响正常系统

- 测评程序启动时指定本次阶段，启动后不能在200题中途切换。
- 阶段设置不增加到 `knowledge_qa` 的公开参数中，模型和普通用户不能通过问题修改它。
- 正常系统没有测评设置时，继续使用当前完整检索流程。
- 每个阶段单独启动一个进程，避免上一个阶段留下的内存状态影响下一个阶段。
- 程序在第一题开始前保存本次实际配置；配置与阶段要求不一致时停止运行。
- `knowledge_qa` 的正常返回内容保持不变。测评新增的 Token、批次耗时和评分结果只写入测评文件。

这意味着项目里始终只有一个 `knowledge_qa`，不会复制出第二套 RAG 工具。

## 四、后续怎样逐步放开检索步骤

所有阶段使用相同的200题、相同题目顺序、相同知识库、相同查询嵌入模型、相同回答模型和内部提示词。每次只在前一阶段基础上增加下一组检索能力。

| 阶段 | 实际检索过程 | 与前一阶段相比增加什么 |
|---|---|---|
| S1 | 稠密30条 → COSINE固定阈值0.45 → 前5条 | 最简单的比较起点 |
| S2 | 稠密30条＋稀疏30条 → RRF合并到30条 → 前5条 | 同时加入稀疏检索和RRF |
| S3 | S2 → 重排模型 → 前5条 | 加入重排模型 |
| S4 | S3 → 动态过滤 → 最多5条 | 加入动态过滤，恢复当前完整检索流程 |

S1 到 S2 是一次组合改造。它只能说明“加入稀疏检索并使用RRF合并排序”整体带来了什么变化，不能分别宣称其中某一步贡献了多少。

S2 已经改用 RRF 分数。RRF 分数与 COSINE 分数含义不同，所以 S1 的0.45阈值不能继续套用。S2 直接取 RRF 排名前5条。

S3 使用重排模型重新排序后直接取前5条。S4 再启用当前动态过滤规则，最终资料可能少于5条，也可能为空。

每个阶段完成后先由人工查看六项指标、失败情况和具体题目，再决定是否进入下一阶段。程序不根据某个分数自动放行。

## 五、哪些条件必须保持不变

| 项目 | 固定方式 |
|---|---|
| 题集 | `second_round_eval_data/testset_200.jsonl`，固定200题，不修改、不拆分 |
| 题目顺序 | 始终按文件原顺序逐题执行 |
| 知识库 | 使用已经核对的实验集合；运行期间只读 |
| 查询嵌入模型 | 始终读取项目 `.env` 中的 `EMBEDDING_*` 配置 |
| 回答模型 | 始终读取项目 `.env` 中的 `LLM_*` 配置 |
| 回答方式 | 使用 `knowledge_qa` 内部已有提示词、拒答和引用规则 |
| Ragas 裁判模型 | `REFEREE_MODEL=MiniMax-M3`，地址和密钥从 `.env` 读取 |
| Ragas 评分嵌入模型 | 复用查询嵌入模型 |
| Ragas 版本 | 0.4.3，使用现有 `.venv-eval` 和 `requirements-eval.txt` |
| 运行数量 | 每个阶段完整运行200题，不用小批量成绩代替 |
| 查询运行方式 | 一题完成后再运行下一题，不同时运行多题 |

Ragas 评分不计入查询耗时，可以同时评分4题以缩短等待时间；每道题内部的四项指标仍按固定顺序执行，成绩按题集原顺序保存。

测评结果要记录题集文件校验值、知识库集合、模型名称和所有检索参数。密钥只从 `.env` 读取，不能写入结果文件。

当前题集已经核对为200题，字段为：

```text
question
reference
ground_truth_chunk_ids
ground_truth_text
query_type
```

其中130题为 `single_hop`，70题为 `multi_hop`。五个字段保持原样，不为测评程序修改题集。

## 六、每道题需要保存什么

每道题只保存计算六项指标和人工检查真正需要的内容：

| 内容 | 来自哪里 | 用途 |
|---|---|---|
| 原始问题 | `question` | 调用工具和评分 |
| 标准答案 | `reference` | 检索内容和答案正确性评分 |
| 标准资料及编号 | `ground_truth_text`、`ground_truth_chunk_ids` | 人工回查，不送入工具 |
| 问题类型 | `query_type` | 分组查看 |
| 实际回答 | `knowledge_qa` 的 `answer` | 答案正确性和忠实度评分 |
| 最终资料 | `knowledge_qa` 的 `citations` | 检索内容覆盖率、检索内容精度和忠实度评分 |
| 拒答状态 | `knowledge_qa` 的 `is_refusal` | 记录异常拒答 |
| 运行状态 | 工具是否成功及错误原因 | 区分系统失败与评分失败 |
| Token | 系统各模型调用的实际值或估算值 | 计算平均每题 Token |

### 为什么最终资料已经足够

`knowledge_qa` 的 `citations` 按回答模型实际看到的顺序保存资料，并包含每条资料的完整正文。它与生成回答时使用的是同一组资料。

因此，只保存最终送给回答模型的0～5条完整资料，就足以计算四项质量指标。本轮不保存最初30条候选和中间筛选结果，也不增加另一组检索数据。

`sources` 中的正文可能只是缩略文本，评分时不能使用它。评分统一读取 `citations[].text`。

## 七、六项指标怎样计算

本轮只保留以下六项核心指标，不再增加总分。

| 序号 | 指标 | 它回答的问题 | 所需内容 | 计算者 |
|---:|---|---|---|---|
| 1 | Context Recall，检索内容覆盖率 | 最终资料是否覆盖了标准答案需要的内容 | 原始问题、标准答案、最终资料 | Ragas＋裁判模型 |
| 2 | Context Precision，检索内容精度 | 有用资料是否排在前面，无关资料是否挤占位置 | 原始问题、标准答案、按真实顺序排列的最终资料 | Ragas＋裁判模型 |
| 3 | Answer Correctness，答案正确性 | 实际回答与标准答案是否相符，有没有答错或漏答 | 原始问题、实际回答、标准答案 | Ragas＋裁判模型＋评分嵌入模型 |
| 4 | Faithfulness，忠实度 | 实际回答中的说法是否得到最终资料支持 | 原始问题、实际回答、最终资料 | Ragas＋裁判模型 |
| 5 | P50/P95端到端查询耗时 | 一般查询和较慢查询分别需要多久 | 每道题完整调用 `knowledge_qa` 的耗时 | 测评程序 |
| 6 | 平均每题 Token 消耗 | 完整查询平均消耗多少模型 Token | 200题系统 Token 总数、题数 | 测评程序 |

四项 Ragas 分数各自独立展示，不相加，也不换算成“多少题答对”。即使某个阶段得到满分，也只代表它在这套题和本次评分条件下得到该结果，不自动成为上线结论。

### 为什么评分需要嵌入模型

本轮的 Answer Correctness 固定使用 Ragas 0.4.3 当前定义：

```text
答案正确性 = 75% 事实判断 + 25% 答案语义相似度
```

后面的25%需要把实际回答和标准答案转成向量，因此必须提供评分嵌入模型。它直接复用查询嵌入模型，但只参与离线评分，不参与被测的 `knowledge_qa` 查询。

## 八、P50和P95端到端查询耗时怎样计算

每个阶段按以下顺序运行：

1. 单独启动测评程序，加载本阶段配置、工具和知识库；
2. 对每一道题，在调用 `knowledge_qa` 的前一刻开始计时；
3. `knowledge_qa` 返回回答或错误后立即停止本题计时；
4. 保存本题耗时，然后才开始下一题；
5. 200题全部完成后，再运行 Ragas 评分。

每道题记录的是一次完整工具调用的端到端耗时，包括查询嵌入、检索、回答生成、引用整理、引用检查和工具内部重试。测评程序启动、知识库加载、Ragas评分、报告生成和结果文件写入不计入本题耗时。

正式采集为每道题设置600秒总时限。达到时限后会取消本题调用、记录系统失败，再开始下一题，避免后台调用与后续题目重叠。这个上限只防止无限等待，不改变正常完成题目的实际耗时。

200个耗时从小到大排列，固定使用“最近名次法”计算：

```text
P50 = 排序后的第100个耗时
P95 = 排序后的第190个耗时
```

P50表示一般情况下需要等待多久；P95表示约95%的查询能在多久以内完成。两项共同组成第五项核心指标，同时保留全部200题的原始耗时，便于查看具体慢题。

如果某道题调用失败，仍保存从调用开始到返回错误的实际耗时，并纳入200个耗时的排序，同时单独报告失败数量，避免速度数字掩盖失败。如果整个程序中途停止，本次运行标记为“未完成”，不能作为该阶段正式成绩。

## 九、平均每题 Token 怎样计算

正式计算为：

```text
平均每题 Token 消耗 = 200题的系统 Token 总数 ÷ 200
```

系统 Token 包括本次 `knowledge_qa` 为回答问题实际触发的：

- 查询嵌入模型输入 Token；
- 回答模型输入 Token；
- 回答模型输出 Token；
- 后续阶段新增的在线模型 Token，例如重排模型可统计的输入；
- 因系统重试而重复消耗的上述 Token。

稀疏检索和RRF本身没有调用对话模型，不凭空增加 Token。

回答模型输入已经包含 `knowledge_qa` 内部系统提示词、最终资料和原始问题，不再把这些文字重复计算一次。

### 接口没有返回 Token 时怎么办

1. 接口返回实际 Token 数时，使用实际值；
2. 接口没有返回时，根据这次调用的准确输入和输出文本估算；
3. 每部分都标明是“接口实际值”“估算值”还是“粗略估算”；
4. 估算结果不能伪装成接口实际返回值；
5. 如果调用超时导致部分输出根本没有返回，只统计能够确认或估算的部分，并注明无法确认的部分。

报告列出整批系统 Token、平均每题系统 Token，以及查询嵌入、回答输入、回答输出和后续模型各自的数量。

Ragas 裁判模型和评分嵌入模型的 Token 单独记录，用来了解评分本身消耗了多少，不进入第六项指标。报告不输出人民币单价或人民币成本。

## 十、失败和拒答怎样处理

本题集没有应该拒答的问题。

| 情况 | 记录方式 |
|---|---|
| `knowledge_qa` 正常回答 | 保存回答、最终资料和 Token，进入四项质量评分 |
| `knowledge_qa` 意外拒答 | 记录为“异常拒答”，保留实际空资料或拒答原因 |
| 模型、网络或知识库失败 | 记录为“系统失败”，保留错误类型 |
| 回答为空 | 记录为“空回答”，不使用占位文字代替 |
| 某项 Ragas 失败 | 只记录该项“评分失败”，其他成功分数仍保留 |
| 某项没有足够内容评分 | 记录为“无法评分”，不填0，也不填满分 |

四项质量指标分别按成功评分的题目计算平均值，并同时显示实际数量，例如：

```text
Context Recall：0.xx，有效评分 196/200
```

不同指标可以有不同的有效题数。报告还要显示异常拒答数、系统失败数、空回答数和各项评分失败数，不能只展示平均分。

P50、P95和系统 Token 都以全部200次尝试为范围。失败前已经发生的耗时、模型调用和 Token 也要计入，避免失败较多的阶段看起来反而更快或更省。

## 十一、测评框架需要完成什么

为了启动第一阶段，只需要完成以下工作：

1. **阶段控制**：让同一个 `knowledge_qa` 在测评进程中按 S1、S2、S3、S4 选择检索步骤；正常系统仍走完整流程。
2. **顺序运行**：读取固定200题，按文件顺序逐题调用 `knowledge_qa`。
3. **结果采集**：保存实际回答、最终引用资料、每题端到端耗时、拒答、错误和 Token。
4. **Ragas 评分**：接入四项质量指标，裁判模型读取 `REFEREE_*`，评分嵌入复用 `EMBEDDING_*`。
5. **报告生成**：计算六项指标，展示有效评分数量和各种失败数量。
6. **运行隔离**：每个阶段保存到独立目录，不覆盖其他阶段结果。

正式运行还使用了两项保护：每道查询最多600秒、每项 Ragas 评分最多600秒。评分每4题保存一次结果和评分 Token，意外中断时可从已保存的连续题目继续。

建议每次运行只产生以下文件：

| 文件 | 内容 |
|---|---|
| `manifest.json` | 阶段、题集校验值、知识库、模型名称、检索参数和开始时间 |
| `results.jsonl` | 200题的实际回答、最终资料、端到端耗时、运行状态和 Token |
| `scores.jsonl` | 每题四项 Ragas 分数或失败原因 |
| `summary.json` | 六项汇总指标和各种数量 |
| `report.md` | 供人工查看的简明报告 |

测评文件放在 `second_round_eval_data/runs/<运行编号>/`。原始题集保持不变，密钥不得进入任何结果文件。

## 十二、正式运行前先检查什么

这些检查不调用付费接口，也不使用部分题目的成绩代替正式200题：

- 确认题集恰好200行、五个字段齐全、文件校验值已记录；
- 确认测评程序直接调用 `knowledge_qa`，没有启动 ReAct，也没有调用 `search_public_kb`；
- 确认送入工具的只有原始 `question`；
- 用假数据检查 S1 确实不会调用稀疏检索、RRF、重排和动态过滤；
- 用假数据检查 S2 同时加入稀疏检索和RRF，并且不再使用COSINE阈值0.45；
- 检查200题只能顺序执行，不能同时发起多题；
- 检查 `citations[].text` 与回答模型实际收到的资料一致且顺序一致；
- 检查实际 Token、估算 Token 和评分 Token 不会混在一起；
- 检查失败、异常拒答、空回答和单项评分失败不会被静默删除；
- 检查正常系统未设置测评阶段时仍使用完整检索流程；
- 运行现有相关测试，确认没有改变 `knowledge_qa` 的公开输入和返回格式。
- 确认 MiniMax-M3 评分请求关闭 thinking，只返回 Ragas 需要的结构化结果，并使用 `max_completion_tokens=4096`。

只有这些检查通过，测评程序才具备运行第一阶段的条件。然后完整运行200题，不安排小批量正式测评。

实际实现从正式工具注册表确认 `knowledge_qa` 后，直接调用它注册的完整业务函数。它仍执行原有的查询嵌入、检索、内部提示词回答、拒答和引用流程。测评不经过通用工具线程池外壳，因为该外壳超时返回后，后台线程可能仍在运行并与下一题重叠；绕开这一层才能保证一题真正结束后再开始下一题。这个处理没有拆分检索与回答，也没有改成 `search_public_kb`。
