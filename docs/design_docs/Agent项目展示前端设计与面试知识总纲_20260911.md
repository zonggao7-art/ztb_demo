# 招投标智能助手：项目展示前端设计与面试知识总纲

> 版本：2026-09-11  
> 目标：完成一个适合展示 Agent 能力的前端，并让项目负责人掌握足以应对 Agent/LLM 岗位面试追问的前端、接口和飞书接入知识  
> 非目标：把项目负责人训练成专业前端工程师，或系统学习全部前端知识  
> 文档状态：设计与面试准备大纲；不代表前端和飞书接入已经实现

## 0. 怎样使用这份大纲

本文把知识深度分为三级：

- **M（Must）**：必须能脱稿解释，面试官继续追问一层也不慌；
- **U（Understand）**：理解用途和边界，能结合项目说明，但不要求手写完整代码；
- **O（Optional）**：知道名词即可，除非项目后续真的采用，否则不要主动展开。

你的目标不是背诵 API，而是能够回答四类问题：

1. 为什么前端这样设计；
2. 一次请求经过哪些组件；
3. 为什么选择这种通信方式；
4. 发生超时、取消、断线或重复事件时怎么办。

## 1. 面试定位与设计原则

### 1.1 项目定位

这是一个 Agent 项目，前端是 Agent 能力的展示与交互载体。面试重点仍应落在：

- LangGraph/受约束 Agent 如何组织；
- RAG、MySQL 和工具调用如何形成证据；
- 流式输出、会话状态和失败恢复如何处理；
- 引用、SQL 和最终答案为什么要经过程序门禁；
- 网页和飞书怎样复用同一个业务入口。

前端的价值是让这些能力可见、可操作、可验证，而不是用动画掩盖系统行为。

### 1.2 设计原则

- 前端不直接访问 LLM、MySQL 或 Milvus；
- 所有模型、数据库和飞书密钥只存在后端；
- 网页和飞书只做渠道适配，不复制 Agent 业务逻辑；
- 前端依据结构化事件渲染，不解析自然语言猜测 Agent 状态；
- 不向用户展示模型私有思维链，只展示可解释的阶段和工具状态；
- `final`、`error`、`cancelled` 是不同终态；
- 半截流不能作为成功答案保存；
- 作品集声明必须区分当前实现、范围验证和后续设计。

## 3. 面向作品集的产品设计大纲

### 3.1 目标用户

- 第一目标用户：面试官和技术面试参与者；
- 第二目标用户：希望查询招投标法规、公司、项目或报价信息的受控演示用户；

2. **结构化询价**：展示 MySQL 查询结果和结构化表格；

5. **多轮会话**：同一 `thread_id` 下保持上下文；
6. **失败恢复**：取消、错误或超时后，下一轮仍能正常工作；
7. **飞书渠道**：同一 Agent 能力通过飞书应用机器人提供问答。

### 4.1 前端技术栈

| 技术 | 深度 | 在项目中的作用 |
| --- | --- | --- |
| HTML | M | 页面结构和语义 |
| CSS | U | 布局、响应式和状态样式 |

| TypeScript | M | 约束请求、事件和组件数据 |

| Playwright | U | 验证完整用户流程 |

### 4.2 为什么暂不选择其他工具

#### Next.js：O

当前核心是调用现有 Python 后端的交互式 Agent 页面，没有明确的 SSR、SEO 或 React 全栈需求。Vite 更容易保持前后端边界清晰。若后续出现官网 SEO、服务端 React 或统一全栈部署需求，再评估 Next.js。

#### Redux：O

第一版状态主要围绕一个聊天请求和事件流。`useReducer` 或轻量自定义 Hook 足够解释和测试。只有跨页面、跨模块状态明显膨胀时，再考虑专门状态库。

#### WebSocket：U

WebSocket 适合持续双向通信。当前网页模式是“用户通过一次 HTTP POST 提问，服务器持续推送结果”，SSE 已满足主要方向。飞书 SDK 内部可能使用 WebSocket 长连接收事件，但这与浏览器是否需要 WebSocket 是两项独立决策。

## 5. 一次网页请求的完整数据流

这是必须脱稿解释的核心链路。

```text
1. 用户在 React 输入框提交问题
2. 前端生成或取得当前 thread_id
3. 前端 POST /chat/stream，发送 JSON 请求体
4. FastAPI 用 Pydantic 校验 question/thread_id/deadline_s
5. FastAPI 调用共享 AgentGraph.astream()
6. AgentGraph 产生统一 StreamEvent
7. FastAPI 将每个事件编码为 SSE frame
8. 浏览器用 fetch 取得 Response
9. 浏览器从 response.body 持续读取字节块
10. SSE 解析器处理粘包、拆包和 UTF-8 边界
11. reducer 根据事件类型更新请求与消息状态
12. React 将状态渲染成文字、阶段、引用或表格
13. 收到 final/error/cancelled 后结束本轮
```

必须记住：**网络 chunk 不等于一条业务事件。** 一个 chunk 可能包含多条 SSE frame，一条 frame 也可能被拆到多个 chunk 中。因此浏览器端需要缓冲区，并按空行识别完整 frame。

## 6. API 与流式协议设计

### 6.1 请求模型

当前请求语义：

```json
{
  "question": "招标方式有哪些？",
  "thread_id": "demo-session-001",
  "deadline_s": 60
}
```

你要能解释：

- `question` 是本轮用户输入；
- `thread_id` 用于关联同一会话，不等于可信用户身份；
- `deadline_s` 是本轮总时限，不是前端等待动画时长；
- B 阶段不能信任浏览器随意声明的 `thread_id`，必须加入后端身份与授权。

### 6.2 SSE frame

当前后端每条事件格式类似：

```text
id: request-123
event: token
data: {"type":"token","request_id":"request-123","payload":{"delta":"你好"},"ts":...}

```

空行表示一条 frame 结束。

### 6.3 为什么是 POST + `fetch` 流

- 用户问题、会话 ID 和时限适合放在 JSON 请求体；
- 原生 `EventSource` 构造器主要围绕 URL 建立 GET 连接，无法直接表达当前 POST JSON 请求；
- `fetch` 可以发 POST，并通过 `response.body` 取得 `ReadableStream`；
- 浏览器端使用 `TextDecoder` 增量解码，再做 SSE frame 解析。

面试不要求手写完整解析器，但应能说出“缓冲、按空行分帧、解析 `data`、按 `type` 分发”。

### 6.4 统一事件模型

所有事件共有：

| 字段 | 含义 |
| --- | --- |
| `type` | 事件类型 |
| `request_id` | 本次请求标识 |
| `payload` | 不同事件携带的数据 |
| `ts` | 时间戳 |

常用事件：

| 事件 | 前端行为 | 是否终态 |
| --- | --- | --- |
| `meta` | 初始化本轮元数据 | 否 |
| `stage` | 更新 Agent 阶段 | 否 |
| `token` | 追加回答文字 | 否 |
| `retrieval` | 更新检索进度 | 否 |
| `citations` | 保存并展示引用 | 否 |
| `table` | 保存并展示结构化表格 | 否 |
| `partial` | 展示受控中间结果 | 否 |
| `heartbeat` | 维持连接，不产生正文 | 否 |
| `final` | 完成本轮并发布最终结果 | 是 |
| `error` | 标记技术失败 | 是 |
| `cancelled` | 标记取消或中止 | 是 |

兼容事件 `router/message` 不应成为新前端设计的主要依赖。

## 7. 前端状态与 React 知识

### 7.1 必须理解的状态机：M

```text
idle
  └─ submitting
       └─ streaming
            ├─ succeeded
            ├─ failed
            └─ cancelled
```

错误做法是散落大量 `isLoading/isDone/hasError` 布尔值，因为可能产生“既完成又错误”等非法组合。候选做法是使用联合状态或 reducer，让每个事件触发明确状态转换。

### 7.2 `useState` 与 `useReducer`：M

- `useState`：适合输入框文字、侧栏开关等简单局部状态；
- `useReducer`：适合多种流式事件共同修改消息、引用、表格和终态；
- reducer 输入是“旧状态 + 事件”，输出是新状态；
- reducer 应尽量保持纯函数，便于离线测试。

面试时不需要背 Hook 定义，但要能解释为什么事件流比若干独立布尔状态更适合 reducer。

### 7.3 组件与 props：M

- 组件是可复用的界面单元；
- props 是父组件传给子组件的数据；
- state 是随交互变化的数据；
- 数据通常从父级状态流向展示组件；
- 不让引用组件自己发请求猜数据，而是接收已经解析好的引用对象。

### 7.4 TypeScript 联合类型：M

前端应将事件表达为可区分联合类型。概念示例：

```ts
type StreamEvent =
  | { type: "token"; request_id: string; payload: { delta: string } }
  | { type: "citations"; request_id: string; payload: { citations: Citation[] } }
  | { type: "table"; request_id: string; payload: { records: Record<string, unknown>[] } }
  | { type: "final"; request_id: string; payload: FinalPayload }
  | { type: "error"; request_id: string; payload: ErrorPayload };
```

价值不是“代码更高级”，而是新增或遗漏事件时更容易在开发期发现。

### 7.5 React 列表 key：U

消息列表每项需要稳定 key，帮助 React 正确识别哪条消息发生变化。不能在每次渲染时随意生成新 key，否则可能导致组件状态错位或无谓重建。

## 8. 并发、取消与错误恢复

### 8.1 `AbortController`：M

用户点击“停止生成”时：

1. 前端调用 `AbortController.abort()`；
2. `fetch` 被取消；
3. 后端感知客户端断开；
4. 后端关闭 Agent 流并回收相关任务；
5. 前端将本轮标为取消，而不是成功。

只隐藏加载动画不等于取消请求，上游模型或数据库可能仍在消耗资源。

### 8.2 `request_id`：M

每轮请求要有独立 `request_id`。前端只让当前请求的事件修改当前消息，避免上一轮迟到事件污染新一轮。

需要能回答：`thread_id` 表示会话，`request_id` 表示某一轮执行，两者不是同一个概念。

### 8.3 错误分类：M

| 情况 | 正确语义 |
| --- | --- |
| 业务上证据不足并明确拒答 | 可以是 `final`，因为业务流程完整结束 |
| 模型、数据库或网络故障 | `error` |
| 用户停止或连接取消 | `cancelled` |
| 已收到部分 token 但没有终态 | 不得记录为成功 |

### 8.4 恢复验证：U

重点不是只测一次成功，而是验证：

- 首轮超时后第二轮能否成功；
- 取消后资源是否释放；
- 两个会话并发是否串数据；
- 断流后是否产生假 `final`；
- 心跳是否被误显示为正文。

## 9. 引用、表格与 Agent 可观测性

### 9.1 引用展示：M

- 引用来自 `citations` 结构化事件；
- 前端展示文档名、章节、页码或 chunk 标识等后端提供字段；
- 前端不通过正则从回答正文“猜”引用；
- 点击引用只能展示真实存在、后端允许公开的证据；
- 前端展示引用不等于引用内容一定正确，正确性仍需后端校验和评测。

### 9.2 表格展示：M

- `table` 事件与自然语言回答分开；
- 列名、空值、数字格式和分页应有稳定规则；
- 前端只展示后端已授权返回的字段；
- 不因为数据库存在某字段，就默认可向公网用户展示。

### 9.3 Agent 阶段展示：M

可以展示：

- 正在理解问题；
- 正在检索法规；
- 正在查询结构化数据；
- 正在校验引用；
- 正在组织答案。

不应展示：

- 模型私有思维链；
- 原始 SQL 和敏感工具参数；
- API Key、内部地址或数据库错误堆栈；
- 未经程序授权的工具提议。

## 10. HTTP、浏览器和 FastAPI 知识

### 10.1 HTTP 最小知识集：M

必须理解：

- URL、方法、Header、请求体、状态码；
- JSON 是数据格式，不是通信协议；
- POST 常用于提交请求体；
- HTTP 状态成功不代表 Agent 业务答案正确；
- SSE 使用一个保持打开的 HTTP 响应连续传输事件。

### 10.2 FastAPI 的角色：M

FastAPI 在本项目中负责：

- 暴露 HTTP 路由；
- 用 Pydantic 校验请求；
- 管理共享 Agent 生命周期；
- 将异步 Agent 事件包装成 SSE；
- 感知取消并清理资源；
- 后续可以承载认证、限流和健康检查。

FastAPI 不负责：

- React 页面渲染；
- 决定 Agent 可以调用什么工具；
- 替代 LangGraph；
- 自动保证回答正确。

### 10.3 `async/await`：U

- 异步适合模型、数据库、向量库和网络等 I/O 等待；
- `await` 表示当前协程让出执行权等待结果；
- 异步不等于自动并行，也不等于所有代码都更快；
- 长生命周期共享客户端通常应在稳定事件循环中使用，并在服务关闭时回收。

### 10.4 CORS：M

浏览器前端和 FastAPI 如果协议、域名或端口不同，就属于不同源。浏览器会执行同源策略。

开发期候选：

- Vite 代理 `/api` 到 FastAPI；或
- FastAPI 配置允许指定开发源的 CORS。

生产期更适合通过反向代理提供同源地址。必须记住：**CORS 是浏览器访问控制，不是用户身份认证。**

## 11. 安全知识

### 11.1 密钥边界：M

以下内容不能进入前端：

- LLM API Key；
- 数据库账号密码；
- Milvus 敏感连接信息；
- 飞书 App Secret；
- 管理员 Token。

Vite 中以客户端方式暴露的环境变量会进入浏览器构建产物，不能因为变量写在 `.env` 就认为安全。

### 11.2 XSS 与 Markdown：U

模型回答属于不可信内容。渲染 Markdown 时：

- 不直接使用未经清洗的 HTML；
- 对链接协议和外部资源做限制；
- 不让模型文本触发脚本；
- 表格和引用使用结构化组件，而不是拼接 HTML 字符串。

### 11.3 Prompt Injection 与工具权限：M

前端或飞书消息中的指令不能扩大模型权限。模型可以提出工具调用，但最终允许的工具、SQL 只读规则、次数和输出门禁由程序决定。

### 11.4 公开版额外边界：U

B 阶段还需：

- 身份认证与会话授权；
- 速率限制和每日预算；
- 输入长度限制；
- 日志脱敏与保留期限；
- HTTPS；
- Secret 管理与轮换；
- 用户数据删除能力。

## 12. 飞书接入知识总纲

### 12.1 自定义机器人与应用机器人：M

| 类型 | 核心能力 | 本项目用途 |
| --- | --- | --- |
| 自定义机器人 | 通过 Webhook 向群聊推送消息 | 演示报告或通知，主要是单向 |
| 应用机器人 | 接收消息事件并调用开放 API 回复 | 真正的飞书 Agent 问答 |

不能把“Webhook 能向群里发消息”描述成“飞书中已经可以双向问答”。

### 12.2 飞书双向问答数据流：M

```text
用户发送飞书消息
→ 飞书产生消息事件
→ 应用机器人接收 im.message.receive_v1
→ 飞书适配层解析文本、发送者、会话和消息 ID
→ 映射内部 thread_id
→ 调用统一 Agent 服务
→ 得到 final 或 error/cancelled
→ 调用飞书发送/回复消息 API
→ 用户看到机器人回答
```

### 12.3 权限、事件、可用范围：M

三者不同：

- **权限**：应用被允许调用哪些 API；
- **事件订阅**：飞书把哪些事件交给应用；
- **可用范围**：哪些用户或组织能看到并使用应用。

配置了事件但没有发送消息权限，可能收到问题却无法回复；申请了权限但没有订阅事件，也不会收到用户消息。

### 12.4 长连接与 HTTPS 回调：U

| 方式 | 理解重点 |
| --- | --- |
| 官方 SDK 长连接 | 应用常驻连接接收事件，适合本地/常驻服务候选；需要处理连接生命周期和重连 |
| HTTPS 回调 | 飞书请求公网地址；需要 HTTPS、请求验证、回调时限和部署配置 |

A 阶段可先验证长连接候选；B 阶段根据部署环境决定是否保留。不要把飞书侧的长连接和浏览器侧的 SSE 混为一谈。

### 12.5 幂等和防循环：M

- 飞书事件可能重复投递；
- 使用事件 ID 或消息 ID 做幂等去重；
- 忽略机器人自己发出的消息，避免自问自答循环；
- 同一事件不能重复触发昂贵模型调用；
- Agent 成功但飞书回复失败时，要记录为“生成成功、渠道发送失败”，不能混成一个状态。

### 12.6 飞书会话映射：U

需要明确：

- 私聊可以按用户或聊天映射会话；
- 群聊可以按群、话题或用户隔离；
- `thread_id` 不能只依赖用户可伪造文本；
- B 阶段若网页与飞书账号绑定，需要可信身份映射和授权。

### 12.7 长答案策略：U

飞书不必复刻浏览器逐 token 动画。候选方式：

- 等待最终答案后一次回复；
- 先发送“处理中”，再更新或回复最终结果；
- 长答案分段；
- 使用消息卡片展示摘要、引用和查看详情入口。

具体方案应依据飞书消息限制和实际体验验证后决定。

## 17. 高频面试问题与回答要点

### Q1：这个项目为什么需要前端？

回答要点：

- CLI 适合开发和诊断，不适合面试官直观体验；
- 前端将 Agent 的流式回答、检索阶段、引用和表格可视化；
- 前端是展示层，不改变 Agent 的安全与证据边界。

### Q2：为什么选择 React？

回答要点：

- 界面天然可以拆成消息、阶段、引用、表格等组件；
- 状态驱动渲染适合处理持续到达的事件；
- 生态成熟，但没有引入不必要的全栈框架。

不要回答“因为 React 最先进”。

### Q3：TypeScript 有什么用？

回答要点：

- 将后端事件协议映射为明确类型；
- 不同事件拥有不同 payload；
- 编译期发现遗漏分支和字段误用；
- 不能替代运行时输入校验。

### Q4：Vite 是什么？

回答要点：

- 前端开发与构建工具；
- 提供开发服务器、快速刷新、生产构建和开发代理；
- 它不是运行 Agent 的后端服务器。

### Q5：FastAPI 在项目里做什么？

回答要点：

- 接收浏览器 JSON 请求；
- 校验请求；
- 调用异步 AgentGraph；
- 用 StreamingResponse 输出 SSE；
- 管理 Agent 生命周期和断开清理。

### Q6：一次请求是怎么走的？

回答要点：按第 5 节的 13 步，从输入框讲到终态。至少要说出 React、POST、FastAPI、AgentGraph、SSE、reducer、组件渲染。

### Q7：为什么不用普通 JSON 一次性返回？

回答要点：

- Agent 可能经历检索、工具调用和生成，耗时较长；
- 一次性等待用户体验差，也看不到执行阶段；
- 流式事件能提前反馈进度并逐步展示结果。

### Q8：为什么用 SSE 而不是 WebSocket？

回答要点：

- 当前网页请求主要是一次提交、服务器单向持续返回；
- SSE 建立在 HTTP 上，协议和运维更简单；
- 如果将来需要持续高频双向通信，再重新评估 WebSocket。

### Q9：为什么不用原生 EventSource？

回答要点：

- 当前接口是 POST，并通过 JSON 发送问题和会话参数；
- 原生 EventSource 主要以 URL 建立 GET 连接；
- 因此前端使用 `fetch` 发送 POST，并读取 `ReadableStream`。

### Q10：收到 token 后怎么更新页面？

回答要点：

- SSE 解析器先得到完整 `token` 事件；
- reducer 根据 `request_id` 找到本轮助手消息；
- 将 `payload.delta` 追加到正文；
- React 根据新状态重新渲染。

### Q11：为什么不能每收到一个网络 chunk 就 JSON.parse？

回答要点：

- chunk 是传输分块，不是业务消息边界；
- 一条 JSON/SSE frame 可能被拆开，也可能多条合并；
- 必须使用缓冲区按 SSE 空行分帧。

### Q12：用户怎么停止生成？

回答要点：

- 前端保存本轮 AbortController；
- 点击停止时取消 fetch；
- 后端感知断开并关闭 Agent 生成器；
- UI 标记 cancelled，不把半截回答保存为成功。

### Q13：怎样避免多轮请求串数据？

回答要点：

- `thread_id` 区分会话；
- `request_id` 区分单次执行；
- 前端忽略不属于当前请求的迟到事件；
- 后端每请求清理临时状态；
- 用并发与失败恢复测试验证。

### Q14：业务拒答和系统报错有什么区别？

回答要点：

- 证据不足后按规则拒答，是完整业务决策，可以 `final`；
- 模型、数据库、网络等技术失败是 `error`；
- 用户停止是 `cancelled`；
- 三者在 UI、日志和成功率统计中都应分开。

### Q15：CORS 是什么？

回答要点：

- 浏览器限制不同源页面随意访问接口；
- 开发期可以用 Vite 代理或明确的 CORS 白名单；
- CORS 不是登录，也不能阻止非浏览器客户端直接请求 API。

### Q16：前端怎么保证安全？

回答要点：

- 密钥只放后端；
- 模型内容按不可信输入处理；
- Markdown 安全渲染；
- 前端不能授权工具，真正权限在后端程序；
- 公开版还需要认证、限流和 HTTPS。

### Q17：为什么引用不用从回答文本里提取？

回答要点：

- 文本解析脆弱且可能把模型生成的伪引用当真；
- 后端已有结构化 `citations` 事件；
- 前端按结构化字段显示，关联和验证边界更清晰。

### Q18：飞书怎么接入 Agent？

回答要点：

- 应用机器人订阅消息事件；
- 适配层解析消息并映射内部会话；
- 调用同一个受控 Agent 服务；
- 得到终态后调用飞书回复 API；
- 不在飞书渠道复制一套 Agent 逻辑。

### Q19：自定义机器人和应用机器人有什么区别？

回答要点：

- 自定义机器人通过 Webhook 向群推送，适合通知；
- 应用机器人可以接收事件并调用开放 API，适合双向问答；
- “能推送”不等于“能接收问题并回答”。

### Q20：飞书为什么要做消息去重？

回答要点：

- 事件系统可能因重试产生重复投递；
- 重复事件可能导致重复模型费用和重复回复；
- 按事件或消息 ID 建立幂等记录；
- 同时过滤机器人自身消息避免循环。

### Q21：网页和飞书怎样共享会话？

回答要点：

- A 阶段可以分别映射稳定 `thread_id`；
- 不能直接认为飞书用户就是网页用户；
- B 阶段若要统一，需要可信账号绑定和授权关系。

### Q22：为什么 A 先不做登录和数据库历史？

回答要点：

- A 的目标是验证 Agent 展示和渠道闭环；
- 登录、授权、持久化解决的是多用户公开服务问题；
- 分阶段可以缩小故障面，并用 A 的真实需求决定 B 的投入。

### Q23：如果模型返回恶意 HTML 怎么办？

回答要点：

- 模型输出不是可信 HTML；
- 使用安全 Markdown 渲染并禁用或清洗原始 HTML；
- 引用、表格用结构化组件展示；
- 不允许输出触发脚本或获取浏览器密钥。

### Q24：前端怎样测试？

回答要点：

- 单元测试 SSE 分帧和 reducer；
- 组件测试各种终态和空数据；
- 端到端测试发送、流式、取消、错误恢复；
- 飞书额外测重复事件、回复失败和防循环。

### Q25：这部分代码是你独立完成的吗？

建议如实表述：

> 项目由我独立负责问题定义、技术路线、边界和验收，具体编码大量使用了 AI 辅助。我会检查接口契约、运行测试、分析故障并决定是否接受实现。对前端部分，我重点掌握了它与 Agent 的数据流、流式状态、异常恢复和飞书渠道设计，而不是把自己包装成资深前端工程师。

这比声称所有代码逐行手写更可信，也能把讨论拉回你的决策和验证能力。

## 18. 两个可直接使用的面试版本

### 18.1 60 秒版本

> 这个项目的前端定位不是普通聊天壳，而是展示 Agent 的执行过程和证据。前端计划采用 React、TypeScript 和 Vite，后端复用现有 FastAPI `POST /chat/stream` 接口。FastAPI 调用异步 AgentGraph，并以 SSE 返回 stage、token、citations、table 和 final 等结构化事件。浏览器通过 fetch 发送 POST，再读取 ReadableStream，用事件 reducer 更新回答、阶段、引用和表格。用户停止时会取消请求，error、cancelled 和业务拒答分别处理。飞书侧通过应用机器人订阅消息事件，再调用同一个 Agent 服务回复，避免不同渠道复制业务逻辑。

前端和飞书完成后，把“计划采用”改为“采用了”，并补充真实验证结果。

### 18.2 三分钟版本结构

1. **为什么做**：CLI 不利于面试官直接体验，也无法直观展示流式、引用和工具过程；
2. **怎么分层**：React 负责交互，FastAPI 负责 HTTP/SSE，AgentGraph 负责业务决策，数据和模型仍在后端；
3. **怎么流式**：POST 提交问题，`fetch + ReadableStream` 解析 SSE，reducer 按类型更新 UI；
4. **怎么保证语义**：`final/error/cancelled` 分离，引用与表格走结构化事件，私有思维链不展示；
5. **怎么恢复**：AbortController、request_id 隔离、断流不记成功、失败后下一轮恢复测试；
6. **怎么接飞书**：应用机器人收事件，适配层映射会话，调用统一 Agent，再通过回复 API 返回；
7. **怎么迭代**：A 完成受控作品集，B 再加入身份、持久化、限流和公网部署。

- [ ] 不看文档画出网页请求和飞书请求两条数据流；
- [ ] 60 秒说明技术方案，术语使用准确；
- [ ] 解释 React、FastAPI、AgentGraph 各自边界；
- [ ] 解释 POST SSE 为什么用 `fetch + ReadableStream`；
- [ ] 解释 chunk 为什么不是 frame；
- [ ] 解释 reducer、request_id、thread_id 和三个终态；
- [ ] 解释停止生成不是隐藏加载动画；
- [ ] 解释引用和表格为什么使用结构化事件；
- [ ] 解释 CORS、密钥和 Prompt Injection 权限边界；
- [ ] 解释飞书自定义机器人与应用机器人；
- [ ] 解释飞书事件、回复、去重和会话映射；
- [ ] 说明 A/B 分期理由；
- [ ] 被追问不会的前端细节时，能诚实说明边界并把话题拉回 Agent 集成和验证。
