# 零基础术语表：这些词到底在说什么

> 日期：2026-09-12
> 用途：你在读总纲、A 阶段方案、抓包解读时被术语卡住就翻这里。
> 原则：**每个词都用大白话解释一遍，不假设你有任何前端基础。**

---

## 一、先认识四个"角色"

| 词 | 大白话 | 打个比方 |
| --- | --- | --- |
| **前端** | 你在浏览器里**看得见、点得着**的那部分。网页的样子、按钮、输入框、文字的排版。 | 餐厅的**大堂和菜单** |
| **后端** | 你看不见的那部分。它跑在一台你没见过的电脑上，负责思考、查法规、查数据库。 | 餐厅的**厨房** |
| **浏览器** | 你正在用的 Chrome / Edge。它是**跑前端代码的地方**。 | 你坐的那张桌子 |
| **服务器** | 跑后端代码的那台电脑。 | 后厨那栋楼 |

**关键一句**：你以后要写的 React，是**前端**；项目里已经有的 Python（FastAPI + Agent），是**后端**。这两个是**两台不同电脑上的两套代码**，得靠网络互相喊话。

---

## 二、它们怎么互相喊话

| 词 | 大白话 |
| --- | --- |
| **接口 / API** | 后端**对外开的窗口**。前端只能从这个窗口递话进去、拿答案出来，不能翻进后厨自己炒菜。 |
| **HTTP** | 前后端打招呼的**规矩**。就像寄信有固定格式：收件人、寄件人、内容。 |
| **请求（request）** | 前端**递进去**的那句话。"帮我查一下招标方式有哪些。" |
| **响应（response）** | 后端**递出来**的答案。 |
| **POST** | HTTP 里的一种**动作类型**，意思是"我要**提交**一批数据给你"。本项目用的是 POST。 |
| **JSON** | 一种**写数据的格式**，长得像 `{"问题":"招标方式有哪些？"}`。就是一个键配一个值，人也能看懂。**它不是协议，只是数据长这样。** |
| **状态码** | 后端在信封上盖的**章**。`200` = 收到了、处理了。`422` = 你递的数据格式不对。`500` = 后端自己崩了。 |
| **协议** | 双方约定好的**说话规矩**。前端后端都必须遵守，否则互相听不懂。 |

⚠️ **一个反直觉的点**：状态码 `200` 只代表"通信成功了"，**不代表后端给的答案是对的**。查法规没查到，也算 `200`。

## 三、流式 —— 本项目最核心、也最容易绕晕的部分

### 3.1 什么是"流式"

普通方式：前端问一句，然后**干等**，后端想 11 秒，最后一次性把整段答案丢过来。
流式方式：后端**一边想一边往外说**，前端**一边听一边显示**。

本项目的做法 ≈ **打电话（流式）**，而不是**发短信等回复（一次性）**。

| 词 | 大白话 |
| --- | --- |
| **流式 / 流（stream）** | 数据**分很多次**陆续送过来，不是等全部准备好才一起给。 |
| **SSE** | 一种**专门用来"流式"的通信方式**。全称 Server-Sent Events，服务器持续往外推事件。特点：**只有后端能说话，前端只能听**（本项目正好只需要这样）。 |
| **`text/event-stream`** | 告诉浏览器"我接下来要流式说话"的一个标记。 |

### 3.2 chunk 和 frame —— 你需要记住的最关键一组词

| 词 | 大白话 | 比方 |
| --- | --- | --- |
| **chunk（数据块）** | 网络**每次实际送到你手上**的那一坨字节。送多大、在哪里断开，**是网络和操作系统决定的，跟内容没关系。** | 外卖骑手**每趟能带多少** |
| **frame（帧）** | 后端说的**一条完整消息**。有明确的开头，也有明确的结尾（结尾标志是**一个空行**）。 | 外卖里的**一道菜** |

**一句话记住**：

> **收到几坨（chunk）≠ 有几条消息（frame）。**
> 一坨里可能装着两条半消息，一条消息也可能被拆成三坨送来。

你那次的真实数据：**93 个 chunk → 13 条 frame。**

### 3.3 术语周围的零件

| 词 | 大白话 |
| --- | --- |
| **空行** | frame 的**句号**。后端每说完一条消息，就打一个空行。前端靠"找空行"来判断"这条消息说完了"。 |
| **缓冲区（buffer）** | 前端的**暂存筐**。收到一块就先扔筐里，边扔边找空行；找到空行就说明筐里攒够了一条完整消息，拿出来用，筐清空。 |
| **事件（event）** | 后端说的**每一条消息**。每条消息都带一个"标签"，告诉前端"我这条是干什么用的"。 |
| **心跳（heartbeat）** | 后端在**长时间没话说**的时候，定期喊一声"我还在，别挂电话"。它**没有任何内容**，前端收到后什么都不该显示。本项目默认每 15 秒喊一次。 |

### 3.4 后端会说的 11 种消息（事件类型）

| 标签 | 前端该干什么 | 是不是最后一条 |
| --- | --- | --- |
| `meta` | 记下这一轮的起始信息 | 否 |
| `stage` | 更新"正在干什么"的进度显示 | 否 |
| `token` | 往答案里追加文字 | 否 |
| `retrieval` | 更新检索进度 | 否 |
| `citations` | 保存并展示引用来源 | 否 |
| `table` | 保存并展示表格 | 否 |
| `partial` | 展示中间结果 | 否 |
| `heartbeat` | **什么都不做** | 否 |
| `final` | 结束本轮，发布最终结果 | **是** |
| `error` | 技术出错了 | **是** |
| `cancelled` | 被取消了 | **是** |

**"终态"** = 最后那三种。前端看到终态就知道"这一轮结束了"，可以把输入框解锁了。

## 四、两个容易搞混的身份编号

| 词 | 大白话 | 比方 |
| --- | --- | --- |
| **`thread_id`** | **会话**编号。同一个 `thread_id` 的多轮对话，后端知道它们是一伙的，能记住上文。 | 你这次**打电话**的号码 |
| **`request_id`** | **单次请求**编号。你问的**每一句**都有一个全新的编号。 | 通话里**每一句话**的编号 |

**为什么要分开**：如果上一轮的答复迟到了、跑到这一轮才冒出来，前端靠 `request_id` 就能识别出"这不是我这一轮的，丢掉"。不然上一轮的答案会插到这一轮里，页面就串了。

## 五、安全与调试

| 词 | 大白话 |
| --- | --- |
| **密钥 / API Key** | 调用大模型要付钱的**凭证**，相当于银行卡密码。**只能放后端**，放前端等于把密码贴在菜单上。 |
| **`.env`** | 存放密钥的**本地文件**。它被 `.gitignore` 排除，意思是"不会上传到代码仓库"。 |
| **CORS** | 浏览器的一条**安全限制**：网页只允许访问"和它同一个来源"的接口，否则拦下来。前端和后端端口不一样就会撞上。⚠️ **它只是浏览器的规矩，不是身份验证**——用 curl 这类工具绕过它易如反掌。 |
| **curl** | 一个**命令行工具**，可以手打一条命令就当一次浏览器用。A0 就靠它。 |
| **同源** | 协议、域名、端口**三者完全相同**才算"同源"。`localhost:5173` 和 `localhost:8000` **不同源**（端口不同）。 |

## 六、以后会用到的东西（现在只要知道它是什么）

| 词 | 大白话 |
| --- | --- |
| **React**（本项目里指前端的那个） | 一个**写网页的工具**。核心思路：把页面拆成一个个小零件（"组件"），每个零件管自己那一小块。⚠️ 注意和 **ReAct**（Agent 的思考模式）是同形不同义的词。 |
| **TypeScript（TS）** | JavaScript 的**加强版**，多了"类型检查"：写错字段名会在开发时就报错，而不是等用户点了才崩。 |
| **Vite** | 前端代码的**运行和打包工具**。开发时帮你起个本地小服务器，改代码立刻刷新。 |
| **FastAPI** | 本项目后端的**窗口层**。负责接收前端的请求、校验格式、然后把 Agent 的结果流式送回去。 |
| **uvicorn** | 真正**把 FastAPI 跑起来的那个程序**。 |
| **Agent / AgentGraph** | 后端的**大脑**。决定这次要不要查法规、要不要查数据库，最后组织出答案。 |

## 七、A0~A7 是什么

A 阶段方案的**八个施工步骤**，A0 是第 0 步，A1~A7 依次往后。**不是八个知识模块，是八个动手任务。**

| 步骤 | 大白话 | 要不要写代码 |
| --- | --- | --- |
| **A0** | **先听**：把后端当成一个黑盒子，先搞清楚它到底会说什么 | ❌ 完全不写代码 |
| A1 | 把后端说的格式**抄成前端的说明书**（类型定义） | 写一点点 |
| A2 | 搭**页面的空壳子**，用假数据看长什么样 | 写页面 |
| A3 | 让页面**真的连上后端** | 核心一步 |
| A4 | 把引用、表格做成正经的展示组件 | 写页面 |
| A5 | 接入飞书，让飞书里也能问 | 写适配层 |
| A6 | 故意制造各种故障，验证页面表现正确 | 测试 |
| A7 | 包装成作品集 + 练面试说辞 | 写文档 |

## 八、A0 到底是干什么的（单独说清楚）

A0 **不是模拟**，恰恰相反——它用的是**真实的后端、真实的数据库、真实的大模型**。

它做的事情只有一件：**在写任何前端代码之前，先用最简单的工具把后端"听"一遍，录下来。**

**为什么必须这么干**：前端的工作是"把后端说的话翻译成人能看的样子"。
如果连后端会说什么都不知道，你根本没法设计前端——你会一边写页面一边猜后端，猜错了就返工。

**为什么用 curl 而不是浏览器**：因为你还没有浏览器端的东西可听。curl 相当于"**手打版的浏览器**"，能替你发一次同样的请求。

**为什么 A0 的结论以后不作废**：后端的行为**不会因为你换了客户端而改变**。今天 curl 收到的 13 条消息，以后 React 收到的还是这 13 条。所以 A0 听到的东西，就是 A3 要对接的契约。

---

## 九、你现在不需要记住任何术语

真的。第一次抓包看不懂是**正常状态**，不是能力问题。

建议的用法：**先记住"chunk ≠ frame""心跳是来报活的""迟到的消息靠 request_id 丢掉"这三句**，
其他词卡住了就翻回来查。等你真正开始写页面（A2/A3），这些词会自己变成常识——
因为那时候你需要用它，而不是背它。
