## 1. 你连踩了三个坑，都不是浪费

### 坑 1：PowerShell 吃掉了 JSON 的双引号

第一次请求返回：

```json
{"detail":[{"type":"json_invalid","loc":["body",1],"msg":"JSON decode error",
 "input":{},"ctx":{"error":"Expecting property name enclosed in double quotes"}}]}
```

这不是后端的问题。PowerShell 里用**单引号**包 JSON 传给原生 exe 时，内层双引号会被剥掉，
后端收到的不是合法 JSON。

**修法（推荐）**：请求体写文件，用 `--data-binary @file`，彻底绕开引号地狱：

```powershell
'{"question":"招标方式有哪些？","thread_id":"demo-001","deadline_s":60}' | Out-File -Encoding utf8 request.json
curl.exe -s -N -X POST http://127.0.0.1:8000/chat/stream -H "Content-Type: application/json" --data-binary "@request.json" -o raw_sse.txt
```

你第二次用 `\"` 转义也能成，但那是让 shell 去猜，脚本一多就崩。

### 坑 2：不加 `-s`，进度条会糊在正文上

你屏幕上那串 `% Total % Received ... Dload Speed` 和 `id: .../event: ...` 交错的东西，
就是 curl 的进度表（走 stderr）和正文（走 stdout）在终端里互相插队。

加 `-s` 就干净了。**注意**：这次它只糊了屏幕，没进文件——`Tee-Object` 只接管了 stdout，
你算是运气好。

### 坑 3（最阴）：`Tee-Object -FilePath` 默认写 UTF-16LE

这是本次最有价值的一个坑。

你那份 `raw_sse.txt` 开头两个字节是 `FF FE`，之后**每个字符后面都跟一个 `\x00`**。
也就是说字节流里根本没有 `\n\n`，只有 `0a 00 0a 00`。

结果就是：**一个完全正确的 SSE 解析器，在这份文件上返回 0 帧。**

```text
LF-LF      出现 0 次
CRLF-CRLF  出现 0 次   （在原始 UTF-16 字节流里）
```

这跟前面两个坑性质不同。前两个是"命令写错了"，这个是：

> **抓包工具把数据改了，看起来却像代码有 bug。**

分不清"数据错"和"代码错"，是排障时最贵的一种错。
这次还好，`03_read_sse_timeline.py` 会直接把它喊出来——**解析器没问题，需要修的是抓包方式。**

顺带一个副产品：PowerShell 还顺手把 `LF` 换成了 `CRLF`。修复后统计是
`CRLF-CRLF x13 | LF-LF x0`，13 个分隔符对应 13 帧，严丝合缝。
**这也是为什么解析器必须同时支持 `\n\n` 和 `\r\n\r\n`**——现实里两种都会出现。

## 2. 这份输出的全貌

93 个网络 chunk → **13 条业务帧**。这就是"chunk ≠ frame"用你自己的数据给出的证明。

| # | 事件 | 距上条 | 距开始 | 字节 | 载荷摘要 |
| ---: | --- | ---: | ---: | ---: | --- |
| 1 | `meta` | — | 0.000s | 158 | `mode=unified` |
| 2 | `stage` | 0.003s | 0.003s | 129 | `agent_start` |
| 3 | `stage` | 0.836s | 0.838s | 190 | `tool_call` `tool=knowledge_qa` `running` `s1` |
| 4 | `stage` | **9.991s** | 10.829s | 198 | `tool_call` `done` `ok=true` ← **静默 10 秒** |
| 5 | `stage` | 0.852s | 11.682s | 152 | `agent_finish` `complete` |
| 6 | `stage` | 0.000s | 11.682s | 134 | `validation_start` |
| 7 | `stage` | 0.001s | 11.683s | 134 | `validation_done` |
| 8 | `token` | 0.002s | 11.685s | 349 | 80 字符 |
| 9 | `token` | 0.000s | 11.685s | 351 | 80 字符 |
| 10 | `token` | 0.000s | 11.685s | 355 | 80 字符 |
| 11 | `token` | 0.000s | 11.685s | 243 | 43 字符 |
| 12 | `citations` | 0.000s | 11.685s | **19,959** | 5 条引用 / 2 个文档 / 原文共 5880 字符 |
| 13 | `final` | 0.001s | 11.686s | **24,598** | `answer` 283 字符 + 完整 `business_result` |

首帧到终态：**11.686 秒**。载荷总量 46,950 字节，**最大一帧占 52%**。

### 怎么读一条 frame

每条帧固定三行 + 一个空行：

```text
id: d9a85c2ba3254a2c9dc6bbb307c733fd
event: stage
data: {"type":"stage","request_id":"...","payload":{...},"ts":1789202590.772476}

```

- `id` = `request_id`，本轮请求身份
- `event` = 事件类型（给 `addEventListener` 用的名字）
- `data` = JSON，**业务数据全在这里**。`event` 和 `data.type` 是重复的（协议冗余，方便前端两种取法）

> 注意 `data` 里的 `payload` 才是内容，外层 `type/request_id/ts` 是信封。
> 写 reducer 时该读 `payload`，不是整个 `data`。

## 3. 四个关键发现

### 3.1 静默 10 秒 —— 而心跳一次都没来

第 3 帧（`tool_call running`）到第 4 帧（`tool_call done`）之间隔了 **9.991 秒**，
期间**一个字节都没有**。

这就是心跳存在的理由。而 `service/api.py:113` 读的心跳间隔默认是 **15 秒**：

```python
idle_seconds = getattr(agent._settings, "stream_heartbeat_s", 15)
```

静默 10 秒 < 15 秒，所以 **heartbeat 一次都没触发**。

**对前端意味着什么**：用户点完发送，第 0.8 秒看到"正在检索"，然后**盯着屏幕 10 秒毫无动静**。
如果你不在前端本地做计时/进度提示，用户会以为页面卡死了，然后去点刷新。

**面试点**：心跳不是"给用户看的进度"，而是"防代理和浏览器判定连接已死"。
真要让用户知道"还在干活"，得前端自己解决。

### 3.2 ★ token 不是模型实时输出，是校验后按 80 字符重放

第 8~11 帧四条 `token`，**时间戳完全相同**（都是 `1789202602.4547353`），
而且长度正好是 80 / 80 / 80 / 43。

证据在 `agent/graph.py:524-556`：

```python
async for kind, item in events:
    if kind == "custom":
        event = normalize_custom_event(item, request_id)
        if event.type is EventType.STAGE:   # ← 只放行 STAGE
            yield event
    ...
if not result or "execution_status" not in result:
    raise RuntimeError("incomplete_stream")
# All tokens/citations/tables below are derived from the committed verified result.
answer = result["answer"]
for offset in range(0, len(answer), 80):    # ← 按 80 字符切片重放
    yield make_event(EventType.TOKEN, request_id, {"delta": answer[offset:offset + 80]})
```

也就是说，在受控路径下：

1. 图内部**真实**的模型 token 事件被**主动丢弃**（`if event.type is EventType.STAGE` 只放行阶段）；
2. 等整个结果**通过校验**后，把已提交的 `answer` **按 80 字符切片**，一晚推给前端；
3. 所以四条 token 共享同一个时间戳。

**这是设计，不是 bug。** 理由写在那一行注释里：所有 token / 引用 / 表格都**源自已提交且已验证的结果**。
如果直接透传模型原始输出，用户就会看到还没过引用校验的内容——那等于绕过了程序门禁。

**这只影响一件事，但影响很大**：前端的"逐字打字机"动画是**表演**，不是复刻真实 token 流。
面试时如果说"我实现了逐 token 流式渲染模型输出"，被追问一句"你怎么保证流出去的内容已过引用校验"
就会很难看。准确的说法见 §4。

### 3.3 传输量 95% 是引用原文和 final 重复

| 内容 | 字节 | 占比 |
| --- | ---: | ---: |
| 4 条 token（真正的答案文字只有 283 字符） | 1,298 | 2.8% |
| `citations`（5 条引用，含**原文全文**） | 19,959 | 42.5% |
| `final`（answer + 完整 business_result，**把前面全又传了一遍**） | 24,598 | 52.4% |

**为了 283 个字符的答案，你传了 46,950 字节。**

两个具体后果：

- `citations` 帧里带着 chunk 的**完整原文**（单帧 8,047 字符），前端不该原样渲染，应该只取
  `doc_name` / `chapter` / `page_number`，正文放进抽屉里按需展开；
- `final` 帧把 `answer` 传了**两次**（`payload.answer` 和 `payload.business_result.answer`），
  还顺带把 citations 又带了一遍。冗余是刻意的（final 要自包含，方便重放和归档），
  但前端 reducer 要**认准其中一个来源**，否则你会得到两份状态。

### 3.4 校验发生在第一个 token 之前

看帧序：第 6 帧 `validation_start` → 第 7 帧 `validation_done` → 第 8 帧才是第一个 `token`。

`final` 里的 `citation_validation` 显示门禁全部通过：

```json
{"all_passed": true, "is_refusal": false, "context_chunks": 5,
 "cited_markers": [1,2,4,5], "uncited_chunks": [3], "unknown_markers": [],
 "rules": [R1 chunk_id 完整性 ✓, R2 chunk_uid ✓, R3 数据源可定位 ✓,
           R4 原文片段完整 ✓, R5 上下文无遗漏引用 ✓, R6 引用标记有效 ✓,
           R7 全部被标记引用 — enabled=false]}
```

引用顺序也对得上：答案里的【来源1】【来源2】【来源4】【来源5】正好是 `cited_markers`，
而 chunk 3 没有被引用（R5 允许，R7 严格模式被关掉了）。

**这就是总纲 §9.1 说的"引用正确性仍需后端校验"，在你自己的数据里跑通了。**
前端拿到的 `citations` 是**已经过门禁的结构化字段**，不需要也不应该去正文里正则提取。

## 4. 一个必须记下来的坑：`request_id` 有两套，值还不一样

同一个 `final` 帧里：

| 位置 | 值 |
| --- | --- |
| 信封 `request_id`（也是每条帧 `id:` 行） | `d9a85c2ba3254a2c9dc6bbb307c733fd` |
| `payload.business_result.execution.request_id` | `59f36fcfe00a46738b84fa57882243d7` |

**两个不同的 ID。**

前端 reducer 一定会按 `request_id` 过滤"是不是本轮的迟到事件"（总纲 §8.2）。
如果你从 `business_result.execution.request_id` 取值，就会和信封对不上，
轻则本轮事件全被丢弃（页面永远转圈），重则跨轮污染。

**当前唯一可靠的判定基准是信封层（`event.request_id` / `id:` 行）。**
这个不一致值得记进待修清单。

## 5. 面试怎么说（把发现转成表述）

**不能说**：

> 前端接收模型逐 token 流式输出，实时渲染打字机效果。

**应该说**：

> 后端的流式分两类事件。`stage` 是图执行期间实时产出的，前端用它渲染可观测的执行阶段。
> 而 `token` 是**门禁通过之后**、由已提交结果按 80 字符切片重放的，这样流到前端的每个字都
> 已经过引用校验，不会出现"先给用户看、事后才发现引用是编的"。
> 代价是答案不是逐字实时到达，所以前端不用打字机动画伪装实时性，而是按块渲染。
> 另外静默期实测可达 10 秒，超过心跳间隔 15 秒的行为边界之外，前端必须自己给等待反馈。

这段话一次覆盖了总纲 §16.1 里的"为什么不展示原始思维链""引用为什么用结构化事件"
"`final/error/cancelled` 的语义"三条，而且是**你亲手测出来的**。
