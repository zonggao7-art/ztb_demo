# 统一 Agent 任务执行与结束状态规则

> 状态：已采纳，首版程序边界已实现并完成离线回归  
> 决策日期：2026-09-14  
> 决策来源：第三轮 ReAct 正式测评失败复盘后的用户确认  
> 适用范围：当前单轮边界下的统一 Agent、六个只读授权工具，以及后续修复与回归题集  
> 不适用：不追溯改写 `third_round_formal_20260912_01` 与 `third_round_reliability_formal_20260912_01` 的冻结结果

## 一、总原则

只有查询对象、查询目的和参数来源都明确时，系统才可以执行业务工具。

能安全拆分且互不依赖的明确子任务可以部分执行；缺失信息会改变查询主体、查询范围、结果解释或依赖对象时，系统不得猜测。后续参数只能来自本轮用户原文或本轮已核验工具结果，并且必须满足精确性与唯一性要求。

以下判断优先于“尽量帮助用户完成任务”：

1. 不为了减少一次澄清而猜测查询范围或主体。
2. 不因为字符串出现在用户问题中，就自动认为它是完整、合法、语义正确的工具参数。
3. 不因为上游结果中出现了某个字段，就自动认为该字段是唯一可用于下游的值。
4. 不通过修改阈值、忽略失败样本或迁就现有题集来替代产品规则。

## 二、工具执行前的统一判断

每一个拟执行动作都必须依次满足：

1. **能力明确**：用户要求能够映射到六个授权工具中的一个具体能力。
2. **主体明确**：公司、项目编号或法规问题具有唯一且足够精确的表达。
3. **范围明确**：诸如“相关情况”“风险”“比较”等表达已经细化为可执行维度。
4. **来源合规**：参数来自本轮原文或本轮已核验结果，而不是历史对话、模型补全或未经核验的推断。
5. **依赖唯一**：依赖上游结果的动作只有一个符合要求的候选，或者用户已经明确要求处理全部候选。
6. **请求合规**：请求不要求绕过引用、伪造结论、保证资格、混淆主体角色或突破能力边界。

任一必要条件不满足时，不得执行对应工具。系统应根据下文规则选择 `clarify`、`unsupported` 或在已经完成其他独立任务时选择 `partial`。

## 三、五项正式产品口径

### 3.1 模糊请求

“查一下某公司”“查询相关情况”“看看风险”“比较两家公司”等表述，如果没有明确查询维度，系统应返回 `clarify`，且在获得明确范围前不调用工具。

可直接执行的表达包括但不限于：

- 查询某公司的工商信息；
- 查询某公司的经营范围；
- 查询某公司的处罚记录；
- 查询某公司作为中标供应商的历史；
- 查询明确项目编号的中标情况；
- 回答内容明确的法规问题。

“风险”不能默认等同于“行政处罚”，“相关情况”不能默认等同于工商、经营范围、处罚和中标历史的全集，“比较”必须先明确比较维度。

### 3.2 部分任务缺少参数

多个子任务能够独立成立、结果互不依赖且不会因缺失部分而产生误导时，系统可以执行已经明确的子任务，并以 `partial` 结束，同时列出尚缺信息。

下列情况不得部分执行：

- 缺失参数会改变整个任务的比较、排序或筛选口径；
- 后续动作依赖尚未完成的前序动作；
- 已知部分的单独结果容易被误解为完整结论；
- 用户表达了全有或全无的交付要求。

因此，“查询某公司的工商信息，并回答一个完整法规问题”在公司名称缺失时，可以只回答独立法规问题并返回 `partial`；“比较两家公司”缺少比较维度时，不应先查询两家公司全部信息。

### 3.3 上游返回多个候选

当用户使用单数表达，例如“再查询该中标供应商的工商信息”，而上游返回多个不同供应商时，系统必须停止下游执行并返回 `clarify`。

只有在以下条件之一成立时，才能处理多个候选：

- 用户在本轮明确要求“所有”“全部”“分别查询”；
- 上游结果虽有多条记录，但下游目标字段去重后只有一个值；
- 后续已经通过用户澄清指定了目标候选。

不得任意选择第一条、金额最高者、排序靠前者，也不得在用户使用单数表达时擅自遍历全部候选。

### 3.4 复合主体与联合体

用户使用逗号、顿号、“和”“以及”等连接多个公司名称时，默认解释为多个独立主体，并分别执行对应查询。

只有在用户明确使用“联合体”“共同中标主体”等表达，或者输入本身具有经过核验的联合体整体标识时，才把完整组合字符串作为一个查询主体。

数据库中恰好存在一个以逗号连接的 `successful_bidder` 字段，不能单独证明用户本轮想查询该联合体整体。数据存储形式不能替代用户意图判断。

### 3.5 字段为空

工具成功执行、精确记录存在，但目标字段为 `NULL` 或空值时，系统应：

- 如实输出“记录存在，但该字段未收录”；
- 将本次查询标记为 `complete`；
- 不把字段为空描述成查无主体、工具失败或现实中不存在；
- 不自动调用其他工具补猜该字段。

这里的 `complete` 表示本轮授权查询已得到真实终态，不表示用户期望的信息一定存在。只有工具失败、仍有可执行任务未完成或实际执行被中断时，才使用 `partial`。

## 四、结束状态定义

| 状态 | 唯一含义 | 是否允许已有工具结果 |
|---|---|---|
| `clarify` | 能力受支持，但必要主体、范围、参数或候选选择尚不明确 | 原则上无；已有独立任务已完成时改用 `partial` |
| `unsupported` | 即使参数完整也不属于授权能力，或请求要求绕过安全、证据与角色边界 | 不允许为满足该请求而调用工具 |
| `partial` | 至少一个授权子任务已经完成，但其他独立子任务缺参数、失败或无法继续 | 允许，且必须明确已完成与未完成部分 |
| `complete` | 所有明确且受支持的任务都到达真实终态 | 允许；精确无匹配和字段为空也可属于真实终态 |

结束状态必须由程序根据已执行动作、结果状态、缺失字段和依赖关系复核，不能只依赖模型自行选择。

## 五、精确参数的横向规则

项目编号、企业名称和其他精确标识不得由模型静默删改、补全或改写。

系统后续应同时保留：

- 用户原始值；
- 程序按冻结规则得到的规范化值；
- 采用了哪些规范化步骤；
- 工具最终实际使用的值。

格式规范化只能由确定性程序完成。对于项目编号末尾的“号”、括号、空格和连接符，应先审计数据库实际分布，再冻结统一规则。当前的子串包含关系不能单独作为精确参数授权依据。

## 七、后续执行边界

下一阶段应先根据本规则形成新的回归用例和预期结果，再讨论实现方案。不得直接覆盖第三轮题集、阈值、运行产物或失败基线。

在获得实现授权前，只允许：

- 检查相关代码和数据分布；
- 建立失败样本到规则条款的映射；
- 提出可选实现路径及其风险；
- 设计新运行编号和回归范围。

不得在本规则记录阶段直接修改统一 Agent、工具、数据库或评分器。

## 八、首版实现记录（2026-09-14）

用户明确授权“开始实现”后，已在不修改第三轮冻结题集、正式阈值、历史运行产物和评分器的前提下完成首版落地：

1. 新增 `agent/execution/request_policy.py`，在模型调用前对高置信度模糊请求、缺参请求和越界请求给出确定性的 `clarify/unsupported` 终态；命中后模型调用数和工具调用数均为零。
2. `agent/execution/unified.py` 不再以“参数是用户问题的任意子串”作为授权条件。公司主体和项目编号改为完整当前轮参数绑定；项目编号末尾的“号”不会被静默删除。
3. 后续公司参数只允许来自本轮已核验记录的 `successful_bidder`，项目参数只允许来自已核验的 `project_number`；多个不同候选在用户未明确要求全部处理时以 `ambiguous_dependency` 拒绝下游执行。
4. 逗号、顿号、“和”“与”“以及”连接且可拆出多个完整主体时，组合参数默认被拒绝，要求逐主体调用；明确联合体表达仍保留整体查询入口。
5. 工具回执新增 `input_binding` 审计信息，记录字段、来源、原始值、规范化值、规范化步骤与最终执行值。首版没有对项目编号做字符格式归一化，只允许原值精确传递；复合主体拆分是当前唯一记录的确定性转换。
6. 结束动作增加程序复核：预先识别到的独立缺参项、未完成的明确能力、真实工具失败均可把模型的 `complete` 降为 `partial`；经营范围记录存在但字段为空时，程序把错误的 `partial` 修正为 `complete`。
7. 统一执行策略版本由 `agent-loop-v2 / unified-agent-v2` 更新为 `agent-loop-v3 / unified-agent-v3`，便于后续运行区分规则版本。
