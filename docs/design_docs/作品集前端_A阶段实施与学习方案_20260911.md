# 招投标智能助手：作品集前端 A 阶段实施与学习方案

> 版本：2026-09-11  
> 面向对象：没有前后端基础、希望在面试中完成真实项目演示的独立开发者  
> 文档性质：讨论稿；记录边界和决策点，不等于已完成实现  
> 后续阶段：[公开使用版 B 阶段升级方案](./公开使用版_B阶段升级方案_20260911.md)

## 1. A 阶段解决什么问题

A 阶段不是“画一个聊天页面”，而是完成一个**可重复、可解释、可恢复的作品集演示闭环**：

1. 面试官能在浏览器里向真实 Agent 提问；
2. 页面能实时展示执行阶段、增量回答、引用和表格；
3. 超时、拒答、取消和服务错误有不同的显示；
4. 可以在飞书里向应用机器人发送问题并得到回复；
5. 演示者能解释浏览器、FastAPI、AgentGraph 和飞书之间的数据流；
6. 所有演示结论都能区分“已经实现”“本次验证通过”和“尚未完成”。

### 1.1 A 阶段的使用边界

- 使用场景：本人本地演示、屏幕共享、受控网络环境下的面试演示。
- 用户规模：单用户或极少量受控用户。
- 数据：继续使用当前 MySQL、Milvus 和模型服务，不复制生产数据到浏览器。
- 会话：先满足当前演示会话；是否持久化到数据库留到 B 阶段。
- 飞书：优先验证“飞书应用机器人问答”；权限受限时，降级为自定义机器人单向推送。
- 安全：密钥只放后端环境变量，不进入 Git、浏览器代码、截图或演示材料。

### 1.2 A 阶段明确不做

- 注册、登录和多租户权限；
- 面向公网的匿名无限访问；
- 管理后台；
- 计费；
- 大规模并发与高可用；
- 当前仍为占位能力的文档问答前端；
- 把模型原始思考过程直接展示给用户；
- 为了视觉效果绕过程序的引用、SQL 或输出安全边界。

## 2. 先建立一张系统地图

### 2.1 浏览器链路

```text
React 页面
  │  POST /chat/stream：question + thread_id + deadline_s
  ▼
FastAPI service/api.py
  │
  ▼
AgentGraph
  │
  ├─ MySQL 结构化查询
  ├─ Milvus 法规检索
  └─ LLM 生成与受控工具执行
  │
  ▼
SSE：meta / stage / token / citations / table / final / error / cancelled
```

FastAPI 是后端接口层，不负责画页面。React 是浏览器界面，不应持有数据库或模型密钥。

### 2.2 飞书链路

```text
飞书用户
  ▼
飞书应用机器人
  ▼  消息事件 im.message.receive_v1
飞书适配层
  ▼
同一个受控 Agent 服务入口
  ▼
最终答案 / 引用摘要
  ▼  回复消息接口
飞书会话
```

飞书适配层只能转换渠道协议，不应复制一套业务逻辑，更不能绕过 Agent 的输出门禁。

### 2.3 飞书的两条路线

| 路线 | 能力 | 适合场景 | 限制 |
| --- | --- | --- | --- |
| 自定义机器人 Webhook | 向群聊推送文本、富文本等消息 | 发送演示报告、错误通知 | 主要是单向推送，不等于聊天机器人 |
| 飞书应用机器人 | 接收消息事件、调用发送/回复消息接口 | 在飞书中直接向 Agent 提问 | 需要创建应用、配置机器人能力、权限和可用范围 |

截至本文核对时间，飞书官方 Python SDK包含事件订阅和 `lark.ws.Client` 长连接示例。A 阶段可把长连接作为本地演示候选，因为它不要求我们先设计完整的公网回调服务；正式实施前仍要在你的飞书租户中验证应用创建权限、事件配置和可用范围。

如果无法创建应用机器人，A 阶段不会伪造“双向飞书问答”。届时改做：网页完成问答后，将结果摘要通过自定义机器人 Webhook 推送到指定群聊。

## 3. 候选技术基线

这是一套待你确认的候选组合，不是已经替你完成的架构决策。

| 层 | 候选工具 | 作用 |
| --- | --- | --- |
| 前端语言 | TypeScript | 为请求、事件和组件属性提供类型检查 |
| 前端框架 | React | 组织聊天、阶段、引用和表格组件 |
| 构建工具 | Vite | 开发服务器、构建和开发代理 |
| 样式 | CSS Modules 或 Tailwind CSS，二选一 | 保持视觉规则一致 |
| 后端接口 | 现有 FastAPI + Uvicorn | 暴露流式 HTTP 接口 |
| 流式协议 | 现有 SSE envelope | 浏览器增量接收 Agent 事件 |
| 飞书 | 飞书应用机器人 + 官方 Python SDK | 收取消息事件并回复 |
| 前端测试 | Vitest + React Testing Library | 测事件归约和组件状态 |
| 端到端测试 | Playwright | 模拟用户提问、取消和错误恢复 |

第一版不需要 Next.js、Redux 或 WebSocket。若后续需求证明它们有明确价值，再单独决策。

## 4. 你需要补到什么程度

目标不是先学完一门“前端课程”，而是在每个实现阶段补足能解释和排错的知识。

### 4.1 浏览器基础

你需要能回答：

- HTML、CSS、JavaScript 各负责什么？
- 浏览器为什么不能直接导入并运行 Python Agent？
- 点击发送按钮后，数据经过了哪些层？
- 为什么 API Key 不能放在前端？

完成标准：可以用自己的话画出第 2 节的数据流。

### 4.2 React 与 TypeScript

只先学习以下内容：

- 组件、属性、状态；
- 列表渲染和条件渲染；
- `useState`、`useReducer`、`useEffect` 的基本职责；
- TypeScript 的 `type`、联合类型和可选字段；
- 为什么流式消息更适合“事件归约器”，而不是到处修改多个布尔变量。

完成标准：能解释一条 `token` 事件怎样让某条助手消息追加文字。

### 4.3 HTTP、FastAPI 与 SSE

需要理解：

- 请求、响应、状态码、JSON、Header；
- GET 与 POST 的区别；
- CORS 和同源策略；
- `async/await` 代表等待 I/O，不代表自动变快；
- `StreamingResponse` 为什么可以分段返回；
- 当前端主动取消时，后端为什么必须清理生成器和上游任务。

由于当前接口是 `POST /chat/stream`，浏览器端候选实现是 `fetch` + `ReadableStream`，不能把原生 GET `EventSource` 当成直接替代品。

### 4.4 飞书基础

需要理解：

- App ID、App Secret、应用身份 Token 分别是什么；
- 权限、事件订阅、机器人可用范围为什么是三个不同问题；
- 收到消息事件和调用回复消息 API 是两个动作；
- 飞书可能重复投递事件，为什么需要按事件或消息 ID 去重；
- App Secret 为什么只能存在后端。

完成标准：能解释“收到飞书消息”不等于“已经成功回复消息”。

## 5. 前端产品范围

### 5.1 P0：必须完成

- 产品名称、简短定位和能力边界；
- 新建会话、示例问题和问题输入；
- 用户消息与助手消息；
- Agent 阶段展示，但不展示模型私有思维链；
- token 增量输出；
- 法规引用卡片；
- 价格查询表格；
- 停止生成、重试；
- 空输入、超时、取消、网络断开、服务错误和业务拒答；
- 桌面端完整布局、移动端可用布局；
- 飞书应用机器人文本问答最小闭环，或有证据的降级方案。

### 5.2 P1：完成 P0 后再选

- 本地保存最近会话；
- Markdown 代码块与复制按钮；
- 引用详情抽屉；
- 表格排序和导出；
- 深色模式；
- 执行耗时摘要；
- 网页结果一键推送到飞书。

P1 不应阻塞面试演示。

## 6. 前端状态模型

不要只设计“加载中/加载完成”两个状态。建议先讨论并确认下面的状态机：

```text
idle
  └─ submitting
       └─ streaming
            ├─ succeeded
            ├─ failed
            └─ cancelled
```

业务拒答如果以 `final` 结束，仍是一次完整业务结果；技术错误以 `error` 结束；用户取消或断开以 `cancelled` 结束。未收到终态的半截输出不能保存为成功答案。

每条流式事件至少按以下字段解释：

```text
type        发生了什么
request_id  属于哪一次请求
payload     该事件携带的业务数据
ts          事件时间
```

前端需要忽略不属于当前 `request_id` 的迟到事件，避免上一轮输出污染下一轮。

## 7. 分阶段实施与教学检查点

### A0：外部条件确认

调查任务：

- 当前后端能否在已知 Python 环境启动；
- `/chat/stream` 的真实事件顺序和 payload；
- 是否有权限创建飞书企业自建应用并启用机器人；
- 面试展示采用本地屏幕共享，还是需要面试官从外网打开 URL。

你需要掌握：浏览器、服务器、API、Agent 四层区别。

通过条件：形成一页“当前事实与未决项”，不修改业务代码。

### A1：冻结前后端契约

实施任务：

- 为 `ChatRequest` 和 `StreamEvent` 写前端 TypeScript 类型；
- 为每个事件类型保存一份脱敏样例；
- 记录事件合法顺序、终态和错误语义；
- 确认开发期使用 Vite 代理还是 FastAPI CORS。

你需要掌握：HTTP 请求体、SSE frame、TypeScript 联合类型。

通过条件：仅使用假事件即可验证解析器和状态转换。

### A2：建立静态界面骨架

实施任务：

- 创建独立前端目录；
- 完成聊天区、阶段区、引用区、输入区的静态组件；
- 使用假数据确认桌面与移动布局；
- 选择视觉方向和样式方案。

你需要掌握：React 组件、props、CSS 布局。

通过条件：不连接后端也能演示所有组件状态。

### A3：接入真实流式接口

实施任务：

- 用 `fetch` 发送 POST；
- 增量读取 `response.body`；
- 正确处理半个 frame、多个 frame 和 UTF-8 分片；
- 用 reducer 将事件转换为页面状态；
- 用 `AbortController` 实现停止生成。

你需要掌握：异步迭代、分片不等于消息边界、终态。

通过条件：连续多轮请求不会串流；取消后下一轮仍能正常回答。

### A4：实现领域结果组件

实施任务：

- `citations` 映射为可回查的引用卡片；
- `table` 映射为结构化查询表格；
- `stage/retrieval` 映射为用户可理解的进度文案；
- Markdown 渲染必须进行安全处理，不能信任模型生成的 HTML。

你需要掌握：领域数据和展示组件之间的映射关系。

通过条件：知识问答、价格查询、一般对话至少各有一条受控样例。

### A5：接入飞书应用机器人

实施前人工配置：

- 在飞书开放平台创建或选择企业自建应用；
- 启用机器人能力；
- 只申请完成问答所需的最小消息权限；
- 订阅消息接收事件；
- 设置应用可用范围；
- 将 App ID、App Secret 写入本地 `.env`，不发送到聊天或提交到 Git。

代码侧候选边界：

- 接收文本消息；
- 忽略机器人自己发送的消息，避免回复循环；
- 按消息 ID 去重；
- 将飞书会话映射成稳定的 `thread_id`；
- 调用统一 Agent 服务；
- 先只回复最终文本和有限引用摘要，不在飞书里伪造网页的 token 流；
- 超时或失败时发送明确的失败消息，不把半截回答当成功。

你需要掌握：事件驱动、权限、身份、幂等。

通过条件：同一飞书会话连续两轮可保持上下文；重复事件不会触发两次模型调用；机器人不会回复自己的消息。

### A6：异常与恢复验证

至少覆盖：

- 后端未启动；
- 网络中途断开；
- 请求超时；
- 用户主动取消；
- 收到 token 后没有终态；
- 飞书重复投递；
- 飞书回复 API 失败；
- 第一轮失败后第二轮恢复；
- 两个会话并发时不串 `thread_id`。

通过条件：每一种失败都能在网页或飞书中得到准确状态，并且不会污染下一轮。

### A7：作品集包装与演练

交付物：

- README 中的启动步骤；
- 一张架构图；
- 一段 3 至 5 分钟演示脚本；
- 三条稳定问题；
- 一条可控的拒答或错误恢复演示；
- 一份“已实现/已验证/未完成”清单；
- 必要时准备录屏，避免现场外部模型或数据库波动导致完全无法展示。

通过条件：在全新终端按 README 能启动；演示者不看代码也能解释一次请求的数据流。

## 8. 人机协作方式

为了让你真正获得前后端知识，每个阶段采用下面的节奏：

1. 我先指出当前代码证据、未知量和一个核心概念；
2. 你用自己的话复述数据流或给出第一版页面/伪代码；
3. 我负责搜索、脚手架、重复性代码、测试和 review；
4. 遇到技术选型时，我给出选项、风险和反例，由你决定；
5. 每完成一阶段，你亲自运行并解释验收结果；
6. 没有你的明确“实现”授权，不修改代码。

这使面试中的表述从“我有一个能跑的项目”升级为“我能解释它为什么这样设计、失败时怎样恢复”。

## 9. A 阶段验收清单

### 功能

- [ ] 浏览器可完成真实多轮问答；
- [ ] 流式阶段、token、引用、表格和终态显示正确；
- [ ] 停止和重试可用；
- [ ] 飞书应用机器人问答闭环，或已明确记录权限受限的降级证据。

### 稳定性

- [ ] 首轮失败不会导致后续请求持续失败；
- [ ] 取消、断开和半截流不会被记录为成功；
- [ ] 不同请求和会话不会互相污染；
- [ ] 飞书事件已做去重和防自回复循环。

### 安全

- [ ] 前端构建产物没有任何模型、数据库或飞书密钥；
- [ ] `.env` 未提交；
- [ ] Markdown/富文本输出经过安全处理；
- [ ] 飞书权限遵循最小化原则。

### 作品集表达

- [ ] 能解释 React 与 ReAct 的区别；
- [ ] 能解释 FastAPI 在系统中的位置；
- [ ] 能解释为什么使用 POST 流和 `ReadableStream`；
- [ ] 能区分自定义机器人与应用机器人；
- [ ] 能说明已经验证的范围和仍未完成的部分。

## 10. 开始实施前需要你确认的三个决策

1. A 阶段是否确认采用 `React + TypeScript + Vite`；
2. 视觉方向选择“政企专业工作台”还是“偏科技感的 AI 产品”；
3. 你是否有权限在当前飞书租户创建企业自建应用并启用机器人。

确认这三个问题后，下一认知步骤应是 A0 基线调查，而不是直接生成整个前端。
