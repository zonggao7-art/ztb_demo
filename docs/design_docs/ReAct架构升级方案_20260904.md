# ReAct 架构升级方案

> 版本：2026-09-05 易读版
>
> 状态：方案已批准，M0～M4 已落地，M5 生产验证尚未完成
>
> 范围：只升级现有知识问答和结构化数据查询；文档问答等占位能力暂不考虑

## 1. 先看结论

这次升级不是让模型“更自由”，而是让模型在明确规则内完成多步任务。

可以把整套系统理解为五个角色：

- **Router（分流员）**：理解用户想做什么，提出固定流程、多步流程、补充信息或不支持；旧流程由配置选择，不由模型决定。
- **程序规则（门卫）**：检查模型的提议是否合法。模型只能建议，程序才有批准权。
- **ReAct 执行器（办事员）**：一次做一步，根据上一步结果决定下一步。
- **工具（业务系统）**：查询法规知识库或 MySQL，只返回真实数据。
- **输出层（审核员）**：核对来源、任务完成情况和风险提示，通过后才把答案交给用户。

整体流程如下：

```text
用户问题
  ↓
Router 提出执行方案
  ↓
程序校验方案是否合法
  ├─ static：一个现有流程就能完成
  ├─ react：需要多个步骤，且后一步可能依赖前一步结果
  ├─ clarify：缺少必要信息，先向用户询问
  └─ unsupported：当前明确不支持
  ↓
受控工具调用 → 证据登记 → 程序核验 → 发布答案
```

当前必须特别区分两件事：

| 问题 | 当前答案 |
|---|---|
| ReAct 的代码链路是否打通 | **是**。路由、规则校验、工具调用、证据登记和输出审核已能离线闭环运行。 |
| 是否已经达到可直接上生产的状态 | **否**。三条事故用例已通过真实 LLM、MySQL、Milvus 链路检查，但全量评测和生产验收仍未完成。 |
| 系统默认进入哪条链路 | **hybrid 新架构**。默认所有会话进入受控分流，固定流程能完成的任务不需要 ReAct 循环；这不是生产验收通过的声明。已有显式配置仍优先。 |

## 2. 为什么要升级

旧架构擅长处理“一问一答”的固定任务，例如：

- 只查某家公司的基本信息；
- 只查一个项目的中标记录；
- 只问一条招投标法规。

但下面这类问题需要多步协作：

> 查出某项目的中标单位，再检查这家单位有没有处罚记录，并结合相关法规说明风险。

它至少包含三步，而且第二步的公司名称来自第一步查询结果。旧流程很难自然表达这种依赖关系；ReAct 适合解决的正是这类问题。

升级目标不是取代现有流程，而是形成“双轨制”：

- 简单问题继续走成熟的固定流程，成本低、结果稳定；
- 确实需要多步处理的问题才进入受控 ReAct；
- 新流程出现问题时，可以立刻切回旧流程。

## 3. 最重要的设计原则

### 3.1 模型负责理解，程序负责裁决

模型擅长理解自然语言，但不能被当作权限系统。企业生产环境中的职责划分如下：

| 模型可以做什么 | 程序必须控制什么 |
|---|---|
| 判断用户大致想完成哪些任务 | 是否允许进入 ReAct |
| 提出任务顺序和建议工具 | 工具是否在白名单内 |
| 根据查询结果提出下一步 | 参数是否来自可信来源 |
| 生成规定格式的答案草案 | 数据、引用和任务是否真实完整 |

一句话概括：**模型提出方案，程序检查方案；模型生成草案，程序决定能否发布。**

### 3.2 不靠关键词判断复杂度

系统不会因为用户说了“同时”“并且”“结合相关法规”就机械地启动 ReAct，也不会简单地按“要调用几个工具”来判断。

Router 需要理解的是任务结构：

- 一个现有业务分支能完整处理，且后续步骤不依赖查询结果：走 `static`；
- 需要组合多种能力，或者后一步必须使用前一步的结果：走 `react`；
- 必要条件缺失或存在关键歧义：走 `clarify`；
- 请求超出已经开放的能力：走 `unsupported`。

例如：

| 用户问题 | 建议模式 | 原因 |
|---|---|---|
| “查询 A 公司的基本信息” | `static` | 一个固定分支可以完整处理 |
| “查项目 P 的中标单位，再查该单位的处罚” | `react` | 第二步依赖第一步结果 |
| “帮我查一下这家公司” | `clarify` | 不知道具体是哪家公司 |
| “分析我刚上传的招标文件” | `unsupported` | 文档问答目前还是占位能力 |

### 3.3 Router 的结果也必须受约束

Router 不是输出一段随意的文字，而是填写一张固定格式的“执行申请单”，主要包括：

- 执行模式；
- 最多 6 个任务及其先后关系；
- 每个输入来自哪里；
- 建议使用哪些工具；
- 为什么这样判断；
- 是否缺少必要字段。

程序随后检查格式、工具范围、字段来源、任务依赖、开关、灰度范围和执行预算。格式错误时最多允许模型修正一次；仍不合格就停止，不带病执行。

## 4. 为什么使用官方 Agent 循环

本方案使用 LangChain 1.x 的官方 `create_agent` 来执行“模型选择工具—工具返回结果—模型决定下一步”的基础循环，不自行重写这段通用调度逻辑。

这里的“复用官方循环”不等于把系统交给模型自由发挥。企业真正需要定制的控制点仍由我们自己实现，包括：

- 哪些请求可以进入 ReAct；
- 哪些工具可以调用；
- 参数能从哪里取得；
- 一次允许调用几个工具；
- 总时长和调用次数上限；
- 哪些数据可以成为证据；
- 什么样的答案允许发布；
- 失败时能否回退到旧流程。

选择官方循环的原因很直接：消息格式、工具调用 ID、停止条件等底层细节已经由框架统一处理。我们把精力放在业务规则和安全边界上，更容易测试、升级和审计。

## 5. ReAct 如何被“管住”

### 5.1 只开放六个现有工具

| 工具 | 用途 |
|---|---|
| `search_public_kb` | 从法规知识库检索原始片段 |
| `knowledge_qa` | 基于知识库生成辅助回答 |
| `query_company_info` | 查询企业基本信息 |
| `query_company_penalty` | 查询企业处罚记录 |
| `query_bid_records` | 查询招投标记录 |
| `search_business_data` | 在结构化业务数据中查找候选记录 |

本阶段不开放任意 SQL、写数据库、文件上传、文档问答、多模态、MCP 或多智能体协作。

### 5.2 一次只执行一个业务工具

每次模型回复最多申请一个业务工具，单个请求内的工具并发数固定为 1。若模型一次提出批量调用，系统会在任何工具真正执行前拒绝该批次。

2026-09-05 联调补充：同时向模型服务声明关闭并行工具调用；若服务仍返回批量申请，只允许模型纠正一次，所有被拒绝的工具申请与纠正调用仍计入原有预算。每项批准任务取得成功工具结果后，下一步只开放答案提交，不再允许改写参数继续查询。

这样做虽然牺牲一点速度，但能清楚知道“哪一步用了什么输入、得到什么结果”，也便于超时、取消、重试和审计。

### 5.3 参数必须有来源

公司名、项目编号、日期等关键参数不能凭空出现，只能来自：

- 当前用户问题；
- 允许使用的最近对话；
- 已通过校验的前序工具结果。

当前唯一开放的跨步骤自动传值是：从中标记录中取得 `successful_bidder`，作为后续查询的 `company_name`。如果结果中有多家公司或含义不清，系统应向用户确认，不能擅自选择。

模型不得补造公司、项目、日期或金额单位，也不得静默删除用户给出的筛选条件。

### 5.4 调用次数和时间都有上限

默认预算如下：

| 项目 | 上限 |
|---|---:|
| 整个请求 | 90 秒 |
| Router | 10 秒，最多 2 次尝试 |
| ReAct 执行 | 65 秒 |
| 最终审核预留 | 15 秒 |
| 模型调用 | 最多 8 次 |
| 工具尝试 | 最多 6 次 |
| 单个工具 | 20 秒 |
| 同类纠错重试 | 最多 1 次 |
| 送给模型的单次工具内容 | 最多 4000 字符 |
| 输入容量门槛 | 16000 UTF-8 字节 |

最后一项是保守的容量限制，不等同于精确的模型 token 计算，后续要通过真实模型压测校准。

## 6. 数据如何变成可发布答案

### 6.1 先登记证据，再写答案

每次成功的工具结果都会进入本次请求专属的“证据账本”。账本记录数据来自哪个工具、对应哪条记录或法规片段，并分配稳定的证据编号。

失败结果、未展示给模型的截断内容、以及 `knowledge_qa` 自己生成的概括，都不能冒充原始证据。

### 6.2 模型只能提交结构化答案草案

模型不能直接返回任意长文，而要提交固定类型的内容块：

- `record_fact`：引用某条结构化记录中的指定字段；
- `legal_excerpt`：引用某条法规证据中的原文；
- `comparison`：比较已登记记录的同一字段；
- `limitation`：明确说明没有匹配、证据不足、工具失败或当前不支持。

程序用证据账本中的真实数据渲染最终文字。涉及法规时保留原文引用，不让模型随意改写成更强的法律结论。

2026-09-05 联调补充：模型可只选择法规证据编号，原文由程序填入，减少转抄错字。送给模型的是有限原文摘录；完整原文另行保留用于引用回查。模型没有看到的尾部内容，不能被授权作为答案摘录。

### 6.3 “完成”状态由程序计算

最终状态由程序根据任务和证据计算：

- `complete`：批准的任务都完成，且证据通过检查；
- `partial`：只完成了一部分；
- `clarify`：需要用户补充信息；
- `insufficient_evidence`：证据不足；
- `unsupported`：当前能力不支持；
- `failed`：执行失败。

需要注意：`complete` 只表示“本次批准的任务已完成”，不代表 Router 一定理解了用户的全部意图，也不代表系统已经作出法律结论。

### 6.4 七条发布红线

最终答案发布前必须重新检查：

1. 输出格式合法；
2. 所有引用都来自本次证据账本；
3. 事实与原始数据一致；
4. 没有把 Top-K 或截断结果说成完整全集；
5. 法规引用能够追溯到知识库原片段；
6. 不把“数据库没查到”说成“现实中不存在”或“没有风险”；
7. 每个批准任务都有结果或明确的未完成说明。

任何一条不通过，都不能绕过检查直接输出模型原文。

## 7. 失败、回退和流式输出

### 7.1 回退不是默认动作

只有当旧的固定流程能安全、完整地处理原问题，而且剩余时间充足时，才允许回退一次。以下情况不能靠回退绕过规则：

- 请求本身不受支持；
- 参数或证据校验失败；
- 用户取消；
- 总时限已经耗尽；
- 回退会丢失原问题中的任务或筛选条件。

### 7.2 未审核内容不向用户直播

执行过程中可以显示“正在查询法规”“正在核对企业”等进度，但不实时输出未经核验的模型草稿。只有整张执行图结束且答案通过校验后，才输出正文、引用和表格。

每个请求只能有一个明确的结束状态：成功、失败或取消。

## 8. 会话、日志与安全边界

- 继续使用现有的三字段 `AgentState`，不把内部执行细节塞进公共会话状态。
- 工具原始结果、模型草稿和内部推理不写入长期对话记忆。
- 同一会话同时发起多个请求时先拒绝，避免结果串线；不同会话互不共享证据。
- 日志只记录有限状态码、计数、耗时、工具名和证据编号，不记录密钥、完整 SQL、异常堆栈或大段原文。
- 提示词注入内容一律当作普通数据，不能把知识库文本中的“指令”当成系统命令。

当前会话锁只解决单进程场景。真正部署多实例前，还要补充分布式锁、可信身份与 `thread_id` 绑定。当前版本也不承诺服务崩溃后从某个 ReAct 中间步骤继续执行。

## 10. 上线前必须通过的验收

以下数字是上线门槛，不是当前已经取得的成绩：

| 指标 | 目标 |
|---|---:|
| 发布红线违规 | 0 |
| 路由判断可接受率 | ≥ 95% |
| 必须组合处理的问题召回率 | ≥ 95% |
| 简单问题被误送入 ReAct 的比例 | ≤ 5% |
| 正向任务客观完成率 | ≥ 90% |
| 引用与原证据关联正确率 | 100% |

评测集规划为 200 条：60 条固定流程、60 条 ReAct、40 条需要澄清、40 条不支持或对抗样例。当前只有从 40 个模板扩展出的 200 条草稿，尚未完成人工逐条审核，因此不能作为生产放量依据。

所有核心指标至少连续运行 3 次，并同时记录延迟、模型调用次数、工具调用次数和成本。

## 11. 灰度与回滚

建议按以下顺序开放：

1. 仅内部白名单会话；
2. 5% 会话；
3. 20% 会话；
4. 50% 会话；
5. 评测和监控稳定后再讨论扩大范围。

只要出现一次发布红线违规，就停止扩量并回到旧流程。默认不做新旧流程双跑，避免成本翻倍和外部工具重复调用。

回滚只需要把执行模式切回 `legacy` 并重新加载服务；本次升级不修改数据库数据和 Milvus 集合，因此不涉及数据回滚。

## 12. 已批准的关键决定

此前讨论的 Q1～Q4 已全部批准：

- **Q1：先审核、后发布。** 不向用户流式输出未经验证的正文。
- **Q2：法规回答采用保守边界。** 只输出可追溯原文、数据库事实和受控模板，不直接下“具有资格”“一定合规”“无风险”等结论。
- **Q3：只开放明确的数据依赖。** 当前仅允许中标单位名称进入后续企业查询；存在多个候选时先澄清。
- **Q4：采用本文的预算和上线门槛。** 达不到门槛就不扩大灰度。

## 13. 常用术语

| 术语 | 通俗解释 |
|---|---|
| `legacy` | 保留的旧流程，需要显式配置或启动参数选择，用于回退 |
| `hybrid` | 新旧流程共存，由灰度规则决定具体走哪条 |
| `static` | 任务在执行前就能确定，一个固定分支即可完成 |
| `react` | 一步一步执行，后一步可能依赖前一步结果 |
| schema | 模型必须填写的固定数据格式，可理解为电子表单 |
| evidence ledger | 本次请求的证据登记表，本文称“证据账本” |
| deadline | 整个请求不能超过的总时限 |
| artifact | 工具返回的完整原始结果，可能大于模型实际看到的内容 |

---

这份方案的核心不是“让模型自己想办法”，而是：**允许模型在有限范围内规划下一步，但每一步都必须经过程序规则、真实工具结果和发布审核三道约束。**
